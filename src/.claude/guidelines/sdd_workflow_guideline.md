# SDD（スペック駆動開発）ワークフローガイドライン

> **原則**: 仕様が Single Source of Truth。コードと仕様が食い違ったら、仕様が正。

---

## フェーズ0：壁打ち（ブレスト）

**目的**: 実現したい機能の全体像を明確にする

**やること**:
- AIと自由に発散しながら、機能のアイデアを整理する
- 以下の「5W1H + 制約」テンプレートを埋める
- **最後に必ず**「ここまでの議論で漏れている観点はありますか？」とAIに聞く

### 5W1H + 制約テンプレート

| 観点 | 質問 | 回答 |
|------|------|------|
| Who | 誰が使う？ |  |
| What | 何ができる？ |  |
| Why | なぜ必要？現状の課題は？ |  |
| Where | どのシステム・画面に関わる？ |  |
| When | いつ使う？トリガーは？ |  |
| How | 既存のどの技術・テーブルと関わる？ |  |
| **Constraints** | **やらないこと・制約条件** |  |

**成果物**: 整理メモ（壁打ちの要約）

**承認**: 不要（次フェーズへの入力として十分な情報が集まればOK）

## フェーズ1：ユビキタス言語の整理

**目的**: プロジェクト全体で使う用語を統一し、認識のズレを防ぐ

**やること**:
- 壁打ちで登場した業務用語・技術用語をAIに一覧化させる
- 各用語について「このプロジェクトではどういう意味か」を定義する
- 既に `docs/ubiquitous_language.md` がある場合は、新規用語の追記・既存用語の見直しを行う

**成果物**: `docs/ubiquitous_language.md`（追記または新規作成）

**用語集に含めるべき項目**:
- 業務用語（例：内示、確定注文、カンバン、緊急オーダー）
- 技術用語（例：Entity、Repository、UseCase）
- 略語・社内用語の正式な定義
- 類似用語の区別（例：「材料」と「部品」は同じか別か）

### → 承認ゲート ①

**レビューのチェックポイント**:
- [ ] 壁打ちで出た主要な用語が網羅されているか
- [ ] 定義が自社の業務文脈に合っているか（一般論ではなく）
- [ ] 類似用語の使い分けが明確か
- [ ] チームメンバーが読んで誤解しない表現か

**判定**: GO → フェーズ2へ / NG → 修正点を指示して再生成

---

## フェーズ2：要件定義書の作成

**目的**: 機能要件・非機能要件を構造化して明文化する

**やること**:
- 壁打ちの整理メモをAIに渡し、要件定義書を生成させる
- **`docs/ubiquitous_language.md` の用語を一貫して使用させること**
- 正常系だけでなく、異常系・エッジケースもAIに洗い出させる

**成果物**: `requirements.md`

**含めるべき項目**:
- 機能要件（ユーザーストーリー形式推奨）
- 非機能要件（性能、セキュリティ等）
- 前提条件・制約事項
- スコープ外の明記

### → 承認ゲート ②

**レビューのチェックポイント**:
- [ ] ビジネス要件と整合しているか
- [ ] スコープが適切か（大きすぎ/小さすぎないか）
- [ ] 異常系・エッジケースが考慮されているか
- [ ] 既存システムへの影響が検討されているか
- [ ] 「やらないこと」が明確か
- [ ] ubiquitous_language.md の用語が一貫して使われているか

**判定**: GO → フェーズ3へ / NG → 修正点を指示して再生成

---

## フェーズ3：設計書の作成

**目的**: 承認済み要件に基づき、技術的な設計を行う

**やること**:
- 承認済みの `requirements.md` をAIに渡し、設計書を生成させる
- **`docs/ubiquitous_language.md` の用語を一貫して使用させること**
- アーキテクチャ・データモデル・API設計等を含める

**成果物**: `design.md`

**含めるべき項目**:
- アーキテクチャ概要（どの層に何を置くか）
- データモデル / テーブル設計
- API / インターフェース設計
- 既存コードへの変更点
- エラーハンドリング方針

### → 承認ゲート ③

**レビューのチェックポイント**:
- [ ] 既存アーキテクチャとの整合性
- [ ] データモデルの妥当性（既存テーブルとの関係）
- [ ] パフォーマンスへの影響
- [ ] セキュリティ上の懸念がないか
- [ ] テスト可能な設計になっているか
- [ ] ubiquitous_language.md の用語が一貫して使われているか

**判定**: GO → フェーズ4へ / NG → 修正点を指示して再生成

---

## フェーズ4：タスク分解

**目的**: 設計書を実装可能な粒度のタスクに分解する

**やること**:
- 承認済みの `design.md` をAIに渡し、タスクリストを生成させる
- 各タスクは1つのコミット/PRに対応する粒度が理想

**成果物**: `tasks.md`

**タスクの粒度の目安**:
- 1タスク = 1〜2時間で完了できる規模
- テストとセットで定義する
- 依存関係を明記する（どの順で実装すべきか）

### → 承認ゲート ④

**レビューのチェックポイント**:
- [ ] タスクの粒度が適切か
- [ ] 依存関係が正しいか
- [ ] テスト方針が各タスクに含まれているか
- [ ] 漏れているタスクがないか

**判定**: GO → フェーズ5へ / NG → 修正点を指示して再生成

---

## フェーズ5：実装

**目的**: 承認済みタスクに沿って、AIにコードを生成させる

**やること**:
- タスクリストの順番に沿って、1タスクずつAIに実装させる
- 各タスク完了後にテストを実行して確認する
- タスク単位でコミットする

**成果物**: コード + テスト

**実装時のポイント**:
- 一度に複数タスクを投げない（コンテキスト膨張を防ぐ）
- クラス名・変数名・メソッド名は `docs/ubiquitous_language.md` の用語に準拠する
- 実装中に仕様変更が必要になったら、コードではなく仕様書を先に修正する
- 仕様書 = 正の原則を守る
