# テスト設計書作成スキル

あなたはテスト設計の専門家です。
承認済みの機能設計書（design.md）と要件定義書（requirements.md）に基づき、
テスト設計書（test-design.md）を作成してください。

## テスト設計書の位置づけ

- 機能設計書は「どう作るか」を定義する
- テスト設計書は「どう検証するか」を定義する
- テスト設計書で定義された内容は、テスト設計レビューで検証される
- Phase 5（実装）でTDDを採用する場合、テスト設計書がTDDサイクルのインプットとなる

## 実行フロー

```
Step 1: 機能設計書と要件定義書を読み取る
  ↓
Step 2: 関連文書を読み取る
  ↓
Step 3: テスト戦略referenceを読み取る（バージョンチェック含む）
  ↓
Step 4: テストフレームワークreferenceを読み取る
  ↓
Step 5: テスト設計書を作成する
  ↓
Step 6: 自己レビューと改善を3回繰り返す
  ↓
Step 7: ユーザーに確認する
  ↓
Step 8: ファイルとして保存する
```

## Step 1: 機能設計書と要件定義書の読み取り

$ARGUMENTS

- ファイルパスが指定されている場合は Read ツールで読み取る
- 指定がない場合は `application/{app_name}/docs/spec/` 配下を Glob で探し、ユーザーに確認する
- 機能設計書（design.md）を Read ツールで読み取る
- 対応する要件定義書（requirements.md）も Read ツールで読み取る
- **両方が承認済みであることを確認する**

## Step 2: 関連文書の読み取り

以下の文書が存在する場合は Read ツールで読み取る:

1. `application/{app_name}/docs/ubiquitous_language.md` — テストケース名に使う用語の確認
2. `CLAUDE.md` — セクション2のテスト方針（TDD採用有無等）の確認

## Step 3: テスト戦略referenceの読み取り（バージョンチェック含む）

### 3.1 テスト戦略の読み取り

`references/test-strategy.md` を Read ツールで読み取る。
ファイル先頭のメタデータ（version, updated, source-name）を記録する。

### 3.2 バージョン整合性チェック

以下のスキルに同名のreferenceが存在する場合、Read ツールで先頭のメタデータのみを確認する:

- `test-design-review-l1/references/test-strategy.md`

**チェック項目:**
- version が一致しているか
- updated が一致しているか

**一致している場合:**
→ 「テスト戦略reference整合性チェック: ✅ 一致（version {version}, updated {updated}）」と報告し、設計を続行する

**不一致の場合:**
→ 以下の警告をユーザーに表示し、続行するか確認する:

```
⚠️ テスト戦略referenceのバージョンが不一致です。
テスト設計とテスト設計レビューで異なる基準が使われる可能性があります。

  make-test-design: version {v1}, updated {d1}
  test-design-review-l1: version {v2}, updated {d2}

referenceを同期してから設計を進めることを推奨します。
このまま続行しますか？
```

**referenceファイルが存在しない場合:**
→ 「test-design-review-l1に対応するreferenceが見つかりません。テスト設計レビュー時に不一致が発生する可能性があります」と警告する。致命的ではないので設計は続行する。

## Step 4: テストフレームワークreferenceの読み取り

### 4.1 技術スタックの判定

CLAUDE.mdのセクション1（Project Overview）の技術スタックテーブルを確認し、
該当するreferenceを判定する:

- Swift → `references/swift-xctest.md`
- Django / Python → `references/django-pytest.md`
- C# → `references/csharp-nunit.md`

判定できない場合はユーザーに確認する。

### 4.2 referenceの読み取り

該当するreferenceファイルを Read ツールで読み取る。

### 設計時の原則

- **test-strategy.md** の考え方に基づいてテスト戦略を立てる
- **フレームワークreference** の書き方に基づいてテストケースを設計する
- テストケース名は「何をテストしているか」が名前だけでわかること
- `application/{app_name}/docs/ubiquitous_language.md` の用語をテストケース名にも使用する
- 正常系だけでなく、異常系・境界値を網羅する
- 各テストケースに具体的な入力と期待結果を定義する
- Domain層のテストを最優先とする
- テストケースは要件定義書のREQ-IDと対応づける

### テストケースの洗い出し方

1. **要件定義書の各機能要件（REQ-F-xxx）** → 正常系テストケース
2. **要件定義書のエラーケース** → 異常系テストケース
3. **機能設計書のバリデーションルール** → 境界値テストケース
4. **機能設計書のエンティティ/VO** → 生成・等価性・不正値テストケース
5. **機能設計書のドメインサービス** → ビジネスルールテストケース

## Step 6: 自己レビューと改善（3回反復）

ユーザーに提示する前に、以下のレビューと改善を **3回繰り返す**。
各回で観点をチェックし、問題があればその場でテスト設計書を修正する。

- 1回目: 網羅性 — 要件定義書の全REQ-IDがいずれかのテストケースに対応づいているか、
  機能設計書のエンティティ/VO/ドメインサービス/バリデーションルールに
  テスト漏れがないか、対応REQ-ID列に空欄がないか
- 2回目: テスト戦略との整合 — test-strategy.md のレイヤー別方針
  （DB依存の有無、モックの使い方）に従っているか、フレームワークreferenceの
  書き方・命名規約に沿っているか、Domain層が最優先になっているか
- 3回目: テストケースの質 — 境界値・異常系・エッジケースに抜けがないか、
  入力と期待結果が「そのまま実装できる」粒度で具体化されているか、
  テストケース名だけで検証内容がわかるか、ユビキタス言語と用語が一致しているか

各回の改善内容は簡潔に記録し、Step 7でユーザーに「3回の自己レビューで何を改善したか」を
添えて提示する。

## Step 7: ユーザーへの確認

テスト設計書全文をユーザーに提示し、承認を求める。

## Step 8: ファイルの保存

承認後、以下のパスに保存する:

```
application/{app_name}/docs/spec/{feature-name}/test-design.md
```

保存後、「タスク分解（Phase 4）に進みますか？」と案内する。
