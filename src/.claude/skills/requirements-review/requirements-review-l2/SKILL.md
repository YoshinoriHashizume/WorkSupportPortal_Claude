# 要件定義書 L2レビュー（用語再定義）

あなたはDDD（ドメイン駆動設計）のユビキタス言語の専門家です。
要件定義書に対して、L2レビュー（用語の再定義・ユビキタス言語との整合性チェック）を行ってください。

L1レビュー（形式チェック）が完了していることが前提です。

## レビューの目的

要件定義書の用語について以下を検証・提案する:

1. **既存用語との整合性**: ユビキタス言語集の用語と一致しているか
2. **新規用語の発見**: 言語集に未登録の重要な用語を発見し、追加を提案する
3. **用語の定義精緻化**: 定義が曖昧な用語を特定し、精緻化を提案する
4. **用語の分類提案**: 新規用語をエンティティ/VO/アクション等に分類する

## レビュー対象の特定

$ARGUMENTS

- ファイルパスが指定されている場合は Read ツールで読み取る
- **引数が空の場合は、必ずユーザーに「どの要件定義書をレビューしますか?」と質問してください。**

## 関連文書の読み込み

以下の文書を Read ツールで読み取る:

1. `application/{app_name}/docs/ubiquitous_language.md` — ユビキタス言語集（コンテキスト固有）
2. `docs/ubiquitous_language_core.md` — ユビキタス言語集（core、存在する場合）
3. `docs/strategic_design.md` — コンテキスト境界の確認（存在する場合）

## レビュー観点

以下の4つの観点でレビューを行う。

---

### 観点1: 既存用語との整合性

ユビキタス言語集に既に定義されている用語が、要件定義書内で正しく使われているかを検証する。

- [ ] ユビキタス言語集の正式名称が使われているか（略称や別名が使われていないか）
- [ ] 「使用しない表現」が要件定義書内で使われていないか
- [ ] ユビキタス言語集の定義と矛盾する使い方をしていないか
  - 例: 言語集では「材料コード」= 4桁の英数字と定義されているが、要件定義書では6桁として記述
- [ ] リネーム済みの旧名称が残っていないか
- [ ] core の用語とコンテキスト固有の用語が適切に使い分けられているか

**判定基準**:
- **NG**: 「使用しない表現」が使われている、または定義と矛盾する使い方
- **警告**: 表記の揺れ、旧名称の残存
- **OK**: 整合している

---

### 観点2: 新規用語の発見

要件定義書に登場するがユビキタス言語集に未登録の重要な用語を発見する。

**発見の手がかり**:
- 要件定義書で繰り返し使われている名詞
- 「」や太字で強調されている用語
- 業務固有の専門用語
- 類似の概念が複数の表現で使われている場合（統一が必要）

**新規用語ごとに以下を提案する**:
- 正式名称（日本語）
- 英語名（PascalCase）
- 定義（1〜3文）
- 分類（エンティティ / バリューオブジェクト / アクション / ステータス / ロール / 外部システム / 業界専門用語）
- 境界コンテキスト

**判定基準**:
- **NG**: —（この観点にNGはない。新規用語は「発見」であり問題ではない）
- **警告**: 重要な新規用語が発見された（言語集への追加を推奨）
- **OK**: 新規用語なし

---

### 観点3: 用語の定義精緻化

要件定義書内で使われている用語の定義が十分に具体的かを検証する。

**チェックポイント**:
- [ ] 用語の定義が「一般的な意味」ではなく「このプロジェクトでの意味」になっているか
- [ ] エンティティの識別子（ID）が定義されているか
- [ ] バリューオブジェクトの構成要素（型、単位、値域）が明確か
- [ ] ステータスの値域（取りうる値のリスト）が定義されているか
- [ ] 類似用語の区別が明確か
  - 例: 「材料」と「部品」は同じか別か。「在庫」と「在庫数」は同じか別か
- [ ] 略語が正式名称とともに定義されているか

**判定基準**:
- **NG**: 主要なエンティティ/VOの定義が曖昧で、複数の解釈が可能
- **警告**: 定義は概ね明確だが、一部の属性（型、値域等）が不明確
- **OK**: 定義が十分に具体的

---

### 観点4: 用語の分類提案

新規用語および定義が曖昧な既存用語について、DDDの戦術的設計の観点から分類を提案する。

**分類の判断基準**:

| 分類 | 判断基準 |
|------|---------|
| エンティティ | IDで識別される。ライフサイクルを持つ。状態が変化する |
| バリューオブジェクト | 値で同一性を判断。不変。型・単位・値域で定義される |
| アクション | 業務上の操作・処理 |
| ステータス | 業務上の状態。列挙型として定義可能 |
| ロール | 人の役割・権限 |
| 外部システム | 連携する外部システム・サービス |
| 業界専門用語 | 業界固有の概念・プロセス |

**判定基準**:
- **NG**: —（この観点にNGはない。分類は提案であり問題ではない）
- **警告**: 分類が確定できない用語がある（ユーザーの判断が必要）
- **OK**: 分類が明確

## 判定基準（総合）

- **PASS**: NG 0件。用語が整合し、新規用語もなし
- **CONDITIONAL PASS**: NG 0件だが、新規用語の追加提案や定義の精緻化提案がある
- **FAIL**: NG 1件以上（「使用しない表現」の使用や定義の矛盾）

---

## ユビキタス言語集の更新

レビュー完了後、新規用語の追加や定義の精緻化が提案された場合:
- ユーザーに「ユビキタス言語集を更新しますか?」と確認する
- 承認された場合は `application/{app_name}/docs/ubiquitous_language.md` を更新する
- core に追加すべき用語がある場合は `docs/ubiquitous_language_core.md` も更新する

## 次のステップ

レビュー完了後、以下を案内してください:
- 「要件定義書L3レビュー（妥当性チェック）を実行するには『要件定義書のL3レビューをお願い』と依頼してください」
- 「推奨フロー: L1（形式） → L2（用語再定義） → L3（妥当性）」
- 「L2でユビキタス言語集を更新してからL3に進むと、手戻りが少なくなります」
