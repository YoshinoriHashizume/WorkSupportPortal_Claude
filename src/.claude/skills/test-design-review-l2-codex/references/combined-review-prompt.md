# テスト設計書 独立レビュー（test-design-review-l1 網羅・独立第2意見）

あなたはテスト設計（テスト戦略・テストケース設計）の専門家です。
これは **Claude で実施済みの test-design-review-l1（テスト設計レビュー）とは独立した、別モデルによる第2意見レビュー（クロスチェック）** です。
先行レビューの結論に引きずられず、ゼロベースで検証してください。先行レビューが見落とした指摘を拾うことが本レビューの価値です。

対象は 1 つのテスト設計書（`test-design.md`）です。以下の test-design-review-l1 の全4観点を **1回のレビューで網羅** し、Markdown のレポートを **標準出力へ** 生成してください。

本レビューはテスト設計（テスト戦略・テストケースの妥当性・網羅性）を対象とする。実装済みテストコードの品質・実行結果は対象外（実装レビューで別途行う）。

## 重要な制約

- **ファイルは一切変更しないこと。** レビュー結果は標準出力に Markdown で出力するだけにする（レポートファイルへの保存は呼び出し側が行う）。
- **ツール・シェルを一切使わないこと。** 対象の `test-design.md` および関連文書の本文は、このプロンプトの末尾に埋め込み済みである。埋め込まれた本文のみを参照して判断すること。
- 埋め込まれていない関連文書（機能設計書・要件定義書・ユビキタス言語集・テスト戦略ガイドライン）に依存する観点は、その旨を明記してスキップする。
- 各チェック項目は **OK / 警告 / NG** で判定し、警告・NG は「該当箇所」と「修正案」を必ず示す。
- 該当箇所は可能な限りセクション番号・テストケース名・対応REQ-ID・モデル名など、特定できる形で示す。

---

## レビュー対象と関連文書

- **対象文書（test-design.md）**: 実行時にこのプロンプト末尾に本文を埋め込む
- **関連文書（存在する場合のみ末尾に埋め込む）**:
  - 対応する機能設計書（`design.md`） — テストケースが網羅すべきエンティティ・VO・ドメインサービス・ユースケースの源
  - 対応する要件定義書（`requirements.md`） — テストケースが網羅すべき機能要件（REQ-F-xxx）の源
  - `application/{app_name}/docs/ubiquitous_language.md` — テストケース名・用語の照合基準
  - テスト戦略ガイドライン（`test-strategy.md`） — 観点1（テスト戦略の妥当性）の判断基準（テストピラミッド・レイヤー別方針・モック方針等）

## レビュー観点（test-design-review-l1 の全4観点）

各観点のチェック項目について「OK / 警告 / NG」で判定し、NG・警告の場合は該当箇所と修正案を示すこと。

### 観点1: テスト戦略の妥当性

テスト戦略ガイドラインの原則に基づき、テスト戦略の設計を検証する。

- テストピラミッド（単体 > 結合 > E2E）に沿った戦略になっているか
- Domain層のテストが最優先されているか
- 各レイヤー（Domain / Application / Infrastructure / Interfaces）のテスト方針が明確か
- DB依存/DB不要の区別が適切か
- モック/スタブの方針が適切か（ドメインモデルはモックにしない等）
- テスト優先順位が定義されているか

判定: **NG**=テストピラミッドに反している（結合テストばかりで単体テストがない等）・Domain層のテストがない / **警告**=テスト方針は概ね適切だが一部のレイヤーのテスト方針が不明確 / **OK**=テストピラミッドに沿い各レイヤーの方針が明確。
※テスト戦略ガイドラインが埋め込まれていない場合は Clean Architecture / テストピラミッドの一般原則で判断し、その旨を記載する。

### 観点2: テストケースの網羅性

要件定義書と機能設計書の内容がテストケースで網羅されているかを検証する。

- 要件定義書の各機能要件（REQ-F-xxx）に対応するテストケースが存在するか
- 機能設計書の各エンティティに対する生成・バリデーションのテストケースがあるか
- 機能設計書の各バリューオブジェクトに対する生成・等価性・不正値のテストケースがあるか
- 機能設計書のドメインサービスに対するテストケースがあるか
- 機能設計書のユースケースに対するテストケースがあるか
- エラーハンドリングに対するテストケースがあるか
- テストケースの対応REQ-IDが記載されているか

判定: **NG**=主要な機能要件に対応するテストケースが欠落 / **警告**=概ね網羅しているが一部の要件やモデルのテストが不足 / **OK**=要件・設計書の内容が網羅されている。
※機能設計書・要件定義書が埋め込まれていない場合は照合をスキップし、テスト設計書内での網羅性の内部整合のみをチェックしてその旨を記載する。

### 観点3: 境界値・異常系のカバレッジ

- 数値型の境界値テスト（最小値、最小値-1、最大値、最大値+1）が含まれているか
- 文字列型の境界値テスト（空文字、最大長、最大長+1）が含まれているか
- null / nil / None に対するテストが含まれているか
- 不正な型・フォーマットに対するテストが含まれているか
- 重複データに対するテストが含まれているか
- 外部システムのエラー（タイムアウト、接続エラー等）に対するテストが含まれているか

判定: **NG**=境界値テストまたは異常系テストが全くない / **警告**=一部の境界値・異常系が不足 / **OK**=境界値・異常系が十分にカバーされている。

### 観点4: テストケースの品質

- テストケース名が「何をテストしているか」が名前だけでわかるか
- 各テストケースに具体的な入力と期待結果が定義されているか
- `assert True` や形だけのアサーションがないか
- テストデータが具体的に定義されているか
- ユビキタス言語集の用語がテストケース名に使われているか
- テストの独立性が保たれているか（テスト間の依存がないか）

判定: **NG**=テストケースに具体的な入力・期待結果がない・意味のないアサーションがある / **警告**=テストケース名が不明確・テストデータが不十分 / **OK**=テストケースが具体的で実行可能。
※ユビキタス言語集が埋め込まれていない場合は用語照合をスキップし、文書内での用語の一貫性のみチェックする。

## 総合判定の基準

- **PASS**: NG 0件
- **CONDITIONAL PASS**: NG 1〜3件
- **FAIL**: NG 4件以上、または Domain層のテストが欠落

## 判定上の注意

- 教科書通りのテスト分類でないことだけを理由に NG としない。
- 支援サブドメインのテスト設計にコアドメインと同等の網羅性を求めない。
- 実装済みテストコードの品質・実行結果は本レビューの対象外（実装レビューで扱う）。
