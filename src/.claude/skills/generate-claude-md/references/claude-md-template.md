## 2. プロジェクト固有の設定

> **このセクションの使い方（プロジェクト開始後に削除してよい）:**
>
> CLAUDE.mdは一度に完成させるものではなく、段階的に育てる。
> ここにはreferenceを読まなくても守るべきクリティカルなルールのみ書く（3〜5行程度）。
> 詳細な命名規則・コーディング規約・アーキテクチャ定義はスキルのreferenceに配置し、

>
> - Step1: プロジェクト開始時 → 開発環境の最低限の情報
> - Step2: 戦略的設計の後 → strategic_design.md への参照

> - Step4: 最初の機能の実装後 → 命名規則・規約の要点

## 3. 絶対ルール

以下のルールはプロジェクトの種類・規模に関わらず厳守すること。

### コード変更の制約

1. **読解・分析を依頼された場合、ファイルの変更は一切行わない**
2. **実装に着手する前に、必ず以下を提示し、ユーザーの承認を得る:**
   - 変更対象ファイルの一覧
   - 各ファイルの変更概要(何を追加/修正/削除するか)
   - 変更の影響範囲
3. **1回の変更は1ファイルを基本とする。** 複数ファイルの同時変更が必要な場合は事前に一覧を提示する
4. **既存コードの削除を伴う変更は、削除対象を明示してから実行する**

### 仕様の原則

1. **仕様書が Single Source of Truth（唯一の信頼できる情報源）である**
2. コードと仕様が食い違った場合、仕様が正しい。コードを修正すること
3. 実装中に仕様変更が必要になった場合、コードではなく仕様書を先に修正すること
4. すべての成果物で対象アプリケーションの `docs/ubiquitous_language.md` に定義されたユビキタス言語を使用すること

### 禁止事項

1. **タスクを作成しファイルへ書き出すことなく実装を開始することは禁止する**
2. 実装に移るときは、必ず確認を取ること
3. 判断に迷う場合は、必ずユーザーに確認すること

### 問題発生時

- ビルドエラーやテスト失敗が発生した場合、エラーメッセージを正確に報告し、修正案を提示してから修正する
- 意図しない変更が発生した場合、差分を確認し、ユーザーに報告する

## 4. SDD（スペック駆動開発）ルール

### 基本原則

- 仕様書が Single Source of Truth
- 要件定義書は**問題空間（WHAT）** — 何が要求されているかを定義する
- 設計書は**解決空間（HOW）** — どうモデル化し実装するかを定義する
- 設計書は**機能設計**（design.md）と**テスト設計**（test-design.md）に分離する
- すべての成果物で対象アプリケーションの `docs/ubiquitous_language.md` のユビキタス言語を使用する
- **どんな小さなツールでも、戦略的設計の地図上で位置を確認してから着手する**

### 戦略的設計（プロジェクト全体で1回、または大きな変更時）

プロジェクト全体の構造を整理する。各機能開発の前提として参照する。

| ステップ | 成果物 |
|---------|--------|
| ビジネスの全体像の把握 | BMC（ビジネスモデルキャンバス） |
| Big Picture Event Storming | イベントフロー図 |
| サブドメイン分類・コンテキスト識別・マッピング | `docs/strategic_design.md` |
| ユビキタス言語（core）の整理 | `docs/ubiquitous_language_core.md` |

詳細は SDD スキル（`sdd/SKILL.md`）を参照。

### SDDフロー（各コンテキストごとの開発サイクル）

ユーザーからSDD/スペック駆動開発での開発を求められた場合、以下のフェーズに従って進めること。
詳細なガイドラインは SDD スキル（`sdd/SKILL.md`）を参照すること。

| フェーズ | 成果物 | 承認 |
|---------|--------|------|
| 0: 壁打ち | 整理メモ（5W1H + 制約） | 不要 |
| 1: ユビキタス言語整理 | `application/{app_name}/docs/ubiquitous_language.md` 更新 | **必要** |
| 2: 要件定義書 | `application/{app_name}/docs/specs/{feature}/requirements.md` | **必要** |
| 2.5: Design Level Event Storming | イベントフロー図（オプション） | **必要**（実施する場合） |
| 3: 設計書 | `application/{app_name}/docs/specs/{feature}/design.md` + `test-design.md` | **必要** |
| 4: タスク分解 | `application/{app_name}/docs/specs/{feature}/tasks.md` | **必要** |
| 5: 実装 | コード + テスト | タスクごとに確認・報告 |

**各フェーズの承認が得られるまで次のフェーズに進んではならない。**

各文書の先頭には必ず下記を明記する:
```
文書ID: (例:REQ-FEATURE-NAME-2026-001)
作成日: 2026/01/01
更新日:
対応文書: (源となった文書のパス)
```

### Phase 2.5: Design Level Event Storming（オプション）

要件定義書の「WHAT」を、ドメインモデルの「HOW」に変換する橋渡しとして実施する。

**実施する場合**: 新しいコンテキストを初めて作るとき、複雑なビジネスルールが絡む機能
**省略してよい場合**: 既存コンテキスト内の小さな機能追加、単純なCRUD機能

### レビュー体系

3つの独立したレビュー体系を持つ。それぞれ異なるタイミング・頻度で実施する。

**戦略的設計レビュー（まれに実施）**:

| レベル | 対象 | 観点 |
|--------|------|------|
| L1 | BMC | 9要素の網羅性、要素間の整合性 |
| L2 | Big Picture Event Storming | イベントの網羅性、境界の発見 |
| L3 | サブドメイン + コンテキスト | 分類の妥当性、コンテキストマッピングの適切さ |

**要件定義書レビュー（Phase 2の後）**:

| レベル | 観点 |
|--------|------|
| L1 | 形式・用語・構造チェック |
| L2 | 用語再定義 → ユビキタス言語反映 |
| L3 | 妥当性・網羅性チェック |

※推奨フロー: L1 → L2 → L3（用語を確定させてから妥当性チェックをした方が手戻りが少ない）

**設計レビュー（Phase 3/5の後）**:

| レベル | 対象 | 観点 |
|--------|------|------|
| L1 | 機能設計書（design.md） | 戦略的設計との整合性、ドメインモデルの妥当性、ビジネスルールの配置、ユビキタス言語との整合性 |
| L2 | テスト設計書（test-design.md） | テスト戦略の妥当性、テストケースの網羅性、境界値・異常系のカバレッジ |
| L3 | 実装コード | 設計書との整合性、Clean Architectureのレイヤー違反、命名の準拠、設計パターンの一貫性 |

### ユビキタス言語の2層構造

| 層 | ファイル | スコープ |
|---|---------|---------|
| core | `docs/ubiquitous_language_core.md` | プロジェクト横断。全コンテキストで同じ意味の用語 |
| コンテキスト固有 | `application/{app_name}/docs/ubiquitous_language.md` | 各アプリケーション（コンテキスト）固有の用語 |

core の用語集を更新した場合は、他のプロジェクトにも反映すること。

### SDDを省略してよい場合

- 単純なバグ修正（1ファイル以内の修正）
- 既存機能の軽微な調整（UI文言変更等）
- ユーザーが明示的にバイブコーディングを指定した場合

省略する場合でも、命名は対象アプリケーションの `docs/ubiquitous_language.md` に準拠する。迷う場合はユーザーに「SDDフローで進めますか？」と確認すること。

### 成果物の保存先

```
docs/                                              # プロジェクト全体
├── strategic_design.md                            # 戦略的設計書（プロジェクト全体で1つ）
└── ubiquitous_language_core.md                    # ユビキタス言語 core（プロジェクト横断）

application/{app_name}/docs/                       # アプリケーション（コンテキスト）ごと
├── ubiquitous_language.md                         # ユビキタス言語（コンテキスト固有）
└── specs/{feature-name}/
    ├── requirements.md                            # 要件定義書（問題空間: WHAT）
    ├── design.md                                  # 機能設計書（解決空間: HOW）
    ├── test-design.md                             # テスト設計書（テスト戦略・テストケース）
    └── tasks.md                                   # タスクリスト
```

- `{feature-name}` はケバブケースで命名する
- 仕様書はGit管理対象とし、コードと一緒にコミットすること

## 5. Task Documentation

### タスクファイルの配置

```
application/{app_name}/docs/specs/{feature-name}/tasks.md
```

※ タスクは必ず仕様書と同じディレクトリに置く。

### タスクファイルの記述ルール

1. **状況チェックシート**: ファイルの先頭に必ず記述

   **凡例**: [ ] 未着手 / [~] 進行中 / [✅2026/02/01 13:05] 完了 / [- 2026/02/15 14:12] スキップ

   - **時刻の正確性**: 必ず `date '+%Y/%m/%d %H:%M'` コマンドで取得した実際の時刻を記載する。推測や概算で書かない
   - **即時記録**: 各ステップ完了時にその都度時刻を取得して記録する。複数ステップをまとめて同一時刻で記録することは禁止

2. **タスク実行レポート**: タスク完了時に必ず書く。懸念事項・改善事項・設計のGoodポイント・チーム共有ポイントを記述する(必ず日時を記録)。"--------------------"で前後を囲む

## カスタムスキル

<!-- プロジェクトごとにスキルの配置先を記載する -->
配置先: `.claude/skills/<skill_name>/SKILL.md`

### スキル整備方針

- スキルは実際の作業で繰り返しパターンが見つかったタイミングで作成する。先回りして大量に作らない
- 同じ指示を3回以上繰り返したらスキル化を検討する
- 作成したスキルは実際に使って効果を確認してから定着させる
- 使わなくなったスキルは削除する
- **スキルはできるだけプロジェクトに依存しない形で作成する**。プロジェクト固有の知識はreferenceに分離する
