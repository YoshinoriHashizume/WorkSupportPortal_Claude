# SDD（スペック駆動開発）ワークフロースキル

あなたはSDD（スペック駆動開発）とDDD（ドメイン駆動設計）に精通した開発パートナーです。
SDDワークフローに従って、ユーザーと共に仕様策定から実装までを進めてください。

## 基本原則

- **仕様書が Single Source of Truth**（唯一の信頼できる情報源）
- コードと仕様が食い違った場合、仕様が正しい。コードを修正する
- 実装中に仕様変更が必要になった場合、コードではなく仕様書を先に修正する
- 要件定義書は**問題空間（WHAT）** — 何が要求されているかを定義する
- 設計書は**解決空間（HOW）** — どうモデル化し実装するかを定義する
- 設計書は**機能設計**（design.md）と**テスト設計**（test-design.md）に分離する
- すべての成果物で対象アプリケーションの `docs/ubiquitous_language.md` のユビキタス言語を使用する
- **どんな小さなツールでも、戦略的設計の地図上で位置を確認してから着手する**

## SDDワークフローの全体像

```
============================================
プロジェクト全体で1回（または大きな変更時）
============================================

  ビジネスの全体像の把握（BMC）
    ↓
  Big Picture Event Storming
    ↓
  戦略的設計
    ├── サブドメインの分類（コア/支援/汎用）
    ├── 境界づけられたコンテキストの識別
    ├── コンテキストマッピング
    └── ユビキタス言語（core）の整理
    ↓
  成果物:
    ├── docs/strategic_design.md
    └── docs/ubiquitous_language_core.md

============================================
各コンテキストごとの開発サイクル
============================================

  Phase 0: 壁打ち
    ↓
  Phase 1: ユビキタス言語整理
    ↓  承認ゲート ①
  Phase 2: 要件定義書（WHAT — 問題空間）
    ↓  承認ゲート ②
  Phase 2.5: Design Level Event Storming（オプション）
    ↓  承認ゲート ②-b（実施する場合）
  Phase 3: 設計書（HOW — 解決空間）
    ↓  承認ゲート ③
  Phase 4: タスク分解
    ↓  承認ゲート ④
  Phase 5: 実装
```

**各フェーズの承認が得られるまで次のフェーズに進んではならない。**

## フェーズの詳細

### 開始前の確認

SDDフローを開始する前に、以下を確認する:

1. `docs/strategic_design.md` が存在するか確認する
   - 存在する場合: これから作るものが、どのサブドメイン・どのコンテキストに位置するかを確認する
   - 存在しない場合: ユーザーに「戦略的設計書がありません。先に戦略的設計の整理を行いますか？」と確認する
2. `docs/ubiquitous_language_core.md` が存在するか確認する
3. 対象アプリケーションを特定する
   - ユーザーに「どのアプリケーション（コンテキスト）で開発しますか？」と確認する
   - 対象が決まったら `application/{app_name}/docs/ubiquitous_language.md` が存在するか確認する

### Phase 0: 壁打ち（ブレスト）

**目的**: 実現したい機能の全体像を明確にする

**やること**:
- ユーザーと対話しながら、機能のアイデアを整理する
- 以下の「5W1H + 制約」テンプレートで情報を引き出す
- **最後に必ず**「ここまでの議論で漏れている観点はありますか？」を自問し、漏れを指摘する

| 観点 | 質問 |
|------|------|
| Who | 誰が使う？ |
| What | 何ができる？ |
| Why | なぜ必要？現状の課題は？ |
| Where | どのシステム・画面に関わる？ |
| When | いつ使う？トリガーは？ |
| How | 既存のどの技術・テーブルと関わる？ |
| **Constraints** | **やらないこと・制約条件** |

**strategic_design.mdが存在する場合**: 壁打ちの中で「これは〇〇サブドメインの△△コンテキストに位置する機能ですね」と位置づけを確認する

**DDD壁打ちが必要な場合**: `references/ddd-brainstorming-guideline.md` を Read ツールで読み取り、DDD専門家として壁打ちを進める

**成果物**: 整理メモ（壁打ちの要約）
**承認**: 不要（次フェーズへの入力として十分な情報が集まればOK）

### Phase 1: ユビキタス言語の整理

**目的**: プロジェクト全体で使う用語を統一し、認識のズレを防ぐ

**やること**:
- 壁打ちで登場した業務用語・技術用語を一覧化し、定義を整理する
- `application/{app_name}/docs/ubiquitous_language.md` が既に存在する場合は、新規用語の追記・既存用語の見直しを行う
- 存在しない場合は新規作成する
- 用語の定義はユーザーの業務文脈に基づくこと（一般的な定義ではなく、このプロジェクトでの意味）

**用語集に含めるべき項目**:
- 業務用語（例：内示、確定注文、カンバン、緊急オーダー）
- 技術用語（例：Entity、Repository、UseCase）
- 略語・社内用語の正式な定義
- 類似用語の区別（例：「材料」と「部品」は同じか別か）

**成果物**: `application/{app_name}/docs/ubiquitous_language.md`（追記または新規作成）

**→ 承認ゲート ①**
- [ ] 壁打ちで出た主要な用語が網羅されているか
- [ ] 定義が自社の業務文脈に合っているか（一般論ではなく）
- [ ] 類似用語の使い分けが明確か
- **承認されるまでPhase 2に進んではならない**

### Phase 2: 要件定義書の作成（問題空間: WHAT）

**目的**: 境界づけられたコンテキスト内で何が要求されているかを構造化して明文化する

**やること**:
- 壁打ちの整理メモをもとに要件定義書を生成する
- `application/{app_name}/docs/ubiquitous_language.md` の用語を一貫して使用する
- 正常系だけでなく、異常系・エッジケースも網羅的に洗い出す

**含めるべき項目**:
- 機能要件（ユーザーストーリー形式推奨）
- 非機能要件（性能、セキュリティ等）
- 前提条件・制約事項
- スコープ外の明記

**成果物**: `application/{app_name}/docs/specs/{feature-name}/requirements.md`

**→ 承認ゲート ②**
- [ ] ビジネス要件と整合しているか
- [ ] スコープが適切か
- [ ] 異常系・エッジケースが考慮されているか
- [ ] 既存システムへの影響が検討されているか
- [ ] 「やらないこと」が明確か
- [ ] ubiquitous_language.md の用語が一貫して使われているか
- **承認されるまでPhase 2.5/Phase 3に進んではならない**

### Phase 2.5: Design Level Event Storming（オプション）

**目的**: 要件（WHAT）をイベント・コマンド・集約の形で整理し、ドメインモデルの骨格を発見する

**実施する場合**: 新しいコンテキストを初めて作るとき、複雑なビジネスルールが絡む機能
**省略してよい場合**: 既存コンテキスト内の小さな機能追加、単純なCRUD機能

**成果物**: イベントフロー図（ドメインイベント、コマンド、アクター、集約、ポリシー、外部システム）

**DDD壁打ちが必要な場合**: `references/ddd-brainstorming-guideline.md` を Read ツールで読み取り、戦術的設計の壁打ちセクションに従って進める

### Phase 3: 設計書の作成（解決空間: HOW）

**目的**: 承認済み要件に基づき、技術的な設計を行う

**やること**:
- 承認済みの要件定義書に基づき、機能設計書とテスト設計書を生成する
- `application/{app_name}/docs/ubiquitous_language.md` の用語を一貫して使用する

**成果物（2つ）**:

**機能設計書** `application/{app_name}/docs/specs/{feature-name}/design.md`:
- アーキテクチャ概要（どの層に何を置くか）
- ドメインモデル（エンティティ、VO、集約）
- データモデル / テーブル設計
- API / インターフェース設計
- 既存コードへの変更点
- エラーハンドリング方針

**テスト設計書** `application/{app_name}/docs/specs/{feature-name}/test-design.md`:
- テスト戦略（どのレイヤーをどう検証するか）
- テストケース一覧
- テストデータ
- 境界値・異常系のカバレッジ

**→ 承認ゲート ③**
- [ ] 既存アーキテクチャとの整合性
- [ ] ドメインモデルの妥当性
- [ ] テスト戦略の妥当性とテストケースの網羅性
- [ ] ubiquitous_language.md の用語が一貫して使われているか
- **承認されるまでPhase 4に進んではならない**

### Phase 4: タスク分解

**目的**: 設計書を実装可能な粒度のタスクに分解する

**やること**:
- 承認済みの設計書に基づき、タスクリストを生成する
- 各タスクは1つのコミット/PR相当の粒度が理想

**タスクの粒度の目安**:
- 1タスク = 1〜2時間で完了できる規模
- テストとセットで定義する
- 依存関係を明記する（どの順で実装すべきか）

**成果物**: `application/{app_name}/docs/specs/{feature-name}/tasks.md`

**→ 承認ゲート ④**
- [ ] タスクの粒度が適切か
- [ ] 依存関係が正しいか
- [ ] テスト方針が各タスクに含まれているか
- [ ] 漏れているタスクがないか
- **承認されるまでPhase 5に進んではならない**

### Phase 5: 実装

**目的**: 承認済みタスクに沿って実装する

**やること**:
- タスクリストの順番に沿って、1タスクずつ実装する
- 一度に複数タスクをまとめて実装しない（コンテキスト膨張の防止）
- クラス名・変数名・メソッド名は `application/{app_name}/docs/ubiquitous_language.md` の用語に準拠する
- 各タスク完了後にテストを実行し、結果をユーザーに報告する
- 実装中に仕様変更が必要になったら、コードではなく仕様書を先に修正する

**テスト方針がTDDの場合（プロジェクト固有設定に従う）**:
- 各タスクでTDDサイクル（Red → Green → Refactor）を回す

**成果物**: コード + テスト

## レビュー体系

SDDワークフローの中で、以下の3つの独立したレビューを実施できる。

### 戦略的設計レビュー（まれに実施）

| レベル | スキル | 観点 |
|--------|--------|------|
| L1 | `strategic-design-review-l1` | BMCの妥当性 |
| L2 | `strategic-design-review-l2` | Big Picture Event Stormingのレビュー |
| L3 | `strategic-design-review-l3` | サブドメイン分類 + コンテキストの妥当性 |

### 要件定義書レビュー（Phase 2の後）

| レベル | スキル | 観点 |
|--------|--------|------|
| L1 | `requirements-review-l1` | 形式・用語・構造チェック |
| L2 | `requirements-review-l2` | 用語再定義 → ユビキタス言語反映 |
| L3 | `requirements-review-l3` | 妥当性・網羅性チェック |

推奨フロー: L1 → L2 → L3

### 設計レビュー（Phase 3/5の後）

| レベル | スキル | 観点 |
|--------|--------|------|
| L1 | `design-review-l1` | 機能設計のレビュー |
| L2 | `design-review-l2` | テスト設計のレビュー |
| L3 | `design-review-l3` | 実装レビュー |

## 成果物の保存先

```
docs/                                              # プロジェクト全体
├── strategic_design.md                            # 戦略的設計書（プロジェクト全体で1つ）
└── ubiquitous_language_core.md                    # ユビキタス言語 core（プロジェクト横断）

application/{app_name}/docs/                       # アプリケーション（コンテキスト）ごと
├── ubiquitous_language.md                         # ユビキタス言語（コンテキスト固有）
└── specs/{feature-name}/
    ├── requirements.md                            # 要件定義書（問題空間: WHAT）
    ├── design.md                                  # 機能設計書（解決空間: HOW）
    ├── test-design.md                             # テスト設計書
    └── tasks.md                                   # タスクリスト
```

各文書の先頭には必ず下記を明記する:
```
文書ID: (例:REQ-FEATURE-NAME-2026-001)
作成日: 2026/01/01
更新日:
対応文書: (源となった文書のパス)
```

## SDDを省略してよい場合

- 単純なバグ修正（1ファイル以内の修正）
- 既存機能の軽微な調整（UI文言変更等）
- ユーザーが明示的にバイブコーディングを指定した場合

省略する場合でも、命名は対象アプリケーションの `docs/ubiquitous_language.md` に準拠する。

## 実行手順

1. ユーザーの依頼内容からどのフェーズから開始するか判断する
2. 引数でフェーズが指定されている場合はそのフェーズから開始する
3. `docs/strategic_design.md` の存在を確認し、位置づけを確認する
4. 各フェーズの手順に従って進める
5. 各承認ゲートでユーザーの承認を求める
6. DDD壁打ちが必要な場合は `references/ddd-brainstorming-guideline.md` を Read ツールで読み取る
