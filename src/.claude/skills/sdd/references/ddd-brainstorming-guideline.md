# DDD（ドメイン駆動設計）壁打ちガイドライン

本ガイドラインは、DDDの戦略的設計・戦術的設計の考え方に基づいて、
要件定義・設計の壁打ちを行う際の指針である。

AIはこのガイドラインを読んだ上で、DDDの専門家として壁打ちの相手を務める。
ただし、**ビジネスの判断は人が行う**。AIの役割は以下の3つに限定する:

1. **問いかけ**: 「この判断の根拠は何ですか？」「別の分け方をした場合のトレードオフは？」
2. **知識の提供**: DDDのパターンや原則を、現在の文脈に合わせて説明する
3. **整理と記録**: 壁打ちの結果を構造化して文書に落とし込む

---

## 1. 戦略的設計の壁打ち

### 壁打ちの全体の流れ

```
Step 1: 業務の全体像を把握する（BMC）
  ↓
Step 2: サブドメインを識別・分類する
  ↓
Step 3: 境界づけられたコンテキストを識別する
  ↓
Step 4: コンテキスト間の関係を整理する（コンテキストマッピング）
  ↓
Step 5: ユビキタス言語（core）を整理する
  ↓
Step 6: strategic_design.md として記録する
```

### Step 1: 業務の全体像を把握する

**AIが聞くべき問い:**
- 「この業務は、誰のために、何を達成するためのものですか？」
- 「この業務の始まりはどこで、終わりはどこですか？」
- 「関わる人・部門・外部組織は誰ですか？ それぞれの役割は？」
- 「現在どのようなシステムが使われていますか？」
- 「現在の業務で困っていること、改善したいことは何ですか？」
- 「部門ごとに同じ言葉を違う意味で使っていることはありますか？」

**注意**: まだ解決策（アプリケーション）の話はしない。業務そのものを理解することに集中する。

### Step 2: サブドメインを識別・分類する

| 分類 | 判断基準 | 設計への影響 |
|------|---------|-------------|
| **コアサブドメイン** | 事業の競争優位・業務価値の中核 | 最も設計に時間をかける |
| **支援サブドメイン** | コアを支えるが差別化要因ではない | 適度な品質で効率的に実装 |
| **汎用サブドメイン** | どの事業にも共通する一般的な問題 | 既存サービスに委ねる |

**AIが聞くべき問い:**
- 「最も業務価値が高い部分はどこですか？」
- 「従来のやり方と比べて、最も改善される部分はどこですか？」
- 「この部分は既存のシステムやサービスに任せられますか？」

**コツ**: コアサブドメインは1つか2つ。「全部コア」は分類できていない証拠。

### Step 3: 境界づけられたコンテキストを識別する

**境界を見つける手がかり:**

| 手がかり | 説明 |
|---------|------|
| 言葉の意味が変わる | 同じ用語が部門/工程で異なる意味を持つ |
| 担当者が変わる | 異なる人/部門が責任を持つ |
| 時間軸が変わる | 業務のフェーズが切り替わる |
| システムが変わる | 異なるシステムが管轄する |
| データの主導権が変わる | データの作成・更新の責任者が変わる |

### Step 4: コンテキストマッピング

**主要なパターン:**

| パターン | 意味 | いつ選ぶか |
|---------|------|-----------|
| 顧客/供給者 | 上流が下流のニーズを考慮 | 自社内の別チーム間 |
| 順応者 | 下流が上流のモデルにそのまま従う | 変更できない外部システム |
| 腐敗防止層（ACL） | 外部モデルを自モデルに変換する層 | 外部モデルがドメインモデルと異なる場合 |
| 公開ホストサービス | 標準化されたインターフェースで公開 | 複数の消費者にデータを提供 |
| 公表された言語 | 共通のデータ交換フォーマット | CSV、JSON等のデータ交換 |
| 共有カーネル | モデルの一部を共有 | 合意の上で共有、変更を同期できる場合 |
| 別々の道 | 統合しない | 統合コストが利益を上回る場合 |

### Step 5: ユビキタス言語（core）の整理

**coreに含める用語の基準:**
- 全コンテキストで同じ意味を持つ用語
- 外部システムの名称
- コンテキスト間で受け渡されるデータのキー項目
- 組織・ロールの名称

**coreに含めない用語の基準:**
- 特定のコンテキストでのみ意味を持つ用語
- コンテキストごとに意味が異なる用語
- 実装技術の用語

### Step 6: strategic_design.md として記録する

```markdown
# 戦略的設計書

## メタ情報
- プロジェクト名:
- 最終更新日:
- バージョン:

## 1. ビジネスモデルキャンバス（BMC）
（9要素を記述）

## 2. ドメインの分類
### 2.1 コアサブドメイン
### 2.2 支援サブドメイン
### 2.3 汎用サブドメイン

## 3. 境界づけられたコンテキスト
（各サブドメイン内のコンテキスト一覧と責務）

## 4. コンテキストマップ
（テキストベースの図 + 関係一覧テーブル）

## 5. 設計判断の記録
（選択肢、選んだもの、理由、トレードオフ）

## 6. 未解決の問い
```

## 2. 戦術的設計の壁打ち

戦術的設計は、1つの境界づけられたコンテキスト内部の設計を扱う。
SDDワークフローの Phase 2.5 または Phase 3 で行う。

### 2.1 ドメインモデルの作成手順

**Step 1: ドメインの関心事を特定する**

要件定義書から以下を抽出する:
- **名詞**: エンティティ、バリューオブジェクトの候補
- **動詞**: ドメインサービス、アプリケーションサービスの候補
- **形容詞/状態**: ステータス、列挙型の候補
- **ルール/条件**: ビジネスルール、バリデーションの候補

**Step 2: エンティティとバリューオブジェクトを区別する**

| 問い | エンティティ | バリューオブジェクト |
|------|------------|------------------|
| 同一性の判断基準は？ | IDで識別 | 値で識別 |
| ライフサイクルがある？ | ある | ない（不変） |
| 変更を追跡する必要がある？ | ある | ない |

### 2.2 集約の設計

**集約の設計原則:**
1. 小さく保つ
2. 集約ルートを決める（外部からは集約ルート経由でのみアクセス）
3. 集約間はIDで参照（オブジェクト参照ではなく）
4. 1トランザクション = 1集約

**AIが聞くべき問い:**
- 「このデータとこのデータは、必ず同時に整合性を保つ必要がありますか？」
- 「この集約を更新するとき、他の集約も同時に更新する必要がありますか？」

### 2.3 ビジネスルールの具体化

**ビジネスルールの見つけ方:**

| パターン | 例 | ルールの種類 |
|---------|-----|------------|
| 「〜の場合は〜する」 | 在庫0かつ実在庫≠0の場合は赤表示 | 条件分岐ルール |
| 「〜でなければならない」 | 区分コードは1〜31の範囲 | バリデーションルール |
| 「〜から計算される」 | 差異 = 実在庫 - 理論在庫 | 導出ルール |
| 「〜したとき〜が起きる」 | アップロード完了時に記録を登録 | イベント駆動ルール |

**ビジネスルールの配置先:**

| ルールの種類 | 配置先 | 理由 |
|------------|--------|------|
| エンティティ固有のバリデーション | エンティティ自身 | 自分の整合性は自分で守る |
| VOの制約 | VOのコンストラクタ | 不正な値は生成させない |
| 複数エンティティにまたがるルール | ドメインサービス | 特定のエンティティに属さない |
| ユースケースの制御フロー | アプリケーションサービス | 技術的な制御はドメインの外 |
| 技術的な制約 | インフラストラクチャ層 | タイムアウト、リトライ等 |

### 2.4 インプットとアウトプットの明確化

各ユースケースについて以下を明確にする:

```
ユースケース名:
  トリガー: （誰が、何をしたときに実行されるか）
  インプット:
    - （必要なデータと、その出所）
  処理:
    - （ドメインルールの適用）
  アウトプット:
    - （生成されるデータと、その送り先）
  エラーケース:
    - （異常系とその対処）
```

## 3. 壁打ちの進め方

### 壁打ちの姿勢

**やること:**
- 人の発言を整理し、構造化して返す
- 「なぜそう思うか」を掘り下げる問いを投げる
- DDDの概念を、今の文脈に合わせた具体例で説明する
- 代替案とトレードオフを提示する
- 壁打ちの途中経過をこまめに整理する

**やらないこと:**
- 人に代わってビジネスの判断を下す
- DDDの教科書的な正解を押し付ける
- 人の判断を「DDDの原則に反する」と否定する
- 壁打ちの全体を一度に進めようとする

### 壁打ちのセッション構成

1回で全ステップを終える必要はない。分割を推奨する:

| セッション | 内容 | 所要時間の目安 |
|-----------|------|-------------|
| セッション1 | Step 1〜2（全体像とサブドメイン分類） | 30〜60分 |
| セッション2 | Step 3〜4（コンテキストとマッピング） | 30〜60分 |
| セッション3 | Step 5〜6（ユビキタス言語 core と文書化） | 30〜60分 |

### 既存プロジェクトへの適用

既にアプリケーションが存在するプロジェクトに適用する場合:

1. 既存の文書・コードから逆算して戦略的設計を整理する
2. 「暗黙的にやっていたこと」を明示化することが主な作業
3. 大幅な設計変更を目的とせず、**現状の設計判断を言語化して記録する**ことに価値がある

## 4. 小規模プロジェクトでの現実的なアプローチ

- **完璧を目指さない**: strategic_design.md は「今の理解」を記録するもの。後から更新する前提で作る
- **形式より実質**: パターン名を正確に当てはめることより、「外部との境界が守られているか」が重要
- **暗黙知の明示化に価値がある**: 「なぜこう分けたか」を書き残すだけで、将来の自分や後任者への大きな贈り物になる
- **サブドメイン分類は3〜5個で十分**: 小規模プロジェクトで10個以上は分けすぎ
- **どんな小さなツールでも地図上で位置を確認する**: バラバラに作ったツールが後から統合の障害になるリスクを防ぐ
