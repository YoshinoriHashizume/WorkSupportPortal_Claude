# テスト戦略ガイドライン

本ファイルは、テスト設計の基本的な考え方を言語・フレームワーク非依存で定義する。
テスト設計書の作成（make-test-design）およびテスト設計レビュー（design-review-l2）で
共通の基準として使用する。

---

## 1. テストの分類

### 1.1 単体テスト（Unit Test）

**目的**: 1つのクラス・関数・メソッドが正しく動作することを検証する。

**対象**:
- エンティティのビジネスロジック（バリデーション、状態遷移、計算）
- バリューオブジェクトの生成・等価性判定・不正値の拒否
- ドメインサービスのビジネスルール
- アプリケーションサービスのユースケースフロー（リポジトリはモック）

**特徴**:
- 外部依存なし（DB、API、ファイルシステムを使わない）
- 高速に実行できる（ミリ秒単位）
- 失敗時に原因箇所が特定しやすい

**Clean Architectureにおける単体テスト対象**:

| レイヤー | 単体テスト対象 | DB依存 |
|---------|-------------|--------|
| Domain層 — エンティティ | ビジネスルール、バリデーション、状態遷移 | 不要 |
| Domain層 — バリューオブジェクト | 生成、等価性、不正値の拒否 | 不要 |
| Domain層 — ドメインサービス | 複数エンティティにまたがるルール | 不要 |
| Application層 — ユースケース | 制御フロー（リポジトリはモック/スタブ） | 不要 |

### 1.2 結合テスト（Integration Test）

**目的**: 複数のコンポーネントが連携して正しく動作することを検証する。

**対象**:
- リポジトリ実装（実際のDBに対する読み書き）
- APIクライアント（実際のAPIまたはモックサーバーに対する通信）
- ビュー/コントローラー（HTTPリクエスト→レスポンスの一連の流れ）

**特徴**:
- 外部依存あり（DB、API等を実際に使用する）
- 単体テストより遅い
- コンポーネント間の結合部分の不具合を検出できる

**Clean Architectureにおける結合テスト対象**:

| レイヤー | 結合テスト対象 | DB依存 |
|---------|-------------|--------|
| Infrastructure層 — リポジトリ | DB読み書き、エンティティ変換 | 必要 |
| Infrastructure層 — APIクライアント | API通信、レスポンス変換 | 不要（デモJSON使用） |
| Interfaces層 — ビュー | HTTPリクエスト→レスポンス | 必要 |

### 1.3 E2Eテスト（End-to-End Test）

**目的**: ユーザーの操作シナリオ全体が正しく動作することを検証する。

**特徴**:
- 最も実行が遅い
- 環境構築が複雑
- 小規模プロジェクトでは省略してよい場合が多い

---

## 2. テストピラミッド

```
        /  E2E  \          ← 少数（重要なシナリオのみ）
       /----------\
      / 結合テスト  \       ← 中程度（外部連携の検証）
     /--------------\
    /  単体テスト     \     ← 多数（ビジネスロジックの核心）
   /------------------\
```

**原則**: 単体テスト > 結合テスト > E2Eテスト の順に数を多くする。

**理由**:
- 単体テストは高速・安定・原因特定が容易
- 結合テストはDBやAPIの状態に依存するため不安定になりやすい
- E2Eテストは環境全体に依存するため最も不安定

## 3. Clean Architectureにおけるテスト方針

### 3.1 Domain層のテスト（最優先）

Domain層はビジネスロジックの核心であり、最も重点的にテストする。

**エンティティのテスト項目**:
- 正常な値での生成
- 不正な値での生成拒否（バリデーション）
- ビジネスルールの適用（状態遷移、計算、判定）
- エッジケース（境界値、null/空、最大/最小）

**バリューオブジェクトのテスト項目**:
- 正常な値での生成
- 不正な値での生成拒否
- 等価性の判定（同じ値 → 等しい、異なる値 → 等しくない）
- 不変性の確認（生成後に変更できないこと）

**ファーストクラスコレクションのテスト項目**:
- コレクションの操作（フィルタ、ソート、集計）
- 空コレクションの振る舞い
- 要素数の境界値（0個、1個、多数）

**ドメインサービスのテスト項目**:
- ビジネスルールの適用結果
- 複数エンティティの組み合わせパターン
- エッジケース

### 3.2 Application層のテスト

**ユースケースのテスト項目**:
- 正常フロー（入力→処理→出力）
- エラーフロー（バリデーションエラー、ビジネスルールエラー）
- リポジトリの呼び出し順序・引数の検証
- 戻り値（DTO）の正確性

**モック/スタブの方針**:
- リポジトリはモック/スタブで置き換える
- ドメインモデルは実物を使う（モックにしない）
- 外部サービスのクライアントはモック/スタブで置き換える

### 3.3 Infrastructure層のテスト

**リポジトリ実装のテスト項目**:
- CRUD操作（Create, Read, Update, Delete）
- エンティティ ↔ DBモデル/APIレスポンスの変換が正しいか
- 検索条件の正確性
- トランザクション境界

**APIクライアントのテスト項目**:
- リクエストの形式（URL、メソッド、ヘッダー、ボディ）
- レスポンスの変換（JSON → ドメインモデル）
- エラーレスポンスのハンドリング
- タイムアウト、リトライ

### 3.4 Interfaces/Presentation層のテスト

**ビュー/コントローラーのテスト項目**:
- HTTPステータスコード
- レスポンスボディの構造
- 認証・認可
- バリデーションエラーのレスポンス

## 4. テストケースの設計原則

### 4.1 テストケース名

**原則**: 何をテストしているかが名前だけでわかること。

**良い例**:
- `test_create_area_no_with_valid_value_returns_area_no`
- `test_create_area_no_with_empty_string_raises_validation_error`
- `test_survey_result_with_quantity_difference_is_flagged`

**悪い例**:
- `test_area_no_1`
- `test_create`
- `test_validation`

### 4.2 テストの構造（Arrange-Act-Assert）

```
Arrange: テストの前提条件を準備する
Act:     テスト対象の操作を実行する
Assert:  期待される結果を検証する
```

### 4.3 テストの独立性

- 各テストケースは他のテストケースに依存しない
- テストの実行順序が変わっても結果が変わらない
- テストデータは各テスト内で準備・後片付けする

### 4.4 意味のあるアサーション

- `assert True` や形だけのアサーションは禁止
- 具体的な入力と期待される出力を検証する
- 1つのテストケースで検証する観点は1つに絞る

## 5. 境界値・異常系のテスト

### 5.1 境界値テスト

数値、文字列長、日付等に対して以下をテストする:

| パターン | 例 |
|---------|-----|
| 最小値 | 0、空文字、最古の日付 |
| 最小値 - 1 | -1、null |
| 最大値 | 上限値、最大文字列長 |
| 最大値 + 1 | 上限値 + 1 |
| 典型値 | 通常使用される中間値 |

### 5.2 異常系テスト

| パターン | テスト内容 |
|---------|----------|
| null / nil / None | null入力時の振る舞い |
| 空文字 / 空配列 | 空データの処理 |
| 不正な型 | 文字列が期待される場所に数値 |
| 重複 | 同じデータの二重登録 |
| 同時実行 | 競合状態の処理 |
| タイムアウト | 外部通信のタイムアウト |
| データ不整合 | DBの状態が想定と異なる場合 |

## 6. テストデータの管理

### 方針

| 方式 | 用途 | 利点 |
|------|------|------|
| テストコード内に直接記述 | 単純なテストデータ | 可読性が高い |
| Fixture / Factory | 複雑なテストデータ | 再利用性が高い |
| 実ファイル（TestDataフォルダ） | Excel、CSV等のファイルテスト | 実データに近い検証ができる |
| デモJSON | API連携のテスト | 実APIなしでテスト可能 |

### テストデータの原則

- テストデータはテストコードと一緒にGit管理する
- 本番データをテストに使わない（個人情報、機密情報のリスク）
- テストデータは最小限にする（テスト対象の検証に必要な分だけ）
