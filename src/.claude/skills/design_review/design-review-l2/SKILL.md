# テスト設計書 Design-L2レビュー（テスト設計レビュー）

あなたはテスト設計の専門家です。
テスト設計書（test-design.md）に対して、Design-L2レビュー（テスト戦略・テストケースの妥当性チェック）を行ってください。

## レビューの目的

テスト設計書が以下の基準を満たしているかを検証する:

1. **テスト戦略の妥当性**: テストピラミッドに沿った戦略が定義されているか
2. **テストケースの網羅性**: 要件定義書・機能設計書の内容が網羅されているか
3. **境界値・異常系のカバレッジ**: 境界値・異常系が十分にテストされているか
4. **テストケースの品質**: テストケース名・入出力が具体的で実行可能か

## レビュー対象の特定

$ARGUMENTS

- ファイルパスが指定されている場合は Read ツールで読み取る
- **引数が空の場合は、必ずユーザーに「どのテスト設計書をレビューしますか?」と質問してください。**
- パスのヒント: テスト設計書は通常 `application/{app_name}/docs/specs/{feature-name}/test-design.md` に配置されています。

## 関連文書の読み込み

以下の文書が存在する場合は Read ツールで読み取り、レビューの基準として使用してください:

1. 対応する機能設計書 — `application/{app_name}/docs/specs/{feature-name}/design.md`
2. 対応する要件定義書 — `application/{app_name}/docs/specs/{feature-name}/requirements.md`
3. `application/{app_name}/docs/ubiquitous_language.md` — 用語の確認

## テスト戦略referenceの読み込み（バージョンチェック含む）

### referenceの読み取り

`references/test-strategy.md` を Read ツールで読み取る。
ファイル先頭のメタデータ（version, updated, source-name）を記録する。

### バージョン整合性チェック

以下のスキルに同名のreferenceが存在する場合、先頭のメタデータのみを確認する:

- `make-test-design/references/test-strategy.md`

**一致**: 「テスト戦略reference整合性チェック: ✅ 一致」と報告
**不一致**: 警告を表示し、続行するか確認する

## レビュー観点

以下の4つの観点でレビューを行う。

---

### 観点1: テスト戦略の妥当性

test-strategy.mdの原則に基づき、テスト戦略の設計を検証する。

- [ ] テストピラミッド（単体 > 結合 > E2E）に沿った戦略になっているか
- [ ] Domain層のテストが最優先されているか
- [ ] 各レイヤー（Domain / Application / Infrastructure / Interfaces）のテスト方針が明確か
- [ ] DB依存/DB不要の区別が適切か
- [ ] モック/スタブの方針が適切か（ドメインモデルはモックにしない等）
- [ ] テスト優先順位が定義されているか

**判定基準**:
- **NG**: テストピラミッドに反している（結合テストばかりで単体テストがない等）、Domain層のテストがない
- **警告**: テスト方針は概ね適切だが、一部のレイヤーのテスト方針が不明確
- **OK**: テストピラミッドに沿い、各レイヤーの方針が明確

---

### 観点2: テストケースの網羅性

要件定義書と機能設計書の内容がテストケースで網羅されているかを検証する。

- [ ] 要件定義書の各機能要件（REQ-F-xxx）に対応するテストケースが存在するか
- [ ] 機能設計書の各エンティティに対する生成・バリデーションのテストケースがあるか
- [ ] 機能設計書の各バリューオブジェクトに対する生成・等価性・不正値のテストケースがあるか
- [ ] 機能設計書のドメインサービスに対するテストケースがあるか
- [ ] 機能設計書のユースケースに対するテストケースがあるか
- [ ] エラーハンドリングに対するテストケースがあるか
- [ ] テストケースの対応REQ-IDが記載されているか

**判定基準**:
- **NG**: 主要な機能要件に対応するテストケースが欠落している
- **警告**: テストケースは概ね網羅しているが、一部の要件やモデルのテストが不足
- **OK**: 要件・設計書の内容が網羅されている

---

### 観点3: 境界値・異常系のカバレッジ

- [ ] 数値型の境界値テスト（最小値、最小値-1、最大値、最大値+1）が含まれているか
- [ ] 文字列型の境界値テスト（空文字、最大長、最大長+1）が含まれているか
- [ ] null / nil / None に対するテストが含まれているか
- [ ] 不正な型・フォーマットに対するテストが含まれているか
- [ ] 重複データに対するテストが含まれているか
- [ ] 外部システムのエラー（タイムアウト、接続エラー等）に対するテストが含まれているか

**判定基準**:
- **NG**: 境界値テストまたは異常系テストが全くない
- **警告**: 一部の境界値・異常系が不足
- **OK**: 境界値・異常系が十分にカバーされている

---

### 観点4: テストケースの品質

- [ ] テストケース名が「何をテストしているか」が名前だけでわかるか
- [ ] 各テストケースに具体的な入力と期待結果が定義されているか
- [ ] `assert True` や形だけのアサーションがないか
- [ ] テストデータが具体的に定義されているか
- [ ] ユビキタス言語集の用語がテストケース名に使われているか
- [ ] テストの独立性が保たれているか（テスト間の依存がないか）

**判定基準**:
- **NG**: テストケースに具体的な入力・期待結果がない、または意味のないアサーションがある
- **警告**: テストケース名が不明確、またはテストデータが不十分
- **OK**: テストケースが具体的で実行可能

## 判定基準（総合）

- **PASS**: NG 0件
- **CONDITIONAL PASS**: NG 1〜3件
- **FAIL**: NG 4件以上、またはDomain層のテストが欠落
