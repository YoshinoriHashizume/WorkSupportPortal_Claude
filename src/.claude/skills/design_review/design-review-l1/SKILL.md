# 設計書 Design-L1レビュー（機能設計レビュー）

あなたはドメイン駆動設計(DDD)の戦術的設計の専門家です。
設計書に対して、Design-L1レビュー（ドメイン設計の妥当性チェック）を行ってください。

本スキルはプログラミング言語やフレームワークに依存しない。
Clean Architectureの実装レベルの検証はDesign-L3（実装レビュー）で行う。

## レビューの目的

設計書が以下の基準を満たしているかを検証する:

1. **戦略的設計との整合性**: コンテキスト境界・サブドメイン分類を守っているか
2. **ドメインモデルの妥当性**: エンティティ、VO、集約の設計が適切か
3. **ビジネスルールの配置**: ルールが適切なコンポーネントに配置されているか
4. **ユビキタス言語との整合性**: 用語が言語集と整合しているか

## レビュー対象の特定

$ARGUMENTS

- 上記の引数でファイルパスが指定されている場合は、そのファイルを Read ツールで読み取ってレビューを実施してください。
- **引数が空、または設計書のパスが不明な場合は、必ずユーザーに「どの設計書をレビューしますか?」と質問してください。** 推測で勝手にファイルを選ばないこと。
- パスのヒント: 設計書は通常 `application/{app_name}/docs/specs/{feature-name}/design.md` に配置されています。

## 関連文書の読み込み

以下の文書が存在する場合は Read ツールで読み取り、レビューの基準として使用してください:

1. `docs/strategic_design.md` — 戦略的設計書
2. `application/{app_name}/docs/ubiquitous_language.md` — ユビキタス言語集（コンテキスト固有）
3. `docs/ubiquitous_language_core.md` — ユビキタス言語集（core、存在する場合）
4. 対応する要件定義書 — 設計書の「対応文書」欄に記載されたファイル

## アーキテクチャreferenceの読み込み（バージョンチェック含む）

### 技術スタックの判定

CLAUDE.mdのセクション1（Project Overview）の技術スタックテーブルを確認し、
該当するreferenceを判定する:

- Swift → `references/swift-clean-architecture.md`
- Django / Python → `references/django-clean-architecture.md`
- C# → `references/csharp-clean-architecture.md`

判定できない場合はユーザーに確認する。

### referenceの読み取りとバージョンチェック

該当するreferenceファイルを Read ツールで読み取る。
ファイル先頭のメタデータ（version, updated, source-name）を記録する。

以下のスキルに同名のreferenceが存在する場合、先頭のメタデータのみを確認する:

- `make-design/references/{同名ファイル}`
- `design-review-l3/references/{同名ファイル}`

**一致**: 「アーキテクチャreference整合性チェック: ✅ 一致」と報告
**不一致**: 警告を表示し、続行するか確認する

## レビュー観点

以下の4つの観点でレビューを行う。各チェック項目について
「OK / 警告 / NG」で判定し、NG・警告の場合は該当箇所と修正案を示すこと。

---

### 観点1: 戦略的設計との整合性

- [ ] 設計書が対象とするコンテキストが明確か
- [ ] 設計書の内容が対象コンテキストの境界を越えていないか
- [ ] 外部システムとの連携方式がコンテキストマッピングに沿っているか
- [ ] コンテキスト間のデータ受け渡しが上流/下流の関係と整合しているか
- [ ] サブドメインの分類に応じた設計の詳細度になっているか

**判定基準**:
- **NG**: コンテキスト境界を越えている、またはコンテキストマッピングと矛盾
- **警告**: 対象コンテキストが不明確
- **OK**: 対象コンテキストが明確で整合している

**strategic_design.mdが存在しない場合**: この観点はスキップし、その旨を記載する。

---

### 観点2: ドメインモデルの妥当性

- [ ] エンティティとバリューオブジェクトの区別は適切か
- [ ] バリューオブジェクトは不変で、不正な値を生成できない設計になっているか
- [ ] 集約の境界は適切か（小さく保たれているか、集約間はIDで参照か）
- [ ] 集約ルートが明確で、外部から集約内部に直接アクセスする設計になっていないか
- [ ] ファーストクラスコレクションの使い方は適切か
- [ ] ドメインサービスの使い方は適切か（ドメインモデル貧血症になっていないか）

**判定基準**:
- **NG**: エンティティ/VOの区別が不適切、集約がコンテキスト境界を跨いでいる、貧血症が深刻
- **警告**: 集約の境界が暗黙的、VOの構成要素が不明確
- **OK**: ドメインモデルの構造が明確でDDD原則に沿っている

---

### 観点3: ビジネスルールの配置

referenceのアーキテクチャ定義を参照し、ビジネスルールが適切なレイヤー・コンポーネントに配置されているかを検証する。

**配置原則**:

| ルールの種類 | 配置先 |
|------------|--------|
| エンティティ固有のバリデーション | エンティティ自身 |
| バリューオブジェクトの制約 | VOのコンストラクタ |
| 複数エンティティにまたがるルール | ドメインサービス |
| ユースケースの制御フロー | アプリケーションサービス |
| 技術的な制約 | インフラストラクチャ層 |

- [ ] エンティティ固有のバリデーションがエンティティ自身に配置されているか
- [ ] バリューオブジェクトの制約がVOのコンストラクタに配置されているか
- [ ] 複数エンティティにまたがるルールがドメインサービスに配置されているか
- [ ] ビジネスルールがプレゼンテーション層やインフラストラクチャ層に漏れ出していないか

**判定基準**:
- **NG**: ビジネスルールがインフラ層やプレゼンテーション層に配置
- **警告**: 配置先が不明確
- **OK**: 適切なコンポーネントに配置されている

---

### 観点4: ユビキタス言語との整合性

- [ ] モデル名がユビキタス言語集の英語名と一致しているか
- [ ] 日本語表記がユビキタス言語集の正式名称と一致しているか
- [ ] 「使用しない表現」が設計書内で使われていないか
- [ ] 新たに登場した概念がユビキタス言語集に反映されるべきか
- [ ] 設計書内で複数の表記が混在していないか

**判定基準**:
- **NG**: 主要概念がユビキタス言語集と矛盾
- **警告**: 軽微な不一致、新規用語の追加漏れ
- **OK**: 用語が整合している

## 判定基準（総合）

- **PASS**: NG 0件
- **CONDITIONAL PASS**: NG 1〜3件
- **FAIL**: NG 4件以上、またはドメインモデルが根本的に不適切
