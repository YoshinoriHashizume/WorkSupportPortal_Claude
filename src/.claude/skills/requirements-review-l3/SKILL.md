# 要件定義書 L3レビュー（妥当性・網羅性チェック）

あなたは要件定義とDDD戦略的設計の専門家です。
要件定義書に対して、L3レビュー（内容の妥当性と網羅性のチェック）を行ってください。

L1レビュー（形式チェック）とL2レビュー（用語再定義）が完了していることが前提です。

## レビューの目的

要件定義書の内容が以下の基準を満たしているかを検証する:

1. **ビジネス要件との整合性**: 要件がビジネス上の目的・課題と合致しているか
2. **戦略的設計との整合性**: コンテキスト境界・サブドメイン分類と整合しているか
3. **スコープの適切性**: 大きすぎず小さすぎないか、「やらないこと」が明確か
4. **異常系・エッジケースの考慮**: 正常系だけでなく例外的な状況が検討されているか
5. **既存システムへの影響**: 既存システムとの連携・影響が検討されているか

## レビュー対象の特定

$ARGUMENTS

- ファイルパスが指定されている場合は Read ツールで読み取る
- **引数が空の場合は、必ずユーザーに「どの要件定義書をレビューしますか?」と質問してください。**

## 関連文書の読み込み

以下の文書が存在する場合は Read ツールで読み取り、レビューの基準として使用してください:

1. `docs/strategic_design.md` — 戦略的設計書
2. `application/{app_name}/docs/ubiquitous_language.md` — ユビキタス言語集（L2で更新済みの前提）
3. `docs/ubiquitous_language_core.md` — ユビキタス言語集（core）
4. L1/L2レビュー結果がこの会話内にあれば参照する

## レビュー観点

以下の5つの観点でレビューを行う。

---

### 観点1: ビジネス要件との整合性

要件定義書の「背景と目的」がビジネス上の課題解決と合致しているかを検証する。

- [ ] 「なぜこの機能が必要なのか」が明確に記述されているか
- [ ] 目的が具体的か（「業務を効率化する」のような抽象的な表現ではなく、具体的な改善点が記述されているか）
- [ ] BMC（ビジネスモデルキャンバス）の「価値の提案」と整合しているか
- [ ] 機能が解決しようとしている課題が、BMCの「コスト構造」や「主要な活動」と対応しているか
- [ ] 想定ユーザーが明確で、BMCの「顧客セグメント」と整合しているか

**判定基準**:
- **NG**: 要件がビジネス上の目的と矛盾している、または目的が不明確
- **警告**: 目的は記述されているが抽象的
- **OK**: ビジネス要件と明確に整合している

**strategic_design.mdが存在しない場合**: BMCとの照合はスキップし、要件定義書内での整合性のみチェックする。

---

### 観点2: 戦略的設計との整合性

要件定義書の内容がstrategic_design.mdのサブドメイン分類・コンテキスト境界と整合しているかを検証する。

- [ ] 要件定義書が対象とするコンテキストが明確か
- [ ] 要件がコンテキストの境界を越えていないか
  - 例: [B]実棚卸調査の要件定義書に[E]分析・解析の要件が含まれていないか
- [ ] 外部システム（SLIMS、MARI等）との連携がコンテキストマッピングと整合しているか
- [ ] サブドメインの分類（コア/支援/汎用）に応じた要件の粒度になっているか
  - 支援サブドメインなのに過剰に高い非機能要件が定義されていないか

**判定基準**:
- **NG**: 要件がコンテキスト境界を明らかに越えている
- **警告**: 対象コンテキストが不明確
- **OK**: 戦略的設計と整合している

**strategic_design.mdが存在しない場合**: この観点はスキップし、その旨を記載する。

---

### 観点3: スコープの適切性

要件定義書のスコープが適切に設定されているかを検証する。

- [ ] スコープが大きすぎないか（1回の開発イテレーションで完了可能な範囲か）
- [ ] スコープが小さすぎないか（ビジネス価値のある最小単位が含まれているか）
- [ ] 「やらないこと」（スコープ外）が明確に記述されているか
- [ ] スコープ外として記述された内容に、本来含めるべき要件が紛れていないか
- [ ] 将来の拡張性への言及があるか（「今回は対応しないが、将来的に〜」）
- [ ] 依存する前提条件が記述されているか（「○○が完了していること」等）

**判定基準**:
- **NG**: スコープが不明確、または「やらないこと」が記述されていない
- **警告**: スコープは記述されているが、境界が曖昧な箇所がある
- **OK**: スコープが明確で適切

---

### 観点4: 異常系・エッジケースの考慮

正常系だけでなく、例外的な状況が検討されているかを検証する。

**チェックすべき異常系パターン**:

| パターン | 例 |
|---------|-----|
| 入力値の不正 | 必須項目の未入力、型の不一致、範囲外の値 |
| データの不整合 | 外部システムとのデータ不整合、重複データ |
| 外部システムの障害 | API接続エラー、タイムアウト、認証失敗 |
| 権限の不足 | 権限のないユーザーがアクセスした場合 |
| 同時実行 | 複数ユーザーが同時に同じデータを操作した場合 |
| データ量の上限 | 大量データ処理時のパフォーマンス |
| 業務例外 | 棚卸し途中で中断した場合、差異が許容範囲を超えた場合 |

- [ ] 各機能要件に対して、異常系のシナリオが記述されているか
- [ ] 異常系の「期待される振る舞い」（エラーメッセージ、フォールバック等）が記述されているか
- [ ] 境界値（最小値、最大値、空、null等）が考慮されているか
- [ ] 外部システム障害時の振る舞いが記述されているか

**判定基準**:
- **NG**: 異常系が全く考慮されていない
- **警告**: 一部の異常系は考慮されているが、重要なパターンが漏れている
- **OK**: 主要な異常系・エッジケースが網羅されている

---

### 観点5: 既存システムへの影響

要件が既存のシステム・データ・業務フローに与える影響が検討されているかを検証する。

- [ ] 既存データベースのスキーマ変更が必要な場合、その影響が記述されているか
- [ ] 既存APIの変更が必要な場合、後方互換性が検討されているか
- [ ] 既存画面の変更が必要な場合、影響範囲が記述されているか
- [ ] 既存の業務フローへの影響（運用変更）が検討されているか
- [ ] データ移行が必要な場合、移行方針が記述されているか
- [ ] 他のコンテキストへの影響が検討されているか

**判定基準**:
- **NG**: 既存システムへの明らかな影響があるのに検討されていない
- **警告**: 影響は認識されているが、具体的な対応方針が記述されていない
- **OK**: 既存システムへの影響が適切に検討されている

## 判定基準（総合）

- **PASS**: NG 0件。要件の内容が妥当で網羅的
- **CONDITIONAL PASS**: NG 1〜2件。主要な要件は妥当だが、補強が必要な箇所がある
- **FAIL**: NG 3件以上、またはスコープが不明確でビジネス要件と矛盾

---

## レビュー結果の記録（requirements.md への追記）

レビュー完了後、レビュー対象の `requirements.md` 末尾に「## レビュー履歴」セクションを追記する。
**新規ファイルは作成しない**（散らかり防止のため、すべての記録を SSOT である requirements.md に集約する）。

### 記録手順

1. `date '+%Y/%m/%d %H:%M'` で現在時刻を取得する
2. 要件定義書を Read で読み直し、末尾に `## レビュー履歴` セクションが存在するか確認する
3. 存在しない場合: 末尾に新規追加する（`## レビュー履歴` 見出し + 今回のレビュー結果）
4. 存在する場合: 既存セクション内の末尾に `### L3レビュー (YYYY/MM/DD HH:MM)` を追記する
5. Edit ツールで該当箇所のみ追記する（要件定義書の本文は触らない）
6. 同じレベルの再レビュー時も、既存記録は残したまま新規サブセクションとして追記する

### 追記フォーマット

````markdown
## レビュー履歴

### L3レビュー (YYYY/MM/DD HH:MM)

**観点別サマリー**:

| 観点 | OK | 警告 | NG |
|------|-----|------|-----|
| 1. ビジネス要件との整合性 | X件 | X件 | X件 |
| 2. 戦略的設計との整合性 | X件 | X件 | X件 |
| 3. スコープの適切性 | X件 | X件 | X件 |
| 4. 異常系・エッジケースの考慮 | X件 | X件 | X件 |
| 5. 既存システムへの影響 | X件 | X件 | X件 |

**総合判定**: PASS / CONDITIONAL PASS / FAIL

**指摘事項**:

| # | 観点 | 重要度 | 該当箇所 | 指摘内容 | 対応 |
|---|------|--------|---------|---------|------|
| 1 | 観点4 | NG | §X.X | ... | 未対応 / 修正済み(commit abc1234) |

**未解決の指摘**: X件 (NG: X件 / 警告: X件)

**承認**: 承認者 / 承認日時（PASS の場合）

**次のアクション**: PASS → Phase 2.5/3 へ進む / CONDITIONAL → 指摘修正後に再レビュー
````

### 注意事項

- 要件定義書の本文（背景・目的・機能要件等の各セクション）は変更しない。レビュー履歴セクションのみに追記する
- 「対応」列は、指摘を実際に修正した時点で更新する（コミットハッシュを記載できれば併記）
- レビュー履歴は経緯を残すための監査ログ。**過去の指摘も削除しない**
- L3 で PASS となった場合は「承認」欄に承認者・承認日時を記録し、Phase 3 への移行可否の判断材料とする

---

## 次のステップ

レビュー完了後、以下を案内してください:
- 「要件定義書の承認が得られたら、Phase 2.5（Design Level Event Storming）または Phase 3（設計書の作成）に進めます」
- 「Phase 2.5を実施する場合は『Design Level Event Stormingを行いたい』と依頼してください」
- 「Phase 3に直接進む場合は『機能設計書を作成して』と依頼してください」

## 補足

- strategic_design.mdが存在しない場合、観点2はスキップして良い
- 小規模な機能追加の場合、観点5（既存システムへの影響）を重点的にチェックする
- 異常系の提案は「完璧」を目指すのではなく、「重要なもの」を漏れなく拾うことを目的とする
