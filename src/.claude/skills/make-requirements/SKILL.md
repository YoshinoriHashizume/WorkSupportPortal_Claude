# 要件定義書作成スキル

あなたは要件定義の専門家です。
壁打ちの整理メモや既存資料に基づき、要件定義書（requirements.md）を作成してください。

## 要件定義書の位置づけ

- 要件定義書は**問題空間（WHAT）** — 何が要求されているか
- 機能設計書は**解決空間（HOW）** — どうモデル化し実装するか（本スキルの対象外）
- 要件定義書は SDD フロー Phase 2 の成果物であり、**承認ゲート②** を経て Phase 3（設計）へ進む
- 作成した要件定義書は requirements-review-l1 / l2 / l3 で検証される

## WHAT / HOW 分離の原則（重要）

要件定義書には **WHAT のみ** を書く。以下は書かず、機能設計書（design.md）に委ねる:

- クラス設計・エンティティ/バリューオブジェクトの構造
- 処理手順・アルゴリズム・レイヤー配置
- 具体的なコード・関数シグネチャ

要件に処理フローが不可欠な場合は「実装レベルの手順は design.md で定義する」と明記し、
要件レベル（何を満たすべきか）の記述にとどめる。

## 実行フロー

```
Step 1: 入力（壁打ちメモ／参照資料）を読み取る
  ↓
Step 2: 関連文書を読み取る
  ↓
Step 3: 対象アプリ・機能名(feature-name)を確定する
  ↓
Step 4: 標準テンプレートで要件定義書を作成する
  ↓
Step 5: 自己レビューと改善を3回繰り返す
  ↓
Step 6: ユーザーに全文提示して承認を得る（承認ゲート②）
  ↓
Step 7: ファイルとして保存する
  ↓
Step 8: L1レビューを案内する
```

## Step 1: 入力の読み取り

$ARGUMENTS

- ファイルパスが指定されている場合は Read ツールで読み取る（壁打ちの整理メモ、既存要件、調査結果メモ等）
- 指定がない場合はユーザーに「要件の元になる情報（壁打ちメモ・課題・調査結果など）を教えてください」と確認する
- 情報が不足している場合は、Phase 0（壁打ち）相当の質問（5W1H + 制約）で不足を埋めてから進む

## Step 2: 関連文書の読み取り

以下の文書が存在する場合は Read ツールで読み取る:

1. `docs/strategic_design.md` — このコンテキストがどのサブドメイン・境界に位置するか
2. `application/{app_name}/docs/ubiquitous_language.md` — 用語（コンテキスト固有）
3. `docs/ubiquitous_language_core.md` — core用語
4. `CLAUDE.md` — セクション2のプロジェクト固有ルール

ubiquitous_language.md が存在する場合、要件定義書内の用語はこれに一貫して従う。
存在しない場合は「先にユビキタス言語集を整理しますか？（make-ubiquitous-language）」と案内してよい（必須ではない）。

## Step 3: 対象アプリ・機能名の確定

- 対象アプリケーション（`application/{app_name}`）を確定する。不明ならユーザーに確認する
- 機能名 `{feature-name}` を**ケバブケース**で確定する（例: `django-auth-integration`, `async-logging`）
- 同一アプリ内に既存の要件定義書（`application/{app_name}/docs/spec/` 配下）があるか Glob で確認する。この一覧は Step 7 のフォルダ連番採番にも使う（既存フォルダ数・既存プレフィックスの把握）

## Step 4: 要件定義書の作成

`references/requirements-template.md` を Read ツールで読み取り、テンプレートに沿って作成する。

### テンプレートの使い方

テンプレートは **必須セクション** と **条件付き任意セクション** で構成される。

- **必須セクション**は必ず記述する（requirements-review-l1 の必須セクション定義に対応）
- **条件付き任意セクション**は機能の性質に応じて追加し、該当しない場合は入れない（薄い章を作らない）

### 要件IDの採番規約

- **既定はシンプル形式**を使う:
  - 機能要件: `REQ-F-001`, `REQ-F-002`, ...
  - 非機能要件: `REQ-NF-001`, `REQ-NF-002`, ...
- **機能名入り形式**（`REQ-{FEAT}-F-001` / `REQ-{FEAT}-NF-001`）は、以下のいずれかに該当する場合のみ提案する:
  - 同一アプリ内に既にシンプル形式の要件定義書があり、要件IDの衝突・混同の恐れがある
  - 1アプリに複数機能の要件定義書が並存し、横断参照でIDを一意に識別したい
- 採番は連番・欠番なし・形式統一を厳守する（L1 観点4に対応）
- 判断に迷う場合はユーザーに「要件IDは既定のシンプル形式（REQ-F/REQ-NF）でよいですか？」と確認する

### 日付の取得

- 文書メタデータの作成日は `date '+%Y/%m/%d'`、更新日は初版では空欄にする
- 推測で日付を書かない

### 作成時の原則

- ubiquitous_language.md の用語を一貫して使用する（表記揺れを作らない）
- 正常系だけでなく、**異常系・エッジケース・スコープ外**を網羅的に洗い出す（L3観点に対応）
- 既存システムへの影響を検討する
- 「やらないこと（スコープ外）」を明確にする
- WHAT / HOW 分離の原則（上記）を守る
- 文書末尾に「## レビュー履歴」の空セクション枠を置く（review-l1/l2/l3 が追記する。新規ファイルを作らせないため）

## Step 5: 自己レビューと改善（3回反復）

ユーザーに提示する前に、以下のレビューと改善を **3回繰り返す**。
各回で観点をチェックし、問題があればその場で要件定義書を修正する。

- 1回目: 網羅性 — 機能要件・非機能要件・異常系・エッジケース・スコープ外に漏れがないか
- 2回目: 整合性 — ユビキタス言語との一貫性、要件ID採番、WHAT/HOW分離が守られているか
- 3回目: 妥当性 — ビジネス要件との整合、スコープの適切さ、既存システムへの影響

各回の改善内容は簡潔に記録し、Step 6でユーザーに「3回の自己レビューで何を改善したか」を添えて提示する。

## Step 6: ユーザーへの確認（承認ゲート②）

要件定義書の全文をユーザーに提示し、承認を求める。以下を自己点検してから提示する:

- [ ] ビジネス要件と整合しているか
- [ ] スコープが適切か
- [ ] 異常系・エッジケースが考慮されているか
- [ ] 既存システムへの影響が検討されているか
- [ ] 「やらないこと」が明確か
- [ ] ubiquitous_language.md の用語が一貫して使われているか
- [ ] WHAT のみを記述し、HOW（設計）が混入していないか

**承認されるまで保存・次フェーズに進んではならない。**

## Step 7: ファイルの保存

承認後、以下のパスに保存する:

```
application/{app_name}/docs/spec/{NN}_{feature-name}/requirements.md
```

- フォルダ名の先頭に **2桁ゼロ埋めの連番プレフィックス `{NN}_`** を付ける（起案順が一目で分かるようにするため）。例: `01_app-access-control`, `02_login-entry`
- **ファイル名 `requirements.md` は固定**（日付やアプリ名を付けない）。起案日は文書メタデータの `作成日` / `文書ID` に記録済みであり、下流スキル（make-design / requirements-review-l1〜l3 / make-test-design）が固定名で参照するため
- `design.md` / `test-design.md` / `tasks.md` も同じ `{NN}_{feature-name}/` フォルダ内に置く（4点セットでフォルダ単位に並ぶ）

### 連番プレフィックスの採番規則

Step 3 で把握した既存フォルダ一覧（`application/{app_name}/docs/spec/` 直下のフィーチャーフォルダ）を基に決める:

```
{NN} = max( 既存の NN_ プレフィックスの最大値, 既存フィーチャーフォルダの総数 ) + 1
     → 2桁ゼロ埋め（01, 02, 03, ...）
```

- プレフィックス無しの既存フォルダが混在していても破綻しないルール。既存が `login-entry`, `app-access-control`（プレフィックス無し2件）なら新規は `03_...` になる（既存2件は将来 01/02 に手動リネーム可能な余地を残す）
- プレフィックス済み `01_`, `02_` があれば新規は `03_...`
- 既存フォルダが1件も無ければ `01_...`
- 採番は連番・欠番なしを原則とする。判断に迷う場合はユーザーに確認する

※ 仕様書の格納階層は **`docs/spec/`（単数形）で統一する**。実フォルダ・全スキル・CLAUDE.md の標準は `docs/spec/`（単数形）である。新規作成分も必ず `docs/spec/` に置く。

## Step 8: 次のステップの案内

保存後、以下を案内する:

- 「要件定義書L1レビュー（形式・用語・構造チェック）を実行するには『要件定義書のL1レビューをお願い』と依頼してください」
- 「推奨フロー: L1（形式） → L2（用語再定義） → L3（妥当性）→ 承認後 Phase 3（設計書）へ」
