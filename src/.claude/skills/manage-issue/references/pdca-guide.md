# PDCA運用ガイド

Issueを Plan→Do→Check→Act のサイクルで回すための運用指針。
特に **Plan段階の分岐判断** と **既存SDD/レビュー体系との接続** を定義する。

---

## 1. PDCA全体像

```
┌─ P (Plan) ──────────────────────────────────────────────┐
│  起票    : Issue登録（事象/改善内容 = 問題空間WHAT）       │
│  トリアージ: 種別・優先度・影響範囲を判定                  │
│  対策決定 : 「軽微 / 本格SDD」を分岐 ← 最重要判断          │
└──────────────────────────────────────────────────────────┘
                    ↓
┌─ D (Do) ────────────────────────────────────────────────┐
│  軽微 → Issue内 `## 対策案` に書いて即実装（1ファイル修正）│
│  本格 → spec/{feature}/ を新設し design.md へ流す          │
└──────────────────────────────────────────────────────────┘
                    ↓
┌─ C (Check) ─────────────────────────────────────────────┐
│  検証    : 再現解消 / テスト / Design-L3レビュー / verify  │
│  結果記録 : Issueの `## 検証結果` に追記                   │
└──────────────────────────────────────────────────────────┘
                    ↓
┌─ A (Act) ───────────────────────────────────────────────┐
│  標準化  : 再発防止をCLAUDE.md/スキル/ユビキタス言語へ反映 │
│  クローズ : ステータス=Closed、振り返りを記録              │
│  横展開  : 派生Issueがあれば新規起票                       │
└──────────────────────────────────────────────────────────┘
```

---

## 2. Plan：対策の分岐判断基準

トリアージ後、以下の観点で **軽微 / 本格** を判定する。
これは CLAUDE.md「SDDを省略してよい場合」を Issue に組み込んだもの。

### 軽微（Issue1枚で完結）と判断する条件（概ね全て満たす）

- 修正範囲が **1ファイル以内**
- 新しいビジネスルール・ドメインモデルの変更を伴わない
- UI文言変更・単純なバグ修正・設定調整レベル
- 既存の設計方針を変えない

→ 対策は `## 対策案 (Plan)` に直接記述。設計書は作らない。

### 本格（spec委譲）と判断する条件（いずれか該当）

- 複数ファイル・複数レイヤーにまたがる
- 新しいビジネスルール・ドメインモデル・集約の追加/変更
- 新機能規模の改善
- 既存の設計方針・アーキテクチャに影響する

→ `spec/{feature}/` を新設し、既存SDDフロー（make-requirements →
make-design → make-test-design → タスク分解 → 実装）に乗せる。
Issueは起点・状態管理に徹する。

### 迷ったら

**判断に迷う場合は必ずユーザーに確認する**（CLAUDE.md 禁止事項3）。
「軽微対応で進めるか、本格SDDに乗せるか」を提示して選んでもらう。

---

## 3. 本格対策時のトレーサビリティ

双方向リンクで「設計の出自」を追えるようにする。

- **Issue → spec**: Issueの `## 対策案 (Plan)` に
  「詳細設計は `spec/{feature}/design.md` を参照」と記載
- **spec → Issue**: design.md 等の先頭 `対応文書:` に
  Issueの文書ID（例 `ISSUE-ACCOUNTS-IMP-2026-002`）を記載

これにより design.md 側から「なぜこの設計が生まれたか＝どのIssue起点か」を辿れる。

---

## 4. Check：既存レビュー体系との接続

Issueの検証は、既存の仕組みを流用する。

| 検証観点 | 使う仕組み |
|---|---|
| 実装が設計通りか・レイヤー違反がないか | implement-review-l1（実装レビュー） |
| 変更が実際に動くか（挙動確認） | verify スキル |
| 不具合の再現手順が解消したか | Issueの再現手順を再実行 |
| テストの網羅（本格対策時） | make-test-design → テスト実行 |

検証結果は Issueの `## 検証結果 (Check)` に記録する。

---

## 5. Act：標準化の反映先

再発防止・横展開のため、得た知見を適切な場所へ反映する。

| 知見の種類 | 反映先 |
|---|---|
| 開発プロセス・作業手順の改善 | 該当スキルの更新、または新スキル作成 |
| プロジェクト全体の遵守ルール | CLAUDE.md（改善ログに追記） |
| 用語の追加・再定義 | ユビキタス言語集（make-ubiquitous-language） |
| 設計方針の変更 | strategic_design.md / 該当 design.md |
| 別途対応が必要な事項 | 派生Issueを新規起票 |

**Act は「1件直して終わり」にせず、同種の問題を仕組みで防ぐ** ことを狙う。
反映が不要な場合は「反映先: なし」と明記してよい（何もしないことの明示化）。

---

## 6. ステータス遷移

```
Open ──トリアージ──▶ Triaged ──実装開始──▶ InProgress ──実装完了──▶ Verifying ──検証OK──▶ Closed
  │                     │
  │                     └──対応しないと判断──▶ Rejected
  └──優先度/時期の都合──▶ Deferred
```

- ステータス変更時は必ず frontmatter の `ステータス` と `更新日` を更新し、台帳（README.md）にも反映する
- Closed / Rejected 時は台帳の「クローズ済み」表へ移す
