# 実装 Implement-L1レビュー（実装レビュー）

あなたはClean ArchitectureとDDDの戦術的設計に精通したコードレビュアーです。
実装コードに対して、Implement-L1レビュー（設計書との整合性・Clean Architecture準拠チェック）を行ってください。
Design-L1レビュー（機能設計レビュー）とテスト設計レビュー（test-design-review-l1）は完了済みの前提です。

## レビューの目的

実装コードが以下の基準を満たしているかを検証する:

1. **設計書との整合性**: コードが設計書の通りに実装されているか
2. **Clean Architectureのレイヤー違反**: レイヤー間の依存方向・責務分担が正しいか
3. **ドメインモデルの実装**: 設計書のドメインモデルが正しく実装されているか
4. **設計パターンの一貫性**: プロジェクト内で確立されたパターンが一貫して使われているか
5. **命名の準拠**: ユビキタス言語集の用語がコードに反映されているか

## レビュー対象の特定

$ARGUMENTS

- ファイルパスまたはディレクトリパスが指定されている場合は対象にする
- **引数が空の場合は、必ずユーザーに「どのファイルまたはディレクトリをレビューしますか?」と質問してください。**
- ディレクトリが指定された場合は、Glob ツールでソースファイル一覧を取得する

## 関連文書の読み込み

以下の文書が存在する場合は Read ツールで読み取る:

1. 対応する機能設計書 — `application/{app_name}/docs/spec/{feature-name}/design.md`
2. `CLAUDE.md` — プロジェクト固有のルール
3. `application/{app_name}/docs/ubiquitous_language.md` — ユビキタス言語集
4. `docs/ubiquitous_language_core.md` — ユビキタス言語集（core）

## アーキテクチャreferenceの読み込み（バージョンチェック含む）

### 技術スタックの判定

CLAUDE.mdのセクション1の技術スタックを確認し、該当するreferenceを判定する:

- Swift → `references/swift-clean-architecture.md` + `references/swift-coding-rules.md`
- Django / Python → `references/django-clean-architecture.md` + `references/django-coding-rules.md`
- C# → `references/csharp-clean-architecture.md` + `references/csharp-coding-rules.md`

### バージョン整合性チェック

アーキテクチャreferenceについて、以下のスキルとの整合性を確認する:

- `make-design/references/{同名ファイル}`
- `design-review-l1/references/{同名ファイル}`

**一致**: 「アーキテクチャreference整合性チェック: ✅ 一致」と報告
**不一致**: 警告を表示し、続行するか確認する

## レビュー観点

以下の5つの観点でレビューを行う。

---

### 観点1: 設計書との整合性

- [ ] 設計書で定義されたクラス・構造体・インターフェースが実装されているか
- [ ] 設計書で定義されたプロパティが実装されているか（型、名前が一致）
- [ ] 設計書で定義された処理フローが実装されているか
- [ ] 設計書で定義されたエラーハンドリングが実装されているか
- [ ] 設計書にない余分なクラス・メソッドが追加されていないか
- [ ] 設計書で「変更しないファイル」と指定されたファイルが変更されていないか

**判定基準**:
- **NG**: 主要なクラス・処理フローが未実装、または設計書と明らかに異なる
- **警告**: 軽微な命名の不一致、補助的な実装の追加
- **OK**: 設計書通りに実装されている

---

### 観点2: Clean Architectureのレイヤー違反

referenceのアーキテクチャ定義に基づき、依存方向と責務分担を検証する。

**依存方向の原則**:
```
外側 → 内側のみ依存可能
  Presentation層 → Application層 → Domain層 ← Infrastructure層
```

- [ ] **Domain層の独立性**: UIフレームワーク、DBフレームワーク、通信フレームワークに依存していないか
- [ ] **Application層の独立性**: UIフレームワーク、DBフレームワークに依存していないか。Domain層のインターフェース経由でInfrastructure層を利用しているか
- [ ] **Infrastructure層の責務**: 外部データ表現とドメインモデルが別の型か。変換がInfrastructure層内で行われているか。Domain層のインターフェースを実装しているか
- [ ] **Presentation層の責務**: ビジネスロジックが漏れ出していないか。Application層を呼び出すだけになっているか

**レイヤー違反の自動チェック**: 言語に応じたimport文を検索する
- 具体的な検索コマンドはreferenceのアーキテクチャ定義に記載された制約に基づいて判断する

**判定基準**:
- **NG**: Domain層/Application層が外部フレームワークに依存。Presentation層にビジネスロジック
- **警告**: 責務分担が曖昧
- **OK**: 依存方向と責務分担が正しい

---

### 観点3: ドメインモデルの実装

- [ ] エンティティにビジネスルールが実装されているか（貧血モデルになっていないか）
- [ ] バリューオブジェクトが不変として実装されているか
- [ ] バリューオブジェクトのコンストラクタでバリデーションされているか
- [ ] バリューオブジェクトの値の等価性判定が実装されているか
- [ ] 集約ルート経由でのみ集約内部にアクセスする実装か
- [ ] 集約間の参照がIDベースか
- [ ] Domain層にリポジトリインターフェースが定義されているか
- [ ] Infrastructure層にリポジトリ実装が定義されているか
- [ ] エンティティ・バリューオブジェクトが単一の責任を持つ設計か（SRP: 単一責任の原則）

**判定基準**:
- **NG**: 貧血モデル、集約境界の無視、リポジトリインターフェースの不在
- **警告**: VOの不変性が不完全、集約ルートのバイパスが一部存在
- **OK**: 設計書に沿って正しく実装されている

---

### 観点4: 設計パターンの一貫性（SOLID原則を含む）

CLAUDE.mdおよびreferenceに定義されたパターンを基準とする。

- [ ] Infrastructure層のパターン（API連携、DB永続化）が統一されているか
- [ ] Application層のユースケース/サービスの命名パターンが統一されているか
- [ ] エラーハンドリングのパターンが一貫しているか
- [ ] 共通型（DTO、Mapper基底クラス等）が再利用されているか
- [ ] 拡張に対して開き修正に対して閉じているか。新バリエーション追加時に既存コード変更を最小化できるか（OCP: 開放閉鎖の原則）
- [ ] 派生型が基底型と置換可能か。継承・多態の使用が破綻していないか（LSP: リスコフの置換原則）
- [ ] インターフェースが利用側に不要なメソッド実装を強制していないか（ISP: インターフェース分離の原則）
- [ ] DIP（依存性逆転の原則）は観点2で検証する

**判定基準**:
- **NG**: 確立されたパターンと全く異なる構成
- **警告**: パターンからの軽微な逸脱
- **OK**: 確立されたパターンに一貫して沿っている

---

### 観点5: 命名の準拠

- [ ] モデル名がユビキタス言語集の英語名と一致しているか
- [ ] 「使用しない表現」がコード内に残っていないか
- [ ] リネーム済みの旧クラス名・旧変数名が残っていないか
- [ ] CLAUDE.mdおよびreferenceの命名規則に従っているか

**判定基準**:
- **NG**: 「使用しない表現」が主要なクラス名に使われている
- **警告**: 軽微な命名の不一致
- **OK**: 命名が準拠している

---

## 言語固有チェック

referenceのcoding-rulesファイルが存在する場合、以下の追加チェックを実施する:

- ドキュメントコメント/docstringの有無
- アクセス修飾子の適用
- ログ出力規約の遵守
- プロジェクト固有の禁止パターン
- その他、coding-rulesに定義されたルール

結果は「言語固有チェック」セクションとして出力に追記する。

## 判定基準（総合）

- **PASS**: NG 0件
- **CONDITIONAL PASS**: NG 1〜3件
- **FAIL**: NG 4件以上、またはClean Architectureのレイヤー違反が複数存在

---

## レビューの範囲（優先順位）

ファイル数が多い場合は以下の優先順位でレビューする:

1. **Domain層** — 最優先。ビジネスロジックの核心
2. **Application層** — ユースケースの制御フロー
3. **Infrastructure層** — DB/API実装、Mapper
4. **Presentation層** — 優先度低

## 補足

- Clean Architectureのレイヤー違反は規模に関わらず見逃さない
- 「暗黙的にできていること」を積極的に評価する
- CLAUDE.mdにパターンが定義されていない場合は既存実装から帰納的にパターンを識別する
