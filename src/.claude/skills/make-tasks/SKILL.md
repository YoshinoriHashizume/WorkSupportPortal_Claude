# タスクリスト作成スキル（Phase 4: タスク分解）

あなたはSDD（スペック駆動開発）のタスク分解の専門家です。
承認済みの機能設計書（design.md）とテスト設計書（test-design.md）に基づき、
実装フェーズ（Phase 5）で使うタスクリスト（tasks.md）を作成してください。

## 前提

- Phase 3（設計書 + テスト設計書）が承認済みであること
- 未承認の場合は「先に設計書の承認が必要です」とユーザーに確認する
- タスク分解は **Phase 4**。作成した tasks.md はユーザー承認を得てから Phase 5（実装）へ進む

## 対象の特定（最初に必ず行う）

タスク分解を始める前に、**どのアプリケーション（app_name）のどの feature を対象にするか**を確定する。
次の優先順位で判断し、特定できない場合は必ずユーザーに確認する。

1. **引数から特定する**
   - 引数に design.md / test-design.md / feature ディレクトリのパスが渡されていれば、
     そのパスから `app_name` と `{feature-name}` を特定する
     （例: `application/inventory/docs/spec/merge-results/design.md` → app=inventory, feature=merge-results）
2. **会話文脈から特定する**
   - 直前までの会話で対象アプリ・feature が明確なら、それを使用する
3. **特定できない場合は確認する（1・2で決まらない時のみ）**
   - `Glob` で `application/*/docs/spec/*/` を探索し、候補（アプリ名 × feature 名）を一覧化する
   - **どのアプリケーションのどの feature のタスク分解を行うかをユーザーに確認する**
   - 対象が確定するまで tasks.md を作成しない

> **重要**: 対象アプリ・feature が曖昧なまま tasks.md を作成してはならない。
> 誤ったディレクトリへの出力や、別 feature の設計書に基づく誤ったタスク分解を防ぐため、
> 不明な場合は必ず確認を挟む。

## 配置先

```
application/{app_name}/docs/spec/{feature-name}/tasks.md
```

※ タスクは必ず仕様書（requirements.md / design.md / test-design.md）と**同じディレクトリ**に置く。
※ `{feature-name}` はケバブケースで命名する。

## 文書ヘッダー

ファイル先頭に必ず記述する:

```
文書ID: (例:TASK-FEATURE-NAME-2026-001)
作成日: YYYY/MM/DD
更新日:
対応文書: (源となった design.md / test-design.md のパス)
```

作成日・更新日は `date '+%Y/%m/%d'` コマンドで取得した実際の日付を記載する。

## 記述ルール

### 1. 状況チェックシート（ファイル先頭に必ず記述）

タスク一覧の各行にステータスを持たせ、進捗が一目で分かるようにする。

**凡例**:

| 記号 | 意味 |
|------|------|
| `[ ]` | 未着手 |
| `[~]` | 進行中 |
| `[✅2026/02/01 13:05]` | 完了（完了日時を記録） |
| `[- 2026/02/15 14:12]` | スキップ（スキップ日時を記録） |

- **時刻の正確性**: 必ず `date '+%Y/%m/%d %H:%M'` コマンドで取得した実際の時刻を記載する。
  推測や概算で書かない
- **即時記録**: 各ステップ完了時にその都度時刻を取得して記録する。
  複数ステップをまとめて同一時刻で記録することは禁止

### 2. タスクの粒度

- 1タスク = 原則1ファイルの変更（CLAUDE.mdの「1回の変更は1ファイルを基本とする」に準拠）
- Clean Architectureのレイヤー順（domain → use_cases → infrastructure → interfaces）で並べる
- Phase 5 は TDD を採用するため、各実装タスクの前にテスト作成タスクを置く（Red → Green → Refactor）
- 依存関係のあるタスクは順序を明示する

### 3. タスク実行レポート（タスク完了時に必ず書く）

各タスク完了時に、以下を記述する（必ず日時を記録）:

- 懸念事項
- 改善事項
- 設計のGoodポイント
- チーム共有ポイント

レポートは `"--------------------"` で前後を囲む。

## tasks.md のテンプレート

```markdown
文書ID: TASK-{FEATURE-NAME}-2026-001
作成日: 2026/MM/DD
更新日:
対応文書: ./design.md, ./test-design.md

# {feature-name} タスクリスト

## 状況チェックシート

**凡例**: [ ] 未着手 / [~] 進行中 / [✅YYYY/MM/DD HH:MM] 完了 / [- YYYY/MM/DD HH:MM] スキップ

| # | タスク | レイヤー | 状態 |
|---|--------|---------|------|
| 1 | {Entity}のテスト作成 | domain | [ ] |
| 2 | {Entity}の実装 | domain | [ ] |
| 3 | {UseCase}のテスト作成 | use_cases | [ ] |
| 4 | {UseCase}の実装 | use_cases | [ ] |
| ... | ... | ... | ... |

## タスク詳細

### タスク1: {Entity}のテスト作成
- 対象ファイル:
- 内容:
- 完了条件:

...

## タスク実行レポート

（各タスク完了時にここへ追記する）
```

## 自己レビューと改善（3回反復）

tasks.md を生成した後、ユーザーに提示する前に、以下のレビューと改善を **3回繰り返す**。
各回で観点をチェックし、問題があればその場で tasks.md を修正する。

- 1回目: 網羅性 — design.md のドメインモデル・ユースケース・API、test-design.md の
  全テストケースがタスクに漏れなく落ちているか。マイグレーション、URL登録、
  テンプレート等の付随作業が抜けていないか
- 2回目: 粒度・順序 — 1タスク=1ファイルが守られているか。Clean Architecture の
  レイヤー順（domain → use_cases → infrastructure → interfaces）と TDD 順
  （テスト作成 → 実装）が崩れていないか。依存関係のあるタスクが逆順になっていないか
- 3回目: 実行可能性 — 各タスクの「対象ファイル」「内容」「完了条件」が、
  他者がそのまま着手できる具体性を持つか。完了条件が検証可能（テストが通る等）か。
  ユビキタス言語集の用語で記述されているか

各回の改善内容は簡潔に記録し、ユーザー提示時に「3回の自己レビューで何を改善したか」を添える。

## 実行手順

1. 「対象の特定」に従い、対象アプリ（app_name）と feature を確定する（不明な場合はユーザーに確認）。
   確定後、その feature の design.md / test-design.md を Read で読み取り、承認済みか確認する
2. ドメインモデル・ユースケース・テストケースからタスクを洗い出す
3. Clean Architectureのレイヤー順 + TDD順にタスクを並べる
4. `date '+%Y/%m/%d'` で作成日を取得し、文書ヘッダーを埋める
5. 上記テンプレートに沿って tasks.md を生成する
6. 「自己レビューと改善（3回反復）」に従い、レビューと修正を3回繰り返す
7. ユーザーに提示し、Phase 4 の承認を求める（承認後に Phase 5 実装へ）
