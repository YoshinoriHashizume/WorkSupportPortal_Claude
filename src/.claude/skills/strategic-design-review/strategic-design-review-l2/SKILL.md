# 戦略的設計 L2レビュー（Big Picture Event Stormingのレビュー）

あなたはDDD戦略的設計とEvent Stormingの専門家です。
Big Picture Event Stormingの結果に対して、
L2レビュー（イベントの網羅性・整合性チェック）を行ってください。

## レビューの目的

Big Picture Event Stormingの結果が以下の基準を満たしているかを検証する:

1. **ドメインイベントの網羅性**: 業務全体の主要なイベントが洗い出されているか
2. **イベントフローの整合性**: イベントの時系列・因果関係が正しいか
3. **境界の発見**: イベントの流れからサブドメインやコンテキスト境界のヒントが読み取れるか
4. **BMCとの整合性**: イベントがBMCの主要な活動と対応しているか

## レビュー対象の特定

$ARGUMENTS

- ファイルパスが指定されている場合は Read ツールで読み取る
- 引数が空の場合は `docs/strategic_design.md` 内の Event Storming セクション、または別ファイルを探す
- 見つからない場合はユーザーに質問する

## Big Picture Event Stormingの構成要素（参照用）

| 要素 | 色（付箋） | 意味 |
|------|----------|------|
| ドメインイベント | オレンジ | 業務上起きた出来事（過去形で表現） |
| コマンド | 青 | イベントを引き起こすアクション |
| アクター | 黄（小） | コマンドを実行する人・ロール |
| 外部システム | ピンク | イベントに関与する外部システム |
| ホットスポット | 赤/ピンク | 問題点、疑問、議論が必要な箇所 |
| タイムライン | — | イベントの時系列の流れ |
| スイムレーン | — | 業務フェーズや部門ごとの区分け |

## レビュー観点

以下の4つの観点でレビューを行う。

---

### 観点1: ドメインイベントの網羅性

業務全体の主要なイベントが漏れなく洗い出されているかを検証する。

**チェック項目:**

- [ ] 業務の開始から終了までの主要なイベントが洗い出されているか
- [ ] 各部門/担当者の活動がイベントとして表現されているか
- [ ] 正常系だけでなく、異常系のイベントも含まれているか
  - 例: 「在庫不足が検出された」「差異が発見された」「緊急対応が発生した」
- [ ] 外部システムとの連携ポイントがイベントとして表現されているか
  - 例: 「CSVが出力された」「データがアップロードされた」「APIから取得された」
- [ ] 業務のトリガーとなるイベント（開始条件）が明確か
  - 例: 「四半期の棚卸し日が到来した」「内示が受信された」
- [ ] 業務の完了を示すイベントが明確か
  - 例: 「棚卸しレポートが提出された」「在庫差異が解消された」

**判定基準:**

- **NG**: 主要な業務フェーズに対応するイベントが欠落している
- **警告**: イベントは概ね網羅されているが、異常系や外部システム連携のイベントが不足
- **OK**: 業務全体のイベントが網羅されている

---

### 観点2: イベントフローの整合性

イベントの時系列と因果関係が正しいかを検証する。

**チェック項目:**

- [ ] イベントが時系列に並んでいるか（タイムラインが明確か）
- [ ] イベント間の因果関係が明確か（「Aが起きたからBが起きる」）
- [ ] 並行して起きるイベントが識別されているか
- [ ] イベントを引き起こすコマンドとアクターが対応づけられているか
- [ ] あるイベントの結果が次のコマンドのトリガーになる連鎖が正しいか
- [ ] イベント間に時間的なギャップ（待ち時間、バッチ処理等）がある場合、それが明記されているか
- [ ] 分岐（条件によって異なるイベントが発生する）が表現されているか

**判定基準:**

- **NG**: イベントの時系列が明らかに矛盾している、または因果関係が不明確
- **警告**: イベントの順序は概ね正しいが、一部の因果関係が暗黙的
- **OK**: イベントの時系列と因果関係が明確

---

### 観点3: 境界の発見

イベントの流れから、サブドメインや境界づけられたコンテキストの境界が読み取れるかを検証する。

**境界を示唆するパターン:**

| パターン | 説明 | 例 |
|---------|------|-----|
| アクターの変化 | イベントの前後で担当者が変わる | 現場担当者 → 丸栄NW → 財務グループ |
| 言語の変化 | イベントの前後で使われる用語が変わる | 「実在庫数」→「在庫金額」 |
| 時間軸の変化 | イベントの前後で業務のリズムが変わる | 四半期イベント → 日常業務 |
| 外部システムの介在 | イベント間に外部システムが挟まる | SLIMS → Django → AppSuite |
| ホットスポットの集中 | 問題点が特定の領域に集中している | → その領域がコアサブドメインの可能性 |

**チェック項目:**

- [ ] イベントの流れの中で、アクターが切り替わるポイントが識別されているか
- [ ] イベントの流れの中で、使われる用語（言語）が変わるポイントが識別されているか
- [ ] イベントの流れの中で、外部システムが介在するポイントが識別されているか
- [ ] ホットスポット（問題点・疑問点）がどの領域に集中しているか分析されているか
- [ ] これらの境界ポイントが、strategic_design.mdのサブドメイン分類やコンテキスト境界と整合しているか
- [ ] イベントストーミングの結果、新たに発見されたコンテキスト境界があるか

**判定基準:**

- **NG**: 境界の分析が全くされていない
- **警告**: 境界のヒントは読み取れるが、明示的な分析がされていない
- **OK**: イベントの流れから境界が識別され、戦略的設計書との整合性が確認されている

---

### 観点4: BMCとの整合性

イベントストーミングの結果がBMCの主要な活動と対応しているかを検証する。

**チェック項目:**

- [ ] BMCの「⑤ 主要な活動」に記載された活動が、イベントとして表現されているか
- [ ] BMCの「① 価値の提案」を実現するためのイベントチェーンが存在するか
- [ ] BMCの「⑧ コスト構造」で言及された異常時コストに対応する異常系イベントが含まれているか
- [ ] BMCの「⑦ キーパートナー」がイベントのアクターまたは外部システムとして登場しているか

**判定基準:**

- **NG**: BMCの主要な活動に対応するイベントが大幅に欠落している
- **警告**: BMCとの対応は概ね取れているが、一部の活動が未カバー
- **OK**: BMCの内容とイベントストーミングの結果が整合している

---

## 判定基準（総合）

- **PASS**: NG 0件。イベントが網羅的で、境界の分析も行われている
- **CONDITIONAL PASS**: NG 1〜2件。主要なイベントはカバーされているが、補強が必要
- **FAIL**: NG 3件以上、または主要な業務フェーズのイベントが欠落

---

## L3への引き継ぎ

レビュー完了後、以下を案内してください:
- 「戦略的設計レビュー L3（サブドメイン + コンテキストレビュー）を実行するには『戦略的設計レビュー L3をお願い』と依頼してください」
- 「推奨フロー: L1（BMC） → L2（Event Storming） → L3（サブドメイン + コンテキスト）」

## レビュー手順

1. 戦略的設計書またはイベントストーミング結果を Read ツールで読み取る
2. BMCセクションも Read ツールで読み取る（観点4の参照用）
3. 観点1〜4の順にレビューを実施する
4. イベントの流れから境界ポイントを識別し記録する
5. 検出事項を重要度とともに整理する
6. レビュー結果をユーザーに報告する
7. L3への引き継ぎを案内する
