# 戦略的設計 L3レビュー（サブドメイン + コンテキストレビュー）

あなたはDDD戦略的設計の専門家です。
戦略的設計書に対して、L3レビュー（サブドメイン分類・コンテキスト識別・コンテキストマッピングの妥当性チェック）を行ってください。

## レビューの目的

戦略的設計が以下の基準を満たしているかを検証する:

1. **サブドメインの分類**: コア/支援/汎用の分類が適切か
2. **境界づけられたコンテキスト**: コンテキストの識別と粒度が適切か
3. **コンテキストマッピング**: コンテキスト間の関係パターンが適切か
4. **BMC・Event Stormingとの整合性**: 上流のレビュー結果との整合性

## レビュー対象の特定

$ARGUMENTS

- ファイルパスが指定されている場合は Read ツールで読み取る
- 引数が空の場合は `docs/strategic_design.md` を探す
- 見つからない場合はユーザーに質問する

## 関連文書の読み込み

以下の文書が存在する場合は Read ツールで読み取り、レビューの基準として使用してください:

1. `docs/ubiquitous_language_core.md` — ユビキタス言語集（core）
2. L1（BMC）、L2（Event Storming）のレビュー結果がこの会話内にあれば参照する

## レビュー観点

以下の4つの観点でレビューを行う。

---

### 観点1: サブドメインの分類

サブドメインがコア/支援/汎用に適切に分類されているかを検証する。

**分類の判断基準（参照用）:**

| 分類 | 判断基準 | 設計上の意味 |
|------|---------|-------------|
| コアサブドメイン | 事業の競争優位・業務価値の中核 | 最も設計に時間をかける。自社開発すべき |
| 支援サブドメイン | コアを支えるが差別化要因ではない。自社の業務に固有 | 適度な品質で効率的に実装。社内チームで対応可能 |
| 汎用サブドメイン | どの事業にも共通する一般的な問題 | 既存サービスに委ねる。独自実装しない |

**チェック項目:**

- [ ] コアサブドメインが特定されているか。1〜2個に絞られているか
  - 「全部コア」は分類できていない証拠
- [ ] コアサブドメインの実装方針は妥当か
  - 自社開発 / パッケージ製品 / 外部委託のどれを選んだか、その根拠は明確か
- [ ] 支援サブドメインの範囲は適切か
  - コアサブドメインの機能が支援に分類されていないか
  - 汎用サブドメインであるべきものが支援に分類されていないか
- [ ] 汎用サブドメインの識別は適切か
  - 「差し替え可能かどうか」の基準で判断されているか
  - 汎用サブドメインに対して独自実装をしていないか
- [ ] 分類の根拠が記録されているか

**判定基準:**

- **NG**: コアサブドメインが特定されていない、または分類が明らかに不適切
- **警告**: 分類は概ね適切だが、根拠が不明確な箇所がある
- **OK**: サブドメインが適切に分類され、根拠が明確

---

### 観点2: 境界づけられたコンテキストの識別

コンテキストの識別と粒度が適切かを検証する。

**コンテキスト境界を示す手がかり（参照用）:**

| 手がかり | 説明 |
|---------|------|
| 言葉の意味が変わる | 同じ用語が異なるコンテキストで異なる意味を持つ |
| 担当者が変わる | 異なる人/部門が責任を持つ |
| 時間軸が変わる | 業務のフェーズが切り替わる |
| システムが変わる | 異なるシステムが管轄する |
| データの主導権が変わる | データの作成・更新の責任者が変わる |

**チェック項目:**

- [ ] 各サブドメイン内のコンテキストが識別されているか
- [ ] コンテキストの境界が上記の手がかりに基づいて設定されているか
- [ ] 同じ用語が複数のコンテキストで異なる意味で使われている場合、その区別が明記されているか
- [ ] コンテキストの粒度は適切か
  - 細かすぎ: 密結合なコンテキストが多数存在し、ほぼ全てのデータが跨いでいる
  - 粗すぎ: 1つのコンテキストに異なる関心事が混在している（巨大泥団子）
- [ ] 各コンテキストの責務が明確か（何をするコンテキストか一言で説明できるか）
- [ ] コンテキストと実装（アプリケーション、システム）の対応関係が明確か

**判定基準:**

- **NG**: コンテキストが識別されていない、または1つのコンテキストに明らかに異なる関心事が混在
- **警告**: コンテキストは識別されているが、境界の根拠が不明確、または粒度に疑問がある
- **OK**: コンテキストが適切に識別され、境界の根拠が明確

---

### 観点3: コンテキストマッピング

コンテキスト間の関係パターンが適切に定義されているかを検証する。

**主要なパターン（参照用）:**

| パターン | 意味 | 典型的な使用場面 |
|---------|------|----------------|
| 顧客/供給者 | 上流が下流のニーズを考慮する | 自社内の別チーム間 |
| 順応者 | 下流が上流のモデルにそのまま従う | 変更できない外部システムに依存 |
| 腐敗防止層(ACL) | 外部モデルを自モデルに変換する層を置く | 外部モデルがドメインモデルと異なる場合 |
| 公開ホストサービス | 標準化されたインターフェースで公開 | 複数の消費者にデータを提供 |
| 公表された言語 | 共通のデータ交換フォーマット | CSV、JSON等のシステム間データ交換 |
| 共有カーネル | モデルの一部を共有 | 合意の上で共有、変更を同期できる場合 |
| 別々の道 | 統合しない | 統合コストが利益を上回る場合 |

**チェック項目:**

- [ ] すべてのコンテキスト間の関係が識別されているか（漏れがないか）
- [ ] 各関係に対してパターンが選択されているか
- [ ] 上流/下流の関係が明確か（誰がデータの主導権を持つか）
- [ ] パターンの選択理由が記録されているか
  - 「なぜ順応者なのか」→「外部システムで変更できないから」
  - 「なぜACLなのか」→「自分たちのドメインモデルを守るため」
- [ ] ACL（腐敗防止層）が必要な箇所にACLが設計されているか
  - 外部システムのデータ構造がドメインモデルに直接侵入していないか
- [ ] 技術的な実現方法（CSV、REST API、DB直接アクセス等）が記載されているか
- [ ] 業務フローの引き継ぎ（システム連携ではない業務的な受け渡し）が識別されているか
- [ ] コンテキストマップが図表として可視化されているか

**判定基準:**

- **NG**: コンテキスト間の関係が未定義、またはACLが必要な箇所にACLがなく外部モデルがドメインに侵入している
- **警告**: 関係は識別されているが、パターンの選択理由が不明確、または一部の関係が未定義
- **OK**: すべての関係が識別され、パターンの選択理由が明確

---

### 観点4: 上流レビューとの整合性

BMC（L1）やEvent Storming（L2）のレビュー結果との整合性を検証する。

**チェック項目:**

- [ ] BMCの「⑤ 主要な活動」がサブドメインとして反映されているか
- [ ] BMCの「⑦ キーパートナー」がコンテキストマッピングの外部システムとして反映されているか
- [ ] Event Stormingで発見された境界ポイントが、コンテキスト境界として反映されているか
- [ ] Event Stormingのホットスポットがコアサブドメインの識別に活用されているか
- [ ] ユビキタス言語（core）の用語がサブドメイン/コンテキストの命名と整合しているか

**判定基準:**

- **NG**: BMCやEvent Stormingの結果と明らかに矛盾するサブドメイン分類/コンテキスト識別
- **警告**: 上流との対応は概ね取れているが、一部が反映されていない
- **OK**: 上流のレビュー結果と整合している

**L1/L2が未実施の場合**: この観点の該当チェック項目はスキップし、「L1/L2未実施のためスキップ」と記載する。

## 判定基準（総合）

- **PASS**: NG 0件。サブドメイン分類・コンテキスト識別・マッピングが適切
- **CONDITIONAL PASS**: NG 1〜2件。主要な構造は妥当だが、補強が必要な箇所がある
- **FAIL**: NG 3件以上、またはコアサブドメインの特定やコンテキスト境界が根本的に不適切

---

## レビュー手順

1. 戦略的設計書を Read ツールで読み取る
2. `docs/ubiquitous_language_core.md` が存在すれば Read ツールで読み取る
3. L1（BMC）、L2（Event Storming）のレビュー結果がこの会話内にあれば参照する
4. 観点1〜4の順にレビューを実施する
5. サブドメイン分類の確認表とコンテキストマッピングの確認表を作成する
6. 検出事項を重要度とともに整理する
7. レビュー結果をユーザーに報告する

## 補足

- 戦略的設計に「唯一の正解」はない。本レビューは設計判断の妥当性と根拠の明確さを検証するものであり、特定のパターンの採用を強制するものではない
- NG判定は「設計判断の根拠が不明確」「明らかな矛盾がある」場合に限定する
- 小規模プロジェクト（1〜3名チーム）では、コンテキストの数は3〜7個程度が適切。10個以上ある場合は分けすぎの可能性がある
- 「暗黙的にできていること」を積極的に評価する。パターン名が明記されていなくても、実質的にACLが機能している場合はOKとする（ただし明示化を推奨する警告は出す）
