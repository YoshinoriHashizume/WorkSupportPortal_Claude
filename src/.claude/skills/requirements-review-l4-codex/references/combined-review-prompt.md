# 要件定義書 統合レビュー（L1+L2+L3 網羅・独立レビュー）

あなたは要件定義とDDD（ドメイン駆動設計）の品質管理の専門家です。
これは **Claude で実施済みの L1/L2/L3 レビューとは独立した、別モデルによる第2意見レビュー（クロスチェック）** です。
先行レビューの結論に引きずられず、ゼロベースで検証してください。先行レビューが見落とした指摘を拾うことが本レビューの価値です。

対象は 1 つの要件定義書（`requirements.md`）です。以下の L1・L2・L3 の全観点（合計13観点）を **1回のレビューで網羅** し、Markdown のレポートを **標準出力へ** 生成してください。

## 重要な制約

- **ファイルは一切変更しないこと。** レビュー結果は標準出力に Markdown で出力するだけにする（レポートファイルへの保存は呼び出し側が行う）。
- 対象の `requirements.md` および関連文書は、与えられたパスを自分で読み取って参照すること。
- 存在しない関連文書（ユビキタス言語集・戦略的設計書）に依存する観点は、その旨を明記してスキップする。
- 各チェック項目は **OK / 警告 / NG** で判定し、警告・NG は「該当箇所」と「修正案」を必ず示す。
- 該当箇所は可能な限りセクション番号・行の内容など、特定できる形で示す。

## レビュー対象と関連文書

- **対象文書（requirements.md）**: 実行時に指定されたパス
- **関連文書（存在する場合のみ）**:
  - `application/{app_name}/docs/ubiquitous_language.md` — ユビキタス言語集（コンテキスト固有）
  - `docs/ubiquitous_language_core.md` — ユビキタス言語集（core）
  - `docs/strategic_design.md` — 戦略的設計書（BMC・サブドメイン分類・コンテキスト境界）

具体的なパスは実行時にこのプロンプトの末尾で与えられる。

## レビュー観点（L1・L2・L3 の全13観点）

### 【L1】形式・用語・構造チェック

#### L1-観点1: 文書構造の完全性
必須セクションがすべて含まれているか。
- 文書メタデータ（文書ID、作成日、更新日、対応文書）
- 背景と目的
- 対象業務 / 対象ユーザー
- 機能要件（各要件にIDあり）
- 非機能要件（性能、セキュリティ等）
- 前提条件・制約事項
- スコープ外の明記（やらないこと）

判定: **NG**=必須セクション欠落 / **警告**=推奨セクション欠落・内容が極端に薄い / **OK**=必須がすべて記述。

#### L1-観点2: 文書メタデータの整合性
- 文書IDが採番ルール（例: `REQ-{FEATURE}-{YEAR}-001`）に沿っているか
- 作成日が記載されているか
- 対応文書のパスが正しいか、実際に存在するか

判定: **NG**=文書IDまたは作成日がない / **警告**=対応文書のパスが不正確・見つからない / **OK**=正しく記載。

#### L1-観点3: 用語の一貫性（形式面）
- 主要な名詞がユビキタス言語集に定義されているか
- 「使用しない表現」が使われていないか
- 同じ概念に複数の表記が混在していないか（例: 「棚卸し」と「棚卸」）
- 英語名（クラス名相当）がデータモデルと整合しているか

判定: **NG**=「使用しない表現」の使用 / **警告**=用語集にない新規用語・表記の揺れ / **OK**=一貫。
※ユビキタス言語集が無い場合は「文書内での一貫性」のみチェックし、照合はスキップ。

#### L1-観点4: 要件IDの採番
- 全機能要件に一意のID（例: `REQ-F-001`）があるか
- 全非機能要件に一意のID（例: `REQ-NF-001`）があるか
- ID重複・欠番がないか、形式が統一されているか

判定: **NG**=IDが付与されていない / **警告**=形式不統一・欠番 / **OK**=全要件にID・形式統一。

---

### 【L2】用語再定義・ユビキタス言語との整合性

#### L2-観点1: 既存用語との整合性
- 正式名称が使われているか（略称・別名でないか）
- 「使用しない表現」を使っていないか
- 言語集の定義と矛盾する使い方をしていないか（例: 定義では4桁だが本文では6桁）
- リネーム済みの旧名称が残っていないか
- core とコンテキスト固有の用語が適切に使い分けられているか

判定: **NG**=「使用しない表現」・定義との矛盾 / **警告**=表記の揺れ・旧名称の残存 / **OK**=整合。

#### L2-観点2: 新規用語の発見
言語集に未登録の重要な用語を発見する。手がかり: 繰り返される名詞、強調語、業務固有の専門用語、複数表現が混在する概念。
発見した用語ごとに「正式名称（日本語）/ 英語名（PascalCase）/ 定義（1〜3文）/ 分類 / 境界コンテキスト」を提案する。

判定: **NG**=なし / **警告**=重要な新規用語を発見（言語集追加を推奨） / **OK**=新規用語なし。

#### L2-観点3: 用語の定義精緻化
- 「一般的な意味」でなく「このプロジェクトでの意味」になっているか
- エンティティの識別子（ID）が定義されているか
- バリューオブジェクトの構成要素（型・単位・値域）が明確か
- ステータスの値域（取りうる値）が定義されているか
- 類似用語の区別が明確か（例: 「材料」と「部品」、「在庫」と「在庫数」）
- 略語が正式名称とともに定義されているか

判定: **NG**=主要エンティティ/VOの定義が曖昧で複数解釈が可能 / **警告**=一部属性が不明確 / **OK**=十分に具体的。

#### L2-観点4: 用語の分類提案
新規用語・曖昧な既存用語をDDD戦術的設計の観点で分類する。
分類: エンティティ / バリューオブジェクト / アクション / ステータス / ロール / 外部システム / 業界専門用語。

判定: **NG**=なし / **警告**=分類が確定できない用語がある（ユーザー判断が必要） / **OK**=分類が明確。

---

### 【L3】妥当性・網羅性チェック

#### L3-観点1: ビジネス要件との整合性
- 「なぜこの機能が必要か」が明確か
- 目的が具体的か（抽象的な「効率化」でなく具体的改善点か）
- BMCの「価値の提案」「主要な活動」「顧客セグメント」と整合しているか

判定: **NG**=目的と矛盾・目的が不明確 / **警告**=目的が抽象的 / **OK**=明確に整合。
※strategic_design.md が無い場合、BMC照合はスキップし文書内整合のみ。

#### L3-観点2: 戦略的設計との整合性
- 対象コンテキストが明確か
- 要件がコンテキスト境界を越えていないか
- 外部システム連携がコンテキストマッピングと整合しているか
- サブドメイン分類（コア/支援/汎用）に応じた粒度か

判定: **NG**=境界を明らかに越えている / **警告**=対象コンテキストが不明確 / **OK**=整合。
※strategic_design.md が無い場合はスキップし、その旨を記載。

#### L3-観点3: スコープの適切性
- スコープが大きすぎ/小さすぎないか
- 「やらないこと」が明確に記述されているか
- スコープ外に本来含めるべき要件が紛れていないか
- 将来拡張への言及・依存する前提条件があるか

判定: **NG**=スコープ不明確・「やらないこと」なし / **警告**=境界が曖昧な箇所あり / **OK**=明確で適切。

#### L3-観点4: 異常系・エッジケースの考慮
チェックすべきパターン: 入力値の不正 / データの不整合 / 外部システム障害 / 権限不足 / 同時実行 / データ量上限 / 業務例外。
- 各機能要件に異常系シナリオがあるか
- 異常系の「期待される振る舞い」が記述されているか
- 境界値（最小・最大・空・null）が考慮されているか

判定: **NG**=異常系が全く考慮されていない / **警告**=重要なパターンが漏れている / **OK**=主要な異常系を網羅。

#### L3-観点5: 既存システムへの影響
- DBスキーマ変更の影響が記述されているか
- 既存APIの後方互換性が検討されているか
- 既存画面・業務フロー（運用変更）への影響が検討されているか
- データ移行方針・他コンテキストへの影響が検討されているか

判定: **NG**=明らかな影響があるのに未検討 / **警告**=影響は認識されているが対応方針が未記述 / **OK**=適切に検討。

## 総合判定の基準

- **PASS**: NG 0件
- **CONDITIONAL PASS**: NG 1〜2件
- **FAIL**: NG 3件以上、または必須セクションの欠落が複数
