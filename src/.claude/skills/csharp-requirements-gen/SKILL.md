# C# Clean Architecture → 要件定義書生成スキル

## 概要

このスキルは C# Clean Architecture プロジェクトを層別に静的解析し、
SDD Phase 0〜5 に準拠した要件定義書（Markdown）を生成する。

**入力**: C# プロジェクトのルートパス（またはアップロードされたファイル群）
**出力**: `requirements.md`（SDD要件定義書フォーマット）

---

## Phase 0: 前提確認

作業開始前に以下を確認する。

1. **プロジェクトルートの特定**
   - `$ARGUMENTS` で対象パスが指定されている場合はそれを使う
   - 指定がない場合はカレントディレクトリを使用する
   - **引数なし かつ `.sln` がカレントから見つからない場合**: ユーザーに対象ソリューションのパスを質問する
   - `.sln` ファイルの場所を起点にする
   - `bin/`, `obj/`, `.git/` は解析対象から除外

2. **層構成の把握**（Glob ツールで構造確認）
   - Glob パターン `**/*.csproj` で `.csproj` 一覧を取得
   - Glob パターン `**/*.cs` で C# ファイル一覧を取得
   - 取得結果から `bin/`, `obj/`, `.git/` を除外して層を判定する

3. **対象がC#プロジェクトであることの確認**
   - `.sln` または `.csproj` が1つも見つからない場合: 「C# Clean Architectureプロジェクトが見つかりません。本スキルはC#プロジェクト専用です」と報告して中止する
   - Python/Django/Swift等の他言語プロジェクトと判定された場合も同様に中止する

4. **ユーザーへの確認事項**（不明な場合のみ聞く）
   - ドメインの業務内容（例：棚卸管理、在庫管理）
   - 対象読者（エンジニア向け / 非エンジニア向け）
   - 出力言語（日本語 / English）

## Phase 1: プロジェクト構造スキャン

### 1-1. ソリューション構成の把握

Globツールで以下の情報を取得する:

- `**/*.csproj` — `.csproj` 一覧と参照関係（`bin/`, `obj/` 配下は除外）
- `**/*.cs` — C# ファイル一覧（`bin/`, `obj/` 配下は除外）

取得したファイル一覧からディレクトリ単位にグルーピングし、
各プロジェクト／ディレクトリのファイル数をカウントすることで層を判定する。

**大規模プロジェクト（ファイル数500超）の場合**:
主要な `.csproj` を優先的に分析し、その旨を要件定義書の「7.2 コード分析の限界」に記載する。

### 1-2. 層マッピングの作成

以下の命名パターンで層を判定する：

| フォルダ名パターン | 対応する層 |
|---|---|
| `Domain`, `Domain.*` | ドメイン層 |
| `Application`, `UseCase`, `Usecases`, `AppService` | アプリケーション層 |
| `Infrastructure`, `Infrastracture`, `Infra` | インフラ層 |
| `Presentation`, `WinForms`, `Web`, `Api`, `UI` | プレゼンテーション層 |
| `*Module`, `Common`, `Shared`, `Core` | 共有モジュール |
| `*Tests`, `*Test`, `UnitTests`, `UsecaseTests` | テスト |

⚠️ **スペルミス（例: `Infrastracture`）はそのまま記録し、注記に残す**

---

## Phase 2: ドメイン層の分析

**このPhaseの開始時に Read ツールで `references/domain_analysis_guide.md` を読み込み、
その判定基準と抽出項目に従って分析を実施する。**

### 分析対象ファイルの絞り込み

Globツールで以下を取得する:

- `<domain_dir>/**/*.cs` — ドメイン層配下のC#ファイル一覧（`bin/`, `obj/` 除外）

取得したファイルを Read ツールで1つずつ読み込み、
`domain_analysis_guide.md` の判定基準（Entity / Value Object / Domain Service /
Aggregate Root / Repository Interface / Domain Event / Specification）に従って抽出する。

**ドメイン層が特定できない場合**:
Phase 1 で作成した層マッピング結果をユーザーに提示し、
どのプロジェクト／ディレクトリをドメイン層とみなすか確認する。

### 抽出項目

各 `.cs` ファイルを読み込み、以下を抽出する：

| 分類 | 判定基準 | 抽出情報 |
|---|---|---|
| **Entity** | `class` + `Id`プロパティ保有 or 命名で判断 | クラス名、プロパティ一覧、メソッド一覧 |
| **Value Object** | `readonly struct` + `IEquatable<T>` 実装 or `record` | 型名、内包する値の意味 |
| **Domain Service** | `Service` サフィックス + ドメインロジック | サービス名、責務、メソッドシグネチャ |
| **Aggregate Root** | `IAggregateRoot` 実装 or ルート相当の Entity | 集約名、境界 |
| **Repository Interface** | `IRepository<T>` 継承 or `I*Repository` 命名 | インターフェース名、操作一覧 |
| **Domain Event** | `IDomainEvent` 実装 or `*Event` 命名 | イベント名、含まれるデータ |
| **Specification** | `ISpecification<T>` 実装 or `*Specification` 命名 | 仕様名、判定条件の説明 |

## Phase 3: アプリケーション層（ユースケース）の分析

### ユースケース抽出

Globツールで `<usecase_dir>/**/*.cs` を取得し、`bin/`, `obj/` 配下は除外する。
各 AppService / UseCase クラスのパブリックメソッドを**1メソッド = 1ユースケース**として抽出する。

### 抽出フォーマット

```
UC-001: <ユースケース名>
  メソッド: <クラス名>.<メソッド名>(<引数型>): <戻り値型>
  概要: <メソッド名・引数名・コメントから推測した処理概要>
  関連ドメインオブジェクト: <使用しているEntityやValue Object>
```

---

## Phase 4: インフラ・プレゼンテーション層の補完分析

### インフラ層

- **Repository 実装**: `I*Repository` の実装クラス → 永続化先（DB種別・ファイル等）を特定
- **外部サービス**: HTTP クライアント、ファイルIO、外部API呼び出しの有無

### プレゼンテーション層

- **エントリポイント**: `Form` クラス / Controller / コマンドハンドラ
- **画面・操作一覧**: `Form` クラス名 → 画面名として記録
- **呼び出し先ユースケース**: `AppService` の呼び出し箇所を追跡

### 共有モジュール（`*Module` / `Common`）

- 横断的関心事（ログ、例外、バリデーション共通処理）を記録

---

## Phase 5: 要件定義書の生成

**このPhaseの開始時に Read ツールで `references/requirements_template.md` を読み込み、
そのテンプレートに従って `requirements.md` を生成する。**

### 文書ヘッダの必須項目

要件定義書の先頭には必ず以下を記載する（CLAUDE.md の SDDルールに準拠）:

```
文書ID: REQ-{FEATURE}-{YEAR}-001
作成日: {dateコマンドで取得した日付}
更新日:
対応文書: {対象ソリューションの相対パス}
```

### ユビキタス言語の照合

`docs/ubiquitous_language.md` が存在する場合は Read ツールで読み込み、
抽出したドメイン用語と照合する:

- 既存のユビキタス言語と一致する用語 → そのまま使用
- 既存に無い新用語 → 要件定義書の「2. ユビキタス言語」セクションに追加候補として記載
- コード上の命名と日本語定義にズレがある場合 → 「7.1 技術的負債・要確認事項」に記載

### 生成ルール

1. **ユビキタス言語セクション**はドメイン層から抽出したクラス名・メソッド名を元に作成
2. **機能要件**はユースケース一覧（UC-001〜）を元に記述
3. **ドメインモデル**は Entity・Value Object・Aggregate の関係を記述
4. **非機能要件**はインフラ層から読み取れる範囲で記述（読み取れない場合は `[要確認]` と記載）
5. コードに存在しない情報には必ず `[推定]` または `[要確認]` を付与する
6. スペルミス等の技術的負債は「補足・注記」セクションにまとめる

### ユーザーへの承認依頼

生成した要件定義書の全文をユーザーに提示し、以下を確認する:

- 内容に誤りや過不足がないか
- `[推定]` `[要確認]` 箇所の妥当性
- 保存先パスの確認

**承認を得てから Phase の出力ファイル保存に進む。**

---

## 出力ファイル

Phase 5 でユーザー承認を得た後、Write ツールで以下のパスに保存する:

```
docs/specs/{feature-name}/requirements.md
```

- `{feature-name}` は対象ソリューション名をケバブケースにして決定する
  （例: `InventoryManagement.sln` → `inventory-management`）
- `docs/specs/{feature-name}/` ディレクトリが存在しない場合は作成する
- 既存の `requirements.md` が存在する場合は、上書き前にユーザーに確認する
- ユーザーが出力先を明示的に指定した場合はそちらを優先する

保存後、「次は設計書（design.md）の作成に進みますか？ `make-design` スキルが利用できます」と案内する。

## エラーハンドリング

| 状況 | 対応 |
|------|------|
| 引数なしで起動 かつ カレントに `.sln` が無い | ユーザーに対象ソリューション（.slnまたはルートディレクトリ）のパスを質問 |
| 指定パスが存在しない | 「指定されたパスが見つかりません」と報告し、正しいパスを質問 |
| `.sln` / `.csproj` が1つも無い | 「C# Clean Architectureプロジェクトが見つかりません。本スキルはC#プロジェクト専用です」と報告して中止 |
| 他言語プロジェクトと判定される | 非該当を報告して中止（Django/Python → `docs/specs/` のSDDフロー、Swift → 他スキル等を案内） |
| ドメイン層が特定できない | 層マッピング結果を提示し、どのプロジェクトをドメイン層とみなすかユーザーに確認 |
| ファイル数500超の大規模プロジェクト | 主要な `.csproj` を優先分析し、その旨を要件定義書の「7.2 コード分析の限界」に記載 |
| 実装がほぼ空／テストコードしかない | 「解析可能な実装が見つからないため、要件定義書の逆引き生成は困難です」と報告 |
| `docs/specs/{feature-name}/` に既存の `requirements.md` がある | 上書き前にユーザーに確認（差分を示すのが望ましい） |
