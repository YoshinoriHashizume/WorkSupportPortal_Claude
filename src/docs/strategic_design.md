# 戦略的設計

文書ID: SD-WORK-SUPPORT-PORTAL-2026-001
作成日: 2026-08-25
更新日: 2026-08-27
対応文書: [ubiquitous_language_core.md](./ubiquitous_language_core.md)（UL-CORE-2026-001）、各アプリの機能仕様書、[アプリケーション仕様書.md](../../Document/アプリケーション仕様書.md)（SPEC-APP-2026-001）

本書は WorkSupportPortal（業務支援ポータル）の **戦略的設計** を定義する。
サブドメインの分類・境界コンテキストの範囲・コンテキスト間の関係を示し、
**個々の機能がこの地図上のどこに位置するか**を判断するための基準を与える。

本書は要件定義（L3レビュー 観点2「戦略的設計との整合性」）の検証基準として用いる。
新しい機能を着想した時点で、まず本書の地図上での位置を確認してから要件定義に着手する。

---

## 1. ビジネスの前提

丸栄興業／丸栄ニューウェーブは、**基幹システム MARI（Oracle）** を業務の記録の中心に据えている。
MARI は受注・出荷・売上・在庫・品目構成（BOM）を保持するが、
**参照系の業務（照合・傾向把握・棚卸の突合）** に必要な画面を十分に備えていない。

その隙間は、これまで Excel マクロ・VB.NET WinForms・個人端末上のスクリプトで埋められてきた。
これらは属人化しており、実行環境の維持・引き継ぎ・監査に難がある。

**WorkSupportPortal の存在理由**は、この「基幹周辺業務」を **Web ポータル上の共有された仕組みへ移すこと** にある。

### 1.1 中核となる制約

| 制約 | 内容 | 帰結 |
|------|------|------|
| **Oracle（MARI）は参照専用** | 基幹への書き込みは一切行わない（SELECT のみ） | 業務判断の記録は必ずポータル側（PostgreSQL）に持つ |
| **Oracle への都度問い合わせを避ける** | 一覧表示のたびに基幹へ問い合わせない | 集計結果は **スナップショット**（core E-004）として凍結保存する |
| **在庫数量は MARI を信用しない** | 実在庫は SLIMS が正 | 在庫は SLIMS CSV の取込結果を用いる |
| **認証は desknet's NEO に依存** | 当面の認証基盤は desknet's Login API | アイデンティティ／アクセスは腐敗防止層を挟んで隔離する |

## 2. サブドメインの分類

| サブドメイン | 分類 | 理由 |
|---|---|---|
| **検収書突合** | **コア** | 受領書と MARI の突合ルール（3項目一致・`〇`/`△`/`×`）は自社固有の業務知識であり、競合優位ではないが**代替が効かない**。誤りが支払・請求に直結する |
| **在庫発注アラート** | **コア** | 「入荷が途絶えた品目の在庫が出荷され続けていないか」という判断は自社の発注体制に固有。アラート判定条件が業務価値そのもの |
| **資産棚卸突合** | **支援** | 台帳と現地実績の突合という一般的な業務。desknet's のデータ構造に依存するが、判断ロジックは単純 |
| **出荷トレンド分析** | **支援** | 出荷推移の可視化。判断は人が行い、システムは材料を提供する |
| **生産管理参照（5年9組）** | **支援** | MARI の BOM 展開結果を見やすく提示する参照機能。ロジックは基幹側の構造に従う |
| **アイデンティティ／アクセス** | **汎用** | 認証・利用申請・メニュー権限。desknet's Login API と Django 標準に委ねる |
| **ポータル基盤** | **汎用** | メニュー・お気に入り・お知らせ・利用状況。一般的なポータル機能 |

**分類の使い方**: 支援・汎用サブドメインに対して、コア相当の非機能要件（高可用性・厳密な監査証跡・複雑なドメインモデル）を課さない。
逆にコアサブドメインでは、判定条件・突合ルールをユビキタス言語として厳密に定義し、テストで固定する。

## 3. 境界コンテキスト

各コンテキストは `src/application/{app_name}/` の 1 ディレクトリに対応する。
**コンテキストをまたぐ直接参照は行わない**（Python の import レベルでも）。例外は §3.1（共有カーネル）と §4.3（合成ルート）に限る。

| # | 境界コンテキスト | 実装 | メニューグループ | サブドメイン | 責務 |
|---|---|---|---|---|---|
| A | **検収書比較** | `application/receipt_comparison/` | 生産管理 | コア | 受領書（完成品 CSV／支給品 TXT）と MARI の出荷・売上・受入を突合し、照合状況を管理する |
| B | **在庫発注アラート** | `application/inventory_order_alert/` | 生産管理 | コア | 最終入荷日が古い／入荷実績がない品目について、在庫出荷の継続を検知し確認体制を支援する |
| C | **生産管理参照（5年9組）** | `application/gonenkukumi/` | 生産管理 | 支援 | MARI の BOM 展開による品番・工程情報の検索と Excel 出力 |
| D | **出荷トレンド一覧** | `application/shipment_trend/` | 営業 | 支援 | 得意先×内作品番の出荷推移を可視化し、アクションの優先判断を支援する |
| E | **資産棚卸結果** | `application/asset_inventory/` | 総務 | 支援 | desknet's の資産データと棚卸データを突合し、結果を確認・CSV 出力する。差異のある行は ASP 取り込み用データ（CSV）として出力する |
| F | **アクセス管理** | `application/portal/`（利用申請・権限） | 全社／管理 | 汎用 | 利用申請の承認、メニューグループ／メニュー単位の認可 |
| G | **ポータル基盤** | `application/portal/`（メニュー・お気に入り・お知らせ・利用状況） | 全社／管理 | 汎用 | メニュー提示、お気に入り、お知らせ、データベース管理画面、**メニュー利用ログの記録と利用状況の集計** |
| H | **売上共通（Oracle ACL）** | `application/sales/` | — | — | Oracle 接続の共有腐敗防止層と、その例外語彙。**参照専用** |
| I | **アイデンティティ（認証）** | `application/identity/` | — | 汎用 | desknet's Login API によるログイン、開発用ログイン、ログイン画面 |

### 3.1 共有カーネル

| 共有物 | 範囲 | 参照してよいコンテキスト |
|---|---|---|
| `application/sales/infrastructure/oracle/` | Oracle 接続とクエリ実行の共通基盤。**SELECT のみ** | A・B・C・D |
| `application/sales/domain/value_objects/errors.py`（`OracleNotConfiguredError` / `OracleQueryError`） | Oracle 参照の失敗を表す例外。接続基盤と対で使う | A・B・C・D |
| `application/shared/domain/value_objects/`（`prefix_filter` / `code_sort` / `dependent_cust_filter` / `list_table`） | 一覧の絞り込み・並び替え・表示整形の汎用ロジック。**業務判断を含まない** | 全て |
| `application/identity/domain/value_objects/errors.py`・`application/identity/infrastructure/desknet/` | desknet's API の腐敗防止層とその例外 | E（資産棚卸のアクセスキー取得） |
| `application/portal/interfaces/favorites.py` の認可述語（`is_portal_admin` / `can_access_menu_group` / `can_access_menu_item`） | 認可判定のみ | A〜E（`interfaces/` 層からのみ） |
| `docs/ubiquitous_language_core.md` | 2つ以上のコンテキストで共有する用語 | 全て |

**共有カーネル以外の相互参照は禁止する。** 例えば在庫発注アラートが検収書比較のモデルを import してはならない。

### 3.2 コンテキスト境界の判断基準

新しい要件がどのコンテキストに属するかは、次の順で判断する。

1. **どの業務判断を支援するか** — 突合の可否なら A、発注の要否なら B、営業アクションの優先なら D
2. **どのメニューグループの利用者が使うか** — 認可の単位はメニューグループであり、コンテキスト境界と一致させる
3. **データの正がどこにあるか** — MARI（A〜D）／SLIMS（B）／desknet's（E）

上記で決まらない要件は、**コンテキストをまたいでいる兆候**である。要件を分割するか、新しいコンテキストの新設を検討する。

## 4. コンテキストマップ

```
                       ┌─────────────────────────┐
                       │  desknet's NEO (外部)    │
                       │  Login API / AppSuite    │
                       └───────┬─────────┬────────┘
                    認証(ACL)  │         │  資産・棚卸データ(ACL)
                               ▼         ▼
   ┌──────────────────────────────┐   ┌──────────────────┐
   │ I: アイデンティティ（認証）    │   │ E: 資産棚卸結果   │
   │ F: アクセス管理               │   └─────────┬────────┘
   │ G: ポータル基盤               │             │ 取り込み用 CSV
   └───────────┬──────────────────┘             │ （利用者が手作業で貼り付け）
       認可述語 │（上流：F/G → 下流：A〜E　順応者）│
               │                                 ▼
               │                        ┌──────────────────┐
               │                        │  ASP (外部)       │
               │                        │  固定資産管理     │
               │                        └──────────────────┘
   ┌───────────┴───────────────────────────────────────┐
   │        A: 検収書比較   B: 在庫発注アラート          │
   │        C: 5年9組       D: 出荷トレンド一覧          │
   └──────┬──────────────────────────────┬─────────────┘
          │ 参照専用(共有カーネル H)      │ CSV 取込
          ▼                               ▼
   ┌──────────────────┐          ┌──────────────────┐
   │ 基幹 Oracle MARI  │          │  SLIMS (外部)     │
   │  （参照専用）      │          │  在庫 CSV         │
   └──────────────────┘          └──────────────────┘
```

### 4.1 関係の類型

| 上流 | 下流 | 関係 | 内容 |
|---|---|---|---|
| 基幹 Oracle（MARI） | A・B・C・D | **順応者 + 腐敗防止層** | 基幹のスキーマをそのまま受け入れる（変更を要求できない）。ただし H の ACL を通してのみ参照し、**書き込みは行わない** |
| SLIMS | B | **順応者（ファイル連携）** | エクスポートされた CSV の列構成に従う。取込時に検証し、不正なら前回スナップショットを保持する |
| desknet's NEO | E | **腐敗防止層** | AppSuite API のレスポンスをコンテキスト固有のエンティティへ変換する。**入力は API のみ**（CSV 取込は行わない）。CSV は利用者向けの**出力**としてのみ提供する |
| desknet's NEO | I | **腐敗防止層** | Login API を認証基盤として利用する。**当面の措置**であり、将来 Entra ID へ移行する想定 |
| ASP（固定資産管理システム） | E | **順応者（ファイル連携・片方向）** | ASP『資産／異動情報修正入力』の貼り付けレイアウト（75 列）にそのまま従う（変更を要求できない）。ポータルから ASP へ API 接続する手段はなく、**取り込み用データ（CSV）の貼り付けは利用者の手作業**とする。ポータルから ASP へ自動で書き込まない |
| F・G | A〜E | **順応者** | 各アプリは認可述語とメニュー定義に従う。認可の仕様を各アプリが独自に定義しない。**メニュー利用ログの記録も G が一括して担い、各アプリは記録処理を持たない**（REQ-USAGE-STATUS-2026-001 の REQ-NF-006） |

### 4.2 コンテキスト間でデータを共有しない原則

集計結果（core E-004 スナップショット）は **コンテキストごとに別テーブル** として持つ
（`InventoryOrderAlertSummarySnapshot` / `ShipmentTrendSummarySnapshot` 等）。
同じ MARI のデータを見ていても、**判断の文脈が異なればモデルも分ける**。
共通化は用語（core ユビキタス言語集）と Oracle 接続基盤（H）に留める。

### 4.3 合成ルート（`interfaces/wiring.py`）は例外とする

`interfaces/wiring.py` は**合成ルート**であり、依存関係の組み立てだけを担う唯一の場所である。
ここに限り、他コンテキストの `interfaces/wiring.py` を参照してよい
（例: ポータルのダッシュボードが在庫発注アラートの表示用ユースケースを組み立てる）。

| 許可 | 禁止 |
|---|---|
| `wiring.py` から他コンテキストの `wiring.py` を呼ぶ | `domain/` `use_cases/` `infrastructure/` から他コンテキストを参照する |
| 呼び出す先はユースケース／表示用の**公開された組み立て関数**に限る | 他コンテキストの `models.py` やリポジトリを直接触る |

合成ルート以外の層で他コンテキストへ手を伸ばすのは、境界の設計が誤っている兆候である。
とくに **あるコンテキストの `infrastructure/` が他コンテキストのテーブル行を作る**ことは禁止する
（初期化が必要なら、そのコンテキスト自身のリポジトリが既定値を返す責務を持つ）。

## 5. アーキテクチャ方針との対応

境界コンテキストの内部は Clean Architecture で構成する（詳細は `CLAUDE.md` §2）。

| レイヤー | 役割 | 戦略的設計との対応 |
|---|---|---|
| `domain/` | 業務ルール（判定条件・突合ルール） | **サブドメインの中核**。コアサブドメインではここが厚くなる |
| `use_cases/` | 業務の手順 | コンテキストが提供する操作 |
| `infrastructure/` | Oracle / PostgreSQL / 外部 API | **腐敗防止層**が置かれる場所 |
| `interfaces/` | 画面・API・組み立て（`wiring.py`） | コンテキストの**公開インターフェース** |

`domain/` と `use_cases/` に `import django` を書かない規約は、
**業務ルールをフレームワークの都合から隔離する**という戦略的判断に基づく。
