# ドメインモデルが `dict[str, object]` 中心で、エンティティが存在しない

## 現状の課題

2026/08/25 の DDD 設計レビューで検出した指摘 **D-1（エンティティ 0 個）** と
**D-2（dict が主役のデータ受け渡し）** を扱う。両者は同じ構造から生じており、分離して対応できない。

- 集計スナップショットの明細行が `dict[str, object]` のまま、リポジトリ → ユースケース →
  ドメインの判定処理 → テンプレート／CSV まで通貫している。レビュー時点で全域 126 箇所。
- そのため次の問題がある。
  - **キー名がどこにも定義されていない**。`row.get("cust_code")` のようなキー文字列が各層に散在し、
    タイプミスは実行時まで検出されない。
  - **不変条件を置く場所が無い**。行が満たすべき条件（在庫数は非負、内作品番は必須 等）を
    強制できず、判定処理の側で毎回防御的に書いている。
  - **同一性（identity）を持つ概念が値として扱われている**。「どの得意先×内作品番の行か」は
    識別子であり、本来エンティティとして表現すべきもの。
- レビュー時点で、全コンテキストを通じてドメインエンティティは
  `receipt_comparison/domain/entities/comparison_row.py`（D-4 対応で新設）の 1 本のみ。

## 改善提案

集計スナップショットの明細行を、キーと不変条件を持つドメインの型として定義し、
`dict[str, object]` の通貫をコンテキスト境界（永続化・テンプレート）までに封じ込める。

- 明細行を表す型を `domain/entities/` または `domain/value_objects/` に定義する
  （同一性を持つなら Entity、持たないなら VO）。
- リポジトリが ORM 行 → その型へ変換する責務を負う（CLAUDE.md §2 の「変換はリポジトリが担う」）。
- テンプレート／CSV へ渡す直前でのみ `dict` へ落とす。

**段階的に進める。** コアサブドメイン（在庫発注アラート・検収書比較）から着手し、
支援サブドメイン（出荷トレンド一覧・資産棚卸結果・5年9組）は効果を確認してから判断する。

## 期待効果

- キー名の誤りがテスト実行前（型チェック・import 時）に検出できる。
- 行の不変条件をドメインの 1 箇所に集約でき、判定処理から防御的コードを除去できる。
- 判定ルール（アラート判定条件）の変更時に、影響範囲を型で追跡できる。

## 代替案

- **TypedDict の導入**: dict のまま構造だけ型付けする。変更量は小さいが、
  不変条件・振る舞いを持てないため D-1 は解消しない。段階移行の中間形としてなら有効。
- **現状維持**: テストで担保する。レビュー時点で 1050 件のテストが通っており当面は動くが、
  コアサブドメインの判定条件を厚くするほど破綻しやすくなる。
