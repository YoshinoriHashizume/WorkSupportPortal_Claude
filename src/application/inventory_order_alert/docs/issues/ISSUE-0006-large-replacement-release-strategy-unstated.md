# 大規模な置換要件で段階リリースの可否が要件段階で示されていない

## 現状の課題

要件定義書 §1.2 は、置換の影響範囲を **34 ファイル・201 箇所** と定量的に示している。
にもかかわらず、§6（前提条件・制約事項）・§7（スコープ外）のいずれにも
**段階リリースを行うのか、一括で切り替えるのか**の方針が書かれていない。

実際には design.md §9 R-1 が実装フェーズで
「`alert_level.py` を削除することで未修正の import が即座に `ImportError` になる。
段階的な非推奨化はせず**一括で切り替える**」と判断した。

この判断自体は妥当だったが、**要件段階で決めておくべき前提**が設計まで持ち越された結果、次の影響が出た。

- tasks.md §0 が「ステージ2〜6の途中はテストスイート全体が Red のままになる」という
  異例の進め方を採ることになり、その妥当性を要件側の根拠で説明できなかった
- 実装が長時間 Red の状態を通過するため、**中断すると復旧地点が分かりにくい**状態が生まれた
  （実際に本要件の実装中、セッション中断からの復旧時に旧VOを誤って復活させかけた）

## 改善提案

1. 本要件定義書の §6 に、採用したリリース戦略（一括切り替え）とその理由を後追いで明記する
2. 今後の**置換型の要件**に向けて、要件定義のテンプレートに次の観点を追加する
   - 置換対象の規模（ファイル数・箇所数）
   - 段階リリースの可否と、不可の場合はその理由
   - 実装途中で全体テストが Red になることを許容するか

## 期待効果

- 置換型の要件で、実装フェーズに入る前にリリース戦略が合意された状態になる
- 実装が長時間 Red を通過する場合に、その根拠が要件として残る

## 代替案

- 本要件限りの後追い記載にとどめ、テンプレートには反映しない案。
  ただし同種の置換要件は今後も発生しうるため、標準化まで行うほうが効果が大きい
