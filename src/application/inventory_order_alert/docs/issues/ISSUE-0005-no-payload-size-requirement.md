# 配信データ量の非機能要件がなく、見積り誤りを検出できなかった

## 現状の課題

要件定義書 REQ-LFV-NF-001「性能」は次の 3 点しか定めていない。

1. 一覧表示の応答時間は既存と同等
2. 判定軸・判定期間の切り替えで Oracle 集計・SLIMS 再取込を発生させない
3. **対象行数**は既存一覧と同一（行数の増加を伴わない）

いずれも **行数**の観点であり、**1 行あたりの配信データ量**に関する要件がない。

流動区分の切り替えをサーバ往復なしで行うため、design.md §3.2 は
「判定期間 6 値ぶんの結果を各行に事前計算して配信する」方式（案B）を採用した。
この方式は行数を増やさないが、**1 行あたりのペイロードを増やす**。

そのため、design.md §3.2 の見積り「1 行あたり約 90 バイト」が
実測 **163 バイト**（`flowQuadrants` + `noIncomingRecord`）、
責任部署を含めて **222 バイト** と大きくずれていたにもかかわらず、
**要件違反として検出できなかった**（見積りが JSON のキー名と引用符を数えていなかったことが原因）。

実装フェーズのテスト E-001 で実測して初めて判明し、design.md / test-design.md を事後に改訂した。

## 改善提案

REQ-LFV-NF-001 に、配信データ量の観点を追加する。

- 1 行あたりの配信ペイロード増分の**上限値**を要件として定める（例: 既定条件で 250 バイト以内）
- 5,000 行相当での**総ペイポード量の目安**を定める（例: 2 MB 以内）
- 上限は自動テストで固定する（`tests/test_flow_quadrant_edge_cases.py` の E-001 が既に相当する検証を持つため、
  要件との対応を明記する）

## 期待効果

- 設計段階の見積り誤りを、要件との突き合わせで検出できるようになる
- 将来 1 行に項目を追加する変更（例: 契約情報・他入先情報の参照）が入る際に、
  どこまで増やしてよいかの判断基準が要件として存在する

## 代替案

- ペイロードを削る案（行単位の `responsibleDepartment` を廃し、クライアント側で
  `flowQuadrantDepartments` から引く）。222 バイト → 163 バイトに減らせるが、
  現状の実測値でも性能上の問題は観測されていないため、まず上限の明文化を優先する
