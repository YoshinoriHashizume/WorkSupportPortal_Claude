# 在庫発注アラート 機能仕様書

文書ID: REQ-INVENTORY-ORDER-ALERT-2026-001

本書は、検証スクリプト `scripts/verify_post_receipt_shipment_count.py` を **業務支援ポータル上の生産管理 Web アプリ** として実装するための要件を定義する。  
5年9組と同じ Oracle テーブル・BOM 展開ロジックを用い、**最終入荷日が古い、または入荷実績がない品目について、在庫出荷が継続していないかを一覧し、仕入先への確認体制を支援する**。  
**実在庫の正は SLIMS** である。丸栄ニューウェーブが管理する **SLIMS** からエクスポートした CSV を取り込んで表示する。
基幹 Oracle（MARI）の在庫数も **判断材料として併記する**が、正としては扱わない（§4.1.3）。

用語は上記ユビキタス言語集に従う。機能要件の一覧は §2.3、スコープ外は §2.4 に定める。

## 2. 背景・業務目的

### 2.1 背景

得意先からの注文があったが社内在庫がなく仕入先へ発注しようとしたところ、部品を作る設備や金型が既に存在しなかった事例が発生した。  
本来は一定期間の在庫保管が必要だが、仕入先への最終発注から長期間（例: 8 年）経過しており、発注がないため仕入先側で設備を廃棄していた。社内は在庫で一定期間対応できていたため、問題が表面化しにくかった。

### 2.2 本機能の目的

| 目的 | 内容 |
|------|------|
| リスクの可視化 | **最終入荷日** が古い、または **入荷実績がない** 品目について、**最終入荷日以降に得意先向け出荷が継続している** 行を一覧する |
| 在庫の提示 | SLIMS から取り込んだ **最新在庫** を同一行に表示し、在庫のみで出荷している状況を判断しやすくする |
| アラート | 上記条件を満たす行を画面上で強調表示し、生産管理担当者の注意を促す |
| 仕入先確認 | 仕入先への確認状況（未確認／確認中／確認済み）を PostgreSQL に記録し、再確認の漏れを防ぐ |
| 判断材料の提供 | 最終入荷日・最終出荷日・出荷回数・出荷数合計・在庫数を同一行で提示し、入荷発注の要否判断を支援する |

#### 2.2.1 受入基準（指摘 L3-9）

本機能が目的を達成したと判断する基準。5年9組 §10.1 の受入チェックリストに倣う。

| # | 受入基準 | 確認方法 |
|---|---------|---------|
| C-01 | SLIMS CSV を取り込むと在庫と基幹集計を突合した一覧が表示される | 実データの CSV を 1 件取り込み、取込件数と一覧の総件数が一致すること |
| C-02 | §2.1 の事故事例（仕入先が設備・金型を廃棄していた）に該当する品目が洗い出される | 最終入荷日が古く出荷が継続している品目が、§6.2 の判定どおり **供給リスク品** として表示されること |
| C-03 | 仕入先確認の状況（未確認／確認中／確認済み）を記録でき、再表示しても保持される | 確認状態とメモを保存し、再取込後も §7.2 の規則どおりに引き継がれること |
| C-04 | メニュー画面のアラート帯で件数サマリを確認できる | 生産管理メニューグループのユーザーでダッシュボードを開き、件数が **基準判定条件（低流動判定軸・3か月）で表示した一覧**と一致すること。一覧で別の判定条件を選んでいる場合は一致しない（帯は固定条件のため。§5.2・§6.2） |
| C-05 | 在庫の鮮度が画面で判別できる | 「〇年〇月〇日時点の在庫」ラベルが最終取込日と一致すること |
| C-06 | 取込の同時実行でスナップショットが壊れない | 取込中に別ユーザーが取込を試みると排他エラーとなり、既存スナップショットが保持されること（§3「取込の排他」） |

> **未確定**: 「確認漏れがどれだけ減ったか」を測る定量指標は、現行運用に確認記録が存在せず基準値を取れないため設定していない。運用開始後に確認状態の記録実績から定める。

## 3. システム境界・前提

| 区分 | 内容 |
|------|------|
| 基幹 Oracle | **参照のみ**（SELECT）。5年9組と同一スキーマ・同一接続方針。入荷・出荷・BOM・仕入先マスタに加え、**在庫数(MARI)**（`T_ITEM_STOCK.STOCK_ON_HAND_QTY`）を取得する。**実在庫の正は SLIMS** であり、MARI の在庫数は判断材料として併記するのみ |
| SLIMS 在庫 | ユーザーが SLIMS からエクスポートした CSV をアップロードし、PostgreSQL に **最新取込スナップショット** として保存する |
| ポータル PostgreSQL | SLIMS 取込履歴・在庫スナップショット、アラート閾値設定、行単位の仕入先確認状態、確認メモ、確認日時・確認者を保存する。**ユーザー単位のデータは持たず、在庫・集計・確認状態は全員で共有** |
| 認証 | Django 認証（ログイン必須）。画面・API とも `@login_required` を用いるため、未ログイン時は **`/login` へ 302 リダイレクト**する（API も JSON の 401 は返さない） |
| 認可 | **生産管理** メニューグループを持つ一般ユーザーおよび管理者が利用可能（§9） |
| 複数会社 | 5年9組と同様、`MARI_COMPANY_CD` による会社コード条件を Oracle クエリに付与する（未設定時は条件なし・本番既定） |
| データ鮮度（Oracle） | **SLIMS CSV 取込時** に Oracle 集計しスナップショット保存。一覧・メニュー帯はスナップショット表示（§4.1.1） |
| データ鮮度（在庫） | SLIMS CSV **最終取込日** を **「YYYY年M月D日時点の在庫」** 形式で表示する |
| **取込の排他** | SLIMS 取込は **同時に 1 件のみ** 実行できる。取込は「在庫保存 → Oracle 全件集計 → スナップショット保存」を同一リクエストで行い、かつ既存 `SlimsStockSnapshot` を全件削除してから INSERT する（§7.2・§10.4）ため、同時実行するとスナップショットが部分破壊されうる。**取込全体をトランザクションで囲み、排他ロックを取得したユーザーのみが実行できる**。ロックを取得できなかった側は **取込を行わず既存スナップショットを保持** し、一覧画面にエラーメッセージ「別のユーザーが取込中です。しばらく待って再実行してください。」を表示する（§8.2） |
| **確認状態の同時更新** | 行単位の仕入先確認状態・確認メモの同時更新は **後勝ち** とし、確認日時・確認者を上書き保存する（取込のような全件差し替えではないため排他は行わない） |

### 4.1 一覧画面（SCR-01）

#### 4.1.1 表示方針（集計スナップショット）

一覧・メニューアラート帯は **SLIMS 在庫 CSV 取込時に Oracle へ集計した結果**（`InventoryOrderAlertSummarySnapshot`）を表示する。**画面表示の都度 Oracle へは問い合わせない**。

表示する在庫発注データ（SLIMS 在庫・集計結果・確認状態）は **全員で共有** する。いずれかのユーザーが CSV を取込むと、他のユーザーの一覧・メニューアラート帯も同じ内容に更新される。

共有データであるため、**SLIMS 取込は同時に 1 件しか実行できない**（§3「取込の排他」参照）。取込中に別のユーザーが取込を開始した場合は排他エラーとし、先行する取込を中断しない。

| 項目 | 内容 |
|---|---|
| 表示対象 | 直近の SLIMS 取込に紐づく **全件**（`attentionOnly=false` 相当）をスナップショットに保存し、一覧では **フィルター** で絞り込み表示する |
| BOM 基準日 | 取込日（サーバ暦日）を `asOfDate` として集計時に固定し、スナップショットに保存。**一覧画面には表示しない**（在庫時点ラベルで代替） |
| 確認状態 | 表示時のみ PostgreSQL の最新確認状態を行へ **上書き反映**（集計結果自体は再計算しない） |
| 一覧操作 | **フィルタ・ソート・ページング** は **ブラウザ内でローカル処理** する。初回表示時にスナップショット全行を `ioa-list-data`（JSON）として埋め込み、変更時は **ページ再読み込みなし** で表・件数サマリ・ページングを更新する。URL は `history.replaceState` で同期する（ブックマーク・共有用）。判定条件（判定軸・判定期間・流動区分）の切り替えも同様にローカル処理する。**SLIMS CSV 再取込時のみ** 全画面再読み込み |
| ページ見出し | `portal-page-title-row` にタイトル・お気に入りハート・説明文（`portal-page-description`：`SLIMS 在庫と基幹入出荷から、仕入先確認が必要な品目を一覧します。`）を横並び配置 |
| データ更新 | SLIMS CSV の **再取込** のみ（Oracle 集計をやり直す操作は再取込だけである）。判定軸・判定期間の切り替えは表示時に再判定するため再取込を要しない（§6.2） |
| 未取込 | 一覧は空。メニュー帯は「在庫 CSV 未取込」を表示 |
| 集計失敗 | 取込は成功しても Oracle 集計が失敗した場合、エラーメッセージを表示し一覧は空 |

#### 4.1.2 SLIMS 在庫取込

一覧カード見出し行の **CSV 出力** ボタンの左に **SLIMS在庫CSV** ボタンを配置する。クリックでファイル選択ダイアログを開き、`.csv` を選ぶと **即座に取込・集計**（在庫保存 → Oracle 全件集計 → スナップショット保存）を実行する。別途の取込ボタンは設けない。

| 項目 | 内容 |
|---|---|
| ボタン | `SLIMS在庫CSV`（`button-link` 相当）。非表示の `<input type="file">` を `label` で起動 |
| 実行タイミング | ファイル選択確定時に POST 送信（`inventory-order-alert-list.js`） |
| 在庫時点表示 | 最終取込日を **「YYYY年M月D日時点の在庫」** と表示する（例: `2026年6月17日時点の在庫`）。一覧カード見出し行（`h2`）に **「YYYY年M月D日時点の集計結果を表示しています。」** と表示する。その直下に **赤字・小さめ文字** で `※入出荷の実績があるもののみ表示されます。` を表示する |
| 取込メタ情報 | 一覧カード内に在庫行数・ファイル名は **表示しない**。件数サマリは操作行に表示（§4.1.5） |
| 取込警告 | 最終取込から **`stockStaleDays` 日超** 経過している場合、画面上部に黄色バナー「SLIMS 在庫データが古い可能性があります（最終取込: YYYY/MM/DD）」を表示 |
| 取込中表示 | ファイル選択後〜サーバー応答まで、画面全体に半透明オーバーレイとスピナー、「SLIMS 在庫 CSV を取込中...」を表示する。二重取込を防ぐため **ボタン（label）のみ** 無効化する（`<input type="file">` は送信前に `disabled` にしない。disabled だとファイルが POST されず取込されない） |
| 在庫未取込 | 在庫データが 1 件もない状態では一覧カード内に「SLIMS 在庫 CSV を取り込むと、一覧が表示されます。」と表示 |

**SLIMS CSV フォーマット（2026-06 改訂）**

実ファイル `SISJB0001003000108848800.csv`（SLIMS 在庫エクスポート）に基づく。

| 項目 | 内容 |
|---|---|
| 文字コード | **Shift_JIS（CP932）** を第一候補。UTF-8（BOM あり/なし）も自動判別して受け付ける |
| ヘッダー行 | **2 行**。1 行目は英字フィールドコード、2 行目は日本語ラベル。**データは 3 行目から** |
| 品番列 | **`WSHOCD`（商品コード）** = 物理 **2 列目**。一覧の `item_cd`（Oracle **`T_SHIP.CUST_ITEM_CD`**）と **TRIM 後完全一致** で突合 |
| ロケーション列 | **`WLOCCD`（ロケーション）** = 物理 **5 列目** |
| ロケーションフィルタ | `WLOCCD` が **`[0-9][0-9A-Z][0-9]-[0-9]{2}-[0-9]`** 形式（例: `2E4-10-4`）の行 **のみ** 在庫集計対象。それ以外は **無視** |
| 在庫数列 | **`WKSBQT`（引当可能総バラ数）** = 物理 **9 列目**。`SUM` して一覧の `stock_qty` に使用 |
| 入荷日列 | **`WNYUDT`（入荷日）** = 物理 **14 列目**。在庫内訳ダイアログに行単位で表示（`YYYYMMDD`） |
| 集計（品番合計） | 対象行について、同一 `WSHOCD` の `WKSBQT` を **SUM** |
| 集計（ロケーション要約） | 同一 `WSHOCD` + `WLOCCD` の在庫数を **SUM** |
| 在庫内訳（ダイアログ） | CSV 行を **集約せず** そのまま表示 |
| 在庫基準日 | **取込日（暦日）** |

| 物理列 | フィールド | 日本語（2 行目） | 本機能での利用 |
|---|---|---|---|
| 1 | `WBSOKCD` | 倉庫コード | **未使用** |
| 2 | `WSHOCD` | 商品コード | **得意先品番**（突合キー。core V-005） |
| 5 | `WLOCCD` | ロケーション | **必須**（形式フィルタ対象） |
| 8 | `WKATQT` | 引当可能バラ数 | **未使用** |

**在庫数(MARI) の 3 状態**

| 状態 | 意味 | 一覧の表示 | CSV の出力 |
|---|---|---|---|
| 値あり | MARI に在庫がある（`0` を含む） | 数値（`0` はそのまま `0`） | 数値 |
| 該当なし | MARI に該当在庫がない／内作品番を解決できない | 空 | 空 |
| **未取得** | MARI 在庫を取得する前に作られた集計スナップショット | **`－`** | 空 |

- **`0`（在庫なし）と「該当なし」を取り違えない**ことが要点である。`0` は空にしない。

- **共通品は重複計上する**（複数の得意先品番が同じ内作品番に紐づく場合、各行に同じ在庫数を出す。按分しない）。
  **一覧の在庫数を単純合計しても総在庫にはならない**。これは在庫数(SLIMS) も従来から同じ性質である。

#### 4.1.4 フィルター

一覧タイトル直下にフィルタ用セレクト枠（`ioa-filter-panel`）を表示する。**「フィルター」見出しは表示しない**。候補値は **直近スナップショットの集計データ** から重複除去して生成する（Oracle への再問い合わせは行わない）。

| 項目 | クエリ | 内容 |
|---|---|---|
| 担当者コード | `cust_chrg_psn_cd` | `T_SHIP.CUST_CHRG_PSN_CD`。空は「すべて」。セレクト候補は **数値として昇順**（非数字は末尾） |
| 得意先コード | `cust_code` | **`T_SHIP` 出荷あり** の行のみ `T_SHIP.CUST_CD`（`M_CUST` 存在確認後）。表示は `コード - 得意先名`。**担当者コード選択時は当該担当者の行に現れる得意先のみ候補表示**（`dependent_cust_filter` 共通） |
| 得意先品番 | `item_cd` | **`T_SHIP.CUST_ITEM_CD`**。**前方一致**（`application/portal/domain/prefix_filter.py` 共通）。`datalist` で候補補完 |
| 仕入先品番 | `level1_item_cd` | BOM 階層1 外注構成子。**前方一致**（同上） |

- 得意先品番・仕入先品番の入力欄は **セレクトと同じ高さ**（`--portal-control-height`）と幅（`--portal-list-filter-control-width`）。共通 UI は `portal_prefix_filter_field.html` と `portal-list-prefix-filter.js`（`PortalListPrefixFilter`）を使用する。
- **担当者コード変更時**: 得意先コードのセレクト候補を再計算し、選択値は **常に「すべて」にリセット**。得意先品番・仕入先品番の入力も **空にリセット** する。得意先変更では担当者は変えない（[ポータル一覧表_共通仕様.md](../../portal/docs/ポータル一覧表_共通仕様.md) §3.1.2）。
- **得意先コード変更時**: 得意先品番・仕入先品番の入力を **空にリセット** する。

- 変更時は **ブラウザ内ローカル処理**（§4.1.1）で即時反映し、**ページは 1 に戻す**。ソート・表示件数は維持する。**フォーム送信・全画面再読み込みは行わない**。
- 件数サマリ（左: 流動区分4値／右: 確認済み・確認中・未確認）は **絞り込み後** の行を対象とする。左・右いずれも **同じ行集合** を数え、**合計件数は一致**する（左 = 供給リスク品 + 在庫死蔵品 + 在庫過剰リスク品 + 通常流動品、右 = 確認済み + 確認中 + 未確認）。
- CSV 出力は **フィルターに関係なくスナップショット全件** を出力する。

#### 4.1.5 一覧 UI 仕様

- テーブルは **画面内に収まる高さ** で表示し、**本体のみ縦スクロール**する。`.content` を `calc(100dvh - 56px)` の flex 列とし、見出し・フィルター・ツールバー・フッターを除いた残り高さを `.ioa-table-wrap` に割り当てる（固定 `62vh` は使用しない）。
- テーブルヘッダは **sticky** で固定する。
- 列見出し（カラム名）は **中央揃え** とする。
- 列見出しクリックで **単一列ソート** に切り替える（当該列のみ、昇順／降順トグル）。複数列ソート中にクリックした場合も **1 列のみ** にリセットする。**クライアント側** で表を再描画する。
- **複数列ソート**: テーブル上の **並び替え** ボタンからダイアログを開き、最大 **5 条件** まで列と昇順／降順を指定する。**条件行左端の番号をドラッグ＆ドロップ** して優先順位を入れ替えられる。適用時は **クライアント側** でソートを反映し、URL クエリ `sort=col1,col2&dir=asc,desc` を `history.replaceState` で同期する。優先順位は上から。同一列の重複指定は無視する。
- 複数列ソート適用中、列見出しには優先順位番号（1, 2, …）と方向（▲／▼）を表示する。
- **日付列のソート**（`last_incoming_date` / `last_ship_date`）: 空は **最も古い** とみなし、**昇順（古い順）では先頭**、降順（新しい順）では末尾に並べる。複数列ソートでも同一ルールを用いる。
- **確認状態列のソート**（`confirmation_status`）: 列見出し・並び替えダイアログから指定可能。**昇順は未確認→確認中→確認済み**、降順はその逆。ソートキーは表示ラベルではなく **`confirmationStatusKey`（`unconfirmed` / `in_progress` / `confirmed`）** を用いる（確認状態列はプルダウン表示だが、ソートは行データのキーで行う）。
- 初期表示時のソート: **`flow_quadrant` 昇順（供給リスク品→在庫死蔵品→在庫過剰リスク品→通常流動品）**。
- **在庫数列のソート**（`stock_qty` / `mari_stock_qty`）: 既定は降順。**空（該当なし）と未取得（`－`）はいずれも末尾**に落とす。
- **責任部署は一覧列に出さない**（詳細ダイアログへ移した。§4.1.6）。CSV 出力には引き続き含める。
- **ページング**: `page_size`（20 / 50 / 100 / 200、既定 **50**）と `page`（1 始まり）。**テーブル左下** に **表示件数 → セレクト → 前へ → 次へ → 表示範囲** の順で横並びとする。**クライアント側** でページ切替（ボタン・セレクト変更時に全画面再読み込みなし）。
- 表示範囲（例: `1–3 件目を表示（1 / 1 ページ）`）は **次へ** の右に表示する。
- テーブル上部（フィルター直下）の左端に **並び替え** ボタン（ラベルは常に「並び替え」のみ。現在のソート条件はボタンに表示しない）、右端に件数サマリを配置する。
- 件数サマリは **2 段表示**（同一行内）。文字サイズは **12px**（`--portal-font-size-caption`）とする。
  - **左寄せ**: **供給リスク品 / 在庫死蔵品 / 在庫過剰リスク品 / 通常流動品**（フィルター適用後の全行。確認状態に関わらず流動区分列の値で集計）
  - **右寄せ**: **確認済み / 確認中 / 未確認**（同一行集合を確認状態で集計。**左の合計と右の合計は一致**）
- 件数サマリの近くに **現在の判定条件**（例: `低流動判定軸・3か月で判定`）を常時表示する。
- **流動区分の行背景色**（§6.2）。CSS クラスは ASCII キー（`.alert-row--supply-risk` 等）を用いる:
  - **供給リスク品**（`supply-risk`）: 赤（例: `#fde8e8`）
  - **在庫死蔵品**（`dormant-stock`）: 橙（例: `#ffedd5`）
  - **在庫過剰リスク品**（`excess-stock-risk`）: 黄（例: `#fff8e1`）
  - **通常流動品**（`normal-flow`）: 白（通常背景）。表示・CSV・件数サマリで統一
- **確認状態の行背景色**（確認状態が未確認以外のとき、アラート色より優先）:
  - **確認中**: 薄青（例: `#dbeafe`）
  - **確認済み**: 薄緑（例: `#dcfce7`）
  - 確認状態の CSS クラス（`.alert-row--確認済` / `.alert-row--確認中`）は流動区分と独立した概念のため、**日本語のまま据え置く**。
- **行クリック**: データ行をクリックすると **詳細** ダイアログを表示する（確認状態プルダウン等の操作要素クリック時は除く）。構成は §4.1.6 の 4 区分。
- **行のハイライト**: データ行にカーソルを合わせると背景色を変えて現在行を示す。行クリック中は選択行として強調表示する。
- **確認状態列**は一覧上の **プルダウン** で直接変更する。変更時に自動保存（`PUT /api/inventory-order-alert/confirmation`）。**メモ履歴は変更しない**。保存成功後は **ページ再読込せず**、対象行の背景色と件数サマリのみ更新する（行の並び順・スクロール位置は維持）。**変更前の状態は行の `data-confirmation-status` と比較**し、`change` イベント時点の `<select>.value`（既に新値）と混同しない。
- 一覧カード見出し行に **「YYYY年M月D日時点の集計結果を表示しています。」** を表示する。直下に **※入出荷の実績があるもののみ表示されます。**（赤字・12px 相当）を表示する。
- 数量・在庫は **3 桁カンマ区切り**で表示する。
- **ロケーション列は一覧・CSV に含めない**（在庫数集計にのみ内部利用）。
- **CSV 出力** ボタン: 一覧見出し行の右端。ラベルは **「CSV 出力」**（フィルター無関係でスナップショット全件を UTF-8 BOM 付き CSV でダウンロード）。集計データがない場合はボタン非表示。

#### 4.1.6 詳細ダイアログ（在庫内訳・責任部署・メモ）

データ行のクリックで **詳細ダイアログ**（`#ioa-location-dialog`）を開く。幅は `min(960px, calc(100vw - 24px))`（判定ルールダイアログは `min(480px, calc(100vw - 24px))`）。

内容は **4 区分** に分けて見出しを付ける。

| 区分 | 内容 |
|---|---|
| **品目** | 得意先 / 得意先品番 / 仕入先 / 仕入先品番 / 最終入荷日 / 最終出荷日 |
| **流動区分** | 流動区分（入荷実績なしの行はその旨を併記）/ **責任部署** / **判定条件**（例: `低流動判定軸・3か月で判定`） |
| **在庫** | **在庫数(SLIMS)** と **在庫数(MARI)** を併記。続けて **在庫内訳(SLIMS)** の表と在庫時点 |
| **メモ** | 確認メモ履歴と新規メモ入力欄 |

- **責任部署は流動区分の区分に置く**。責任部署は流動区分からの導出値であり、並べて示すことで対応関係が読み取れる。
  判定軸を切り替えると流動区分が変わるため、責任部署も追随する。
- **在庫数は一覧と同じ表示規則**に従う（未取得は `－`、`0` は `0`）。

**在庫内訳（`WLOCCD`）**

SLIMS CSV の **`WLOCCD`（ロケーション）** は取込時に品番ごとの内訳として保持し、**在庫数(SLIMS)（`stock_qty`）の合算** に使用する。

- **一覧・CSV にはロケーション列を出力しない**（在庫数合計のみ表示）。
- 行データには `stock_location_detail`（例: `2D0-03-5=90@20161228;2E1-03-4=10@20161228`）を保持する。`@` 以降は `WNYUDT`（入荷日）。スナップショット読込時は最新 SLIMS 在庫から再付与する。
- 表スタイルは **判定ルールダイアログ**（`#ioa-alert-rules-dialog`）と同一。列は **入荷日 / ロケーション / 在庫数**。**入荷日（`WNYUDT`）** は SLIMS CSV の値（Oracle の最終入荷日と一致しない場合がある）。**入荷日昇順**（空は末尾、同日はロケーション・在庫数）。CSV 上の同一ロケーションが複数行あれば **重複のまますべて** 表示する（一覧の在庫数合計は引き続き SUM）。
- 該当ロケーションがない行は「SLIMS 在庫に該当するロケーションがありません。」を表示する。
- **MARI 在庫にロケーション内訳はない**（品番単位の合計のみ）。

**メモ**

- **確認メモ履歴** を表形式で表示する（列: **登録日時 / 登録者 / 内容**、**新しい順**）。列幅は登録日時・登録者を必要最小（固定幅）とし、**内容** に残り幅を割り当てる。**登録者**は Django ユーザーの **氏名**（姓＋名。未設定時は社員番号）。**新しいメモ** 欄に追記し **保存** で `POST /api/inventory-order-alert/confirmation/memos` を呼び出す（確認状態は変更しない）。履歴は PostgreSQL の `InventoryOrderAlertConfirmationMemoEntry` に蓄積する。

#### 4.1.7 確認状態の更新

仕入先への確認が完了した行の **確認状態**（UL-INVENTORY-ORDER-ALERT-2026-001 S-201）を `確認済み` に更新し、再確認の対象から外せるようにする。

| 項目 | 必須 | 内容 |
|---|---|---|
| 確認状態 | 必須 | `未確認` / `確認中` / `確認済み` のいずれか（一覧の **確認状態列プルダウン** で変更） |
| メモ | 任意 | 仕入先への確認内容、回答概要、発注可否等（1件最大 500 文字）。**在庫内訳ダイアログ**で **時系列に追記**（登録者・登録日時・内容を履歴管理。登録者は氏名表示）。一覧の確認状態プルダウン変更時は **メモ履歴に触れない** |

- 確認状態を変更すると **即時保存** する（別途保存ボタンなし）。保存成功後は **再読込せず** 行背景色・件数サマリを更新する。API 応答に `alertRowClass` と `counts` を含める。

- 保存キー: **`cust_code` + `item_cd`**（同一得意先・品番を一意とする）。
- 保存時に **確認者**（ログインユーザーの社員番号）と **確認日時**（サーバ時刻）を記録する。
- **確認中／確認済み** にした時点の **流動区分** を `confirmed_flow_quadrant` として記録する。判定条件は **基準判定条件（低流動判定軸・3か月）に固定** し、利用者が一覧で選んでいる判定軸・判定期間には依存しない。
- **SLIMS CSV 再取込（データ更新）後**、当該行の最新の流動区分が確認時より **深刻化** した場合（通常流動品→在庫過剰リスク品、在庫死蔵品→供給リスク品 等、流動区分ランクが小さくなる方向）は **自動で未確認** に戻す。判定は基準判定条件で行う（取込バッチは利用者の画面状態を知り得ないため）。取込完了メッセージに戻した件数を表示する。
- 件数サマリ右側（確認済み／確認中／未確認）の横に **リセット** ボタンを表示する。押下時に確認ダイアログを表示し、同意後 **確認中・確認済みをすべて未確認** に戻す（**メモは維持**、`confirmed_flow_quadrant`・確認者・確認日時はクリア）。対象は **全行**（フィルタ適用前の PostgreSQL 全件）。
- `確認済み` にした行は `hideConfirmed=false` 時も一覧に残る。**行背景は薄緑** とする。流動区分の件数サマリには **確認済み・確認中の行も含める**。
- `hideConfirmed=true` のとき **確認済み行は一覧から除外** する（`unconfirmedOnly` 等と AND）。
- `未確認` に戻した場合も上書き保存する（監査ログは将来拡張可）。

#### 4.1.8 操作フロー

1. 担当者が SLIMS から在庫 CSV をエクスポートし、一覧画面で **SLIMS在庫CSV** から取込する。
2. サーバーが SLIMS 在庫を PostgreSQL に保存し、**同一リクエスト内で Oracle から全件集計**して `InventoryOrderAlertSummarySnapshot` に保存する。
3. 一覧・メニューアラート帯は **スナップショット** を読み出して表示する（確認状態のみ都度 JOIN）。
4. 流動区分の判定（§6.2）をサーバー側で行い、一覧を描画する。判定期間6値ぶんの結果を併せて配信し、判定条件の切り替えはブラウザ内で引き直す。
5. 担当者が対応が要る行（通常流動品以外）を確認し、仕入先へ連絡後、一覧の確認状態プルダウンで **確認済み** 等を登録する。
6. 必要に応じ CSV を出力し、社内共有・記録に用いる。

## 6. アラート判定

### 6.1 共通前提

- 対象行は Oracle から取得した **得意先 × 品番** ごとの 1 行とする。
- **最終入荷日以降の出荷** とは、`T_SHIP` において `DEL_FLG != 1` かつ `SHIP_DATE > 最終入荷日` の明細を指す。
- **最終入荷日が空**（入荷実績なし）の場合、**すべての出荷** を「最終入荷日以降の出荷」として集計する（検証スクリプト `aggregate_shipment_stats` と同一）。
- 在庫数は **在庫数(SLIMS)（`stock_qty`）・在庫数(MARI)（`mari_stock_qty`）のいずれも流動区分の判定には使用しない**（判断材料として表示のみ）。

### 6.2 流動区分（判定期間内の入出荷）

一覧画面の **「判定ルール」** ボタンから、次表をポップアップで確認できる（読み取り専用）。

| 期間内入荷 | 期間内出荷 | 流動区分 | CSS キー | 並び順 | 責任部署（暫定） |
|---|---|---|---|---|---|
| なし | あり | **供給リスク品** | `supply-risk` | 0 | 調達G・営業G・生産管理 |
| なし | なし | **在庫死蔵品** | `dormant-stock` | 1 | 調達G |
| あり | なし | **在庫過剰リスク品** | `excess-stock-risk` | 2 | 営業G |
| あり | あり | **通常流動品** | `normal-flow` | 3 | 生産管理 |

#### 判定軸と判定期間

| 判定軸 | 選択できる判定期間 | 既定値 | 補助テキスト |
|---|---|---|---|
| 低流動判定軸（`low_flow`） | 1 か月 / 3 か月 / 6 か月 | **3 か月** | 判定期間内に入出荷のない品目（低流動品）を洗い出します |
| 死蔵判定軸（`dormant`） | 1 年 / 2 年 / 5 年 | **1 年** | 長期にわたり動きのない品目（在庫死蔵品）を洗い出します |

- **期間内入荷** = 最終入荷日が、BOM 基準日（`asOfDate`）から遡った判定期間内にあること
- **期間内出荷** = 最終出荷日が、同じ判定期間内にあること
- **判定期間の起点** = BOM 基準日。N か月前の同日を境界とする（末日は対象月の末日に合わせる）。死蔵判定軸の 1/2/5 年は 12/24/60 か月として同一計算で扱う
- 境界日ちょうどは **期間内**（`>=` 比較）。基準日より未来の日付も **期間内** とみなす
- 日付が空・解析不能な場合は **期間外**（「なし」）として扱い、例外にしない
- **入荷実績なし**（最終入荷日が空）は判定期間に依存しない副次フラグであり、流動区分セル内のバッジで表示する
- 判定ルールポップアップ内の4パターン表は、**行全体**を一覧と同じ背景色で色付けする。流動区分列には色スウォッチを表示する
- 旧アラートレベルのラベル（`重点` / `警告（出荷あり）` / `警告（出荷なし）` / `警告（出荷）` / `警告（入荷）` / `アラート無し` / `アラートなし` / `問題なし` 等）は読込時に流動区分へ正規化する（§6.2.1）
- スナップショット読込時も **毎回再判定** する。スナップショットに流動区分は保存しない
- **確認済み・確認中の行も** 流動区分の件数に含める。行背景は確認状態の色を優先する
- 在庫数・出荷回数は判定に使用しない
- 判定は **例外を投げない**。入力の欠損・不正はすべて安全側（判定不能＝期間外、未知ラベル＝最も低いランク）に倒す

#### 6.2.1 旧アラートレベルからの正規化

確認記録（`confirmed_flow_quadrant`）に残る旧ラベルは、次の写像で流動区分として解釈する。既存データは書き換えない。

| 旧アラートレベル | 正規化後の流動区分 |
|---|---|
| 重点 | 供給リスク品 |
| 警告（出荷なし） / 警告（入荷） | 在庫過剰リスク品 |
| 警告（出荷あり） / 警告（出荷） | 通常流動品 |
| アラート無し / アラートなし / なし / 問題なし / 空 | 通常流動品 |
| 上記以外の未知の値 | 通常流動品（安全側） |

**代表例**（低流動判定軸・3か月、asOf=2026/06/17。境界は 2026/03/17）

| 最終入荷 | 最終出荷 | 流動区分 |
|---|---|---|
| 空 | 2026/06/10 | **供給リスク品**（期間内入荷なし・期間内出荷あり） |
| 2022/01/31 | 2025/02/01 | **在庫死蔵品**（いずれも期間外） |

| フィルタ | 動作 |

## 7. データ取得ロジック

### 7.1 Oracle（入荷・出荷・BOM）

検証スクリプト `scripts/verify_post_receipt_shipment_count.py` の `build_summary_rows` を **正** とする。Web 実装では `infrastructure/oracle/list_rows_builder.py`（`build_list_rows`）と domain 層に集約し、スクリプトと Web で同一結果になるよう共通化済み。

#### 7.1.1 対象ペアの抽出

```sql
SELECT TRIM(CUST_CD) AS CUST_CD,
       TRIM(CUST_ITEM_CD) AS CUST_ITEM_CD,
       MAX(TRIM(CUST_CHRG_PSN_CD)) AS CUST_CHRG_PSN_CD,
       MAX(TRIM(ITEM_CD)) AS INTERNAL_ITEM_CD
  FROM T_SHIP
 WHERE DEL_FLG != 1
   AND TRIM(CUST_ITEM_CD) IS NOT NULL
   AND TRIM(CUST_ITEM_CD) != ''
 GROUP BY TRIM(CUST_CD), TRIM(CUST_ITEM_CD)
 ORDER BY CUST_CD, CUST_ITEM_CD
```

- 一覧の `item_cd` は **`CUST_ITEM_CD`**（得意先品番）。SLIMS `WSHOCD` と突合する。
- **SLIMS にのみ存在する品番**（`T_SHIP` に出荷実績がない `CUST_ITEM_CD`）は一覧行として **生成しない**（混乱防止）。在庫 CSV にあっても Oracle 出荷ペアに無い品番は表示対象外。
- BOM・最終入荷日は **内作品番 `ITEM_CD`** を使用する。解決順序（5年9組 `NAISAK_GET` 準拠）:
  1. 同一 `(CUST_CD, CUST_ITEM_CD)` の `T_SHIP` 行から `MAX(ITEM_CD)`
  2. 上記が無い場合 `M_CUST_ITEM`（`DLV_LOC_CD='*'`、BOM 基準日で有効期間内、同一キーは **最終行** の `ITEM_CD`）
  3. それでも無い場合は `CUST_ITEM_CD` をそのまま使用

#### 7.1.2 BOM・仕入先・最終入荷日

| 処理 | テーブル | 内容 |
|---|---|---|
| 完成品ルート | `M_ITEM` | `SUB_ITEM_CD_01`〜`05` を含むルート集合 |
| 階層1外注 | `M_PS` + `M_ITEM` | `OUTSIDE_TYP = '2'`、`LEVEL = 1`、BOM 基準日で有効な構成 |
| 仕入先 | `M_PUCH_UNIT_COST_H` + `M_VEND_CTRL` | 品目ごとの仕入先コード・略称（5年9組 SICODE_GET2 相当。**最終行を採用**） |
| 最終入荷日 | `T_PAST_INSPC_ACPT` | `(ITEM_CD, VEND_CD)` ごとの `MAX(ACPT_DATE)` |

**最終入荷日の行への反映**（`resolve_last_incoming_for_finished`）:

- 完成品に紐づく各ルート・階層1品目について、仕入先コードが有効（空・`?` 以外）なものを走査する。
- 入荷実績がある組み合わせのうち **最も新しい入荷日** を採用する。
- 入荷実績が 1 件もない場合でも、最初に見つかった有効な **階層1品番・仕入先** を表示する（最終入荷日は空）。

#### 7.1.3 出荷集計

| 項目 | 条件 | 集計 |
|---|---|---|
| 最終出荷日 | `DEL_FLG != 1`、対象 `CUST_CD`・**`CUST_ITEM_CD`** | `MAX(SHIP_DATE)` |
| 最終入荷日以降の出荷回数 | 上記 + `SHIP_DATE > 最終入荷日`（最終入荷日空のとき条件なし） | `COUNT(*)` |
| 最終入荷日以降の出荷数合計 | 同上 | `SUM(NVL(SHIP_QTY, 0))` |

#### 7.1.4 得意先コード・得意先名

| 項目 | 解決方法 |
|---|---|
| 得意先コード | **`T_SHIP` 出荷実績がある行のみ** `T_SHIP.CUST_CD`（`M_CUST_ITEM` に同一 `(CUST_CD, CUST_ITEM_CD)` ペアがある場合に `M_CUST` 存在を確認） |
| 得意先名 | 解決した `cust_code` で **`M_CUST.CUST_NAME`** を参照 |

**注**: `T_SHIP` に出荷実績のない SLIMS 専用品番は §7.1.1 のとおり一覧対象外のため、得意先コード・名の解決も行わない。

### 7.2 SLIMS 在庫・集計スナップショット（PostgreSQL）

| 処理 | 内容 |
|---|---|
| 取込 | CSV 2 行ヘッダをスキップし、3 行目以降をパース。`WSHOCD` / `WLOCCD` / `WKSBQT` を抽出（`WLOCCD` 形式フィルタ適用）し `SlimsStockSnapshot` に **ロケーション行単位** で保存 |
| **集計（取込時）** | Oracle から **全件**（`attentionOnly=false`）を取得し SLIMS 在庫・確認状態を適用。結果を `InventoryOrderAlertSummarySnapshot.rows`（JSON）に保存。**流動区分はスナップショットに保存せず、読込のたびに判定する** |
| 一覧・メニュー表示 | **スナップショットを読み出し**表示。確認状態のみ `InventoryOrderAlertConfirmation` から都度上書き |
| 品番合計 | 同一 `WSHOCD` の `WKSBQT` を **SUM** → 一覧 `stock_qty`（集計時に確定） |
| 在庫内訳 | CSV 行単位（`WKSBQT` / `WNYUDT`）→ ポップアップ |
| 突合 | 一覧行の `item_cd`（**`CUST_ITEM_CD`**）と `TRIM(WSHOCD)` を **完全一致** で LEFT JOIN（集計時） |
| 在庫時点 | `SlimsStockImport.imported_at` の **暦日** から `YYYY年M月D日時点の在庫` ラベルを生成 |
| 未一致 | `stock_qty` / `stock_location_summary` / `stock_as_of_label` を空表示。行自体は Oracle データとして表示を継続 |
| **共有 Oracle への影響**（指摘 L3-18） | 取込時の **Oracle 全件集計** は、共有 Oracle ACL `application/sales/`（REQ-NF-006）を経由するため、同じ基幹 Oracle を参照する **検収書比較・出荷トレンド一覧・5年9組** と接続・DB 負荷を共有する。集計中はこれらのアプリの応答が遅くなりうる。**緩和策**: ①集計は SLIMS 取込時のみで、一覧表示では Oracle を参照しない（REQ-NF-005） ②取込は排他制御により同時に 1 件しか走らない（本表「排他・整合性」） ③参照は SELECT のみでロックを取らない（REQ-NF-006）。取込頻度が上がり相互影響が問題化した場合は、集計の実行時間帯を業務時間外へ寄せる運用、または集計の非同期化を検討する（Issue として起票する） |
| **排他・整合性** | 取込は「在庫保存 → Oracle 全件集計 → スナップショット保存」を同一リクエストで実行するため、**全体を単一トランザクションで囲み、取込の排他ロックを取得したユーザーのみが実行できる**（§3「取込の排他」）。ロックを取得できなかった要求は**取込を行わず、一覧画面にエラーメッセージを表示する**（§3「取込の排他」・§8.2。取込専用の API エンドポイントは持たないため 409 は返さない）。既存スナップショットは変更しない。トランザクション中に Oracle 集計が失敗した場合はロールバックし、**前回のスナップショットを保持**する（REQ-NF-002 の `aggregation_error` はユーザー通知用に記録する） |

> **補足**: SLIMS の `WSHOCD` は得意先品番（**`T_SHIP.CUST_ITEM_CD`**）と突合する。BOM・入荷は `M_CUST_ITEM` で内作品番に変換してから `M_ITEM` / `T_PAST_INSPC_ACPT` を参照する（5年9組と同型）。

### 8.2 SLIMS 在庫 CSV の取込

取込は **専用の API エンドポイントを持たず**、一覧画面 `POST /app/production/inventory-order-alert`（`multipart/form-data`・フィールド名 `slims_csv`）で受け付ける。結果は一覧画面の再描画で返す。

- **認証**: 必須
- **入力**: `multipart/form-data` で CSV ファイル 1 件（`slims_csv`）
- **処理**: 取込排他ロックの取得（§3「取込の排他」）→ フォーマット検証 → PostgreSQL スナップショット置換 → 取込履歴 INSERT → Oracle 全件集計 → 集計スナップショット保存。ロック取得から集計スナップショット保存までを **単一トランザクション** で実行する
- **成功**: 一覧画面に取込件数・在庫時点を含む完了メッセージを表示する
- **失敗**: 一覧画面にエラーメッセージを表示し、**既存スナップショットは変更しない**

| 失敗事由 | 表示メッセージ |
|---|---|
| 形式不正・必須列欠落 | パースエラーの内容（§4.1.1・§6.1） |
| **別のユーザーが取込中**（排他ロック取得失敗） | 別のユーザーが取込中です。しばらく待って再実行してください。 |
| Oracle 集計失敗 | 集計に失敗しました: 〜（REQ-NF-002。前回スナップショットを保持） |

### 8.5 `PUT /api/inventory-order-alert/confirmation`

- **認証**: 必須
- **入力 JSON**:

```json
{
  "custCode": "string",
  "itemCd": "string",
  "status": "unconfirmed|in_progress|confirmed",
  "custCodeFilter": "string (optional)",
  "custChrgPsnCdFilter": "string (optional)",
  "itemCdFilter": "string (optional)",
  "level1ItemCdFilter": "string (optional)"
}
```

- **処理**: PostgreSQL に upsert（**確認状態のみ**）。`confirmed` / `in_progress` 時は `confirmed_at`, `confirmed_by` を更新
- **行キー**: `custCode` / `itemCd` は **対象行** の得意先コード・品番。JSON では `rowKey`（`custCode|itemCd`）としても保持し、`<tr>` と確認状態 `<select>` の **`data-row-key`** に付与する。`custCodeFilter` 等の **一覧フィルタ値と混同しない**。ソート・再描画後も `data-row-key` → WeakMap → 列表示文字列の順で解決する
- **成功**:

```json
{
  "ok": true,
  "confirmationStatusKey": "confirmed",
  "alertRowClass": "確認済",
  "counts": {
    "critical": 0,
    "warningShip": 0,
    "warningIncoming": 0,
    "alertNone": 0,
    "unconfirmed": 0,
    "inProgress": 0,
    "confirmed": 0
  }
}
```

- **counts**: 一覧フィルター（`custCodeFilter` / `custChrgPsnCdFilter` / `itemCdFilter` / `level1ItemCdFilter`）適用後の件数サマリ
- **`alertRowClass`**: 行の背景色を決めるための **内部トークン**（`ROW_CLASS_CONFIRMED` = `確認済`）であり、画面に表示するラベルではない。確認状態の表示ラベルは **確認済み**（UL-INVENTORY-ORDER-ALERT-2026-001 S-201）

### 13.1 SLIMS 取込頻度の確定（指摘 L3-11 / 2026/08/25）

**決定**: SLIMS CSV の取込は **不定期**とする。曜日・時刻を定めた定期取込は行わず、**運用者が在庫を確認したいタイミングで一覧画面から取り込む**。

この決定は `stockStaleDays`（在庫の鮮度警告日数）の位置づけを次のように変える。

| 項目 | 内容 |
|------|------|
| **既定値 7 日の意味** | 取込頻度に依存しない**初期値**である。「1 週間以上前の在庫で判断していないか」という一般的な目安として置く |
| **正式な調整手段** | **設定画面 SCR-02（§4.2）** から変更する。取込頻度が定まらない以上、閾値は各運用者の使い方に合わせて調整することを正とする |
| **警告が過剰な場合** | 取込間隔が空きがちな運用であれば `stockStaleDays` を大きくする（最大 365） |
| **警告が過少な場合** | 頻繁に取り込む運用であれば小さくする（最小 1） |

> 取込頻度を定めないため、**「最後にいつの在庫を見ているか」を利用者が常に確認できること**が重要になる。
> §4.1 の「〇年〇月〇日時点の在庫」表示と `isStale` 判定（§8.1）がその役割を担う。この 2 つは削除・省略してはならない。
