## 1. 背景と目的

### 1.1 背景

在庫発注アラート一覧の在庫数（V-206）は現在、**SLIMS（core SYS-004）の引当可能総バラ数（`WKSBQT`）のみ**を表示しており、列名も単に「在庫数」である。次の課題がある。

| # | 課題 | 内容 |
|---|------|------|
| 1 | 在庫数の出所が判別できない | 列名が「在庫数」のみで、SLIMS 由来であることが画面から読み取れない。基幹（MARI）の在庫と混同されうる |
| 2 | 基幹の在庫と突き合わせられない | MARI にも在庫数が存在するが一覧に出ないため、SLIMS と基幹の差異に気づく手段がない。差異は棚卸・引当の不整合を示す兆候になりうる |
| 3 | 一覧の情報密度が高い | 流動区分（S-203）の導入で列が増えた。責任部署（R-201）は流動区分から一意に導出される値であり、行ごとに常時参照する必要はないが一覧の横幅を占有している |

### 1.2 調査で確定した事実（根拠）

| 観測 | 値 | 意味 |
|---|---|---|
| MARI の在庫数の所在 | `T_ITEM_STOCK.STOCK_ON_HAND_QTY` | 5年9組（`application/gonenkukumi/`）が既に同テーブルを参照済み。内作品番（`ITEM_CD`）単位で合算できる |
| 突合キー | 内作品番 | 一覧は既に `M_CUST_ITEM` で得意先品番→内作品番を解決している。**新たなキー解決は不要** |
| 現在の Oracle 参照タイミング | SLIMS 取込時のみ | 一覧表示時は問い合わせない既存方針（機能仕様書 §4.1.1）を維持したまま追加できる |
| 責任部署の性質 | 流動区分からの導出値 | 独自の情報を持たず、流動区分が分かれば一意に定まる |

### 1.3 目的

1. SLIMS 在庫と MARI 在庫を**同一行に併記**し、両者の差異に気づけるようにする。
2. 在庫数の**出所（SLIMS / MARI）を列名で判別可能**にする。
3. 一覧から責任部署を外し、**詳細ダイアログで確認**できるようにして一覧の可読性を上げる。
4. 詳細ダイアログを**情報の区分が分かる構成**に整理する。

> **実在庫の正は SLIMS のままとする。** MARI 在庫は判断材料としての併記であり、流動区分（S-203）の判定には引き続き用いない。
> これに伴い、戦略的設計 §1.1 の制約「在庫数量は MARI を信用しない」は、**「実在庫の正は SLIMS。MARI 在庫は判断材料として併記する」** へ改訂する（§6.3）。

## 4. 機能要件

要件IDは**機能名入り形式**（`REQ-MSV-F-nnn` / `REQ-MSV-NF-nnn`）を用いる。同一アプリの機能仕様書がシンプル形式（`REQ-F-001`〜）、既存の要件定義書が `REQ-LFV-` 形式を使用しており、ID の衝突・混同を避けるためである。`MSV` は MARI Stock Visibility の略。

### REQ-MSV-F-001: MARI 在庫数の取得

MARI の在庫数を**内作品番単位で合算**して取得し、集計スナップショットに保存できること。

- 取得は **SLIMS 取込時のみ**とし、一覧表示のたびに Oracle へ問い合わせないこと（機能仕様書 §4.1.1 の既存方針を維持）。
- 突合キーは、一覧が既に解決している内作品番を用いる。新たなキー解決の仕組みを設けないこと。
- 実装レベルのクエリ・保存先は design.md で定義する。

### REQ-MSV-F-002: 在庫数の出所の判別

一覧の在庫数列を、**SLIMS 由来と MARI 由来が列名で判別できる**構成にすること。

- 列名は **「在庫数(SLIMS)」「在庫数(MARI)」** とする。
- 両列ともソート可能とし、既存の在庫数列のソート挙動（空の扱いを含む）を踏襲すること。

### REQ-MSV-F-003: 在庫が存在しない場合の表示

**在庫が 0 である場合**と、**突合先にその品番が存在しない場合**を区別して表示すること。

- SLIMS に一致する品番がない場合は **空**（既存の V-206 の定義を維持）。
- MARI に該当在庫がない場合も同様に扱う。0 と空を混同しないこと。

### REQ-MSV-F-004: CSV 出力への反映

CSV 出力に SLIMS 在庫数と MARI 在庫数の**両方**を出力し、**列名で出所が判別できる**こと。

- 既存列の順序は維持し、在庫数列の位置に両列を並べる。
- 文字コード（UTF-8 BOM 付き）は既存を維持する。

### REQ-MSV-F-005: 責任部署の一覧からの除外

責任部署（R-201）を**一覧の列から外し**、詳細ダイアログで確認できること。

- 一覧のソート対象からも外す。
- 責任部署の値そのもの（流動区分との対応）は変更しない。
- 流動区分の列・行背景色・件数サマリは変更しない。

### REQ-MSV-F-006: 詳細ダイアログの構成整理

詳細ダイアログを、**情報の区分が分かる構成**にすること。少なくとも次の 4 区分を見出しで区切って示す。

| 区分 | 含める情報 |
|---|---|
| 行の基本情報 | 得意先・得意先品番・仕入先・最終入荷日・最終出荷日 |
| 流動区分と責任部署 | 現在の判定条件での流動区分、入荷実績なしの有無、責任部署 |
| 在庫 | SLIMS 在庫数・MARI 在庫数、および SLIMS の在庫内訳（V-205） |
| メモ | 既存の確認メモ一覧と入力欄 |

- 既存の在庫内訳・メモの機能（並び順・保存・履歴）は変更しないこと。
- 具体的なレイアウト・見出し文言は design.md で定義する。

### REQ-MSV-F-007: 既存スナップショットとの互換

MARI 在庫を持たない**既存の集計スナップショット**を読み込んでも、一覧・CSV・詳細ダイアログがエラーにならないこと。

- MARI 在庫数の欄は **「－」** を表示し、未取得であることが分かるようにする。
- 再取込を必須としないこと（再取込後に値が入る）。

### REQ-MSV-F-008: 異常系・エッジケースの扱い

以下のケースで一覧が破綻せず、利用者に判断可能な表示を返すこと。

| # | ケース | 期待する扱い |
|---|--------|--------------|
| 1 | MARI に該当在庫がない | 空を表示する（0 とは区別する） |
| 2 | MARI の在庫数が 0 | 0 を表示する |
| 3 | MARI の在庫数が負値 | 値をそのまま表示する。エラーにしない（基幹の値を加工しない） |
| 4 | 内作品番が解決できない行 | MARI 在庫数は空。SLIMS 在庫数と流動区分の表示は従来どおり行う |
| 5 | MARI 在庫の取得クエリが失敗した | **取込全体を失敗させる**。既存の集計エラーと同じ扱いとし、`aggregation_error` を記録して一覧にエラーメッセージを表示する。データの欠けたスナップショットを作らないことを優先する（REQ-MSV-F-009） |
| 6 | 既存スナップショット（MARI 在庫なし）を読み込んだ | REQ-MSV-F-007 のとおり「－」 |
| 7 | 詳細ダイアログを開いた行に在庫内訳がない | 既存の「該当するロケーションがありません」表示を維持する |

### REQ-MSV-F-009: MARI 在庫取得の失敗時の扱い

MARI 在庫数の取得に失敗した場合は、**取込全体を失敗させる**こと。

- 既存の集計エラーと同じ扱いとし、集計スナップショットに `aggregation_error` を記録する。
- **MARI 在庫だけが欠けたスナップショットを作らない**。一部の列だけ値が入らない状態は、利用者が「在庫がない」のか「取得できなかった」のか判断できず、誤った発注判断につながりうるため。
- 直前のスナップショットは保持され、一覧は従来どおりそれを表示する（既存の取込失敗時の挙動を踏襲）。
- **REQ-MSV-F-007 の「－」表示（未取得）とは区別する。** 「－」はこの機能の導入前に作られた古いスナップショットに対する表示であり、取得失敗時のものではない。

> **判断の記録（2026/08/31）**: L3レビュー 指摘 L3-4 に対するユーザー判断。
> 代替案「MARI 在庫だけ空にして取込は成功扱い」は、既存の取込成功条件を変えない利点があるが、
> **欠けたデータのまま在庫を判断させる危険**を避けることを優先した。

### REQ-MSV-F-010: 取込の排他

SLIMS 取込中に別の利用者が一覧を開いた場合の扱いは、**機能仕様書 §7.2 の既存の取込排他機構に従う**こと。

- 本要件で新たな排他制御を設けないこと。
- 取込中の一覧表示は、直前のスナップショット（MARI 在庫を含む／含まない）を読むため破綻しない。

### REQ-MSV-F-011: 共通品の重複計上の許容

一覧の行は **得意先 × 得意先品番**、在庫数の突合単位は **品番** である。複数の得意先品番が同一の品番に紐づく「共通品」の場合、**同一の在庫数が複数行に表示される**。

- これは **SLIMS 在庫数・MARI 在庫数の双方に共通する**性質である。SLIMS 在庫数（V-206）も従来から同じ挙動であり、本要件で新たに生じる問題ではない。
- **得意先ごとに在庫を按分することはできない**（在庫は品番単位で保管され、どの得意先向けかの区別を持たないため）。
- したがって**重複計上を仕様として許容する**。一覧の在庫数を単純合計しても総在庫にはならない点に注意すること。
- 利用者が誤解しないよう、この性質を機能仕様書に明記する（§6.3）。

## 5. 非機能要件

### REQ-MSV-NF-001: 性能

- 取込時の Oracle 問い合わせ増加は**在庫取得の 1 クエリ**に収め、既存の集計 SQL を変更しないこと。
- 一覧表示の応答時間は既存と同等を維持すること。一覧表示時に Oracle へ問い合わせないこと。
- 1 行あたりのクライアント配信データ量の増分を **50 バイト以内**に収めること。

> 配信データ量の上限を要件段階で定めるのは、[ISSUE-0005](../../issues/ISSUE-0005-no-payload-size-requirement.md)（配信データ量の非機能要件がなく見積り誤りを検出できなかった）の再発を防ぐためである。

### REQ-MSV-NF-002: 既存データとの互換性

- 本機能の導入にあたり、既存の集計スナップショット・確認記録・確認メモを削除・初期化しないこと。
- リリース時に SLIMS 在庫 CSV の再取込を必須としないこと。

### REQ-MSV-NF-003: 基幹システムの保護

- 基幹 Oracle（MARI）は**読み取り専用**（SELECT のみ）を維持すること。
- 既存の集計 SQL・接続設定を変更しないこと。

### REQ-MSV-NF-004: 判定への不使用

- 流動区分（S-203）の判定に MARI 在庫数を用いないこと。在庫数は判断材料としての表示に限る。

### REQ-MSV-NF-005: 用語の一貫性

- 画面・CSV・コード・文書のすべてで、在庫数の出所を **SLIMS / MARI** の呼称で統一すること。
- 「基幹在庫」「システム在庫」など出所が曖昧になる表現を利用者に見える箇所で使用しないこと。

### REQ-MSV-NF-006: アーキテクチャ制約

- Clean Architecture の依存方向（interfaces → use_cases → domain ← infrastructure）を維持すること。domain / use_cases に `import django` を持ち込まないこと。
- 組み立ては `interfaces/wiring.py` のみで行うこと。
- 検証は `config/tests/test_clean_architecture.py` で担保する。

### REQ-MSV-NF-007: 品質・テスト

- 実装は TDD で進める（CLAUDE.md §2）。
- 在庫が 0 の場合と突合先に存在しない場合の区別を、自動テストで検証できること。

## 6. 前提条件・制約事項

### 6.2 外部システム / API 制約

| 対象 | 制約 |
|---|---|
| 基幹 Oracle（MARI） | **読み取り専用**（SELECT のみ）。在庫数は既存テーブルから取得でき、新たなテーブルの作成・変更を伴わない |
| SLIMS 在庫 CSV | 既存の取込仕様を変更しない。BOM 基準日（V-209）の扱いも変更しない |
| desknet's NEO | 本要件で新たな連携を追加しない |

### 6.3 既存システムへの影響

**改修対象アプリ**: `application/inventory_order_alert/`（他アプリへの改修は行わない）

| 影響箇所 | 内容 |
|---|---|
| 集計スナップショット（`InventoryOrderAlertSummarySnapshot.rows`） | MARI 在庫数を保持するため**行の構造が変わる**。既存スナップショットには含まれないため、再取込までは未取得（REQ-MSV-F-007） |
| 一覧の在庫数列 | 1 列から 2 列（SLIMS / MARI）へ |
| 一覧の責任部署列 | **削除**（詳細ダイアログへ移設） |
| ソート可能列 | 責任部署を除外し、在庫数 2 列を追加 |
| CSV 出力の列 | 在庫数列を 2 列に。責任部署列は**維持する**（CSV は持ち出し用途であり、一覧の可読性とは要求が異なるため） |
| 詳細ダイアログ | 構成を 4 区分へ整理（REQ-MSV-F-006） |
| Oracle 集計処理 | 在庫取得のクエリを 1 本追加 |
| **戦略的設計（SD-WORK-SUPPORT-PORTAL-2026-001）** | §1.1 の制約「在庫数量は MARI を信用しない／在庫は SLIMS CSV の取込結果を用いる」を、**「実在庫の正は SLIMS。MARI 在庫は判断材料として併記する」** へ改訂する必要がある |
| 機能仕様書（REQ-INVENTORY-ORDER-ALERT-2026-001） | §4.1.3（列定義）・§4.1.5（一覧 UI）・§4.1.6（詳細ダイアログ）・§6.1・§8.3 を本要件に合わせて改訂する。あわせて **共通品の重複計上（REQ-MSV-F-009）** を明記する |
| ユビキタス言語集 | V-206 在庫数 の定義に SLIMS / MARI の呼び分けを反映するかを L2 レビューで判断する |

**旧実装の撤去範囲**: 責任部署の一覧列に関する表示・ソートのコードを撤去する。責任部署の導出ロジック（流動区分→部署）は詳細ダイアログで引き続き用いるため**残す**。

## 7. スコープ外・将来検討事項

| 項目 | 対応方針 |
|---|---|
| SLIMS 在庫と MARI 在庫の**差異を判定・警告する**機能 | 本要件は併記のみ。差異の閾値判定・強調表示は将来検討 |
| MARI 在庫数を流動区分の判定条件に加えること | 判定は期間内の入出荷の有無のみ（機能仕様書 §2.4 #3 を維持） |
| MARI 在庫のロケーション別内訳 | 在庫内訳（V-205）は SLIMS のみ。MARI は合計値のみを扱う |
| 実在庫の正を MARI に切り替えること | 正は SLIMS のまま。切り替えは戦略的設計の中核制約の反転にあたり、別途の検討を要する |
| 得意先ごとの在庫の按分 | 在庫は品番単位で保管され按分できない。重複計上を許容する（REQ-MSV-F-009） |
| 責任部署の組織マスタ連携・一意化 | 業務側で未確定。暫定割当てのまま（既存スコープ外を踏襲） |
| 在庫金額の表示 | 本要件は数量のみ。将来検討 |
| 在庫数の推移（履歴）の保存・トレンド表示 | 本要件では取込時点の値のみを扱う。将来検討 |
| 詳細ダイアログの全面的な UI 刷新 | 本要件は情報の区分けと可読性の改善にとどめる。既存の在庫内訳・メモの機能は変更しない |

## 8. 受け入れ基準

| # | 基準 | 確認方法 |
|---|---|---|
