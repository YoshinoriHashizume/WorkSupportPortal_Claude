## 1. 背景と目的

### 1.1 背景

在庫発注アラート（`application/inventory_order_alert/`）は現在、**最終入荷日と最終出荷日のバランス**からアラートレベル（S-202）を 4 値（重点／警告（出荷あり）／警告（出荷なし）／アラート無し）で判定し、一覧の行背景色で強調している。この判定は「入荷が途絶えているのに出荷が続いている」供給リスクの検知に有効である一方、次の課題がある。

| # | 課題 | 内容 |
|---|------|------|
| 1 | リスクの種類が 1 方向に偏る | 供給が細っているリスク（入荷なし・出荷あり）は検知できるが、**在庫が滞留しているリスク**（入荷あり・出荷なし／入荷も出荷もなし）を同じ土俵で比較できない |
| 2 | 時間スケールが固定 | 警告条件（T-203）の月数設定は 1〜36 か月の単一設定であり、「直近 1 か月で動いていない」短期の兆候と「5 年間まったく動いていない」死蔵とを **同時に扱えない** |
| 3 | 責任部署が読み取れない | どのリスクを誰（調達G／営業G／生産管理）が引き取るのかが画面から分からない |

元資料（2026/07/14 ドラフト）は、期間内の**入荷の有無 × 出荷の有無**で品目を 4 つに分ける「4象限分析」（T-204）を提示している。既存のアラートレベル 4 値は、この 4 象限に自然に吸収される関係にある。

| 既存のアラートレベル（S-202） | 旧条件（入荷／出荷） | 対応する流動区分（S-203） |
|---|---|---|
| 重点 | なし／あり | 供給リスク品（＋入荷実績なし V-214） |
| 警告（出荷あり） | あり／あり（入荷から出荷までが長い） | 通常流動品 |
| 警告（出荷なし） | あり／なし | 在庫過剰リスク品 または 在庫死蔵品 |
| アラート無し | 混在 | 通常流動品 |

> **注**: 警告（出荷あり）は入荷・出荷ともに実績がある状態であり、期間内入荷「あり」×期間内出荷「あり」＝**通常流動品**に対応する。
> 供給リスク品（期間内入荷なし×期間内出荷あり）とは条件が逆である点に注意する。
> なお旧方式は「入荷から出荷までの間隔」を見ていたのに対し、流動区分は「基準日から遡った判定期間内にあるか」を見るため、
> 同じ行でも判定期間の取り方によって対応先は変わる。上表は**条件の対応関係を示すものであり、行単位の一対一変換ではない**。

### 1.2 調査で確定した事実（根拠）

| 観測 | 値 | 意味 |
|---|---|---|
| 流動区分の判定に必要な入力 | 最終入荷日（V-201）・最終出荷日（V-202）・BOM 基準日（V-209） | いずれも **集計スナップショットに保存済み**。Oracle 集計 SQL の追加・変更は不要 |
| 既存コードでの `alert_level` 系識別子の出現 | 34 ファイル・201 箇所 | 置き換えの影響範囲は広いが、大半は表示・整形・ソートの層 |
| DB に流動区分／アラートレベルの値が残る箇所 | 2 箇所 | ①集計スナップショット（`InventoryOrderAlertSummarySnapshot`。再取込で再生成されるため影響小）②確認記録の「確認時のアラートレベル」（`InventoryOrderAlertConfirmation.confirmed_alert_level`。**移行規則が必要**） |
| 警告条件（T-203）の月数設定 | `warningShipmentMonths` / `warningIncomingMonths`（1〜36 か月） | 流動区分は判定期間（V-211）の固定 6 値で判定するため、**判定には用いなくなる** |

### 1.3 目的

1. 得意先 × 得意先品番ごとに、選んだ判定軸（V-210）と判定期間（V-211）での**流動区分（S-203）を一覧上で識別できる**ようにする。
2. 「短期の低流動」と「長期の死蔵」を**同じ画面で軸を切り替えて**確認できるようにする。
3. 各行のリスクに対する**責任部署（R-201）**を画面上で示し、対応の引き取り先を明確にする。
4. 既存のアラートレベルが担っていた供給リスクの検知力を落とさない（**入荷実績なし（V-214）を副次フラグとして残す**）。

本要件は元資料の「見える化」に相当する範囲のみを対象とする（第1弾）。アラート通知・判断支援・アクション追跡は本要件のスコープ外とする（§7）。

## 3. 対象ユーザーと利用シーン

### 3.1 対象ユーザー / 対象業務

- **利用者**: 生産管理メニューグループを持つポータル利用者（調達G・営業G・生産管理の担当者）。既存の在庫発注アラート一覧の利用者と同一であり、本要件で新たな利用者区分は追加しない。
- **業務**: SLIMS 在庫 CSV 取込後に在庫発注アラート一覧を開き、仕入先への確認や発注要否の判断、滞留在庫の処分検討を行う日常業務。
- **利用頻度**: 既存機能と同じく、SLIMS 取込のタイミング（週次相当）および随時の確認時。

### 3.2 利用シーン

| ID | シーン | 概要 |
|---|---|---|
| UC-01 | 供給リスクの確認 | 一覧を開き、**供給リスク品**の行（特に入荷実績なしの行）を確認し、仕入先へ生産継続可否を確認する |
| UC-02 | 短期の低流動の把握 | 判定軸を**低流動判定軸**、判定期間を **1 か月**にして、直近で動きが止まった品目を洗い出す |
| UC-03 | 死蔵在庫の洗い出し | 判定軸を**死蔵判定軸**、判定期間を **5 年**にして、長期間まったく動いていない**在庫死蔵品**を抽出する |
| UC-04 | 在庫過剰の兆候の把握 | **在庫過剰リスク品**（入荷あり・出荷なし）を絞り込み、発注量の見直しや営業への確認を行う |
| UC-05 | 責任部署ごとの引き取り | 流動区分に対応する**責任部署**を確認し、対応を担当部署へ引き渡す |
| UC-06 | 一覧の持ち出し | 流動区分・判定軸・判定期間を含む一覧を CSV で出力し、会議資料や部署内共有に用いる |

## 4. 機能要件

要件IDは**機能名入り形式**（`REQ-LFV-F-nnn` / `REQ-LFV-NF-nnn`）を用いる。同一アプリの機能仕様書（REQ-INVENTORY-ORDER-ALERT-2026-001）が既にシンプル形式（`REQ-F-001`〜`REQ-F-016`）を使用しており、ID の衝突・混同を避けるためである。`LFV` は Low Flow Visibility の略。

### REQ-LFV-F-001: 流動区分の判定

得意先 × 得意先品番の 1 行ごとに、**期間内入荷（V-212）と期間内出荷（V-213）の有無の組み合わせ**から流動区分（S-203）を判定できること。判定結果は次の 4 値のいずれかとする。

| 期間内入荷 | 期間内出荷 | 流動区分 |
|:---:|:---:|---|
| なし | なし | 在庫死蔵品 |
| なし | あり | 供給リスク品 |
| あり | なし | 在庫過剰リスク品 |
| あり | あり | 通常流動品 |

- 「期間内」とは、**BOM 基準日（V-209）から判定期間（V-211）だけさかのぼった日以降**を指す。
- 最終入荷日（V-201）が空の場合は期間内入荷を「なし」、最終出荷日（V-202）が空の場合は期間内出荷を「なし」とする。
- **在庫数（V-206）は判定に用いない**（判断材料として表示するのみ。機能仕様書 §2.4 #3 を維持）。
- 判定に用いる入力はすべて集計スナップショットに保存済みの値とし、判定のために Oracle へ再問い合わせしないこと。
- 実装レベルの手順・判定関数の配置は design.md で定義する。

### REQ-LFV-F-002: 判定軸の切り替え

一覧画面で判定軸（V-210）を **低流動判定軸 / 死蔵判定軸** のいずれかに切り替えられること。

- 初期表示の判定軸は **低流動判定軸**とする。
- 切り替え時、集計スナップショットは作り直さず、**表示時に流動区分を再判定**する（データ更新（core A-003）を要さない）。
- 切り替えても行の集合（表示対象行）は変わらず、各行の流動区分のみが変わる。

### REQ-LFV-F-003: 判定期間の選択

判定軸ごとに定められた**固定の判定期間（V-211）**を選択できること。

| 判定軸 | 選択できる判定期間 | 初期値 |
|---|---|---|
| 低流動判定軸 | 1 か月 / 3 か月 / 6 か月 | 3 か月 |
| 死蔵判定軸 | 1 年 / 2 年 / 5 年 | 1 年 |

- 利用者が上記以外の任意の値を指定することはできない（管理者設定の対象ともしない）。
- 判定軸を切り替えたとき、判定期間は**切り替え先の軸の初期値**にリセットされる。
- 選択した判定期間は表示時の再判定に即時反映され、データ更新を要さない。

### REQ-LFV-F-004: 一覧の流動区分列

一覧の「アラート」列（`alert_level`）を**「流動区分」列に置き換える**こと。

- 表示値は流動区分の 4 値（在庫死蔵品／供給リスク品／在庫過剰リスク品／通常流動品）とする。
- 象限番号（「象限1」等）は画面に表示しない。
- 現在の判定軸と判定期間が一覧上で常に判別できること（列の値だけでは判定条件が分からないため）。

### REQ-LFV-F-005: 流動区分による行の強調

流動区分に応じて一覧の行背景色を変え、リスクの種類を視覚的に識別できること。

- 通常流動品の行は強調しない。
- 確認済み（S-201）の行の扱い（背景色の優先）は既存動作を維持する。
- 具体的な配色値は design.md で定義する。

### REQ-LFV-F-006: 入荷実績なしの表示

**入荷実績なし（V-214）**の行を、流動区分とは独立した**副次フラグ**として一覧上で識別できること。

- 判定期間によらず、最終入荷日が空である行が該当する。
- 旧アラートレベルの「重点」が表していた条件であり、仕入先が設備・金型を廃棄していた事故事例（機能仕様書 §2.1）に直結するため、流動区分への置き換えによって**この情報が失われてはならない**。
- 供給リスク品以外の流動区分になった行でも、入荷実績なしであれば同じ扱いで識別できること。

### REQ-LFV-F-007: 責任部署の表示

各行の流動区分に対応する**責任部署（R-201）**を一覧で確認できること。

- 対応関係はユビキタス言語集 S-203 の表に従う（在庫死蔵品＝調達G／供給リスク品＝調達G・営業G・生産管理／在庫過剰リスク品＝営業G／通常流動品＝生産管理）。
- 責任部署は**表示のみ**に用い、通知・権限・アクション記録には用いない。
- 責任部署の一意化は業務側で未確定であり、現時点の割当ては**暫定**である旨を画面上で判別できるようにするかは design.md で定義する。

### REQ-LFV-F-008: 件数サマリの流動区分化

一覧の件数サマリ（左側）を、アラートレベル別から**流動区分別の件数**に置き換えること。

- 集計対象はフィルター適用後の全行とし、右側の確認状態別件数と**同一の行集合**を数える（左右の合計が一致する既存の性質を維持する）。
- 判定軸・判定期間を変更した場合、件数サマリも即時に再計算される。

### REQ-LFV-F-009: 流動区分による絞り込み

既存の `alertOnly` フィルタ（重点／警告のいずれか）を、**流動区分による絞り込み**に置き換えること。

- 通常流動品を除いた行のみを表示する絞り込みができること（既存の `alertOnly=true` に相当する）。
- 既存の確認状態フィルタ（`unconfirmedOnly` / `hideConfirmed`）および担当者コード・得意先コード・得意先品番・仕入先品番のフィルタは変更せず、AND 条件として組み合わせられること。
- 絞り込みはブラウザ内ローカル処理で即時反映し、ページを 1 に戻す（既存動作を維持する）。

### REQ-LFV-F-010: 流動区分によるソート

一覧を流動区分でソートできること。

- 初期表示のソートは、既存の「アラートレベル昇順」に代えて**流動区分の昇順**とする。
- 流動区分の昇順は **供給リスク品 → 在庫死蔵品 → 在庫過剰リスク品 → 通常流動品** とする（リスクの緊急度順。供給停止は生産停止に直結するため最上位）。
- ソートキーは表示ラベルではなく順序キーを用いる（確認状態列の既存方針と同じ）。
- 単一列ソート・複数列ソート（最大 5 条件）のいずれからも指定できること。

### REQ-LFV-F-011: CSV 出力への反映

CSV 出力（機能仕様書 REQ-F-013）の内容を流動区分に対応させること。

- 「アラート」列を「流動区分」列に置き換える。
- 出力時点の**判定軸と判定期間**、および**入荷実績なし**・**責任部署**が判別できること。
- CSV はフィルターを適用せずスナップショット全件を出力する既存方針を維持する。ただし判定軸・判定期間は画面で選択中の値を用いる。
- 文字コード（UTF-8 BOM 付き）は既存を維持する。

### REQ-LFV-F-012: 選択状態の保持

判定軸と判定期間の選択状態が、一覧内の操作（ソート・ページ移動・フィルタ変更・確認状態の更新）をまたいで保持されること。

- 全画面再読み込みを伴わない操作で選択状態が初期値に戻らないこと。
- 選択状態を URL クエリへ同期するかどうか、およびブラウザ再読み込み後の復元可否は design.md で定義する。

### REQ-LFV-F-013: メニュー画面アラート帯の件数

生産管理メニューグループ向けのメニュー画面アラート帯（機能仕様書 §5.2 / REQ-F-014）の件数を、流動区分に基づく件数に置き換えること。

- 帯に表示する件数の内訳（どの流動区分を何件として示すか）と配色の判定条件は design.md で定義する。
- 帯の集計に用いる判定軸・判定期間は**固定値**とし、一覧の選択状態には依存しない（メニュー画面には軸の選択操作がないため）。採用する固定値は design.md で定義する。
- この結果、**利用者が一覧で固定値以外の判定条件を選んでいる間は、帯の件数と一覧の件数が一致しなくなる**。これは仕様として受け入れる（帯は全社共通の定点観測、一覧は利用者ごとの分析という役割の違いによる）。利用者が数字の食い違いを誤りと受け取らないよう、**帯と一覧の双方に判定条件を明示する**こと。
- あわせて機能仕様書の受入基準 **C-04「件数が一覧と一致すること」を、固定判定条件で表示した一覧との一致に読み替える**よう改訂する（§6.3）。
- 集計は直近の集計スナップショットから行い、Oracle へ再問い合わせしない既存方針を維持する。

### REQ-LFV-F-014: 確認記録との整合

確認記録（E-201）に保存済みの「確認時のアラートレベル」との整合を保つこと。

- 既存の確認記録に保存された旧アラートレベルの値が、置き換え後も**エラーにならず読み込めること**。
- 「データ更新後にリスクが確認時より深刻化した行を自動で未確認に戻す」既存要件（機能仕様書 REQ-F-011）を、流動区分に基づく判定として維持すること。旧アラートレベルと流動区分の**対応規則および確認記録の移行方法**は design.md で確定する。
- 確認記録・確認メモそのもの（保存キー・履歴）は本要件で変更しない。

### REQ-LFV-F-015: 警告条件の扱い

既存の「警告条件」ダイアログ（T-203）と設定値の扱いを整理すること。

- 流動区分は判定期間（V-211）の固定 6 値で判定するため、`warningShipmentMonths` / `warningIncomingMonths` は**判定に用いない**。
- 判定に用いない設定値を利用者が変更できる状態のまま残さないこと（設定値を DB に保持したまま画面から隠すか、画面自体を流動区分の判定条件の説明に置き換えるかは design.md で定義する）。
- 一覧から**現在の判定条件（判定軸と判定期間の意味）を確認できる**手段を残すこと。

### REQ-LFV-F-016: 表示時再判定

流動区分は集計スナップショットに固定保存された値ではなく、**表示のたびに判定する**こと。

- 判定軸・判定期間の変更で SLIMS 在庫 CSV の再取込や Oracle 集計を要求しないこと。
- 集計スナップショットのスキーマ変更を伴うかどうかは design.md で定義する。

### REQ-LFV-F-017: 異常系・エッジケースの扱い

以下のケースで一覧が破綻せず、利用者に判断可能な表示を返すこと。

| # | ケース | 期待する扱い |
|---|--------|--------------|
| 1 | 最終入荷日・最終出荷日がともに空 | 期間内入荷・期間内出荷ともに「なし」→ 流動区分は在庫死蔵品（低流動判定軸の場合は在庫死蔵品と呼称しない扱いに注意。REQ-LFV-F-018 参照） |
| 2 | 最終入荷日が空・最終出荷日あり | 供給リスク品。かつ入荷実績なし（V-214）として識別する |
| 3 | 最終入荷日・最終出荷日が BOM 基準日より未来の日付 | 期間内とみなす（データ不整合として除外しない） |
| 4 | SLIMS 在庫が未取込で BOM 基準日が定まらない | 既存の未取込バナー表示を維持し、流動区分列の値が不定であることが分かる表示とする |
| 5 | 判定軸・判定期間に不正な値／未知の値が指定された | 既定値（低流動判定軸・3 か月）にフォールバックし、エラー画面を出さない |
| 6 | 判定軸に対応しない判定期間が指定された（例: 低流動判定軸に 5 年） | 当該判定軸の既定値にフォールバックする |
| 7 | 確認記録に未知のラベルが保存されている | 読み込み時に正規化し、判定不能な場合も一覧表示を継続する |
| 8 | 対象行が 0 件 | 件数サマリを 0 件で表示し、エラーとしない |

### REQ-LFV-F-018: 呼称の使い分け

低流動判定軸（1・3・6 か月）で期間内入荷・期間内出荷ともに「なし」と判定された行を、**「在庫死蔵品」と断定する表現で扱わないこと**（T-206 の補足）。

- 流動区分の列値としては「在庫死蔵品」を用いるが、低流動判定軸で表示していることが同時に判別できること（REQ-LFV-F-004）。
- 集計・帳票の見出しや説明文で低流動判定軸の結果を指す場合は「低流動品（入出荷なし）」と表現する。

## 5. 非機能要件

### REQ-LFV-NF-001: 性能

- 一覧表示の応答時間は既存（集計スナップショット表示）と同等を維持すること。流動区分の判定によって Oracle への問い合わせを追加しないこと。
- 判定軸・判定期間の切り替えは**ブラウザ内ローカル処理または既存 API の範囲**で完結し、SLIMS 再取込や Oracle 集計を発生させないこと。
- 対象行数は既存一覧と同一（得意先 × 得意先品番）であり、行数の増加を伴わないこと。

### REQ-LFV-NF-002: 既存データとの互換性

- 本機能の導入にあたり、既存の集計スナップショット・確認記録・確認メモを削除・初期化しないこと。
- 既存の確認記録に保存された旧アラートレベルの値によって、一覧表示が失敗しないこと。
- リリース時に SLIMS 在庫 CSV の再取込を必須としないこと（再取込前でも流動区分を表示できること）。

### REQ-LFV-NF-003: 認可

- 認可条件は既存を踏襲する。生産管理メニューグループを持つユーザーのみが一覧・CSV 出力・メニュー画面アラート帯を利用できる。
- 本要件で新たな権限区分・管理者専用機能を追加しないこと（判定期間は固定値のため管理者設定の対象外）。

### REQ-LFV-NF-004: 用語の一貫性

- 画面・API・CSV・コード・文書のすべてで、ユビキタス言語集の用語を用いること。
- 「未流動品」「デッドストック」「不良在庫」「象限1〜4（番号のみ）」を利用者に見える表現として使用しないこと。

### REQ-LFV-NF-005: アーキテクチャ制約

- Clean Architecture の依存方向（interfaces → use_cases → domain ← infrastructure）を維持すること。domain / use_cases に `import django` を持ち込まないこと。
- 組み立ては `interfaces/wiring.py` のみで行い、`composition.py` および `services/` 層を新設しないこと。
- 基幹 Oracle（MARI）は**読み取り専用**であり、本要件で Oracle への更新を行わないこと。
- 検証は `config/tests/test_clean_architecture.py` で担保する。

### REQ-LFV-NF-006: 品質・テスト

- 実装は TDD で進める（CLAUDE.md §2）。流動区分の判定は境界値（判定期間の境界日、空日付、基準日と同日）を含めて自動テストで検証できること。
- 既存のアラートレベルに依存する自動テストは、流動区分への置き換えに合わせて更新すること（削除の対象は design.md / tasks.md で明示する）。

### REQ-LFV-NF-007: 運用・可観測性

- 判定軸・判定期間の不正値フォールバック（REQ-LFV-F-017 #5・#6）が発生した場合の記録要否・記録先は design.md で定義する。
- 本要件で新たな定期バッチ・常駐処理を追加しないこと。

## 6. 前提条件・制約事項

技術スタック（Python 3.12 / Django 5.2 / PostgreSQL 16 / Oracle）は既存アプリを踏襲し、本要件で技術選定を伴わないため 6.1 は設けない。

### 6.2 外部システム / API 制約

| 対象 | 制約 |

| desknet's NEO | 本要件で新たな連携を追加しない |
