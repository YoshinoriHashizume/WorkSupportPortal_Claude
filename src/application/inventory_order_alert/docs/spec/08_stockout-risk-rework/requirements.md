## 1. 背景と目的

### 1.1 背景

06 で作った在庫切れリスク（S-204）を実データで確認したところ、次の問題が分かった。

| # | 問題 | 実測（2026/09/18 取込・2,299 行 / 2,031 照合単位） |
|---|---|---|
| 1 | **予測が当たっていない可能性がある** | 在庫切れ予測月は内示のない 4 か月目以降を月平均で最大 120 か月延長している。この延長部分は根拠がない |
| 2 | **月単位では順序が分からない** | 「月末に大量入荷があるが月初に在庫が尽きる」が表現できない |
| 3 | **いつ発注すれば間に合うかが出ていない** | 危険・注意は出るが、利用者が知りたい「最終ライン」が画面にない |
| 4 | **納期遅れの発注残が補充に数えられていた** | 遅れている発注が「来るもの」として扱われ、在庫切れを過小評価していた。納期遅れは 251 万個ある |
| 5 | **在庫が薄い品目が見えない** | 在庫が尽きなければ一律「対象外」で、安全在庫を下回る品目が埋もれる |
| 6 | **区分名が行動に結びつかない** | 「危険・注意」は危険度の言葉で、次に何をすべきかが分からない |

### 1.2 目的

1. **予測をやめ、内示で裏付けられた範囲だけで判定する**
2. **日次で判定し、在庫切れ日と発注の最終ラインを日付で示す**
3. 在庫が尽きなくても**安全在庫を下回る品目を層別する**
4. **区分名を「次にすべき行動」にする**

## 2. 機能要件

### REQ-SRR-F-001: 予測をやめる

在庫の見通しは **内示（V-219）で裏付けられた範囲だけ**で計算する。月平均需要による延長は行わない。

- 期間は **基準日の翌日から、内示の最終所要日まで**（最長で翌々々月末）
- 内示が 1 件もない照合単位（T-208）は **在庫が動かない**と判断する
- 在庫月数（V-222）・在庫切れ予測月（V-221）は本要件の判定には用いない（表示は別途整理する）

> 内示のない品目でも実際には出荷があるが（実測で 906 単位中 389 単位に出荷実績あり）、**需要の裏付けがないものを推測で判定しない**という方針を採る。これらは流動区分（S-203）で「低流動品」「欠品」として見える。

### REQ-SRR-F-002: 日次で在庫の見通しを立てる

照合単位ごとに、次の式で**日ごと**に在庫を追う。

```
その日の在庫 ＝ 前日の在庫 − その日の内示 ＋ その日に届く予定入荷
起点 ＝ 照合単位の在庫合計（SLIMS。未取得は 0 として計算する）
```

- **内示**は所要日（`UNCNFM_REQUIRED_DATE`）の日付に置く
- **予定入荷**は発注残（V-224）のうち **納期が基準日より後**のものを納期の日に置く
- **納期遅れの発注残**（納期が基準日以前）は**来ないものとして計算に入れない**

### REQ-SRR-F-003: 在庫切れ日・発注期限・安全在庫割れを求める

| 項目 | 定義 |
|---|---|
| **在庫切れ日** | 期間内で在庫が初めて 0 未満になる日。なければ「切れない」 |
| **発注期限** | 在庫切れ日 − リードタイム（V-225）。**この日までに発注すれば間に合う最終ライン** |
| **安全在庫割れ** | 期間内で在庫が安全在庫を下回る日があること（安全在庫が設定されている品目のみ） |
| **納期遅れの発注残** | 納期が基準日以前の発注残の件数・数量 |

- 安全日数は**使わない**（MARI の `SAFETY_LT` は全品目 0 で運用されていない）
- リードタイムが未設定の品目は設定の既定値（既定 5 日）で補い、理由に「リードタイム未設定」を添える

### REQ-SRR-F-004: 対応区分（S-204 を改称）

在庫切れリスク（S-204）を **対応区分** に改め、区分名を**行動**で表す。

| ランク | 対応区分 | 意味 | 一次対応 |
|---|---|---|---|
| 0 | **発注遅れ** | 発注期限を過ぎている。今から発注しても間に合わない | 調達G: 至急手当て |
| 1 | **納期確認** | 発注済みだが納期が遅れている | 調達G: 仕入先へ督促 |
| 2 | **要発注** | 期限までに発注すれば間に合う | 調達G: 最終ラインまでに発注 |
| 3 | **要監視** | 在庫は尽きないが安全在庫を下回る | 生産管理: 様子を見る |
| 4 | **対象外** | 手を打たなくてよい | — |

判定は次の 2 軸の組み合わせで決まる（順番に依存しない）。

| 在庫の見通し ＼ 納期遅れの発注残 | なし | あり |
|---|---|---|
| ① 動かない（内示 0） | 対象外 | 納期確認 |
| ② 切れない（安全在庫以上） | 対象外 | 納期確認 |
| ③ 切れないが安全在庫を下回る | **要監視** | 納期確認 |
| ④ 切れる・発注期限が未来 | **要発注** | 納期確認 |
| ⑤ 切れる・発注期限を過ぎた | **発注遅れ** | **発注遅れ** |

⑤ は、発注し直しても間に合わないため納期遅れの有無によらず最も重い区分とする。

### REQ-SRR-F-005: 理由（補足）

判定根拠を行に持ち、詳細ダイアログに示す。該当するものがすべて並ぶ（複合）。

| 理由 | 条件 |
|---|---|
| 在庫切れ YYYY/MM/DD | 在庫切れ日がある |
| **発注期限 YYYY/MM/DD** | 在庫切れ日がある（最終ライン） |
| 納期遅れの発注残 N 件 M 個 | 納期遅れの発注残がある |
| 安全在庫 N を下回る | 安全在庫割れ |
| リードタイム未設定 | 品目マスタにリードタイムがない |
| 内示なし（在庫は動かない） | 内示が 0 |

### REQ-SRR-F-006: 画面・CSV・API

- 一覧の「在庫切れリスク」列を **対応区分**（5 区分）に置き換える。行の背景色は 発注遅れ＝赤系、納期確認・要発注＝黄系、要監視・対象外＝色なし
- 一覧に **在庫切れ日** と **発注期限** の列を追加し、並べ替えできるようにする
- フィルタの選択肢を 5 区分に置き換える
- CSV に 対応区分 / 在庫切れ日 / 発注期限 / 納期遅れ数量 を出す
- メニュー帯は「発注遅れ N 件 / 要発注 N 件 / 納期確認 N 件」に改める
- 既定の並び順は **対応区分ランク → 発注期限が近い順 → 在庫切れ日が近い順**

### REQ-SRR-F-007: 安全在庫の取得

MARI の品目マスタから **安全在庫**（`M_ITEM.SAFETY_STOCK`）を取込時に取得し、照合単位内の内作品番ぶんを合算して用いる。取得失敗は取込を止めず、安全在庫なしとして続行する。

### REQ-SRR-F-008: 旧区分との互換

旧区分（危険 / 注意 / 監視 / 対象外）で保存された確認記録は、次の写像で読む。

| 旧 | 新 |
|---|---|
| 危険 | 発注遅れ |
| 注意 | 要発注 |
| 監視 | 要監視 |
| 対象外 | 対象外 |

## 3. 非機能要件

### REQ-SRR-NF-001: Oracle への負荷

安全在庫は既存の品目マスタ問い合わせに列を足して取得し、**新しい問い合わせを増やさない**。内示は既に取込ごとに 1 回取得している明細をそのまま使う。

### REQ-SRR-NF-002: 判定の場所

判定は domain に置き、取込時に 1 回だけ行ってスナップショットに保存する。JS では判定しない。

### REQ-SRR-NF-003: 例外を投げない

日付の欠損・不正、在庫未取得、リードタイム未設定はすべて安全側に倒し、例外にしない。

## 4. スコープ外

- 流動区分（S-203）の判定・区分名（変更しない）
- 需要予測（V-220）・在庫切れ予測月（V-221）・在庫月数（V-222）の算出方法（表示は残す）
- 内示のない品目を出荷実績から推定すること（REQ-SRR-F-001 の方針で見送る）
- 安全在庫を MARI へ書き戻すこと（Oracle は読み取り専用）

## 5. 受け入れ基準

| # | 基準 |
|---|---|
| 1 | 実データで対応区分の件数が 5 区分に分かれ、内示 0 の単位が対象外に寄る（設計時の試算は 発注遅れ 244 / 納期確認 104 / 要発注 494 / 要監視 74 / 対象外 1,115〈照合単位・2026/09/18 スナップショット〉。**実装後の実測値は [tasks.md](tasks.md) の「実データ確認の記録」を正とする**。件数は取込のたびに動くため数値そのものは基準にしない） |
| 2 | 内示が 0 の照合単位（879）は、納期遅れの発注残がなければすべて「対象外」になる |
| 3 | 在庫切れ日のある行には必ず発注期限が入り、発注期限 ＝ 在庫切れ日 − リードタイム である |
| 4 | 納期遅れの発注残は在庫の計算に加算されない。加算した場合と比べ在庫切れ日が早くなる行がある（実測: 納期遅れの発注残を持つ照合単位 222 のうち **174 単位**で在庫切れ日が早くなる、または新たに切れる） |
| 5 | 安全在庫が設定されている照合単位（825）のうち、在庫が尽きないが安全在庫を下回るものが「要監視」に層別される（実測 75 単位・89 行。要監視の行はすべて在庫切れ日が空かつ安全在庫割れ） |
| 6 | 在庫が未取得の行は在庫 0 として計算される |
| 7 | 旧区分で保存された確認記録が新区分に正規化される |
| 8 | 89965-X1Y00 は **要発注** になり、在庫切れ日と発注期限が入る（実測・基準日 2026/09/23: 在庫切れ 2026/12/15・発注期限 2026/12/11・リードタイム 4 日〈品目マスタ〉・安全在庫 1,000 を下回る）。**起草時に書いた「在庫切れ 2026/12/11・発注期限 2026/12/03・リードタイム 8 日」は誤り**で、品目マスタの `FIXED_LT` は 4 日である。日付は基準日と内示の世代で動くため、固定値ではなく「要発注かつ発注期限 = 在庫切れ日 − リードタイム」を基準とする |
