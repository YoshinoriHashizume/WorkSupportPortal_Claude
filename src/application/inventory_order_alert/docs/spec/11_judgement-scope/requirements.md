## 2. 背景と課題

### 2.1 きっかけ

利用者から `094ME-41490` について「**発注残が 10/30 にある。今日は 27 日なのでまだ納期遅れではないのに、なぜ要発注なのか**」という指摘を受けた（2026/10/27）。

調査の結果、判定は正しく動いていた（10/30 の発注残 1,000 個は予定入荷として在庫に足され、それでも内示が日 100 個あるため 12/09 に在庫が尽きる）。
しかし **12/09 は 43 日先**であり、「今日 何かする必要はない」行が警告として出ていた。

そこから判定材料を点検したところ、**「今日は手を打てない／打つ必要がない」ものが警告の 3 割を占めている**ことが分かった。

### 2.2 課題

| # | 課題 | 実データ（2026-10-27・2,300 行） |
|---|---|---|
| 1 | **遠い将来の在庫切れが今日の警告として出る** | 在庫切れ日がある 920 行のうち **295 行が 30 日以上先**。最大 94 日先 |
| 2 | **止めてある発注が「納期遅れ」として警告になる** | 納期確認 232 行のうち **54 行（26%）は 3 か月以上前の納期**。電話で止めた発注で、仕入先に聞いても「止めてあります」で終わる |
| 3 | **MRP が自動で手当てする安全在庫割れを人に見せている** | 要監視 86 件のうち **84 件が MRP 発注**。MRP は安全在庫を所要量計算に加味するため自動で発注が起票される |

結果として **警告 1,060 件**のうち、人が今日動く必要があるのは 700 件台である。

### 2.3 業務からの情報（2026-10-27 回答）

| # | 内容 |
|---|---|
| 1 | **MRP は安全在庫を加味する**（正味所要量の計算に織り込む） |
| 2 | 内示受注は来るのに**客先の確定受注が来ないことが多々ある**。内示で安全在庫を割るため MRP が発注を起票するが、確定受注が来ないので**電話で仕入先に発注を止め、発注残がそのまま残る** |
| 3 | **基幹に「発注を止めた」フラグは存在しない** |
| 4 | **基幹に「補給品」フラグも存在しない**（`SPL_ITEM_TYP` は別の意味） |

### 2.4 基幹の調査結果（2026-10-27・SELECT のみ）

| 列 | 実態 | 判定に使えるか |
|---|---|---|
| `PUCH_ODR_STS_TYP` | `1`=989 / `2`=3,543 / `9`=804,865 | ❌ 発注中と完了のみ。停止の値がない |
| `ODR_CANCEL_CAUSE_CD` | 発注残 3,541 件すべて空 | ❌ 運用されていない |
| `CONFIRM_DLV_DATE`（回答納期） | 全 809,397 件中 **10 件**のみ入力 | ❌ 運用されていない |
| `SPL_ITEM_TYP` | 発注残で `1` は 81 件 | ❌ 補給品ではない（業務確認） |
| **`UPDATED_DATE`（最終更新日）** | 納期が未来の発注残 1,553 件のうち **99.9% が 30 日以内に更新**。納期 90 日超過の 1,546 件は 1 件を除き 90 日以上更新なし | ✅ **これだけが使える** |

## 3. 機能要件

### REQ-JS-F-001: 判定ホライズン（V-239）を導入する

対応区分（S-204）は、**在庫切れ日（V-232）が基準日から判定ホライズン日数の範囲内にあるときだけ**、在庫切れ日を判定に使う。

- 範囲外（`在庫切れ日 − 基準日 ≥ 判定ホライズン日数`）の照合単位は、**在庫切れ日が無いものとして 2 軸マトリクスを引き直す**
- 引き直しの結果は 納期確認（納期遅れあり）/ 要監視（安全在庫を下回る・手動発注）/ 対象外 のいずれかになる
- **判定ホライズン日数は設定画面で変更できる**。既定 **30 日**、範囲 **1〜365 日**

### REQ-JS-F-002: 滞留発注残（V-238）を判定から外す

納期を過ぎた発注残のうち、**基幹で滞留判定日数以上まったく更新されていない**明細は **滞留発注残**とし、**納期遅れの件数・数量に数えない**。

- 判定条件: `納期 ≤ 基準日` かつ `基準日 − UPDATED_DATE ≥ 滞留判定日数`
- **滞留判定日数は設定画面で変更できる**。既定 **30 日**、範囲 **1〜730 日**
- 滞留発注残は**件数と数量を別に保持**し、詳細ダイアログに参考として表示する（REQ-JS-F-005）
- **在庫の計算には足さない**（従来の納期遅れと同じ。変更なし）

### REQ-JS-F-003: 要監視を手動発注のみにする

安全在庫（V-231）を下回ることによる **要監視**は、**発注方式（V-227）が手動発注の品番だけ**に出す。

| 発注方式 | 安全在庫を下回る場合 |
|---|---|
| **手動発注** | **要監視**（従来どおり） |
| MRP 発注 | **対象外**（MRP が自動で発注を起票する） |
| 不明 | **対象外**（MRP 発注と同じ扱い） |

- **安全在庫割れ自体の算出・保存・表示は変更しない。** 対応区分に反映するかどうかだけを変える
- 詳細ダイアログの判定サマリ（T-211）には、MRP 発注で安全在庫を下回る場合も**その事実を理由として表示する**

### REQ-JS-F-004: 判定に使わない材料も画面には出す

**判定の対象から外すことと、情報を隠すことは別**とする。次はすべて従来どおり表示する。

| 項目 | 表示場所 |
|---|---|
| 在庫切れ日（V-232）・発注期限（V-233） | 一覧の列・詳細ダイアログの判定サマリ・CSV |
| 在庫シミュレーション（V-237）のグラフ | 詳細ダイアログ（**範囲は翌々々月末まで据え置き**） |
| 安全在庫割れ | 詳細ダイアログの理由 |
| 滞留発注残 | 詳細ダイアログ（REQ-JS-F-005） |

### REQ-JS-F-005: 滞留発注残を詳細ダイアログに表示する

「在庫と発注残」に **滞留発注残** の行を追加する。

- 表記: `滞留 1,234（5 件）— 納期切れのまま更新がないため入荷見込みに数えていません`
- 0 件のときは行を隠す
- **推定であることが読み手に伝わる文言にする**（基幹にフラグがないため）

### REQ-JS-F-006: 一覧の機能を減らさない

一覧の列・ソート項目・フィルタ・件数サマリ・CSV の**構成は変更しない**。件数の中身が変わるだけとする。

- 要監視で絞り込める状態は維持する（件数が減るだけ）
- CSV には **滞留発注残の件数・数量の 2 列を末尾に追加**する

### REQ-JS-F-007: 旧スナップショットの読込

`UPDATED_DATE` を持たない旧スナップショットの発注残は、**滞留と判定しない**（＝従来どおり納期遅れとして数える）。例外にしない。

判定ホライズン・要監視の絞り込みは、保存済みの在庫切れ日・発注方式から引き直せるため旧スナップショットにも適用される。

### REQ-JS-F-008: 設定変更は次回取込から反映する

対応区分は取込時に判定して保存するため、**設定を変えても次に SLIMS 在庫 CSV を取り込むまで一覧は変わらない**。設定画面にその旨を明記する（既定リードタイムと同じ扱い）。

## 4. 非機能要件

| # | 内容 |
|---|---|
| REQ-JS-NF-001 | **Oracle への問い合わせ回数を増やさない。** `UPDATED_DATE` は既存の発注残クエリに列を足すだけで取る |
| REQ-JS-NF-002 | 判定の絞り込みは **domain の純関数**に置く。JS では判定しない |
| REQ-JS-NF-003 | 滞留の判定は**推定**であることを用語集・設計書・画面文言のすべてに残す。業務ルールとして扱わない |
| REQ-JS-NF-004 | 在庫切れ日・発注期限・安全在庫割れ・在庫シミュレーションの**算出ロジックは 1 行も変更しない**。既存テストが全件そのまま通ることを条件とする |

## 5. スコープ外

| # | やらないこと | 理由 |
|---|---|---|
| 1 | 在庫切れ日・発注期限・在庫シミュレーションの算出方法 | spec/08・09 で確定済み。本件は「判定に使うかどうか」だけ |
| 2 | 在庫シミュレーションの描画範囲を縮める | グラフは先を見るためのもの。判定ホライズンとは目的が違う |
| 3 | 流動区分（S-203）の判定 | 別の軸 |
| 4 | 止めた発注を基幹で閉じる運用の整備 | **本来の解決策だが基幹の運用変更であり本アプリの範囲外**。V-238 に課題として記録する |
| 5 | `PUCH_ODR_GNR_TYP` による滞留判定 | `2` と `9` の意味が未確認。`UPDATED_DATE` で足りる |
| 6 | 対応区分を 5 → 4 分類に減らす | 要監視は手動発注で残すため 5 分類を維持する |
