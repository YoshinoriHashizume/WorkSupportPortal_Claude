## 1. 背景と目的

### 1.1 背景

在庫発注アラートは、02（流動区分）・05（判定期間の一本化・推奨アクション・需要予測）を経て「入荷・出荷が止まっている品目」を見える化してきた。しかし本機能の目的を改めて **「お客さんの納期どおりに製品を納める＝在庫切れを起こさない」** と置き直すと、一覧の主軸である流動区分（S-203）は「なぜ補充が来ないか」の理由であって、「**いつ在庫が尽きるか**」「**それまでに補充が来るか**」を直接には示していない。

### 1.2 調査で確定した事実（根拠。2026/09/17 基準、2,299 行。brainstorm.md §5）

| 事実 | 数値 |
|---|---|
| 6 か月以内に在庫切れ見込み（05 の在庫切れ予測月） | 低流動品（入荷なし）94 / 在庫死蔵品 33 / 低流動品（出荷なし）68 / 通常流動品 1,105 |
| うち発注残（状態 2）なし | 83 / 28 / 35 / 636 |
| 対応要の 3 区分で「6 か月以内に在庫切れ かつ 発注残なし」 | **146 行**（一覧 1,003 行の中に埋もれている） |
| 通常流動品で発注残なし | 636 行。JIT で発注が直前に出るため「発注残なし」だけでは危険と言えない |
| 発注残の納期超過 | 3,310 明細中 1,980（1,520 は 3 か月以上前）。業務回答: 閉じ忘れではなく納期遅れの入荷待ち |
| 品目マスタ | `MRP_ODR_TYP` 4（手動発注）565 品番・5（MRP）18,860 品番。`FIXED_LT`（日）は 17,606 品番に値あり、2〜5 日が大半 |

### 1.3 目的

1. 各行について **在庫切れリスク（S-204: 危険／注意／監視／対象外）** を判定し、対応の優先順位を一覧・メニュー帯で一目で分かるようにする
2. 在庫切れの要因のうち **発注忘れ・納期遅れ・数量不足・リードタイム超過・仕入先の長期未発注** を、それぞれ理由として示す
3. 流動区分（S-203）・推奨アクション（T-207）・責任部署（R-201）・需要予測（V-220〜V-222）は据え置き、在庫切れリスクの理由と対処の説明に使う

## 4. 機能要件

### REQ-SOR-F-001: 発注残の取得

- SLIMS 在庫 CSV 取込時に、基幹 Oracle（MARI）の `T_RLSD_PUCH_ODR` から **発注残（V-224）** を取込ごとに 1 回取得する
- 対象: `PUCH_ODR_STS_TYP = '2'` かつ取消（`ODR_CANCEL_SLIP_ISS_FLG`）なし かつ 残数（`PUCH_ODR_QTY` − 当該発注の検収数量合計 `T_PAST_INSPC_ACPT.ACPT_QTY`）> 0
- 取得項目: **発注コード（`PUCH_ODR_CD`、明細の識別子）**、仕入先品番（`ITEM_CD`）、仕入先（`VEND_CD`）、納期（`PUCH_ODR_DLV_DATE`）、回答納期（`CONFIRM_DLV_DATE`、あれば）、残数
- 同じ発注明細は発注コードで識別する。仕入先品番・仕入先・納期・数量が同じでも発注コードが違えば **別の明細として数える**（2026/09/18 追加）
- 納期を過ぎた発注残も **除外しない**（納期遅れの入荷待ちとして扱う）
- 取得に失敗した場合は取込を失敗させず、補充見込みを「不明」として続行し、取込結果メッセージに警告を出す（05 の内示受注と同じ扱い）

### REQ-SOR-F-001a: 工程の連鎖（2026/09/18 追加）

- 完成品（内作品番）から BOM（`M_PS`、有効期間内、外注品 `OUTSIDE_TYP = '2'`）を **末端まで辿った外注工程の列**を「工程の連鎖」とし、各工程の 仕入先品番・仕入先・リードタイムを行に持つ。先頭が完成品直下の工程（従来の `level1`）、以降が上流
- 発注残（F-001）は **連鎖のすべての工程**について取得し、行に持つ。完成品直下の工程の発注残を「補充見込み」、上流工程の発注残を「上流工程の発注残」として区別する
- 背景: 138232-0213 の解析で、上流工程（誠豊電子）の発注 240 個が 3 か月未納なのに、直下の工程（丸栄NW）しか見ていないため補充見込みにも納期遅れにも現れなかった

### REQ-SOR-F-002: 品目マスタの取得（リードタイム・発注方式）

- 取込時に `M_ITEM` から、一覧の仕入先品番（`level1_item_cd`）について **リードタイム（V-225）** と **発注方式（V-227）** を取得する
- リードタイムが空または 0 の品番は **既定リードタイム**（設定値、既定 **5 日**）で代替し、その旨を行に持つ
- 判定に用いるリードタイムは **工程の連鎖の合計**（各工程のリードタイムの和。2026/09/18 追加）。工程ごとの値は詳細ダイアログに示す。発注方式は完成品直下の工程の値を用いる
- 発注方式が 4・5 以外の値は「不明」とする

### REQ-SOR-F-003: 補充見込みの算出

- 行の在庫切れ予測月（V-221）が定まる行について、**補充期限（V-229）** = max(在庫切れ予測月の 1 日, 基準日) ＋ 安全日数 を求める（2026/09/21 追加。従来の「予測月の月末」は、月初に尽きる品目でも月末納期の発注残を間に合うと数えていた）
- **照合単位（T-208）** に属する完成品直下の工程の仕入先品番 × 仕入先の発注残のうち、**納期が補充期限以前** かつ **長期納期超過（V-230）でない** ものの残数を合算し、**補充見込み（V-226）** とする
- 長期納期超過 = 納期からの超過日数 > リードタイム（連鎖の合計）＋ 安全日数。残数は別枠「長期納期超過」として行に持ち、詳細ダイアログに示す（補充見込みには数えない。2026/09/21 追加。業務回答「閉じ忘れではない」は発注が有効かの回答であって、間に合うかの回答ではないため）
- 併せて、納期が基準日より前の発注残（納期超過。長期納期超過を含む）の有無と、最も早い納期を持つ
- 上流工程の発注残（F-001a）のうち「流れている」とみなすのは **納期超過でなく、納期が補充期限以前** のもの（納期なしは含めない。2026/09/21 明確化。従来は納期を問わず数えていたため、来年納期の上流発注残が危険を打ち消していた）
- 回答納期がある場合の優先順位は §6.4 の確認事項 5 に従う（仮置き: 回答納期があればそれを納期とする）
- 在庫切れ予測月が空（需要なし・120 か月超）の行は補充見込みを算出しない

### REQ-SOR-F-004: 不足数量の算出

- **不足数量** = 在庫切れ予測月までの需要合計（当月残の内示 ＋ 翌月からの月別需要。4 か月目以降は月平均）− 在庫合計（照合単位）。0 未満は 0
- 05 の在庫切れ予測月の計算過程から得られる値であり、新たな仮定を置かない

### REQ-SOR-F-005: 在庫切れリスクの判定

各行を次の順に評価し、最初に該当した段階とする。

| 段階 | 条件 |
|---|---|
| **監視** | 需要予測（V-220）の算出根拠が「なし」、または在庫切れ予測月が空、または在庫切れ予測月が **監視期間**（設定値、既定 **6 か月**）より先 |
| **危険** | 猶予日数（V-228）≤ リードタイム（V-225、連鎖の合計）＋ **安全日数**（設定値、既定 **14 日**） かつ **補充見込み（V-226）= 0 または 補充見込み < 不足数量**（2026/09/21 改訂: 従来は = 0 のみ） かつ 次の免除のどちらにも該当しない: (i) **発注方式が MRP 発注 かつ 補充サイクル稼働中**（最終入荷日が「基準日 − （リードタイム＋安全日数）」以降。2026/09/21 改訂: 手動発注・不明は免除しない） (ii) **上流工程に納期超過でなく補充期限以前の納期の発注残がある**（納期超過の発注残と混在していても、その発注残が 1 件でもあれば危険にせず注意。2026/09/18 明確化、2026/09/21 納期の窓を追加） |
| **対象外（MRP 先送り）** | 発注方式が MRP 発注 かつ 流動区分が **通常流動品** かつ 猶予日数 > リードタイム＋安全日数 かつ 補充見込み = 0 かつ 納期超過の発注残なし かつ 上流工程に納期超過なし（所要量計算がまだ発注を起票していない正常状態。2026/09/21 追加。手動発注・不明は注意 (a) に残す。低流動品（入荷なし）／在庫死蔵品／低流動品（出荷なし）は発注前に仕入先の生産可否を確認する時間が要るため注意に残す＝受け入れ基準 1・UC-04） |
| **注意** | 次のいずれか: (a) 補充見込み = 0（猶予はまだある） (b) 補充見込み < 不足数量 (c) 納期超過の発注残（長期納期超過を含む）がある |
| **対象外** | 上記のいずれにも該当しない（補充見込み ≥ 不足数量 かつ 納期超過なし） |

- **補充サイクル稼働中**（最終入荷日が「基準日 − （リードタイム＋安全日数）」以降）の **MRP 発注** の行は危険にしない。発注残が不足数量をカバーすれば対象外、そうでなければ **注意** とし、理由に「直近に入荷あり」を示す（2026/09/18 改訂。JIT で発注が起票から数日で検収されるため、発注残がなくても補充が回っている品目を危険から外す）。**手動発注・不明** の行は直近入荷があっても免除しない（2026/09/21 改訂。手動発注では「前回は入荷したが次を発注していない」が発注忘れそのものであるため）
- 補充見込みが「不明」（取得失敗）の行は **注意** とし、理由に「発注残を取得できませんでした」を示す
- 判定はデータ更新（取込）時に行い、スナップショットに保存する。一覧表示時に再計算しない（05 の需要予測と同じ）
- 在庫合計が未取得（旧スナップショット）の行は **監視** とする（REQ-SOR-F-013）

### REQ-SOR-F-006: 在庫切れリスクの理由

在庫切れリスクが危険・注意の行には、次の理由を該当するものすべて持ち、画面で示す。

| 理由 | 条件 | 対処の示唆 |
|---|---|---|
| 発注忘れの可能性 | 発注方式 = 手動発注 かつ 完成品直下の工程に発注残が **1 件もない**（補充期限より後・長期納期超過も含めてない。2026/09/21 改訂） | 発注を起こす |
| 仕入先の生産可否を先に確認 | 流動区分が低流動品（入荷なし）または在庫死蔵品（1 年以上入荷なし） | 発注前に仕入先へ金型・設備の有無を確認（T-207 と同じ） |
| 納期遅れ | 完成品直下の工程に納期超過の発注残がある（長期納期超過を含む） | 仕入先に納期を確認 |
| 数量不足 | 0 < 補充見込み < 不足数量 | 追加発注・分納の確認 |
| リードタイム内 | 猶予日数 ≤ リードタイム ＋ 安全日数 | 通常の発注では間に合わない。特急・代替を検討 |
| 立ち上がり品 | 流動区分が低流動品（出荷なし）かつ需要予測の算出根拠が内示 | 初回入荷後の継続手配を確認 |
| リードタイム未設定 | 品目マスタのリードタイムが空・0（既定値で代替） | 品目マスタの整備 |
| 直近に入荷あり | MRP 発注 かつ 最終入荷日が「基準日 − （リードタイム＋安全日数）」以降（補充サイクル稼働中。2026/09/21: MRP 発注のみ） | 発注残はないが補充は回っている。念のため次回納入を確認 |
| 上流工程に発注残あり | 上流工程に納期超過でなく補充期限以前の納期の発注残がある（2026/09/18 追加、2026/09/21 納期の窓） | 後工程の発注を先行して起票し、流れを止めない |
| 上流工程で納期遅れ | 上流工程の発注残に納期超過がある（同上） | 止まっている工程（仕入先）へ状況を確認 |

- 「上流工程に発注残あり」と「上流工程で納期遅れ」は **同時に付き得る**（納期超過でない発注残と納期超過の発注残が混在する場合。2026/09/18 明確化）

### REQ-SOR-F-007: 一覧の表示

- 一覧に **在庫切れリスク** 列を追加し、段階名（危険 / 注意 / 監視。対象外は空）を表示する。列は流動区分列の **左**（先頭）に置く
- 行の背景色は **確認状態 > 在庫切れリスクのみ** で決める（危険 = 赤系、注意 = 黄系、監視・対象外 = 色なし）。流動区分は行の色にも色見本にも使わず、文字だけで示す（判定ルールダイアログの行色・色見本も撤去。2026/09/18 改訂: 画面確認で「監視なのに赤い行」が並び、色の意味が二重になって読めなかったため。色の意味を在庫切れリスク 1 つにする）
- 詳細ダイアログの「需要予測」区分に **在庫切れリスク・理由・猶予日数・補充見込み（数量・最も早い納期・納期超過の有無・長期納期超過の残数）・不足数量・リードタイム・発注方式** を追加する
- 詳細ダイアログに **工程の連鎖**（工程順に 仕入先品番 / 仕入先 / リードタイム / 発注残（数量・納期・納期超過））を示す（2026/09/18 追加）
- 詳細ダイアログの推定在庫推移グラフ（V-218）に **予測在庫** を **点線** で描く（2026/09/18 追加）: 現在の在庫（照合単位の SLIMS 在庫）から需要予測（V-220、**照合単位の合計**。当月残と翌月〜翌々々月の月別需要。在庫切れ予測月と同じ値）を引き、完成品直下の工程の発注残を納期の月に加えた 3 か月分。発注残は予定入荷の棒として重ね、在庫切れ予測月（V-221）が範囲内なら縦線で示す。内示も実績もない行・在庫未取得の行は点線を描かない
- セルは段階名のみとし、理由は詳細ダイアログで示す（05 の一覧セル簡略化の方針を踏襲）

### REQ-SOR-F-008: 並び替えと絞り込み

- 既定の並び順を **在庫切れリスクのランク（危険 → 注意 → 監視 → 対象外）→ 猶予日数 昇順 → 流動区分ランク** に変える
- 並び替えダイアログに「在庫切れリスク」「猶予日数」を追加する（猶予日数の空は末尾）
- 絞り込みに「在庫切れリスク」（すべて / 危険 / 注意 / 監視 / 対象外）と「発注方式」（すべて / 手動発注 / MRP 発注）を追加する
- `attentionOnly` は従来どおり通常流動品を除く。在庫切れリスクとは独立

### REQ-SOR-F-009: 件数サマリとメニュー画面のアラート帯

- 一覧の件数サマリ上段を「危険 N 件 / 注意 N 件 / 監視 N 件 / 対象外 N 件」に変え、流動区分の件数は判定ルールダイアログまたは詳細に移す
- メニュー画面のアラート帯は「**危険 N 件 / 注意 N 件 / 未確認 N 件**」を示す。危険 > 0 で赤系、注意のみで黄系。条件ラベルは「判定期間 1年・監視期間 6か月」

### REQ-SOR-F-010: 設定

- 設定画面（SCR-02、管理者）に **安全日数**（1〜60 日、既定 14）、**既定リードタイム**（1〜60 日、既定 5）、**監視期間**（1〜12 か月、既定 6）を追加する
- 設定の変更は **次回取込から** 反映する（判定は取込時に保存するため）。画面にその旨を示す

### REQ-SOR-F-011: 確認記録との整合

- 確認中・確認済みにした時点の **在庫切れリスク** を確認記録に保存する
- データ更新後に在庫切れリスクが **危険に上がった**（注意・監視・対象外 → 危険）行は自動で未確認に戻す（A-201 を在庫切れリスクにも適用）。流動区分の深刻化による未確認化は従来どおり
- 確認記録の項目追加はマイグレーションを伴う（§6.3）

### REQ-SOR-F-012: CSV 出力

- 既存 28 列の順序は変えず、末尾に `在庫切れリスク` / `在庫切れリスクの理由` / `猶予日数` / `補充見込み` / `補充見込みの最早納期` / `納期超過` / `不足数量` / `リードタイム` / `発注方式` を追加する

### REQ-SOR-F-013: 既存データとの互換

- 発注残・品目マスタの項目を持たない旧スナップショットの行は在庫切れリスク「監視」・理由なしとして表示し、エラーにしない
- 判定は取込時に行うため、**本機能のリリース後に SLIMS 在庫 CSV を再取込するまで在庫切れリスクは表示されない**（05 の需要予測と同じ）

### REQ-SOR-F-014: 異常系・エッジケース

| # | ケース | 期待 |
|---|---|---|
| 1 | 発注残の取得失敗（Oracle 例外） | 取込は成功。補充見込み「不明」→ 注意。取込結果メッセージに警告 |
| 2 | 品目マスタに仕入先品番がない | リードタイム既定値・発注方式「不明」。理由に「リードタイム未設定」 |

## 5. 非機能要件

### REQ-SOR-NF-001: 性能

- 発注残・品目マスタの取得は取込ごとに 1 回ずつ。取込時間の増分は **合計 10 秒以内**（内示受注の 4.3 秒と同程度を目安）
- 一覧表示は既存どおりスナップショット読込のみ

### REQ-SOR-NF-002: 既存データとの互換性

- スナップショットは JSON 項目の追加のみ（マイグレーション不要）。確認記録の項目追加はマイグレーションを伴う

### REQ-SOR-NF-003: 認可

- 既存どおり（生産管理メニューグループ。設定は管理者）

### REQ-SOR-NF-004: 用語の一貫性

- 画面・CSV・コード・文書は用語集の V-224〜V-228・S-204 に従う。「アラートレベル」「危険度」は用いない
- **「欠品」の扱いは 2026/09/21 に改訂**: 本書の初版では在庫切れリスク（S-204）の呼び名として「欠品」を使わないと定めていたが、[07_flow-quadrant-refinement](../07_flow-quadrant-refinement/requirements.md) で **流動区分（S-203）の区分名**として「欠品」「欠品（入荷なし）」を正式に採用した（用語集 T-209）。在庫切れリスクの水準（危険 / 注意 / 監視 / 対象外）を指して「欠品」と呼ばない、という規約として読む

### REQ-SOR-NF-005: アーキテクチャ制約

- 判定ロジックは domain に置き、Oracle 取得は infrastructure、制御は use_cases（05 の `enrich_rows` 経路を拡張）。views は wiring 経由

### REQ-SOR-NF-006: 品質・テスト

- 判定表（F-005）と理由（F-006）は domain のテストで全分岐を固定する。実データでの件数（危険・注意）は DECISIONS に記録する

### REQ-SOR-NF-007: 運用

- 発注残の取得失敗は警告として表示し、運用者が気づけること。閾値の変更は設定画面で完結すること

## 6. 前提条件・制約事項

### 6.1 技術スタック

既存どおり（Django 5.2 / PostgreSQL / Oracle 読み取り `oracledb` / 素の JS）。

### 6.2 外部システム / API 制約

- MARI は読み取りのみ。発注の起票・更新は行わない
- `T_RLSD_PUCH_ODR` の残数は検収履歴との差分で求める（5年9組と同じ方法）
- `M_ITEM` の `FIXED_LT` は日単位、`MRP_ODR_TYP` は 4 = 手動 / 5 = MRP（2026-09-17 業務回答。§6.4 で再確認）

| CSV | 末尾に 9 列追加。既存 28 列は不変 |
