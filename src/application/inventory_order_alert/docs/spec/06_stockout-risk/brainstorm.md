# 壁打ち整理メモ: 在庫切れリスク（補充の見込みを含めた在庫切れの検知）

Phase 0 の整理メモ。承認は不要だが、Phase 1（用語）・Phase 2（要件定義書）の入力として残す。
2026/09/17 のユーザーとの対話（目的の再定義 → 在庫切れの要因の洗い出し → 実データ測定 → 業務側の回答）をまとめたもの。

---

## 1. 戦略的設計上の位置づけ

- サブドメイン: **生産管理（コア）**、コンテキスト: **在庫発注アラート**（`application/inventory_order_alert/`）
- strategic_design.md の「アラート判定条件が業務価値そのもの」という位置づけどおり、本件は判定条件の再定義であり、コンテキストは増やさない
- 基幹 Oracle（MARI）は読み取りのみ。発注残・品目マスタの読み取りを追加する

## 2. 目的の再定義（Why）

| 項目 | 内容 |
|---|---|
| **目的** | **お客さんの納期どおりに製品を納める。そのために在庫切れを起こさない** |
| 現状の課題 | 05 までの一覧は「流動区分（入荷・出荷が止まっているか）」が主軸で、**在庫が尽きる時期と、それまでに補充が来るか**が主軸になっていない。実データでは 6 か月以内に在庫切れ見込みの行が 1,300 行あり、そのうち本当に補充の見込みがない行（146 行）が区分の中に埋もれる |
| 従来の目的との関係 | 「仕入先が設備・金型を廃棄する前に気づく」（02・05）は在庫切れ要因の一つ（要因 2）として本目的に包含される |

## 3. 在庫切れの要因（What を決めるための洗い出し）

ユーザーが挙げた 1〜3 に、実データ・調査から見えた 4〜10 を加えて整理した。

| # | 要因 | 側 | 検知に使える材料 | 本件の対象 |
|---|---|---|---|---|
| 1 | 手動発注の発注忘れ | 供給 | `M_ITEM.MRP_ODR_TYP = 4`（手動）＋ 発注残なし ＋ 在庫月数が短い | **対象** |
| 2 | 仕入先の金型・設備廃棄（長期間発注していない） | 供給 | 流動区分（低流動品（入荷なし）／在庫死蔵品）＋ 需要あり。05 で実装済み | **対象**（理由として併記） |
| 3 | 急な出荷増 | 需要 | 内示推移・出荷実績の急増、在庫月数の急減 | 加点材料（第 2 弾で精緻化） |
| 4 | 発注はあるが納期が間に合わない／納期遅れ | 供給 | 発注残の納期 vs 在庫切れ予測月、納期超過の発注残 | **対象** |
| 5 | 発注数量が足りない（分納・一部） | 供給 | 発注残数量 ＋ 在庫 < 予測月までの需要 | **対象** |
| 6 | リードタイムの読み違い（発注点を過ぎている） | 供給 | `M_ITEM.FIXED_LT`（日）vs 在庫切れまでの猶予日数 | **対象** |
| 7 | 在庫データのずれ（SLIMS と実物、SLIMS と MARI） | 在庫 | 在庫数(SLIMS)/(MARI) の乖離、推定在庫推移のマイナス | 対象外（棚卸業務。既存表示で見える） |
| 8 | 品番切替・設変で旧品番の在庫が使えない | 在庫 | `M_CUST_ITEM` の対応変更、照合単位のずれ | 対象外（事例待ち） |
| 9 | 仕入先の廃業・生産中止 | 供給 | データで検知不可。確認メモで補う | 対象外 |
| 10 | 内示のない確定受注・スポット注文 | 需要 | `T_ODR` 受注残を需要に加える | 第 2 弾 |

## 4. 5W1H + 制約

| 観点 | 内容 |
|---|---|
| Who | 生産管理（発注担当）、調達G、営業G。責任部署（R-201）は据え置き |
| What | 各行（得意先 × 得意先品番）について **在庫切れリスク**（危険／注意／監視／対象外）を判定して一覧・メニュー帯に示す。判定材料は 在庫切れ予測月（V-221、実装済み）・**発注残**・**リードタイム**・**発注方式**・流動区分 |
| Why | §2。在庫切れを起こさないため、「いつ尽きるか」と「それまでに補充が来るか」で優先順位を付ける |
| Where | 在庫発注アラート一覧（流動区分列またはその隣）、詳細ダイアログ、メニュー画面のアラート帯、CSV |
| When | SLIMS 在庫 CSV 取込時に判定してスナップショットに保存（05 の需要予測と同じ経路）。一覧表示時は再計算しない |
| How | MARI から `T_RLSD_PUCH_ODR`（発注残: 状態 2、取消なし、発注数量 − 検収数量 > 0、納期）と `M_ITEM`（`FIXED_LT`、`MRP_ODR_TYP`）を取込ごとに 1 回読む。突合キーは 仕入先品番（level1_item_cd）× 仕入先（level1_vend_cd） |
| Constraints | 基幹は読み取りのみ。発注の自動作成・通知は対象外。既存の流動区分・推奨アクション・確認状態は残す。閾値（安全日数・監視の月数）は設定画面で変更できる（既定値は要件で定める） |

## 5. 実データ測定（2026/09/17 基準、2,299 行。DECISIONS.md ステージ17〜19 と本メモ作成時の測定）

| 測定 | 結果 |
|---|---|
| 6 か月以内に在庫切れ見込み | 入荷なし 94 / 死蔵 33 / 出荷なし 68 / 通常 1,105 |
| うち発注残なし（状態 2） | 入荷なし **83** / 死蔵 **28** / 出荷なし **35** / 通常 **636** |
| 発注残の納期超過 | 3,310 明細中 1,980（うち 1,520 は 3 か月以上前）。**業務回答: 閉じ忘れではなく、納期遅れで入荷待ちの発注**として扱う |
| `MRP_ODR_TYP` | 4 が 565 品番、5 が 18,860 品番。**業務回答: 4 が手動発注**（5 は MRP） |
| `FIXED_LT` | 19,432 品番中 17,606 に値あり（2〜5 が大半、最大 20 程度）。**業務回答: 単位は日** |
| 内示取得・需要予測の所要時間 | 内示 4.3 秒、需要予測 0.3 秒（05 実装済み）。発注残の取得は状態 2 に絞れば数秒の見込み |

読み取れること:
- 通常流動品でも 636 行が発注残なし。JIT で発注が直前に出るため、「発注残なし」だけでは危険と言えず、**リードタイムとの比較が必須**
- 対応要の 3 区分で「6 か月以内に在庫切れ かつ 発注残なし」は **146 行**。これが「危険」の中心になる
- 納期超過の発注残は「補充が遅れている」信号として使う（除外しない）

## 6. 判定の骨子（要件定義書で確定する）

```
猶予日数   = 在庫切れ予測月の 1 日 − 基準日（日。当月なら 0）
補充見込み = 在庫切れ予測月の月末までに納期がある発注残の残数合計（仕入先品番 × 仕入先）
不足数量   = 在庫切れ予測月までの需要合計 − 在庫合計（照合単位）
リードタイム = M_ITEM.FIXED_LT（日）。空・0 は既定値（設定）

危険:   猶予日数 ≤ リードタイム + 安全日数 かつ 補充見込み = 0
        （手動発注なら「発注忘れの可能性」、1 年入荷なしなら「仕入先の生産可否を先に確認」を理由に添える）
注意:   在庫切れ予測が監視期間（既定 6 か月）以内で、
        補充見込み = 0（まだ猶予はある）／ 補充見込み < 不足数量 ／ 発注残の納期超過あり
監視:   需要なし、または在庫切れ予測が監視期間より先
対象外: 補充見込み ≥ 不足数量 かつ 納期超過なし（通常の JIT）
```

- 流動区分（S-203）は判定の理由と責任部署を示す軸として残す。既定ソートは 在庫切れリスク → 猶予日数 昇順 に変える
- メニュー帯は「危険 N 件 / 注意 N 件」

## 7. 漏れている観点（自問の結果）

- **在庫切れ予測が月単位**のため、猶予日数が月初基準で粗い（リードタイム 2〜5 日と比べて粒度が合わない）。安全日数（既定 14 日）で吸収するが、将来は需要の日割りが要るかもしれない
- **発注残の突合キー**が仕入先品番 × 仕入先（level1）である一方、需要・在庫は照合単位（T-208）で合算している。同じ仕入先品番を共有する得意先品番間では発注残も共有されるため、照合単位で合算するのが整合的
- **納期超過が 3 か月以上の発注残**を「補充見込み」に数えてよいか（業務回答は「閉じ忘れではない」だが、数量をそのまま当てにしてよいかは別問題）。要件では「注意」に落として納期確認を促す
- **回答納期（`CONFIRM_DLV_DATE`）**がある場合はそちらを優先すべきか
- 立ち上がり品（低流動品（出荷なし）で内示あり）は初回入荷済み・発注残なしが普通。危険に上がりすぎないか実データで確認する
- 確認状態（S-201）との関係: 危険に上がった行の確認記録を戻すか（A-201 の対象に在庫切れリスクを加えるか）
