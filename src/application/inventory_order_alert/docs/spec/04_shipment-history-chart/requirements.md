## 1. 背景と目的

### 1.1 背景

利用者から「詳細ダイアログに在庫変動のグラフを入れたい」という要望があった。壁打ちの結果、次の事実が判明した。

| # | 調査結果 | 出典 |
|---|---|---|
| 1 | SLIMS 在庫数（V-206）は取込のたびに前回データを**全削除して洗い替える**設計であり、時系列データを持たない | `infrastructure/persistence/slims_stock_repository.py` |
| 2 | MARI 在庫数（V-215）も現在値のみで、履歴を保持しない | `infrastructure/oracle/summary_queries.py:fetch_mari_stock_totals()` |
| 3 | 得意先×得意先品番ごとの**出荷実績**（`T_SHIP`）には出荷日が付与されており、月次に束ねれば真の時系列になる | `infrastructure/oracle/summary_queries.py:fetch_all_shipments()` |
| 4 | 流動区分（S-203）の判定自体が「判定期間内の入荷・出荷の有無」で決まる。出荷推移を見せることは、**なぜその行が供給リスク品／在庫死蔵品等に分類されたかの根拠を可視化する**ことに直結する | `ubiquitous_language.md` S-203 |

**在庫数そのものの時系列は存在しないため、文字どおりの「在庫変動グラフ」は実現できない。** 利用者との合意により、判定根拠でもある **出荷実績の月次推移** を表示する方針とした（詳細は 03_mari-stock-visibility/requirements.md §7 が将来検討事項として残していた「在庫数の推移（履歴）の保存・トレンド表示」に対する、現時点で実現可能な代替案でもある）。

### 1.2 調査で確定した事実（根拠）

| 観測 | 値 | 意味 |
|---|---|---|
| 出荷推移の元データ | `fetch_all_shipments()` が返す `T_SHIP` 全件（`cust_code`, `cust_item_cd`, `ship_date`, `ship_qty`） | **既存の SLIMS 取込時集計処理内で、出荷回数（T-201）の算出に既に使われている。同じ取得結果を月次に束ね直すだけでよく、新たな Oracle 問い合わせを追加しない** |
| 突合キー | `cust_code` + `cust_item_cd`（得意先品番） | 一覧行の識別子（`cust_code` + `item_cd`）とそのまま一致する。内作品番への変換は不要 |
| 現在の Oracle 参照タイミング | SLIMS 取込時のみ | 既存方針（機能仕様書 §4.1.1・§7.2「一覧表示のたびに Oracle へ問い合わせない」）を維持したまま追加できる |
| 出荷トレンド（`shipment_trend` アプリ）との関係 | 同じ `T_SHIP` を使うが、集計キー（内作品番）・コンテキスト境界が異なる | `strategic_design.md` によりコンテキストをまたぐ直接 import は禁止。出荷トレンドのクエリ関数は流用せず、本コンテキスト内に自前で実装する |

### 1.3 目的

1. 詳細ダイアログを開いた利用者が、**その品目の出荷が最近どう推移しているか**を視覚的に把握できるようにする。
2. 流動区分（供給リスク品・在庫死蔵品等）に分類された**根拠を直感的に確認**できるようにする。
3. 既存の非機能要件（Oracle への追加負荷をかけない、一覧表示のたびに Oracle へ問い合わせない）を維持したまま実現する。

> **在庫数そのものの推移ではない。** 本要件が扱うのは出荷数量の月次推移である。SLIMS 在庫数（V-206）・MARI 在庫数（V-215）は現在値のみを表示し続け、本要件はこれらを変更しない。

### 1.4 入荷推移の追加（2026/09/03）

初版は出荷推移のみを扱い、入荷推移は「スコープ外・将来検討事項」としていた（§7）。流動区分の判定が **入荷・出荷の両方の有無** で決まる以上、出荷だけでは判定根拠として不十分な場合がある（例: 出荷は続いているが入荷が止まっている「供給リスク品」）。ユーザー指示によりスコープに追加する。

入荷推移は出荷推移と次の点が異なる（design.md で詳細化）。

| 観点 | 出荷推移（V-216） | 入荷推移（V-217） |
|---|---|---|
| 突合キー | 得意先 × 得意先品番 | 内作品番の BOM 階層1構成子 × 仕入先（最終入荷日 V-201 と同じ） |
| 元データ | 既存取得済みの `T_SHIP` 全件を再利用 | `T_PAST_INSPC_ACPT` から**新たに取得**（既存の `fetch_last_incoming_by_item_vend` は日付の MAX のみで数量を持たないため流用不可） |
| Oracle への追加問い合わせ | **なし** | **あり（1 本）**。直近 24 か月分に絞り込んで取得する |

## 3. 対象ユーザーと利用シーン

### 3.1 対象ユーザー / 対象業務

- **利用者**: 生産管理メニューグループを持つポータル利用者。既存の在庫発注アラート一覧の利用者と同一。
- **業務**: 一覧で気になる行（供給リスク品・在庫死蔵品等）を見つけ、詳細ダイアログを開いて出荷の推移を確認し、仕入先への確認や発注判断の材料にする。

### 3.2 利用シーン

|---|---|---|
| UC-01 | 判定根拠の確認 | 「供給リスク品」に分類された行を開き、実際に出荷が続いているのに入荷が止まっていることをグラフで確認する |

## 4. 機能要件

要件IDは**機能名入り形式**（`REQ-SHC-F-nnn` / `REQ-SHC-NF-nnn`）を用いる。`SHC` は Shipment History Chart の略。

### REQ-SHC-F-001: 出荷推移データの算出

得意先×得意先品番ごとに、**月次出荷数量**を算出し、集計スナップショットに保存できること。

- 算出は **SLIMS 取込時のみ**とし、一覧表示・詳細ダイアログ表示のたびに Oracle へ問い合わせないこと。
- 出荷実績の取得は、**既存の出荷回数（T-201）算出処理が使う Oracle 取得結果を再利用**し、新たな Oracle クエリを追加しないこと。
- 対象期間は **BOM 基準日（V-209）から遡って直近 24 か月**とする（範囲の妥当性は DECISIONS.md 参照）。
- 実装レベルの集計方法・保存先は design.md で定義する。

### REQ-SHC-F-002: 詳細ダイアログでのグラフ表示

詳細ダイアログに、月次出荷数量を**折れ線または棒グラフ**で表示する区分を追加すること。

- 横軸は年月、縦軸は出荷数量とする。
- 出荷実績がない月は **数量 0** として扱い、グラフ上に「実績なし」を視覚的に示すこと（欠測扱い＝グラフから欠落、にはしないこと）。
- 表示位置・具体的なレイアウトは design.md で定義する。

### REQ-SHC-F-003: 出荷実績が全くない場合の表示

対象期間内に出荷実績が **1 件もない行**では、グラフの代わりに **「出荷実績がありません」等の分かる表示**を出すこと。

- 空のグラフ（軸だけ描画される等）で利用者を混乱させないこと。

### REQ-SHC-F-004: 既存スナップショットとの互換

出荷推移・入荷推移データを持たない**既存の集計スナップショット**を読み込んでも、一覧・詳細ダイアログがエラーにならないこと。

- 出荷推移・入荷推移データがない場合は REQ-SHC-F-003 と同じ「実績なし相当」の表示にする（未取得と該当なしを区別する必要はない。どちらも判定に使わない付加情報であるため。DECISIONS.md 参照）。
- 再取込を必須としないこと（再取込後にグラフが表示されるようになる）。

### REQ-SHC-F-005: 入荷推移データの算出と表示

出荷推移（REQ-SHC-F-001〜002）に加え、**入荷推移（V-217）も同じグラフ領域に並べて**表示できること。

- 突合キーは最終入荷日（V-201）と同じ（内作品番の BOM 階層1構成子 × 仕入先）。
- 数量は `T_PAST_INSPC_ACPT.INSPC_ACPT_QTY`（検収数量）の月別合計とする。
- 対象期間・0埋めの方針は出荷推移と同じ（直近24か月、固定長、実績なしの月は0）。
- 出荷推移と**視覚的に区別**できること（色・凡例等）。
- 実装レベルの取得方法・保存先は design.md で定義する。

## 5. 非機能要件

### REQ-SHC-NF-001: 性能

- 出荷推移は取込時の Oracle 問い合わせを**追加しない**こと（既存の `fetch_all_shipments()` の結果を再利用する）。
- 入荷推移は取込時の Oracle 問い合わせが **1 本増える**ことを許容する。ただし**直近24か月分に絞り込み**、全件取得はしないこと（REQ-SHC-NF-008）。
- 一覧表示・詳細ダイアログ表示の応答時間を悪化させないこと。表示のたびに Oracle へ問い合わせないこと（取込時のみ）。
- 1 行あたりのクライアント配信データ量の増分を**実測**し、design.md / test-design.md に記録すること（[ISSUE-0005](../../issues/ISSUE-0005-no-payload-size-requirement.md) の再発防止）。

### REQ-SHC-NF-002: 既存データとの互換性

- 既存の集計スナップショット・確認記録・確認メモを削除・初期化しないこと。
- リリース時に SLIMS 在庫 CSV の再取込を必須としないこと。

### REQ-SHC-NF-003: 基幹システムの保護

- 基幹 Oracle は引き続き**読み取り専用**（SELECT のみ）とすること。
- 既存の出荷集計 SQL（`fetch_all_shipments`）・最終入荷日集計 SQL（`fetch_last_incoming_by_item_vend`）を変更しないこと（入荷推移は別クエリとして追加する）。

### REQ-SHC-NF-004: 判定への不使用

- 出荷推移（V-216）・入荷推移（V-217）を流動区分（S-203）の判定に用いないこと。表示専用の付加情報とする。

### REQ-SHC-NF-005: コンテキスト境界の遵守

- 出荷トレンド（`shipment_trend` アプリ）のクエリ関数・コードを直接 import しないこと。本要件の集計処理は在庫発注アラートのコンテキスト内に自己完結させること。

### REQ-SHC-NF-006: アーキテクチャ制約

- Clean Architecture の依存方向（interfaces → use_cases → domain ← infrastructure）を維持すること。domain / use_cases に `import django` を持ち込まないこと。
- 組み立ては `interfaces/wiring.py` のみで行うこと。
- 検証は `config/tests/test_clean_architecture.py` で担保する。
- グラフ描画は外部ライブラリを追加せず、自前実装（既存の出荷トレンドと同様の SVG 手描き方式）とすること（新規の依存関係を増やさないため）。

### REQ-SHC-NF-007: 品質・テスト

- 実装は TDD で進める（CLAUDE.md §2）。
- 月次集計ロジック（月境界・実績なしの月の 0 埋め・対象期間の絞り込み）を自動テストで検証できること。

### REQ-SHC-NF-008: 入荷推移クエリの範囲限定

- 入荷推移の取得クエリは、**直近24か月分に絞り込む WHERE 条件**を持つこと。`T_PAST_INSPC_ACPT` の全件取得は行わないこと。
- クエリの発行回数が SLIMS 取込 1 回につき 1 回であることを自動テストで検証できること。

## 6. 前提条件・制約事項

### 6.1 外部システム / API 制約

| 対象 | 制約 |
|---|---|
| 基幹 Oracle | **読み取り専用**（SELECT のみ）。参照テーブルが `T_SHIP`（既存）に加え `T_PAST_INSPC_ACPT`（既存の最終入荷日集計で参照済みだが、個々の検収明細の取得は本要件で新規） |
| SLIMS 在庫 CSV | 既存の取込仕様を変更しない |
| desknet's NEO | 本要件で新たな連携を追加しない |

### 6.2 既存システムへの影響

**改修対象アプリ**: `application/inventory_order_alert/`（他アプリへの改修は行わない）

| 影響箇所 | 内容 |
|---|---|
| 集計スナップショット（`InventoryOrderAlertSummarySnapshot.rows`） | 出荷推移・入荷推移データを保持するため行の構造が変わる（JSON フィールドへの追加。マイグレーション不要） |
| 詳細ダイアログ | 新しい区分（出荷推移・入荷推移）を追加 |
| Oracle 集計処理 | 出荷推移は新たなクエリを追加しない。**入荷推移は新たなクエリを1本追加**（直近24か月分に絞り込み。REQ-SHC-NF-008） |
| 一覧の列・ソート・CSV 出力 | **変更しない**（本要件は詳細ダイアログのみが対象） |
| 機能仕様書（REQ-INVENTORY-ORDER-ALERT-2026-001） | §4.1.6（詳細ダイアログ）を本要件に合わせて改訂する |

## 7. スコープ外・将来検討事項

| 項目 | 対応方針 |
|---|---|
| 在庫数そのものの推移グラフ | 実現可能なデータが存在しないため対象外（§1.1 参照）。将来、在庫数の時系列を保存する仕組みができた場合に再検討する |
| 一覧上でのミニグラフ（スパークライン等）表示 | 本要件は詳細ダイアログのみ。一覧行への追加は対象外 |
| 出荷推移・入荷推移データを使った新たなアラート・警告判定 | 表示のみ。判定ロジックの追加は行わない（REQ-SHC-NF-004） |
| グラフの期間切り替え（月次以外の粒度、期間の変更） | 初版は固定 24 か月・月次のみ。将来検討 |
| 出荷トレンドアプリとの表示統合・遷移導線 | 本要件では行わない |

| # | 基準 | 確認方法 |

| 8 | 入荷推移が出荷推移と同じグラフ領域に、視覚的に区別できる形で表示される | 一覧画面の目視＋自動テスト |
