### 1.2 テストレイヤーの方針

| レイヤー | テスト種別 | テスト方針 | DB依存 |
|---|---|---|---|
| Domain | 単体 | `build_reconciliation_unit_rows`・`select_representative`・`unit_confirmation`・`merge_memo_entries`、絞り込み・CSV・配信データの複数値対応 | 不要 |
| Application | 単体 | `SaveConfirmationUseCase`・`ConfirmationMemos` が照合単位行の得意先品番すべてに書くこと。集計の読込・保存ポートは偽物 | 不要 |
| Infrastructure | 結合 | 確認記録の一括保存（トランザクション）・メモの複製と `entry_group`、`load_latest_summary` の処理順、取込後の確認リセット、migration 0017 のデータ移行 | 必要 |
| Interfaces | 結合 | 一覧画面・確認 API・メモ API・CSV・サマリ API の HTTP 応答。テンプレート・JavaScript は文字列で確かめる（既存の `test_judgement_scope_interfaces.py` と同じ方式） | 必要 |

### 1.3 テスト優先順位

1. Domain（TC-RUR-D）: まとめ方・代表得意先・確認状態の引き継ぎが本件の核心
2. Infrastructure（TC-RUR-I）: 確認記録の保存単位の変更と移行（データを失わないこと）
3. Application（TC-RUR-A）: 照合単位行への保存
4. Interfaces（TC-RUR-V）: 画面・API・CSV
5. 実データでの受け入れ確認（TC-RUR-R）

### 1.4 TDD方針

CLAUDE.md に従い Phase 5 は TDD で進める。タスクごとに Red → Green → Refactor を回し、Domain → Infrastructure（確認記録）→ Application → Interfaces → 画面の順に積み上げる。
