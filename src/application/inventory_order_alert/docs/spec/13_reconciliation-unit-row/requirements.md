## 1. 背景と目的

### 1.1 背景

一覧は **得意先 × 得意先品番** ごとの行で並んでいる。一方、対応区分（S-204）は照合単位（T-208）で判定しており、同じ照合単位の行はすべて同じ判定になる。このため次の問題がある。

- 同じ得意先品番が得意先の数だけ並び、担当者は同じものを何度も確認する
- 確認記録（E-201）は得意先 × 得意先品番ごとなので、1 行を確認済みにしても同じ照合単位の他の行は未確認のまま残る
- 在庫シミュレーション（V-237）のグラフは、起点（SLIMS 在庫数 V-206）には照合単位の合計を使うのに、内示推移（V-219）・日次出荷（V-234）は **開いた行の得意先の分だけ** を使っている。そのため判定（照合単位で合算）とグラフが食い違う。用語集の V-234 は照合単位の値と定めており、仕様とも合っていない
- 流動区分（S-203）は得意先ごとの出荷で判定しているため、同じ SLIMS 在庫数を共有する照合単位の中で区分が分かれる

### 1.2 調査で確定した事実（根拠）

開発環境（2026/11/25 15:48 取込・1,996 行）で確かめた。

| 観測 | 値 | 意味 |
|---|---|---|
| 照合単位の数 | 1,726 | 照合単位行にまとめると 1,996 → 1,726 行 |
| 2 行以上ある照合単位 | 151 単位（421 行） | 最大 14 行 |
| 151 単位のうち得意先コードが違う | 144 | 大半は同じ得意先品番を得意先コードだけ変えて受けている |
| 151 単位のうち担当者が違う | 70 | 照合単位行では担当者が複数になる |
| 151 単位のうち仕入先が違う | 22 | 仕入先も複数になりうる |
| 151 単位のうち流動区分が違う | 77 | 得意先ごとの出荷で判定しているため |
| 151 単位のうち対応区分・確認状態が違う | 0 | すでに照合単位で揃っている |
| `90361-18001`（トヨタ紡織・秋田工業） | 判定は 12/10 に在庫切れ（2 得意先の内示推移を合算） | 秋田工業の行を開くとグラフは 0 を下回らない（1 日 10 個しか引かない） |

### 1.3 目的

- 同じ照合単位を 1 回の確認で済ませ、確認状態を 1 つにする
- 一覧・グラフ・判定が同じ数量（照合単位の合算）を根拠にし、食い違いをなくす
- どの得意先・担当者で絞り込んでも、関係する照合単位を見落とさない

## 4. 機能要件

### REQ-RUR-F-001: 一覧を照合単位行で表示する

- 一覧は照合単位（T-208）ごとに 1 行（照合単位行 T-213）を表示する
- 得意先品番が空で照合単位に属さない行は、これまでどおり単独で 1 行とする

### REQ-RUR-F-002: 照合単位行の各列の値

照合単位行の各列は次の値とする。

| 列 | 値 |
|---|---|
| 対応区分・在庫切れ日・発注期限 | 今と同じ（すでに照合単位で判定している） |
| 流動区分 | 照合単位の出荷・入荷を合算して判定し直した区分（REQ-RUR-F-003） |
| SLIMS 在庫数（V-206）・MARI 在庫数（V-215） | 照合単位の得意先品番ごとの値を、得意先品番の重複を除いて合算した値 |
| 最終入荷日・最終出荷日 | 照合単位の中で最も新しい日 |
| 出荷回数・出荷数合計 | 照合単位の合計 |
| 得意先コード・得意先名・担当者コード・得意先品番・仕入先コード・仕入先名・仕入先品番 | 代表得意先（V-241）の行の値。値が 2 つ以上あるときは「他 N」の印を添え、ポインタを当てると全件が分かる |
| 確認状態 | 照合単位行の確認記録（REQ-RUR-F-008） |

- 代表得意先は、照合単位の中で内示推移（V-219）の全月の合計が最も多い得意先とする。同数のときは得意先コードの小さい方
- 期間内入荷・期間内出荷・需要予測・在庫月数など、詳細ダイアログと並べ替えに使う数量も照合単位の合算とする

### REQ-RUR-F-003: 流動区分を照合単位の合算で判定する

- 流動区分（S-203）は、照合単位の出荷・入荷・SLIMS 在庫数を合算した値で判定する。区分の定義（しきい値）は変えない
- 得意先ごとの流動区分は持たない。どの得意先の出荷が止まったかは得意先別内訳（V-242）で確かめる

### REQ-RUR-F-004: 絞り込みはどの値でも当たる

- 得意先・担当者・仕入先による絞り込みは、照合単位行に含まれる値のどれか 1 つが一致すれば、その照合単位行を表示する（代表得意先に限らない）
- 絞り込みの選択肢には、照合単位行に含まれるすべての値を出す

### REQ-RUR-F-005: 並べ替え

- 数量・日付の列は、REQ-RUR-F-002 の照合単位行の値で並べる
- 得意先・担当者・仕入先などの文字列の列は、表に出している代表の値で並べる

### REQ-RUR-F-006: 詳細ダイアログに得意先別内訳を出す

- 照合単位行の詳細ダイアログに、得意先別内訳（V-242）を出す。得意先ごとに、得意先コード・得意先名・得意先品番・担当者・内示推移・出荷が分かること
- 得意先が 1 つの照合単位行でも内訳は出してよい（出し方は design.md で定める）
- 表と詳細ダイアログの両方で、得意先が複数あることが分かること

### REQ-RUR-F-007: 内示推移も得意先ごとに分かる

- 詳細ダイアログの内示推移（V-219）は照合単位の合算を示したうえで、得意先ごとの内訳も分かること

### REQ-RUR-F-008: 在庫シミュレーションと推定在庫推移を照合単位の合算にする

- 在庫シミュレーション（V-237）の内示推移・日次出荷・日次入荷・予定入荷は、照合単位の合算を使う。どの照合単位行を開いても、グラフが 0 を下回る日は在庫切れ日（V-232）と一致する
- 推定在庫推移（V-218）も同じ照合単位の合算とする

### REQ-RUR-F-009: 件数サマリ・アラート帯は照合単位行で数える

- 一覧の件数サマリ、メニュー画面のアラート帯の件数（対応区分・流動区分・確認状態）は照合単位行の数で数える

### REQ-RUR-F-010: CSV を照合単位行で出す

- CSV は画面と同じく照合単位行ごとに 1 行とする。行数は一覧の件数と一致する
- 値が 2 つ以上ある列（得意先・担当者・得意先品番・仕入先など）は、すべての値を「、」で区切って 1 つのセルに入れる

### REQ-RUR-F-011: 確認記録を照合単位行ごとに 1 つにする

- 確認状態（S-201）と確認メモ（E-202）は、照合単位行ごとに 1 つとして扱う。照合単位行で確認状態を変えると、その照合単位のすべての得意先品番に同じ確認状態が記録される
- 確認記録は得意先コードによらず、得意先品番に結び付けて残す
- 同じ照合単位行の確認状態を複数の人がほぼ同時に変えたときは、後から保存した方を採る（今と同じ）。一部の得意先品番だけが更新された状態で終わらないこと

### REQ-RUR-F-012: 照合単位の顔ぶれが変わっても確認記録を失わない

取込で照合単位に含まれる得意先品番が変わっても、確認記録を失わない。

| 変化 | 照合単位行の確認状態 | 確認メモ |
|---|---|---|
| 照合単位が分かれた | 分かれたそれぞれが、元の得意先品番の確認記録を引き継ぐ | 同左 |
| 照合単位がまとまった・得意先品番が加わった | 含まれる得意先品番の確認記録のうち、最も新しく更新された確認状態 | 含まれる得意先品番の確認メモをすべて時系列で並べる（同じ確認メモを重ねて出さない） |
| 確認記録のない得意先品番だけになった | 未確認 | なし |

### REQ-RUR-F-013: 既存の確認記録を移行する

- 得意先 × 得意先品番ごとに記録していた既存の確認記録は、得意先品番ごとの記録に移す
- 同じ得意先品番に得意先違いの記録が複数あるときは、最も新しく更新された確認状態を残す。確認メモはすべて残し、時系列で統合する
- 移行で確認記録・確認メモが 1 件も失われないこと（件数を移行の前後で確かめられること）

### REQ-RUR-F-014: 流動区分の悪化による確認リセットを照合単位行で判定する

- 流動区分が悪化したときに確認状態を未確認に戻す既存の振る舞い（機能仕様書 REQ-F-011）は、照合単位行の流動区分（REQ-RUR-F-003）で判定する

## 5. 非機能要件

### REQ-RUR-NF-001: Oracle への問い合わせを増やさない

取込時の Oracle（MARI）への問い合わせ回数を増やさない。合算は取込済みのデータで行う。

### REQ-RUR-NF-002: 照合単位ごとの対応区分を変えない

照合単位ごとの対応区分・在庫切れ日・発注期限は、変更前と同じであること（件数は行数から照合単位行の数に変わる）。

### REQ-RUR-NF-003: 画面に送るデータ量を増やしすぎない

一覧画面へ送るデータ量は、変更前を上回らないことを目安とする。上回る場合は、その量と理由を記録する（ISSUE-0005 の反省）。

### REQ-RUR-NF-004: 旧スナップショットでも画面を開ける

本変更より前に作られた集計スナップショットのままでも、一覧・詳細ダイアログ・CSV が例外にならず表示できる。

### REQ-RUR-NF-005: 判定・合算は domain に置く

照合単位行の値の決め方（合算・代表得意先・確認記録の引き継ぎ）は Django に依存しない domain に置き、画面の JavaScript で計算し直さない。

## 6. 前提条件・制約事項

### 6.1 外部システム / API 制約

- SLIMS 在庫 CSV・基幹 Oracle（読み取り専用）の取得内容は変えない

### 6.2 既存システムへの影響

| 対象 | 影響 |
|---|---|
| 一覧 | 行数が 1,996 → 約 1,726 に減る。複数値の列に「他 N」の印が付く |
| 件数サマリ・アラート帯 | 照合単位行の数で数える（例: 要対応 284 行 → 192 照合単位行） |
| 流動区分 | 77 照合単位で区分が変わりうる（合算で判定し直すため） |
| 詳細ダイアログ | 得意先別内訳が増え、グラフが照合単位の合算になる |
| CSV | 照合単位行ごとの 1 行。複数値は「、」区切り。行数が減る |
| 確認記録 | 保存の単位が得意先 × 得意先品番 → 得意先品番に変わる。データ移行を伴う |
| 確認状態の変更 API | 照合単位行に対して確認状態・確認メモを記録する形に変わる |
| 一覧データ API（`/api/inventory-order-alert/summary`） | 返す行が照合単位行になり、行の形が変わる。ポータルの画面以外に利用者がいるかは未確認（いれば影響する） |
| 本番の導入手順 | 移行の前にデータベースを退避し、migrate（移行を含む）のあと SLIMS 在庫 CSV を取り込み直す。移行の前後で確認記録・確認メモの件数を記録する |

### 6.3 制約

- 照合単位の決め方（二部グラフの連結成分）は変えない
- 確認記録は全員で共有する（ユーザーごとにしない）。これは今と同じ
