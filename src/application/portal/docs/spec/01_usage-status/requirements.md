## 1. 背景と目的

### 1.1 背景

WorkSupportPortal は、これまで Excel マクロ・VB.NET WinForms・個人端末上のスクリプトで行われていた基幹周辺業務を、Web ポータル上の共有された仕組みへ移すために構築されている。
現在 7 つの業務メニューが稼働し、利用申請の許可時に管理者がユーザーへメニューグループ（core V-002）を付与する運用が定着している。

一方で、**移した先が実際に使われているかを確認する手段が存在しない**。

| 現状で分かること | 情報源 |
|---|---|
| ユーザーが最後にログインした日時 | Django ユーザーの `last_login`（ユーザー管理画面に列として表示済み） |
| ユーザーに付与されているメニューグループ | `PortalMenuGroupAccess`（ユーザー管理画面に表示済み） |

**分からないこと**は次のとおりである。

- どのメニューが使われ、どのメニューが使われていないか（メニュー単位の利用が一切記録されていない）
- メニューグループを付与したユーザーが、実際にそのメニューを使っているか
- 誰がいつ CSV／Excel を出力し、ポータルの外へデータを持ち出したか

このため、次の 3 つの業務判断が「感覚」でしか行えない。

1. 使われていないメニューを改修すべきか、廃止すべきか、使い方を教育すべきか
2. 利用申請を許可したユーザーへのフォローが必要か
3. 付与済みのメニューグループが過剰でないか（権限棚卸 A-603）

### 1.2 目的

集計期間（V-602）内のメニュー利用ログ（E-601）を集計して管理者に提示し、上記 3 つの判断に必要な材料を与える。

具体的には次を達成する。

| # | 達成すること | 対応する判断 |
|---|---|---|
| 1 | 使われていないメニューを特定できる | メニューの改廃・教育の判断 |
| 2 | メニューグループを付与したのに使っていないユーザーを特定できる | 定着（T-602）支援・権限棚卸（A-603） |
| 3 | 出力操作（A-602）の実施者と日時を追跡できる | データ持ち出しの証跡 |

本機能は上記の**判断材料を提示するところまで**を担う。「何か月未利用ならメニューを廃止する」といった判断のしきい値は要件として定めず、管理者が集計結果を見て個別に判断する。

### 1.3 戦略的設計上の位置づけ

本機能は [strategic_design.md](../../../../../docs/strategic_design.md) の境界コンテキスト **G: ポータル基盤**（`application/portal/`）に属し、サブドメイン分類は **汎用** である。

§3.2 の判断基準に照らした結果は次のとおり。

| 判断基準 | 本機能の該当 |
|---|---|
| どの業務判断を支援するか | メニューの改廃・権限棚卸というポータル運用そのものの判断 |
| どのメニューグループの利用者が使うか | **管理**（`management`）。既存の お知らせ管理・利用申請・ユーザー管理・データベース と同じ |
| データの正がどこにあるか | ポータル自身（PostgreSQL）。MARI・SLIMS・desknet's のいずれにも依存しない |

3 基準がいずれも G を指すため、コンテキストをまたいでいない。**新しいコンテキストは新設しない。**

なお §2 は「汎用サブドメインにコア相当の非機能要件（厳密な監査証跡）を課さない」と定めている。
本機能は **利活用の把握を主目的とし、監査証跡は出力操作（A-602）に限定する**ことで、この方針に従う（REQ-F-003・REQ-NF-005 に反映）。

## 3. 対象ユーザーと利用シーン

### 3.1 対象ユーザー / 対象業務

**管理者（core R-001）のみ**が対象である。一般ユーザー（core R-002）には画面もメニューも表示しない。

想定する利用頻度は月次〜四半期であり、日常的に監視する画面ではない。

| 業務 | 実施者 | 時期 |
|---|---|---|
| メニューの改廃・教育対象の検討 | 管理者 | 四半期ごと、または新メニューのリリース後 |
| 利用申請を許可したユーザーのフォロー | 管理者 | 許可の 1 か月後を目安 |
| 権限棚卸（A-603） | 管理者 | 年次、または人事異動の後 |
| 出力操作（A-602）の確認 | 管理者 | 必要が生じたとき（随時） |

### 3.2 利用シーン

| ID | シーン | 概要 |
|---|---|---|
| UC-01 | 使われていないメニューを探す | 集計期間を直近 3 か月にし、メニュー別 利用状況を利用回数の昇順で並べて、未利用（S-602）のメニューを確認する |
| UC-02 | 新メニューの立ち上がりを見る | リリース直後のメニューについて、日別推移と利用ユーザー数の伸びを確認する |
| UC-03 | 許可したユーザーがポータルを使い始めたか確認する | ユーザー別 利用状況で、最終ログイン日時（V-606）と利用回数を確認し、休眠（S-605）のユーザーを洗い出す |
| UC-04 | 権限棚卸の対象を洗い出す | メニューグループ付与済み × 未利用の一覧から、未利用のメニューグループ付与（V-612）を確認する |
| UC-05 | データ持ち出しを確認する | 出力操作の記録から、誰がいつどのメニューから CSV／Excel を出力したかを確認する |
| UC-06 | 確認結果を持ち出して検討する | 表示中の集計結果を CSV 出力し、会議資料として用いる |

## 4. 機能要件

### REQ-F-001: 画面表示のメニュー利用ログ記録

ログイン済みユーザーが業務メニューまたは管理メニューの画面を表示したとき、メニュー利用ログ（E-601）を利用種別（S-601）`VIEW` として 1 件記録する。

記録する項目は次の 4 つに限る。

| 項目 | 内容 |
|---|---|
| ユーザー | 表示したユーザー |
| メニューキー（V-601） | 表示した画面が属するメニュー項目 |
| 利用種別（S-601） | `VIEW` |
| 利用日時 | 記録時点のサーバ日時 |

同一ユーザーが同一メニューを繰り返し表示した場合、その都度 1 件ずつ記録する（重複の抑制は行わない）。
どの画面をどのメニューキーへ対応づけるかの判別方法は design.md で定義する。

### REQ-F-002: 出力操作のメニュー利用ログ記録

ログイン済みユーザーが出力操作（A-602）を実行したとき、メニュー利用ログを利用種別 `EXPORT` として 1 件記録する。記録項目は REQ-F-001 と同一で、利用種別のみが異なる。

出力操作は **CSV 出力と Excel 出力の双方**を対象とする。
**出力を担うエンドポイントが `/api/` 配下にある場合も対象とする。** 資産棚卸結果・5年9組の出力は `/api/` 配下にのみ存在するため、経路によって記録の有無を分けると 目的③（出力操作の追跡）が一部の業務で成立しない。
出力が失敗した場合（対象データが 0 件でファイルを生成しなかった場合を含む）は記録しない。

### REQ-F-003: 記録対象の限定

次のものはメニュー利用ログとして記録しない。

| 記録しないもの | 理由 |
|---|---|
| 未ログイン状態のリクエスト（ログイン画面・利用申請状況画面） | ユーザーを特定できず、利用状況の判断材料にならない |
| 静的ファイル（CSS・JavaScript・画像）・ヘルスチェック | 業務上の利用ではない |
| 画面内の非同期問い合わせ（絞り込み・並び替え・選択肢取得の API）。**ただし出力操作（A-602）のエンドポイントは除く** | 1 回の画面表示で多数発生し、利用回数（V-603）を実態から乖離させる。出力操作は経路（`/app` / `/api/`）によらず記録する（REQ-F-002） |
| メニューキー（V-601）に対応づかない画面 | 集計軸を持たず、メニュー別の集計に載らない |
| 出力操作における絞り込み条件・出力件数・出力対象データの中身 | 業務データがログへ混入し、コンテキスト境界を越えるため（§1.3 の汎用サブドメイン方針） |
| ログイン済みだが権限を持たないメニューへのアクセス（拒否されたリクエスト） | 利用の実態ではなく、利用回数（V-603）を過大にする。拒否の記録はアクセス管理の関心事であり本要件では扱わない（§7） |

### REQ-F-004: 利用記録が業務操作を妨げないこと

利用記録（A-601）に失敗した場合でも、ユーザーが要求した画面表示および出力操作は **中断せず完了する**。
記録の失敗をユーザーに表示しない。失敗の検知方法は design.md で定義する。

### REQ-F-005: 利用状況画面の提供と閲覧制限

管理メニューグループ（core V-002 の `management`）に、メニューキー `usage-status`・表示名 **利用状況**（T-601）のメニュー項目を追加し、画面を提供する。

- 管理者（core R-001）のみが表示・利用できる
- 一般ユーザー（core R-002）にはメニューを表示せず、URL を直接指定した場合も利用できない

### REQ-F-006: 集計期間の指定

利用状況画面は、開始日と終了日からなる集計期間（V-602）の指定を受け付ける。

- 既定は **終了日＝当日、開始日＝当日の 29 日前**（直近 30 日）
- 開始日・終了日はいずれも必須とし、**全期間を対象とする指定は設けない**（REQ-NF-002）
- 開始日が終了日より後の場合はエラーとして表示し、集計を行わない
- 終了日に未来日を指定した場合は受け付けるが、集計対象となるログは存在しない
- 集計期間の幅は **最大 366 日** とする。これを超える指定はエラーとして表示し、集計を行わない（REQ-NF-002 で性能を保証できる範囲に限るため）
- 日付の境界はサーバのタイムゾーン（`Asia/Tokyo`）で判定し、**開始日の 00:00:00 から終了日の 23:59:59 まで**を集計対象とする（開始日・終了日を含む）

### REQ-F-007: 全体集計の表示

集計期間における次の値を表示する。

| 項目 | 内容 |
|---|---|
| 利用ユーザー数（V-604） | 集計期間内にメニュー利用ログを 1 件以上持つユーザーの実数 |
| 延べ利用回数（V-603） | 集計期間内のメニュー利用ログの総件数 |
| 出力回数（V-608） | 上記のうち利用種別が `EXPORT` のもの |
| 未利用ユーザー数 | 利用申請が許可（core S-001 の `APPROVED`）かつ有効（S-604）でありながら、集計期間内の利用回数が 0 のユーザー数（S-602） |
| 休眠ユーザー数 | 利用申請が許可（core S-001 の `APPROVED`）かつ有効（S-604）でありながら、最終ログイン日時（V-606）が集計期間の開始日より前であるユーザー数（S-605）。一度もログインしていないユーザー（S-603）もこれに含める |

### REQ-F-008: メニュー別 利用状況の表示

メニュー項目ごとに次を一覧表示する。**利用回数が 0 のメニューも行として表示する**（未利用のメニューを特定することが本機能の目的であるため）。

| 列 | 内容 |
|---|---|
| メニューグループ | core V-002 |
| メニュー名 | メニュー項目の表示名 |
| 表示回数（V-607） | 集計期間内の `VIEW` の件数 |
| 出力回数（V-608） | 集計期間内の `EXPORT` の件数 |
| 利用ユーザー数（V-604） | 集計期間内に当該メニューを利用したユーザーの実数 |
| 最終利用日（V-605） | **集計期間の範囲外も含む**全ログのうちの最終日。1 件もなければ `—` |

行の単位は **メニューキー（V-601）** とする。

- 画面を持たないメニュー項目（子メニューを束ねるだけの親メニュー）は行として表示しない。利用され得ないため、未利用のメニューとして並べると改廃の判断を誤らせる
- 同一のパスであっても指定によって別の画面となるメニュー項目は、それぞれ別のメニューキーとして別の行に集計する

各列について昇順・降順に並び替えできる（REQ-NF-007）。

### REQ-F-009: ユーザー別 利用状況の表示

ユーザーごとに次を一覧表示する。**集計期間内の利用が 0 のユーザーも行として表示する**。

| 列 | 内容 |
|---|---|
| 社員番号（core V-001） | |
| 表示名 | |
| 権限ロール（core R-003） | 管理者／一般ユーザー |
| 付与メニューグループ | core V-002。複数可 |
| 利用回数（V-603） | 集計期間内の総件数 |
| 出力回数（V-608） | 集計期間内の `EXPORT` の件数 |
| 最多利用メニュー（V-610） | 集計期間内で利用回数が最も多いメニュー名。同数の場合の順序は design.md で定義する |
| 最終利用日（V-605） | 全ログのうちの最終日。1 件もなければ `—` |
| 最終ログイン日時（V-606） | 一度もログインしていない場合は `—` |

各列について昇順・降順に並び替えできる（REQ-NF-007）。

対象は利用申請が許可（core S-001 の `APPROVED`）済みのユーザーとする。承認待ち・拒否のユーザーは業務メニューを利用できないため、集計対象から除外する。

### REQ-F-010: メニューグループ付与済み × 未利用の一覧

ユーザーに付与されているメニューグループ（core V-002）のうち、**集計期間内にそのメニューグループ配下のメニューを 1 度も利用していない**組み合わせを一覧表示する。

| 列 | 内容 |
|---|---|
| 社員番号（core V-001）・表示名 | |
| 付与されているメニューグループ | |
| 当該メニューグループの最終利用日（V-605） | 1 件もなければ `—` |
| 付与日（V-613） | メニューグループが付与された日 |

権限棚卸（A-603）の判断材料として提示するものであり、**本画面から付与の解除は行わない**（§7 スコープ外）。

### REQ-F-011: 出力操作の記録の表示

集計期間内の利用種別 `EXPORT` のメニュー利用ログを、利用日時の降順で一覧表示する。

| 列 | 内容 |
|---|---|
| 利用日時 | `yyyy/mm/dd hh:mm` |
| 社員番号（core V-001）・表示名 | |
| メニューグループ・メニュー名 | |

REQ-F-003 のとおり、何を出力したか（絞り込み条件・件数・データの中身）は表示しない。記録していないためである。

### REQ-F-012: 日別推移の表示

集計期間内の日別推移（V-611）、すなわち日ごとの利用回数（V-603）を、日付の昇順で表示する。利用のない日は 0 として表示し、日付を飛ばさない。

### REQ-F-013: メニューグループによる絞り込み

メニューグループ（core V-002）を指定して、REQ-F-008〜REQ-F-012 の表示対象を絞り込める。未指定の場合は全メニューグループを対象とする。

### REQ-F-014: CSV 出力

REQ-F-008〜REQ-F-011 の各一覧について、画面に表示されている内容（集計期間・絞り込みを反映した状態）を CSV として出力できる。

1 回の出力の上限は **10 万行**とする。これを超える場合は出力を行わず、集計期間または絞り込みを狭めるよう促す。

本画面からの CSV 出力もまた出力操作（A-602）であり、メニューキー `usage-status` のメニュー利用ログとして記録する（REQ-F-002）。

### REQ-F-015: 利用状況画面自身の利用も記録すること

利用状況画面の表示は、他のメニューと同様にメニュー利用ログとして記録する。管理者による本画面の利用を特別扱いしない。

### REQ-F-016: 集計対象が 0 件のときの表示

集計期間内にメニュー利用ログが 1 件も存在しない場合、エラーとせず、各一覧を「該当なし」として表示する。
全体集計（V-609、REQ-F-007）の利用ユーザー数・延べ利用回数は 0 と表示する。

これは機能リリース直後（ログが蓄積されていない状態）に必ず発生する。

### REQ-F-017: 削除・改称されたメニューの扱い

メニュー利用ログが記録された後にメニュー項目が削除・改称された場合でも、記録済みのログは削除・変更しない（E-601 は追記のみ）。

メニュー別 利用状況（REQ-F-008）では、現行のメニュー定義に存在しないメニューキーのログを **「（廃止）」の注記付きで表示する**。過去に使われていた事実を失わないためである。

### REQ-F-018: 無効化されたユーザーの扱い

ポータルのユーザーが無効化（退職・異動等）された後も、そのユーザーのメニュー利用ログは削除しない（E-601 は追記のみ）。

- ユーザー別 利用状況（REQ-F-009）および メニューグループ付与済み × 未利用（REQ-F-010）では、既定で有効なユーザーのみを表示する。定着支援・権限棚卸の対象にならないためである
- 一方、全体集計（REQ-F-007）の延べ利用回数、メニュー別 利用状況（REQ-F-008）、出力操作の記録（REQ-F-011）、日別推移（REQ-F-012）には、無効化されたユーザーのメニュー利用ログも含める。過去にそのメニューが使われた事実を欠落させないためである

ポータルのユーザーが**物理的に削除された場合も、そのユーザーのメニュー利用ログは削除しない**（REQ-NF-004）。削除後は、ユーザーを特定できない記録として全体集計・メニュー別 利用状況・日別推移に残す。
退職者本人から個人データの削除を求められた場合は、当該ユーザーのメニュー利用ログを個別に削除する運用で対応する（REQ-NF-004 の「削除できる構造」がこれを担保する）。

## 5. 非機能要件

### REQ-NF-001: 認可

利用状況画面および CSV 出力は、管理者（core R-001）以外からのアクセスを拒否する。
一般ユーザー（core R-002）が URL を直接指定した場合も拒否する。既存の管理メニュー（お知らせ管理・利用申請・ユーザー管理・データベース）と同一の判定に従う。

### REQ-NF-002: 性能

メニュー利用ログは無期限に蓄積される（REQ-NF-004）ため、件数の増加に対して表示性能が劣化しない構成とする。

| # | 要件 |
|---|---|
| 1 | 集計期間（V-602）の指定を必須とし、全期間を走査する表示経路を画面に設けない |
| 2 | 集計期間 3 か月・ログ 50 万件の条件で、画面の表示が 3 秒以内に完了すること |
| 3 | 利用日時・ユーザー・メニューキーによる絞り込みが索引で解決されること（索引の設計は design.md で定義する） |

### REQ-NF-003: 利用記録の非侵襲性

利用記録（A-601）は、記録対象となる画面表示・出力操作の応答時間に **50ms を超える遅延を与えない**。
記録に失敗した場合も業務操作は完了する（REQ-F-004）。

同時実行についても次を満たす。

| # | 要件 |
|---|---|
| 1 | 複数のユーザーが同時に画面を表示しても、利用記録どうしが待ち合わせない（排他制御で競合する構造にしない） |
| 2 | 想定する同時利用は **50 ユーザー**（始業時の一斉アクセスを想定）とし、この条件で上記の 50ms を満たす |

### REQ-NF-004: データ保持

メニュー利用ログは **無期限に保持する**。自動削除・アーカイブは行わない。

- 削除処理を設けないため、運用開始後にログが単調増加することを前提として REQ-NF-002 を満たすこと
- 将来パージが必要になった場合に、メニュー利用ログを利用日時・ユーザーで削除できる構造としておくこと（削除機能そのものは本要件のスコープ外）。個人データの削除要求（REQ-F-018）にもこの構造で対応する
- ポータルのユーザーを削除しても、そのユーザーのメニュー利用ログが連鎖して削除されない構造とすること（REQ-F-018）
- 運用開始前にログの増加量（1 日あたりの記録件数・年間の増加容量）を見積もり、PostgreSQL の容量を監視の対象に加えること。見積りの前提は §6.1 に置く

### REQ-NF-005: 利用目的の限定とプライバシー

本機能は **メニューの改廃・定着支援・権限棚卸・データ持ち出しの確認**のために用いる。個人の勤務時間の把握や勤務評価には用いない。この方針を画面上に明記する。

設計上の担保として次を課す。

| # | 要件 |
|---|---|
| 1 | 記録する項目を REQ-F-001 の 4 項目に限る。IP アドレス・ユーザーエージェント・操作対象データを記録しない |
| 2 | 画面に表示するユーザー単位の値は、**利用回数・最終利用日・最終ログイン日時**にとどめる。ユーザー 1 人の時刻単位の行動履歴を一覧できる画面を設けない（出力操作の記録（REQ-F-011）は、データ持ち出しの証跡として例外的に日時を表示する） |
| 3 | 閲覧できるのは管理者のみとする（REQ-NF-001） |

### REQ-NF-006: アーキテクチャ制約

- Clean Architecture の依存方向（interfaces → use_cases → domain ← infrastructure）に従う
- `domain/` と `use_cases/` に `import django` を書かない
- 組み立ては `application/portal/interfaces/wiring.py` のみで行う。`composition.py` および `services/` 層は新設しない
- **利用記録（A-601）は `application/portal/` の中で完結させる。** 他の境界コンテキスト（`receipt_comparison` / `inventory_order_alert` / `gonenkukumi` / `shipment_trend` / `asset_inventory`）のコードを変更せず、それらから portal のモデル・ユースケースを import させない（strategic_design.md §3.1 の共有カーネル以外の相互参照の禁止）
- 検証は `config/tests/test_clean_architecture.py` に従う

### REQ-NF-007: 表示の一貫性

一覧の絞り込み・並び替え・列表示は [ポータル一覧表_共通仕様.md](../../ポータル一覧表_共通仕様.md) に従い、既存の管理メニューと操作感を揃える。UI フレームワークは導入しない（Django テンプレート＋素の JS/CSS）。

### REQ-NF-008: テスト

Phase 5 は TDD で実装する。少なくとも次を自動テストで固定する。

- 記録対象・記録対象外の判別（REQ-F-001〜REQ-F-003）
- 利用記録の失敗時に業務操作が完了すること（REQ-F-004）
- 一般ユーザーからのアクセスが拒否されること（REQ-NF-001）
- 集計期間の境界（開始日・終了日を含むこと、開始日 > 終了日のエラー）（REQ-F-006）
- ログ 0 件時の表示（REQ-F-016）、現行定義に存在しないメニューキーの表示（REQ-F-017）、無効化・削除されたユーザーの扱い（REQ-F-018）
- **記録対象となる出力エンドポイントの一覧**（`/api/` 配下を含む）。エンドポイントが追加・変更されたときにテストが失敗し、記録漏れに気づけること（REQ-F-002）
- 集計期間の幅が最大値を超える指定がエラーになること（REQ-F-006）

## 6. 前提条件・制約事項

### 6.1 前提条件

| # | 前提 |
|---|---|
| 1 | メニュー利用ログは本機能のリリース以降のものしか存在しない。**リリース前の利用状況は遡って把握できない**（REQ-F-016 の状態から始まる） |
| 2 | 最終ログイン日時（V-606）のみ、Django ユーザーの `last_login` として既存データが存在する |
| 3 | ユーザーの同一性は社員番号（core V-001）による。認証基盤が desknet's NEO から Microsoft Entra ID へ切り替わっても、メニュー利用ログの連続性は保たれる |
| 4 | 容量見積りの前提として、ポータルの利用ユーザーは 100 名程度、1 人 1 日あたりの画面表示は 20 回程度とする。メニュー利用ログは 1 日あたりおよそ 2,000 件・年間およそ 50 万件の増加を見込む（REQ-NF-002 の 50 万件は約 1 年分に相当する）。運用開始後に実測して見直す |

### 6.2 既存システムへの影響

| 対象 | 影響 |
|---|---|
| `application/portal/` のメニュー定義 | 管理メニューグループにメニュー項目 `usage-status` を 1 件追加する |
| `application/portal/` のモデル | メニュー利用ログのテーブルを 1 つ追加する（マイグレーションを追加） |
| ポータル全体のリクエスト処理 | 全画面表示に利用記録の処理が挟まる。応答時間への影響は REQ-NF-003 で上限を定める |
| `application/portal/` のユーザー削除 | ユーザーを削除してもメニュー利用ログが連鎖削除されない構造とする（REQ-F-018・REQ-NF-004）。現在のポータルにはユーザーを物理削除する処理が存在する |
| 他の 5 つの業務コンテキスト | **変更しない**（REQ-NF-006） |
| 既存の CSV／Excel 出力機能 | 機能自体は変更しない。出力の実施が記録対象になる |
| PostgreSQL の容量 | ログが無期限に増加する（REQ-NF-004） |

### 6.3 制約事項

| # | 制約 |
|---|---|
| 1 | 基幹 Oracle（MARI）・SLIMS・desknet's NEO のいずれにも問い合わせない。データの正はポータル自身にある |
| 2 | グラフ描画のための外部ライブラリを導入しない。日別推移（REQ-F-012）は Django テンプレートと CSS で表現する |
| 3 | メニューグループ（core V-002）を絞り込み・集計の軸とする。「部署」を軸とした集計は行わない（core V-002 が「部署」「部署グループ」を使用しない表現と定めているため） |
| 4 | 本要件は 1 つの機能として受け入れるが、実装は 利用記録（REQ-F-001〜REQ-F-004）を先行させ、利用状況画面（REQ-F-005〜REQ-F-016）を後続とする 2 段階で進める。ログは遡って取得できず、記録を先にリリースするほど集計できる期間が長くなるためである。段階の区切りは tasks.md で定義する |
