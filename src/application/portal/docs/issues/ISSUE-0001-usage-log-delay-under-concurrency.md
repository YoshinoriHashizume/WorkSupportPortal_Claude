# 同時 50 ユーザー相当の負荷下で、メニュー利用ログの記録による遅延が 50ms を超える

> **結論（2026/08/28 09:11）**: 本番相当の構成（`gunicorn --workers 3`）で再計測したところ再現せず、
> 差は中央値 **-2.5ms** で基準（50ms 以内）を満たした。起票時の計測が単一プロセス × 50 スレッドで
> 行われていたことによる**計測方法の問題**と判断し、製品コードは変更せず **Rejected** でクローズする。

## 事象（現象）

同時 50 ユーザー相当の負荷をかけた計測で、メニュー利用ログを記録するミドルウェア
（`UsageLoggingMiddleware`）の有無による応答時間の差が中央値で **+56ms / +108ms**（2 回計測）となり、
REQ-NF-003 #2 の「同時 50 ユーザーでも記録による遅延は 50ms 以内」を満たさなかった。

単独利用（1 ユーザー・逐次 30 リクエスト）では差は **-1.9ms**（測定誤差の範囲）で、REQ-NF-003（#1）は満たしている。

## 再現手順

1. テスト DB（PostgreSQL 16）に、ポータル管理者ロールかつ利用申請が承認済みのユーザーを 50 名作成する。
2. 記録対象のメニュー画面（`/app/management/notices`）に対し、50 スレッド × 10 リクエストを同時に実行する。
   各スレッドは自分のユーザーでログイン済みのクライアントを 1 つ持ち、計測前にウォームアップを 1 回行う。
3. 上記を `MIDDLEWARE` から `application.portal.interfaces.usage_logging.UsageLoggingMiddleware` を
   外した設定（記録なし）と、既定の設定（記録あり）の 2 通りで実施し、応答時間の中央値を比較する。
4. 記録ありの実行で `portal_menu_usage_log` に 550 件（ウォームアップ 50 ＋ 計測 500）が追加されることを確認する。

計測は 2026/08/27 に一時的なベンチ用テストで実施し、計測後にファイルは削除した（実測値は
spec/01_usage-status/tasks.md の「タスク34 実行レポート」に記録済み）。

## 期待動作 / 実際の動作

- **期待**: 同時 50 ユーザーでも、記録による応答時間の増加が 50ms 以内であること（REQ-NF-003 #2）。
- **実際**: 中央値で +56ms（1 回目）／+108ms（2 回目）、95 パーセンタイルで +185ms／+71ms。
  なお記録なしの時点で中央値が約 1,500ms あり、応答時間そのものが同時実行の競合で大きく伸びている。

## 影響範囲・環境

- 影響範囲: ポータルの全画面（記録対象のメニュー画面すべて）。実害は応答時間の増加のみで、
  記録の失敗は握りつぶして業務操作を止めない設計（REQ-F-004）のため、機能面の影響はない。
- 環境: DevContainer（Linux / 20 CPU / 15GB）、PostgreSQL 16、Django 5.2、
  単一プロセスの Django テストクライアントを 50 スレッドで同時実行。
  本番の構成（複数ワーカープロセス）とは条件が異なる。

## 原因分析（root cause）

**計測方法の問題**（2026/08/28 09:11 の本番相当構成での再計測により確定）。

起票時の計測は、**単一プロセスの Django テストクライアントを 50 スレッド**で動かしていた。
この構成では GIL によりスレッドが 1 コアを奪い合うため、記録の INSERT が行われる区間だけ
スレッドが切り替わって待たされ、記録ありの側に見かけ上の遅延が上乗せされていた。
本番は `gunicorn --workers 3`（`entrypoint.sh`）の**複数プロセス**構成であり、この競合は起きない。

本番相当の構成で測り直したところ、記録の有無による差は**中央値で -2.5ms（3 ラウンド平均）**、
95 パーセンタイルで -2.2ms となり、REQ-NF-003 #2 の基準（50ms 以内）を満たした。
索引 4 本の更新も、この条件では応答時間に有意な影響を与えていない。

### 再計測の条件（2026/08/28 09:00〜09:10）

| 項目 | 内容 |
|------|------|
| サーバー | `gunicorn config.wsgi:application --workers 3 --timeout 120`（本番の `entrypoint.sh` と同じ） |
| 設定 | `config.settings.production` を土台にした一時ベンチ設定（`DEBUG=False`）。記録なしは `UsageLoggingMiddleware` のみを `MIDDLEWARE` から除外 |
| DB | 専用の `bench_usage`（PostgreSQL 16）。**メニュー利用ログ 50 万件を投入済み**（索引コストを本番相当にするため） |
| 負荷 | 承認済みポータル管理者 50 名・**50 クライアントプロセス**（スレッドではない）× 20 リクエスト = 1,000 リクエスト／回 |
| 対象 | `/app/management/notices`（記録対象のメニュー画面） |
| 手順 | 記録なし → 記録あり を 1 ラウンドとし、順序バイアスを避けるため 3 ラウンド交互に実施 |

### 再計測の結果（同時 50 ユーザー相当）

| ラウンド | 中央値（記録なし） | 中央値（記録あり） | 差 | p95（記録なし） | p95（記録あり） | 差 |
|---------|------------------|------------------|-----|----------------|----------------|-----|
| 1 | 705.1ms | 728.2ms | +23.1ms | 1,179.4ms | 1,194.4ms | +15.0ms |
| 2 | 794.2ms | 792.8ms | -1.4ms | 1,278.1ms | 1,136.9ms | -141.2ms |
| 3 | 823.5ms | 794.4ms | -29.1ms | 1,169.0ms | 1,288.5ms | +119.5ms |
| **平均** | **774.3ms** | **771.8ms** | **-2.5ms** | **1,208.8ms** | **1,206.6ms** | **-2.2ms** |

- 全 6 回とも応答はすべて 200。記録ありの 3 回はいずれも**メニュー利用ログがちょうど 1,000 件**増え、
  記録なしの 3 回は**増分 0 件**だった（記録が確かに効いている／切れていることを毎回確認）。
- 差の符号がラウンドごとに入れ替わっており、**記録の有無は測定誤差に埋もれている**。
- 低並行（3 クライアント × 40 リクエスト）でも、中央値 41.3ms → 42.5ms（**+1.2ms**）で基準内。
  なお低並行の 2・3 ラウンド目は、**別作業のリファクタリングが作業ツリー上で進行中**（`inventory_order_alert` の
  モジュール削除途中）だったため URLconf の import に失敗し、計測として無効。同時 50 ユーザーの
  3 ラウンドは、この事象の発生前に完了しており影響を受けていない。
