作成日: 2026-06-04

本書は、旧 VB.NET WinForms **受領書比較(MARI)** を業務支援ポータル上で再実装した **検収書比較** の要件を定義する。  
受領書（完成品 CSV / 支給品 TXT）と MARI（Oracle）の出荷・売上・受入データを突合し、結果を `〇` / `△` / `×` で管理する。

用語は上記ユビキタス言語集に従う。特に **突合の入力となるファイルは「受領書」**、**機能・画面は「検収書比較」** と呼び分ける（UL-RECEIPT-COMPARISON-2026-001 E-101）。
機能要件の一覧は §2.4、スコープ外は §2.5 に定める。

## 2. 背景・業務目的

### 2.1 背景

得意先および子取引先から受領する受領書と、MARI（Oracle）の出荷/売上/受入実績を突合し、受領内容が基幹システムと一致しているかを生産管理が確認する。旧 WinForms アプリ `ProductionManegementSystem` の受領書比較を Web 化した。

### 2.2 本機能の目的

| 目的 | 内容 |
|------|------|
| 突合の効率化 | 受領ファイル取込と MARI 自動照合で `〇`/`△`/`×` を一覧化 |
| 差異の継続管理 | `〇` 以外の未完了行を次回比較にも引き継ぐ |
| マスタ管理 | 得意先ごとの受入/納品場所・支給品子取引先・品番設定 |
| 帳票出力 | 表示中結果の CSV ダウンロード（印刷は初期対象外） |

#### 2.2.1 受入基準（指摘 L3-9）

本機能が目的を達成したと判断する基準。5年9組 §10.1 の受入チェックリストに倣う。

| # | 受入基準 | 確認方法 |
|---|---------|---------|
| C-01 | 完成品 CSV・支給品 TXT の受領書を取り込み、MARI と突合した結果が `〇`/`△`/`×` で一覧表示される | 旧システムと同一の受領書ファイルで比較し、突合フラグが一致すること |
| C-02 | 突合結果を登録・更新でき、再表示しても保持される | 登録後に同一得意先・同一期間を再表示し、突合フラグと備考が保持されること |
| C-03 | `〇` 以外の未完了行が次回比較にも引き継がれる | 開始日より前の未完了行が一覧に含まれること（§7.3） |
| C-04 | 表示中結果と同一内容の CSV が出力できる | 一覧の行数と CSV の行数が一致すること |
| C-05 | 得意先ごとの受入/納品場所の対象・除外設定が突合に反映される | 除外設定を変更し、突合対象行が設定どおりに増減すること |
| C-06 | 比較日の入力誤り（開始日 > 終了日）が画面・CSV の双方で検知される | 逆転した日付でエラーとなり、比較・出力のいずれも行われないこと（§4.1.1・§10） |

> **未確定**: 「突合作業がどれだけ効率化したか」を測る定量指標（旧 WinForms アプリとの作業時間比較等）は、旧システムの実測値が無いため設定していない。運用開始後に実績を取得してから定める。

### 2.3 旧実装からの引き継ぎ

| 引き継ぐ | 引き継がない |
|----------|----------------|
| MARI 参照のみ、3項目一致で `〇` | WinForms 固有 UI、旧アプリログイン |
| 比較結果保存・CSV 出力 | MySQL（→ PostgreSQL） |
| 納品/受入場所の対象・除外 | TopLink 版、直接印刷 |
| 完成品 CSV / 支給品 TXT の別取込 | |

**旧システムからのデータ移行**（指摘 L3-16・**2026/08/25 確定**）: 上表の「引き継がない: MySQL（→ PostgreSQL）」は **DB 製品を引き継がない** ことを指す。データ移行の方針は **「移行しない（新規稼働）」** で確定した。

| 対象 | 方針（2026/08/25 決定） |
|------|------|
| 旧システムの既存比較結果 | **移行しない**。ポータルは比較結果 0 件の状態で稼働を開始する。旧システムの過去実績は旧システム側で参照する |
| 旧システムの得意先設定（納品/受入場所の対象・除外） | **移行しない**。切替時に**設定画面から再登録する**（§4.2）。件数が限られるため手作業で足りる |
| 切替手順 | 上記を前提に、切替日以降の受領書からポータルで運用する。手順は `Document/` 配下の全体手順書へ追記する |

> **この決定の根拠**: 旧システムは MySQL・WinForms 固有のデータ構造を持ち、突合フラグ・備考の対応付けに検証コストがかかる。
> 比較は**受領書の到着単位で完結する**業務であり、過去実績を引き継がなくても切替日以降の運用は成立する。
> なお §7.3 の未完了データ引き継ぎは **ポータル内で保存した行のみ**を対象とする（旧システムの未完了行は対象外）。

## 4. 画面（ルーティング）

| 画面 ID | 画面 | ルート | 概要 |
|---------|------|--------|------|
| SCR-01 | 検収書比較 | `/app/production/receipt-comparison?type=finished-product\|supplied-parts` | 比較・表示・登録・更新・CSV |
| SCR-02 | 受入/納品場所設定 | `/app/production/receipt-comparison/settings?type=...` | 得意先マスタ・場所/品番設定（**管理者のみ**） |
| — | CSV 出力 | `GET /app/production/receipt-comparison/export?type=...` | 表示中結果のダウンロード |

比較画面は **SSR フォーム POST**（`display` / `compare` / `register` / `update` アクション）で処理する。独立 REST API は設けない。

### 4.1 検収書比較画面（SCR-01）

#### 4.1.1 操作フロー

1. 得意先・比較日（開始〜終了）を指定し **表示** → PostgreSQL の保存済み結果を読込（未登録プレビューはクリア）。
2. **表示後**、比較結果エリア右上の **ファイル選択** で受領書を選ぶと **即時比較**（MARI 取得 + 突合）。結果はセッションに **未登録** 保持。
3. 問題なければ **登録** で PostgreSQL へ保存。
4. 保存済み表示中は **更新** で `receipt_flag`・備考を更新。
5. **CSV** で表示中データ（未登録含む）をダウンロード。

表示前は比較結果カードに「比較結果はありません。」。得意先未選択時はカード内に案内メッセージ（ファイル選択は非表示）。

**比較日の妥当性**: **開始日 > 終了日** を指定した場合は、比較を行わずエラーメッセージ「開始日は終了日以前を指定してください。」を表示する（§10）。これは **比較画面・CSV 出力の双方に共通** の規則であり、日付を自動的に入れ替えて処理を続行してはならない。入力誤りを黙って書き換えると、利用者が意図しない期間の帳票を気づかないまま出力するおそれがあるため。

#### 4.1.2 レイアウト

- 検索条件（得意先・開始日・終了日・表示ボタン）は **`portal-search-disclosure`** の白カード内に配置する。各ラベル（得意先・開始日・終了日）は入力の**左**に横並び表示する。カード下辺に枠と一体のコンパクトなトグル帯（**折りたたむ**／**展開**、12px）を全幅配置し、開閉する（`<summary>` は DOM 上先頭だが CSS `order` で**下辺**に表示）。**ページを開くたびに展開**（`open` 属性 + 読込時 JS で `section.open = true`）。開閉状態は **保存しない**（次回表示時も常に展開）。比較結果カード内の操作・表は折りたたみ対象外。
- 検索条件・操作は上部固定。**比較結果表のみ** `.db-table-wrap` 内で縦スクロール。
- `body.portal-app-page` でビューポート高に収め、ページ全体は縦スクロールしない。
- 表ヘッダは `position: sticky`。
- 得意先セレクトと開始日・終了日入力は **同じ高さ**（40px）。

#### 4.1.3 比較結果一覧列

| # | 表示名 | 編集 |
|---|--------|------|
| 1 | 受領データID | 不可 |
| 2 | 結果（`〇`/`△`/`×`） | 可 |
| 3 | 品目番号(MARI) | 不可 |
| 4 | 売上計上日(MARI) | 不可（支給品は受入日） |
| 5 | 売上実績数量(MARI) | 不可（支給品は受入数） |
| 6 | 得意先指定納品場所コード | 不可 |
| 7 | 品番(受領書) | 不可 |
| 8 | 納入月日(受領書) | 不可 |
| 9 | 納入数(受領書) | 不可 |
| 10 | キャンセル数(受領書) | 不可（**完成品のみ**表示） |
| 11 | 子取引先名 | 不可（**支給品のみ**表示） |
| 12 | 備考 | 可 |

> **品番の呼称について**: 列 `品目番号(MARI)` / `品番(受領書)` の実体は **比較区分によって異なる**（完成品＝得意先品番 `T_SHIP.CUST_ITEM_CD`、支給品＝内作品番 `T_RLSD_PUCH_ODR.ITEM_CD` の末尾5桁除去）。
> 単一の正式名称が存在しないため、本コンテキストでは **総称としての「品番」** を用い、列名は区分共通で固定する（UL-RECEIPT-COMPARISON-2026-001 V-106、core V-005 適用範囲）。
> 一律「得意先品番」へ改称すると支給品側が事実と不一致になるため、改称してはならない。

#### 4.1.4 ソート・メッセージ

- 列ヘッダクリックで昇順/降順（`sort`, `dir` クエリ）。
- **表示・比較直後**の初回ソート: **結果** 列昇順（`×` → `〇` → `△`）。
- 比較・登録・更新 **成功時は画面上部メッセージなし**（未登録は見出し「（未登録）」）。エラー・警告のみ表示。

### 4.2 受入/納品場所設定画面（SCR-02）

- 左: **得意先追加**、右: **得意先一覧**（2 列 Grid。左最大 380px）。
- 行クリックで `<dialog>` ポップアップ: 除外設定、完成品は直送先得意先コード、支給品は子取引先表、受入/納品場所（品番）表。
- **登録済み得意先コードは変更不可**。削除時は比較結果・取込履歴も連鎖削除。
- 完成品一覧列: 得意先コード・得意先名・直送先得意先コード・除外・受入/納品場所。

## 7. 比較ロジック

### 7.1 一致判定（3項目）

| 項目 | 正規化 |
|------|--------|
| 品番 | MARI の `-` 除去。支給品は末尾5桁除去ルールを TXT/MARI で統一 |
| 日付 | MARI 日付 → `MMdd` と受領 `納入月日` を比較 |
| 数量 | 数値同値（`0` は空表示。NULL は `0` 扱い） |

3項目一致 → **`〇`**。不一致・片側のみ → 初期 **`×`**。ユーザーが **`△`** に手動変更可。

### 7.2 表示処理（取込後）

1. MARI 行を一覧に追加。
2. 保存済み結果を読込み、品番・日付・数量一致行へ受領側情報を反映。
3. 受領書各行を MARI と比較。一致 MARI 行は `〇` + 受領側列をセット。
4. 未一致 MARI 行は `×`。未一致受領行は MARI 列空の `×` 行として追加。

### 7.3 未完了データの引き継ぎ

開始日より前の **`receipt_flag != 1`（`〇` 以外）** の保存済み行も次回一覧に含める（旧 `SelectReceiptData` 準拠）。

**遡及期間の上限**（指摘 L3-12・**2026/08/25 確定**）: 遡及の打ち切り条件は **設けない**。`〇` 以外の保存済み行は、開始日よりどれだけ前のものであっても **全件を次回一覧に引き継ぐ**。

| 論点 | 決定 |
|------|------|
| 遡及期間の上限（N か月） | **上限を設けない**（2026/08/25 決定）。未完了行は完了するまで一覧に残り続けることを正とする |
| 未完了行の一括クローズ手段 | **設けない**。クローズは §4.1.1 の突合フラグ更新（1 行ずつの明示的な操作）に限る。誤クローズの影響が大きく、一括操作は用意しない |
| 滞留が問題化した場合 | 上限の導入は仕様変更として扱い、Issue を起票して判断する（`manage-issue`）。本書の記述はそれまで有効である |

> **この決定の根拠**: `〇` 以外は「まだ突合が終わっていない」という業務上の未処理を意味する。
> 期間で自動的に一覧から外すと未処理のまま見えなくなるため、**滞留の可視化を優先する**。

## 8. PostgreSQL 永続化

### 8.1 完成品モデル

`FinishedProductReceiptSupplier`, `FinishedProductReceivingSetting`, `FinishedProductFileImport`, `FinishedProductComparisonResult`

- 得意先コードの桁数を検証してはならない（UL-CORE-2026-001 V-004）。**4 桁**の桁数制約は支給品の子取引先コード（`vendor_code`）にのみ適用する

### 8.2 支給品モデル

- 子取引先: `vendor_code` / `vendor_name`（Oracle 4桁マスタから選択・名称は登録時保存）

### 8.3 比較結果 `receipt_flag`

| 値 | 表示 |
|----|------|
| 0 | `×` |
| 1 | `〇` |
| 2 | `△` |

### 8.4 同時実行時の振る舞い（指摘 L3-4）

複数ユーザーが同一得意先・同一期間を同時に扱った場合の方針を定める。

| 操作 | 方針 |
|------|------|
| 比較（ファイル選択による即時比較） | **ユーザーごとに独立**。比較結果は登録前はセッションに保持され、他ユーザーへ影響しない（§4.1.1 手順2） |
| 登録 | **後勝ち**。同一得意先・同一期間の保存済み行を後から登録した内容で上書きする。排他制御は行わない |
| 更新（`receipt_flag`・備考） | **後勝ち**。行単位の更新であり、同時更新は最後の書き込みが残る |
| 排他ロック | **設けない**。在庫発注アラートの SLIMS 取込のような全件差し替えを行わず、行単位の更新に留まるため、部分破壊が構造的に起きない |

> **補足**: 後勝ちで運用上の問題が生じた場合（例: 同一期間を 2 名が並行して確認している）、更新者・更新日時の表示や排他制御を Issue として起票する。

## 10. エラー・警告（代表）

| 状況 | メッセージ例 |
|------|----------------|
| 区分不正 | 正しい比較区分が読み込まれませんでした |
| ファイル未指定 | 受領書データを選択してください |

| 得意先未選択 | 得意先を選択してください |
| **比較日の逆転**（開始日 > 終了日） | 開始日は終了日以前を指定してください。（**比較画面・CSV 出力の双方**で比較を行わない。§4.1.1） |
| MARI 失敗 | MARIデータの取得に失敗しました |

### 10.1 CSV 出力時のエラー応答（指摘 L3T-4）

比較画面は上記メッセージを画面上に表示するが、**CSV 出力（§8 の `export.csv`）は画面を持たない**ため、応答そのものでエラーを伝える。

| 条件 | HTTP | Content-Type | 本文 |
|---|---|---|---|
| **比較日の逆転**（開始日 > 終了日） | **400 Bad Request** | `text/plain; charset=utf-8` | `開始日は終了日以前を指定してください。` |
| 上記以外（正常） | 200 | `text/csv; charset=cp932`（§3 のとおり Shift_JIS／CP932） | CSV 本文 |

- 本文は **プレーンテキスト**（CSV ではない）とし、ダウンロードされたファイルにエラー文が混入しないようにする。
- 400 のときは MARI へ問い合わせない（比較を行わないため）。
- メッセージ文言は比較画面と同一の定数（`domain/value_objects/comparison_urls.py` の `INVALID_DATE_RANGE_MESSAGE`）を用い、画面と CSV で表現を一致させる。
