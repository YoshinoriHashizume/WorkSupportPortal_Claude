## 2. 実装方針

### 2.1 初回実装の範囲

初回は **Django 基盤 + 通常ログイン + 5年9組単体** を作成する。

| 区分 | 初回で作るもの |
|------|----------------|
| Django 基盤 | `config`、共通テンプレート、静的ファイル、環境変数読込、DB 接続 |
| 認証 | Django 認証、desknet's NEO 認証口、将来 Authlib 用の Entra 認証口 |
| ポータル | ログイン画面、左メニュー、5年9組へのリンク |
| 5年9組 | 検索画面、結果画面、履歴、API、Oracle 参照層、Excel 出力 |
| テスト | ドメイン単体、代表 API、Excel 出力、ログイン画面スモーク |

### 2.2 初回で後回しにするもの

| 区分 | 後回しにする理由 |
|------|------------------|
| 他部門アプリ | 仕様未定義のため、プレースホルダまたはメニュー非表示でよい |
| 詳細な認可管理画面 | 初回は DB 初期データで権限を固定し、管理 UI は後続で作る |
| Oracle 実接続の全ケース確認 | 接続情報・権限・データ状態に依存するため、モック実装後に接続する |
| 本番 Docker 最適化 | 開発実装が安定してから本番イメージを固める |

## 3. 作業前提

### 3.1 開発環境

| 項目 | 内容 |
|------|------|
| OS | Windows 10 / 11 |
| Python | 3.12 系 |
| Web フレームワーク | Django |
| 認証ライブラリ | Authlib |
| DB | PostgreSQL |
| Oracle 接続 | python-oracledb |
| Excel 出力 | openpyxl 等 |
| テスト | pytest / pytest-django / pytest-playwright |

### 3.2 初回の推奨起動方法

初回は **パターン B: Django と PostgreSQL を Docker 上で実行** とする。

理由:

- ホスト OS に Python を直接インストールしなくても起動できる。
- 既存の Next.js 用 Docker 環境と分離できる。
- Oracle 実接続前に画面と API の骨格を確認しやすい。

Docker 上の名前は、既存 Next.js 用コンテナと衝突しないように Django 専用名にする。

| 対象 | 名前 / ポート |
|------|---------------|
| Django サービス | `django_app` |
| Django コンテナ | `worksupportportal-django-app` |
| PostgreSQL サービス | `django_postgres` |
| PostgreSQL コンテナ | `worksupportportal-django-postgres` |
| Django 公開ポート | `http://localhost:3100` |
| PostgreSQL 公開ポート | `localhost:55432` |

## 4. 実行順序

### Phase 0: 既存資産の扱いを決める

1. 現在の旧実装ファイルを残すか、Django 実装へ置き換えるかを決める。
2. 初回実装では、旧実装を参照資料として残し、Django 実装を新規構成で作る。
3. 不要化が確認できた旧実装は、別タスクで削除する。

推奨:

- 旧コードはすぐ削除しない。
- Django 実装が `pytest` と画面確認を通過してから整理する。

### Phase 1: Django プロジェクト作成

作成する主な構成:

```text
config/
  settings.py
  urls.py
  wsgi.py
  asgi.py
apps/
  portal/
  identity/
  gonenkukumi/
    domain/
    application/
    infrastructure/
      oracle/
    templates/
    static/
tests/
```

実行例:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install django authlib requests psycopg[binary] python-oracledb openpyxl gunicorn pytest pytest-django pytest-playwright
django-admin startproject config .
python manage.py startapp portal apps/portal
python manage.py startapp identity apps/identity
python manage.py startapp gonenkukumi apps/gonenkukumi
pip freeze > requirements.txt
```

注意:

- `startapp` の作成先ディレクトリは、実際の Django 設定に合わせて調整する。
- `apps/` 配下を使う場合は、各 app の `AppConfig.name` と `INSTALLED_APPS` を一致させる。

### Phase 2: 環境変数と設定

`.env.local` または `.env` に以下を用意する。

```env
DJANGO_DEBUG="true"
DJANGO_SECRET_KEY="local-secret"
DJANGO_ALLOWED_HOSTS="localhost,127.0.0.1"
DJANGO_CSRF_TRUSTED_ORIGINS="http://localhost:3000"
DATABASE_URL="postgresql://worksupportportal:worksupportportal_local_dev@localhost:5432/worksupportportal"
AUTH_URL="http://localhost:3000"
AUTH_PROVIDER="desknet"
DESKNETS_LOGIN_URL="https://maruei01.dn-cloud.com/cgi-bin/dneo/dneo.cgi"
```

desknet's NEO 認証を使う場合は以下を設定する。

```env
AUTH_PROVIDER="desknet"
DESKNETS_LOGIN_URL="https://maruei01.dn-cloud.com/cgi-bin/dneo/dneo.cgi"
```

Entra ID 接続へ切り替える場合は以下も設定する。

```env
AUTH_MICROSOFT_ENTRA_ID_ID="..."
AUTH_MICROSOFT_ENTRA_ID_SECRET="..."
AUTH_MICROSOFT_ENTRA_ID_ISSUER="https://login.microsoftonline.com/<tenant-id>/v2.0"
```

Oracle 実接続を使う場合は以下も設定する。

```env
ORACLE_USE_MOCK="false"
ORACLE_HOST="192.168.3.204"
ORACLE_PORT="1521"
ORACLE_SID="EXPJ"
ORACLE_USER="EXPJ"
ORACLE_PASSWORD="..."
ORACLE_THICK_MODE="true"
ORACLE_CLIENT_LIB_DIR="/opt/oracle/instantclient_21_13"
```

### Phase 3: PostgreSQL 起動と初期マイグレーション

Docker 上で起動する。

```powershell
docker compose up --build
```

この時点で確認すること:

- Django が PostgreSQL に接続できる。
- `auth_user` 等の Django 標準テーブルが作成される。
- アプリ独自テーブルの migration が成功する。
- ブラウザで `http://localhost:3100/login` を開ける。

コンテナ内で手動コマンドを実行する場合:

```powershell
docker compose exec django_app python manage.py migrate
docker compose exec django_app pytest
```

### Phase 4: 認証・ポータル基盤

作るもの:

| 対象 | 内容 |
|------|------|
| `/login` | ログイン画面。当面は社員番号・パスワードを desknet's NEO Login API で認証する。開発者専用ログインは設けない |
| `/logout` | Django セッションを破棄 |
| `/api/auth/callback/microsoft-entra-id` | 将来 Entra ID へ切り替える場合の Authlib コールバック |
| `/dashboard` または `/app` | ログイン後のメニュー画面 |
| 左メニュー | 生産管理配下に「5年9組」を表示 |

初回の認可:

- 管理画面は作らない。
- 初期データで、開発ユーザーに全メニュー権限を付与する。
- 本番では desknet's のログイン ID（社員番号）を Django ユーザーへ紐付ける。
- Django ユーザーの `username` は社員番号とする。
- desknet's のパスワードは保存しない。認証成功時に Django ユーザーを作成または更新し、Django セッションを発行する。
- 将来 Entra ID へ切り替える場合も、Entra 側から取得する社員番号を同じ `username` に対応付ける。

### Phase 6: 5年9組の DB モデル

作るモデル:

```text
GonenKukumiSearchHistory
```

項目:

- `id`
- `user`
- `executed_at`
- `cust_code`
- `cust_item`
- `option_change`
- `year_month`

対象日付 `asOfDate` は保存しない。

完了条件:

- API 応答では camelCase の契約を維持する。

### Phase 7: Oracle 参照層

初回はモック実装から開始する。

1. `run_gonenkukumi_oracle_search` の戻り値構造を定義する。
2. 画面が描画できる固定データを返す。
3. 画面・Excel 出力・履歴が通った後、Python パッケージ `oracledb` による接続実装へ差し替える。

現在の実装では、`ORACLE_USE_MOCK=true` の間はモックを使い、`ORACLE_USE_MOCK=false` に変更すると Oracle 接続を試行する。

Docker で実 Oracle 接続を確認する例:

```powershell
docker compose exec django_app sh
export ORACLE_USE_MOCK=false
export ORACLE_PASSWORD="<Oracleパスワード>"
export ORACLE_THICK_MODE=true
python manage.py shell
```

Django shell 内で確認する例:

```python
from apps.gonenkukumi.infrastructure.oracle.client import list_customers
list_customers("101")
```

接続確認の初期段階では、`M_CUST` の得意先候補取得、`M_CUST_ITEM` の得意先品目取得、内作品番解決までを確認対象にする。得意先・仕入先の日次集計 SQL は、その後のフェーズで仕様に沿って追加する。

`DPY-3015` が発生する Oracle では thin mode で認証できないため、Docker イメージに Oracle Instant Client を含め、`ORACLE_THICK_MODE=true` で接続する。

実接続時に実装する API:

| API | 内容 |
|-----|------|
| `list_customers` | `M_CUST` から得意先候補を取得 |
| `list_cust_items` | `M_CUST_ITEM` から得意先品目を取得 |
| `run_gonenkukumi_oracle_search` | 一括検索 |

Oracle 実接続の確認項目:

- `M_CUST` から数字 3 桁の得意先が取得できる。
- `M_CUST_ITEM` から内作品番を解決できる。
- `NAISAK_NOT_FOUND` を 404 に変換できる。
- `MARI_COMPANY_CD` を設定した場合のみ SQL に会社コード条件が反映される（本番では未使用）。

### Phase 8: API 実装

作る API:

| メソッド | パス | 内容 |
|----------|------|------|
| `POST` | `/api/gonenkukumi/search` | Oracle 検索、成功時に履歴保存 |
| `GET` | `/api/gonenkukumi/customers` | 得意先候補 |
| `GET` | `/api/gonenkukumi/history` | 検索履歴 |
| `POST` | `/api/gonenkukumi/oracle-result` | 複数月追加用の Oracle 結果取得 |
| `GET` | `/api/gonenkukumi/cust-items` | 得意先品目プリフェッチ |

共通ルール:

- 未ログインは 401。
- 入力不正は 400。
- 内作品番未解決は 404。
- Oracle 未設定は 503。
- Oracle 実行エラーは 502。

## 5. ユーザー確認が必要なタイミング

### 5.1 実装開始前

| 確認 | 推奨値 |
|------|--------|
| 初回対象 | 5年9組単体 + 最小ポータル |
| 認証 | 当面 desknet's NEO Login API、将来 Entra ID。どちらも社員番号で Django ユーザーに紐づける |
| Oracle | まずモック、後で実接続 |
| 旧コード | 残して参照、Django 完成後に整理 |

### 5.2 Oracle 実接続前

確認すること:

- Oracle パスワードを安全に受け取れるか。
- 開発端末またはコンテナから `192.168.3.204:1521` に到達できるか。
- `EXPJ` ユーザーが必要テーブルを SELECT できるか。
- 会社コード条件を付けるか。

### 5.3 desknet's NEO 認証接続前

確認すること:

- desknet's NEO クラウド URL が `https://maruei01.dn-cloud.com/cgi-bin/dneo/dneo.cgi` で正しいか。
- desknet's の API/外部接続アクセスキー利用が有効か。
- ログイン ID が社員番号であること。
- Django ユーザーの `username` を社員番号にすること。
- desknet's Login API の成功応答から `user_id`、`name`、`default_group_id`、`access_key` を受け取れること。
- desknet's のパスワードをポータル DB に保存しないこと。

### 5.4 Entra ID 接続前

確認すること:

- クライアント ID があるか。
- クライアントシークレットがあるか。
- テナント ID があるか。
- リダイレクト URI が登録済みか。
- Entra ID から社員番号を取得できる claim または Microsoft Graph 属性が確定しているか。
- desknet's 認証で作成済みの Django ユーザーと、同じ社員番号で紐づけられるか。

- `docker compose up --build` で起動できる。
- `http://localhost:3100/login` を開ける。
- 通常ログインでログインできる。
- 左メニューから 5年9組を開ける。

- Oracle モックで一連の操作が通る。
- `pytest` が通る。
- 秘密情報が Git 管理対象に含まれていない。

Oracle 実接続と Entra ID 実接続は、初回実装完了後の接続フェーズで確認する。
