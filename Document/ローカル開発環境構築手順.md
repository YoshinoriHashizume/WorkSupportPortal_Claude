## 2. 構成パターンの選び方

次の **2 通り**から選ぶ（併用も可）。

| パターン | 内容 | 向いていること |
|----------|------|----------------|
| **A. DB のみ Docker** | PostgreSQL だけコンテナ。Django は **ホスト** で `python manage.py runserver` | 編集の反映が最も速い。ノート PC の負荷を抑えたいとき |
| **B. すべて Docker（推奨：本番に近いローカル）** | **Django アプリ・PostgreSQL・nginx** を **Docker Compose** で起動 | 仕様どおり「Docker 上」でそろえたい／本番と同じ経路で試したい |

- **Microsoft Entra ID** はどちらのパターンでも、リダイレクト URI を **`AUTH_URL` と一致するオリジン** に合わせる。
- **Oracle（基幹）** は、社内 VPN 等で届く場合のみコンテナ／ホストから接続。届かないときは機能オフまたはモック。
- **エディタでデバッグするときの起動順・注意点** は **§13** にまとめる。

## 5. パターン B：Docker でアプリ・DB・nginx を構築する（メイン手順）

本番想定（nginx → Django → PostgreSQL）に近い形で、**ローカルも Docker 上**にそろえる。

### 5.1 サービス構成

| サービス名（例） | 役割 | 公開ポート（例） |
|------------------|------|-------------------|
| **postgres** | PostgreSQL | `5432`（ホストへマップする場合） |
| **app** | Django（開発サーバーまたは gunicorn） | `3000` |
| **nginx** | リバースプロキシ | `80` → app:3000 |

ブラウザは **`http://localhost`**（nginx 経由）または **`http://localhost:3000`**（app 直）のどちらかでアクセスする想定にする。

### 5.2 `docker-compose.yml` の例（開発用）

リポジトリルートに置く。ファイル名は `compose.yaml` でも可。

```yaml
services:
  postgres:
    image: postgres:16-alpine
    container_name: worksupportportal-postgres
    environment:
      POSTGRES_USER: worksupportportal
      POSTGRES_PASSWORD: worksupportportal_local_dev
      POSTGRES_DB: worksupportportal
    ports:
      - "5432:5432"
    volumes:
      - worksupportportal_pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U worksupportportal -d worksupportportal"]
      interval: 5s
      timeout: 5s
      retries: 5

  app:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: worksupportportal-app
    ports:
      - "3000:3000"
    environment:
      DJANGO_DEBUG: "true"
      DATABASE_URL: postgresql://worksupportportal:worksupportportal_local_dev@postgres:5432/worksupportportal
      AUTH_URL: http://localhost:3000
      # 他: DJANGO_SECRET_KEY, Entra ID 変数は .env から読み込み（下記 5.5）
    env_file:
      - .env.local
    volumes:
      - .:/app
    depends_on:
      postgres:
        condition: service_healthy
    command: sh -c "python manage.py migrate && python manage.py runserver 0.0.0.0:3000"

  nginx:
    image: nginx:alpine
    container_name: worksupportportal-nginx
    ports:
      - "8080:80"
    volumes:
      - ./docker/nginx/local.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - app

volumes:
  worksupportportal_pgdata:
```

**注意（Windows）**: ソースをボリュームマウントして Django 開発サーバーを使う場合、ファイル監視が効かないことがある。そのときは Docker Desktop のファイル共有設定を確認する。

**ポートの調整**: ホストの `80` は競合しやすいため、例では nginx を **`8080`** にしている。ブラウザは `http://localhost:8080`。Entra のリダイレクト URI は **`AUTH_URL` のオリジン**（通常は `http://localhost:3000` のまま app 直アクセスでログイン試験）と整合させる。

### 5.3 `Dockerfile` の例（開発ターゲット）

リポジトリルートに `Dockerfile` を置く。`requirements.txt` がある前提。

```dockerfile
FROM python:3.12-slim
WORKDIR /app

COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 3000
CMD ["python", "manage.py", "runserver", "0.0.0.0:3000"]
```

- 初回はホストで仮想環境を作成し、依存関係を `requirements.txt` に固定してからビルドすると再現性が高い。
- 本番用イメージと開発用で `Dockerfile` を分ける場合は、マルチステージ化し `target:` を指定してもよい。

### 5.4 nginx 設定例 `docker/nginx/local.conf`

```nginx
server {
    listen 80;
    server_name localhost;

    location / {
        proxy_pass http://app:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### 5.5 環境変数（`.env.local`）

Git にコミットしない。Compose の `env_file` で `app` コンテナに渡す。

| 変数 | パターン B（コンテナ内）での注意 |
|------|-----------------------------------|
| `DATABASE_URL` | ホスト名は **`django_postgres`**（Compose サービス名）。例: `postgresql://worksupportportal:worksupportportal_local_dev@django_postgres:5432/worksupportportal`（`docker-compose.yml` の `environment` と二重にならないよう、どちらか一方に統一） |
| `AUTH_URL` | ブラウザがアクセスする URL。例: **`http://localhost:3100`**（`django_app` のポートマッピング `3100:3000`） |
| `DJANGO_SECRET_KEY` | ローカル用の長いランダム文字列 |
| `DJANGO_ALLOWED_HOSTS` | 例: `localhost,127.0.0.1`。nginx 経由も使う場合は必要なホストを追加 |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | 必要時。例: `http://localhost:8080` |
| Entra ID | テナント ID・クライアント ID・シークレット等（仕様どおり） |
**リダイレクト URI**: Azure のアプリ登録で、`AUTH_URL` と同じオリジン + Django 側のコールバックパス（例: `/api/auth/callback/microsoft-entra-id`）を登録する。

```powershell

docker compose up -d
docker compose ps
docker compose logs -f django_app
```

停止・削除（ボリュームは残す）:


### 5.7 マイグレーション（Django）

**コンテナ内**で実行する例:

```powershell

```

またはホストに Python があり `DATABASE_URL` を `localhost:5432` に向けている場合はホストから実行（パターン A と同じ）。

### 5.7.1 初回起動・DB 再作成時の開発ユーザー（`AUTH_DEV_MODE`）

Docker Compose では `AUTH_DEV_MODE=true` のとき、コンテナ起動時に次を **自動実行** する。

1. `python manage.py migrate`
2. `python manage.py bootstrap_local_dev`（開発ユーザー作成・全メニュー権限・利用承認済み）

| 変数 | 既定値 | 内容 |
|------|--------|------|
| `AUTH_DEV_MODE` | `true`（Compose） | `false` なら bootstrap と開発ログインを無効化 |
| `AUTH_DEV_USERNAME` | `10001` | 開発用社員番号（Django `username`） |
| `AUTH_DEV_PASSWORD` | `dev` | 開発用パスワード |
| `AUTH_DEV_LAST_NAME` | `開発` | 表示名（姓） |
| `AUTH_DEV_FIRST_NAME` | `管理者` | 表示名（名） |

**ログイン手順（DB を消した直後など）**

1. `docker compose up -d --build`
2. ブラウザで `http://localhost:3100/login`
3. 画面下部の **ローカル開発ログイン** から、上記社員番号・パスワードでログイン

**開発ログインの非表示**: `AUTH_DEV_MODE=true` でも、開発用ユーザー（既定 `AUTH_DEV_USERNAME`）**以外** に「管理者」グループのユーザーが **1 人以上** 登録されると、ログイン画面のローカル開発ログイン欄と `/auth/dev-login` は **自動的に無効化** される（初回セットアップ後は desknet's NEO 等の通常ログインのみ）。

> **注意**: `docker compose down -v` で PostgreSQL ボリュームを削除すると、ユーザー・お知らせ・SLIMS 取込データ等は **すべて消えます**。その場合も上記手順で開発ユーザーから再ログインできます。本番環境では `AUTH_DEV_MODE=false` にしてください。

**CSRF エラー（403）が出る場合**: ブラウザのアドレスバーが `http://127.0.0.1:3100` の場合は `http://localhost:3100` でも試してください。開発ログイン（`/auth/dev-login`）は `AUTH_DEV_MODE=true` 時のみ CSRF 検証を省略します。

**ログイン後に画面が真っ白・読み込みが終わらない場合**: メニュー画面（`/app`）は在庫発注アラート帯のため Oracle 集計を行います。到達不可や集計が遅い環境では **最大約 10 秒**（`INVENTORY_ORDER_ALERT_BANNER_TIMEOUT_SECONDS`、既定 `10`）でメニューが表示され、帯のみエラー表示になります。上の desknet 用フォームではなく、画面下部の **開発ログイン**（既定 `10001` / `dev`）を使ってください。

**Oracle を使うローカル検証**: Docker Compose の既定は `ORACLE_USE_MOCK=false`（実 Oracle 接続）です。Oracle に接続できない環境だけ `ORACLE_USE_MOCK=true` にしてください。5年9組・検収書比較はモック ON 時、得意先候補が「サンプル得意先A」等のサンプル名になります。在庫発注アラートは常に Oracle 接続を試行します。

**単体テストと開発 DB**: `pytest` は `test_worksupportportal` という別 DB を使います（`conftest.py` で開発 DB への実行を拒否）。開発用 PostgreSQL（`worksupportportal`）に単体テストのサンプルデータが残ると、在庫発注アラート一覧が `ITEM-00` 等のテスト行になることがあります。画面に黄色バナー「単体テスト用のサンプルデータ」が出た場合は、業務 SLIMS CSV を再取込してください。

```powershell
# 例: SLIMS からエクスポートした CSV を CLI から再取込
docker compose exec django_app python manage.py import_slims_stock_csv /path/to/SISJB....csv
```

ブラウザから **SLIMS在庫CSV** ボタンで再取込しても構いません。取込時に Oracle から再集計されます。

#### 在庫発注アラート — スナップショットの開発用パッチ

Oracle の実データを変えずにアラート判定や確認状態復帰を試す場合、**最新の集計スナップショット（PostgreSQL）** を直接パッチできます（`DEBUG=true` 時のみ。本番では `IOA_ALLOW_SNAPSHOT_PATCH=1` が必要）。

```powershell
docker compose exec django_app python manage.py patch_ioa_snapshot_row `
  --cust-code 100 `
  --item-cd 90249-14011 `
  --last-ship-date today `
  --post-shipment-count 2 `
  --reconcile
```

| オプション | 内容 |
|---|---|
| `--last-ship-date` | 最終出荷日（`today` / `YYYY/MM/DD` / `YYYYMMDD`） |
| `--last-incoming-date` | 最終入荷日 |
| `--post-shipment-count` | 最終入荷日以降の出荷回数 |
| `--reconcile` | アラート悪化時に確認状態を未確認へ戻す処理を実行 |

**注意**

- CSV **再取込** すると Oracle から再集計され、パッチは **上書き** されます。
- 出荷日だけ変えても **入荷日から12か月以内の出荷** だと「入出荷バランス良好」となり、アラート無しのままのことがあります。警告化の確認には `--last-incoming-date 2024/01/15` など **古い入荷日** と `--post-shipment-count 1` 以上を併用してください。
- パッチ後はブラウザで一覧を **再読込** してください。

**確認状態復帰の試し方**

1. 一覧で対象行を **確認済み**（アラート無しの状態）にする
2. 上記コマンドで入荷日を古く・出荷ありにパッチし `--reconcile` を付ける
3. 一覧を再読込 → **未確認** に戻っていることを確認

手動で bootstrap だけ実行する場合:

```powershell
docker compose exec django_app python manage.py bootstrap_local_dev
```

## 7. 環境変数の共通メモ

- **パターン B** では `DATABASE_URL` のホストが `postgres` か `localhost` かで切り替わる。Compose の `environment` と `.env.local` が矛盾しないようにする。

## 10. トラブルシューティング

### 10.1 一覧（クイック）

| 現象 | 確認すること |
|------|----------------|
| コンテナがすぐ落ちる・起動しない | `docker compose ps -a` で **Exited** なら `docker compose up -d` を再実行。ログは `docker compose logs django_app`（サービス名は **`django_app`**。`django-app` や `app` ではない） |
| DB に接続できない | サービス名 **`django_postgres`** と `DATABASE_URL` のホスト（`django_postgres`）が一致しているか。`depends_on` と `healthcheck`。**PostgreSQL コンテナが起動しているか**（§10.2） |
| `docker compose` が Docker API に接続できない | **Docker Desktop が起動しているか**（§10.3）。エラー例: `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine` |
| ログインでエラー | desknet's 接続先、ID/PW、DB 起動・`DATABASE_URL`・Django マイグレーションを確認（§10.2） |
| ホットリロードしない | Docker Desktop のファイル共有、WSL 上のパス |
| ログインループ | `AUTH_URL` と Entra のリダイレクト URI のオリジンが一致しているか（nginx 経由なら `8080` にそろえる等） |
| Windows でファイル変更が遅い | WSL2 上にリポジトリを置く、またはパターン A でホスト実行 |
| PowerShell で **`&&` が使えない** | **PowerShell 5.x** では `&&` が使えない。`Set-Location` してから別行でコマンドを実行するか、`;` で区切る（§10.4） |

### 10.2 ログインと DB 接続エラー

通常ログインでサインインするとき、サーバーは **PostgreSQL** 上にユーザーを作成・更新する。次のいずれかでブラウザに汎用エラーが出ることがある（メッセージだけでは DB 障害と分かりにくい）。

- PostgreSQL が **未起動**（ホストにインストールした場合はサービス、Docker の場合はコンテナ）
- **`DATABASE_URL` が誤り**（ホストから叩くときは `localhost:5432`、Compose 内アプリは `postgres:5432`）
- **スキーマ未適用**で Django ORM が失敗する

**切り分け**

1. ターミナルで `python manage.py migrate` を実行し、DB 接続エラーが出ないか確認する。
2. Docker 利用時は `docker compose ps` で **`django_postgres`** が **Up (healthy)**、**`django_app`** が **Up** か確認する。
3. サーバー側ログに Django / DB ドライバのスタックが出ていないか確認する。

**対処の例（DB のみ Docker・ホストで Django 開発サーバー）**

```powershell
docker compose up -d django_postgres
python manage.py migrate
```

### 10.3 Docker Desktop が止まっている

`docker compose` 実行時に **Docker デーモンに接続できない** と出る場合、Docker Desktop を起動してから再度試す（Windows ではタスクバーにクジラアイコンが出るまで待つ）。

### 10.4 PowerShell でのコマンド連結

**PowerShell 7+** では `cd path; python manage.py runserver` のように **`;`** で連結できる。古い **Windows PowerShell 5.1** では **`&&` が構文エラー**になることがある。手順書の例は行を分けるか、`Set-Location` してから次の行で実行するのが安全である。

## 13. ローカルデバッグ時の起動のあり方（Docker・サーバー・DB）

**目的**: エディタでブレークポイントを張るような **ローカルデバッグ** をするとき、Docker・DB・Django を **どの順で・どれだけ** 立ち上げるかを固定する。迷ったら **パターン A（DB のみ Docker + ホストで Django）** を既定とする。

### 13.1 全体の原則

| 原則 | 理由 |
|------|------|
| **Docker Desktop を先に起動する**（Docker を使う場合） | デーモン未起動だと `docker compose` が `npipe://...dockerDesktopLinuxEngine` 等で失敗する（§10.3） |
| **DB をアプリより先に起動し、接続できるまで待つ** | Django の起動時やログイン時に DB へ接続する。DB 未到達だと接続エラーの原因になる（§10.2） |
| **Django とマイグレーションの接続先を揃える** | `DATABASE_URL` が実行環境ごとにずれると、migrate は成功するのにアプリだけ別接続先、という齟齬が起きる |

### 13.2 推奨フロー：パターン A（DB のみ Docker、Django はホスト）

日常のコード編集・**Cursor / VS Code からのデバッグ**に向く。ホスト上の `python manage.py runserver` を想定する。

**起動順（毎回の作業イメージ）**

1. **Docker Desktop** を起動し、デーモンが応答するまで待つ（`docker version` で確認可）。
2. プロジェクトルートで **PostgreSQL のみ**起動する。

   ```powershell
   Set-Location d:\application\WorkSupportPortal
   docker compose up -d django_postgres
   ```

3. **`docker compose ps`** で **`django_postgres`** が **Up**（**healthy**）、**`django_app`** が **Up** であることを確認する。
4. **初回**、または Django モデルを変えたあとは、ホストからマイグレーションを実行する（`.env` の `DATABASE_URL` が **`localhost:5432`** の例と一致していること）。

   ```powershell
   python manage.py makemigrations
   python manage.py migrate
   ```

5. **Django 開発サーバー**をホストで起動する。
   - ターミナル: `python manage.py runserver 0.0.0.0:3000`
   - またはエディタの **実行とデバッグ** から Django 用の構成で起動する
6. ブラウザで **`http://localhost:3000`** を開く（**5 のあと**）。通常ログインでサインインする。

### 13.3 代替フロー：パターン B（app・DB・nginx をすべて Docker）

本番に近い経路で動作確認するとき。コンテナ内の Python にホストのデバッガをアタッチするには、`docker compose` 側の `command` やデバッグ用ポートの追加など **別途設定** が必要になることが多い。コード行単位のデバッグを頻繁に行う場合は、**§13.2 のパターン A** の方が手順が単純である。

起動例は **§5.6**、停止は **§5.6** を参照する。

### 13.4 ポートとプロセスの対応（参照用）

| リソース | ホストから見た例 | 備考 |
|----------|------------------|------|
| Django（開発） | `http://localhost:3000` | パターン A・B とも app が 3000 を公開する想定 |
| PostgreSQL | `localhost:5432` | パターン A: `docker-compose.yml` の `ports: "5432:5432"`。パターン B のコンテナ内アプリは **`postgres:5432`**（§5.5） |
| nginx（任意） | 例: `http://localhost:8080` | リポジトリの Compose 例（README） |

### 13.5 よくある誤り

- **DB を起動せずに** `python manage.py runserver` だけ動かし、ブラウザでページを開く → Django の DB 接続が失敗する。
- **Docker Desktop を起動していない**まま `docker compose up` する → §10.3。
- **アプリ用に `docker compose up -d`（全サービス）** と **ホストの `python manage.py runserver`** を **同時に** 動かし、**どちらも 3000 番を奪い合う** → どちらか一方に統一する（デバッグ主体なら postgres のみ + ホスト Django）。
