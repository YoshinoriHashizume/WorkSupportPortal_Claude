## 2. 構成パターンの選び方

次の **2 通り**から選ぶ（併用も可）。

| パターン | 内容 | 向いていること |
|----------|------|----------------|
| **A. DB のみ Docker** | PostgreSQL だけコンテナ。Next.js は **ホスト** で `npm run dev` | 編集の反映が最も速い。ノート PC の負荷を抑えたいとき |

## 5. パターン B：Docker でアプリ・DB・nginx を構築する（メイン手順）

本番想定（nginx → Next.js → PostgreSQL）に近い形で、**ローカルも Docker 上**にそろえる。

### 5.1 サービス構成

| サービス名（例） | 役割 | 公開ポート（例） |
|------------------|------|-------------------|
| **postgres** | PostgreSQL | `5432`（ホストへマップする場合） |
| **app** | Next.js（`next dev` または `next start`） | `3000` |
| **nginx** | リバースプロキシ | `80` → app:3000 |

ブラウザは **`http://localhost`**（nginx 経由）または **`http://localhost:3000`**（app 直）のどちらかでアクセスする想定にする。

### 5.2 `docker-compose.yml` の例（開発用）

リポジトリルートに置く。ファイル名は `compose.yaml` でも可。

```yaml
services:
  postgres:
    image: postgres:16-alpine
    container_name: coredataintegrationportal-postgres
    environment:
      POSTGRES_USER: coredataintegrationportal
      POSTGRES_PASSWORD: coredataintegrationportal_local_dev
      POSTGRES_DB: coredataintegrationportal
    ports:
      - "5432:5432"
    volumes:
      - coredataintegrationportal_pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U coredataintegrationportal -d coredataintegrationportal"]
      interval: 5s
      timeout: 5s
      retries: 5

  app:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: coredataintegrationportal-app
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: development
      WATCHPACK_POLLING: "true"
      DATABASE_URL: postgresql://coredataintegrationportal:coredataintegrationportal_local_dev@postgres:5432/coredataintegrationportal
      NEXTAUTH_URL: http://localhost:3000
      # 他: NEXTAUTH_SECRET, Entra ID 変数は .env から読み込み（下記 5.5）
    env_file:
      - .env.local
    volumes:
      - .:/app
      # Windows 等では匿名ボリュームだと初回に node_modules が空になる場合があるため、名前付きボリューム + 起動時 npm install を推奨（リポジトリの docker-compose.yml 参照）
      - coredataintegrationportal_node_modules:/app/node_modules
      - coredataintegrationportal_next:/app/.next
    depends_on:
      postgres:
        condition: service_healthy
    command: sh -c "npm install && npm run dev"

  nginx:
    image: nginx:alpine
    container_name: coredataintegrationportal-nginx
    ports:
      - "8080:80"
    volumes:
      - ./docker/nginx/local.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - app

volumes:
  coredataintegrationportal_pgdata:
  coredataintegrationportal_node_modules:
  coredataintegrationportal_next:
```

**注意（Windows）**: ソースをボリュームマウントして `next dev` する場合、ファイル監視が効かないことがある。そのときは `WATCHPACK_POLLING=true`（上記）を有効にするか、Docker Desktop のファイル共有設定を確認する。

**ポートの調整**: ホストの `80` は競合しやすいため、例では nginx を **`8080`** にしている。ブラウザは `http://localhost:8080`。Entra のリダイレクト URI は **`NEXTAUTH_URL` のオリジン**（通常は `http://localhost:3000` のまま app 直アクセスでログイン試験）と整合させる。

### 5.3 `Dockerfile` の例（開発ターゲット）

リポジトリルートに `Dockerfile` を置く。`package.json` がある前提。

```dockerfile
FROM node:22-bookworm-slim
WORKDIR /app

COPY package.json package-lock.json* ./
RUN if [ -f package-lock.json ]; then npm ci; else npm install; fi

COPY . .

EXPOSE 3000
ENV NEXT_TELEMETRY_DISABLED=1
CMD ["npm", "run", "dev"]
```

- 初回はホストで `npm install` して `package-lock.json` を生成してからビルドすると再現性が高い。
- 本番用イメージと開発用で `Dockerfile` を分ける場合は、マルチステージ化し `target:` を指定してもよい。

### 5.4 nginx 設定例 `docker/nginx/local.conf`

```nginx
server {
    listen 80;
    server_name localhost;

    location / {
        proxy_pass http://app:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### 5.5 環境変数（`.env.local`）

Git にコミットしない。Compose の `env_file` で `app` コンテナに渡す。

| 変数 | パターン B（コンテナ内）での注意 |
|------|-----------------------------------|
| `DATABASE_URL` | ホスト名は **`postgres`**（サービス名）。Compose 内の例: `postgresql://coredataintegrationportal:coredataintegrationportal_local_dev@postgres:5432/coredataintegrationportal`（`docker-compose.yml` の `environment` と二重にならないよう、どちらか一方に統一） |
| `NEXTAUTH_URL` / `AUTH_URL` | ブラウザがアクセスする URL。例: **`http://localhost:3000`**（app 直）または nginx 経由に合わせ **`http://localhost:8080`** |
| `NEXTAUTH_SECRET` | ローカル用の長いランダム文字列 |
| Entra ID | テナント ID・クライアント ID・シークレット等（仕様どおり） |
| `AUTH_DEV_MODE` | **`true`** にすると（かつ `NODE_ENV=development` のとき）ログイン画面に **開発用ログイン** が表示され、Entra ID なしでサインインできる。本番では無効。 |

**リダイレクト URI**: Azure のアプリ登録で、`NEXTAUTH_URL` と同じオリジン + Auth.js のコールバックパス（例: `/api/auth/callback/microsoft-entra-id`）を登録する。

**開発用プロバイダ**: `AUTH_DEV_MODE=true` のときのみ Credentials プロバイダ `dev-local` が有効。コールバックは `/api/auth/callback/dev-local`（Auth.js が処理）。

### 5.6 起動・停止

```powershell
docker compose logs -f app
```

```powershell

```

DB ボリュームも消す場合: `docker compose down -v`（**データが消える**）。

### 5.7 マイグレーション（Prisma 等）

**コンテナ内**で実行する例:

```powershell

```

またはホストに Node があり `DATABASE_URL` を `localhost:5432` に向けている場合はホストから実行（パターン A と同じ）。

## 7. 環境変数の共通メモ

- `.env.local` を `.gitignore` に含める。
- **パターン B** では `DATABASE_URL` のホストが `postgres` か `localhost` かで切り替わる。Compose の `environment` と `.env.local` が矛盾しないようにする。
- Entra ID の変数名は **Auth.js のバージョン**（v4: `NEXTAUTH_*`、v5: `AUTH_*` 等）に合わせる。
- **開発用ログイン**を使うときは `AUTH_DEV_MODE=true`（`npm run dev` の development のみ）。`next build` / `next start` の本番モードでは開発用ボタンは出ない。

`NEXTAUTH_SECRET` 生成例（PowerShell）:

```powershell
[Convert]::ToBase64String([System.Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
```

### 7.1 Oracle（任意）

ローカルで基幹に接続しない場合は未定義のまま。接続する場合は VPN・ファイアウォールと、コンテナから到達可能なホスト名を `DATABASE_URL` とは別に定義する（実装に依存）。

**接続先の確定値**（本番・検証と同じ前提で試す場合）は [`アプリケーション仕様書.md` §8.2.1](./アプリケーション仕様書.md#821-接続パラメータ確定) を参照（このドキュメントには値を再掲しない）。パスワードは `.env.local` 等にのみ記載し Git に含めない。コード配置は `ドメイン駆動設計.md` **§5**（`infrastructure/oracle` と `domains/integration`）。

## 10. トラブルシューティング

### 10.1 一覧（クイック）

| 現象 | 確認すること |
|------|----------------|
| コンテナがすぐ落ちる | `docker compose logs app`。`node_modules` を匿名ボリュームで遮っている場合、初回 `docker compose exec app npm install` が必要なことがある |
| DB に接続できない | サービス名 `postgres` と `DATABASE_URL` のホストが一致しているか。`depends_on` と `healthcheck`。**PostgreSQL プロセス／コンテナが起動しているか**（§10.2） |
| `docker compose` が Docker API に接続できない | **Docker Desktop が起動しているか**（§10.3）。エラー例: `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine` |
| 開発ログインで **CallbackRouteError**（Auth.js） | **多くは PostgreSQL 未到達**（Prisma `P1001` 等）。DB 起動・`DATABASE_URL`・`db push` を確認（§10.2） |
| ホットリロードしない | `WATCHPACK_POLLING`、Docker Desktop のファイル共有、WSL 上のパス |
| ログインループ | `AUTH_URL` / `NEXTAUTH_URL` と Entra のリダイレクト URI のオリジンが一致しているか（nginx 経由なら `8080` にそろえる等） |
| Windows でファイル変更が遅い | WSL2 上にリポジトリを置く、またはパターン A でホスト実行 |
| `npx prisma db push` 後に **EPERM**（`query_engine-*.dll` の rename 失敗） | 別プロセスが `node_modules\.prisma` を掴んでいる。開発サーバーやエディタのロックを外し、`npx prisma generate` を再実行（§10.5） |
| PowerShell で **`&&` が使えない** | **PowerShell 5.x** では `&&` が使えない。`Set-Location` してから別行でコマンドを実行するか、`;` で区切る（§10.4） |

### 10.2 開発ログイン（`AUTH_DEV_MODE`）と CallbackRouteError

開発用 Credentials（`dev-local`）でサインインするとき、サーバーは **PostgreSQL** 上にユーザーを upsert する。次のいずれかで **Auth.js の `CallbackRouteError`** がブラウザに出ることがある（メッセージだけでは DB 障害と分かりにくい）。

- PostgreSQL が **未起動**（ホストにインストールした場合はサービス、Docker の場合はコンテナ）
- **`DATABASE_URL` が誤り**（ホストから叩くときは `localhost:5432`、Compose 内アプリは `postgres:5432`）
- **スキーマ未適用**で Prisma が失敗する

**切り分け**

1. ターミナルで `npx prisma migrate status` または `npx prisma db push` を実行し、**`P1001: Can't reach database server`** が出ないか確認する。
2. Docker 利用時は `docker compose ps` で `postgres` が **Up (healthy)** か確認する。
3. サーバー側ログに **`[auth][error]`** や Prisma のスタックが出ていないか確認する。Auth.js のエラーには **`cause`** に元例外が載ることがある（[公式の説明](https://errors.authjs.dev#callbackrouteerror)）。

**対処の例（DB のみ Docker・ホストで `npm run dev`）**

```powershell
docker compose up -d postgres
npx prisma db push
npx prisma db seed
```

### 10.3 Docker Desktop が止まっている

`docker compose` 実行時に **Docker デーモンに接続できない** と出る場合、Docker Desktop を起動してから再度試す（Windows ではタスクバーにクジラアイコンが出るまで待つ）。

### 10.4 PowerShell でのコマンド連結

**PowerShell 7+** では `cd path; npm run dev` のように **`;`** で連結できる。古い **Windows PowerShell 5.1** では **`&&` が構文エラー**になることがある。手順書の例は行を分けるか、`Set-Location` してから次の行で実行するのが安全である。

### 10.5 Prisma Client の生成が Windows で EPERM になる

`db push` のあと **自動 `generate`** が `node_modules\.prisma\client\` 内の DLL を置き換えられず **`EPERM` … rename** で失敗することがある。次を試す。

- `npm run dev` 等の Node プロセスを止める
- ウイルス対策のリアルタイムスキャン対象から `node_modules` を除外できるか検討する（運用ルールに従う）
- `npx prisma generate` を再実行する

### 10.6 Prisma CLI が読む環境変数ファイル

`npx prisma` はプロジェクトルートの **`.env`** を読み込む（Next.js が `.env.local` を読むのとは別）。**`.env` に `DATABASE_URL` が無く `.env.local` のみ**だと、CLI だけ別の接続先／未設定になることがある。`.env.example` を `.env` にコピーするか、**`.env` と `.env.local` の両方に同じ `DATABASE_URL` を揃える**とよい。

## 13. ローカルデバッグ時の起動のあり方（Docker・サーバー・DB）

**目的**: エディタでブレークポイントを張るような **ローカルデバッグ** をするとき、Docker・DB・Next.js を **どの順で・どれだけ** 立ち上げるかを固定する。迷ったら **パターン A（DB のみ Docker + ホストで Next）** を既定とする。

### 13.1 全体の原則

| 原則 | 理由 |
|------|------|
| **Docker Desktop を先に起動する**（Docker を使う場合） | デーモン未起動だと `docker compose` が `npipe://...dockerDesktopLinuxEngine` 等で失敗する（§10.3） |
| **DB をアプリより先に起動し、接続できるまで待つ** | レイアウトやサーバーコンポーネントが **起動直後に Prisma** でクエリする。DB 未到達だと `P1001` / `Can't reach database server at localhost:5432` や Auth.js の **CallbackRouteError** の原因になる（§10.2） |
| **Prisma CLI と Next の接続先を揃える** | `npx prisma` は主に **`.env`**、Next は **`.env.local` も**読む。片方だけ `DATABASE_URL` があると、push は成功するのにアプリだけ別接続先、という齟齬が起きる（§10.6） |

### 13.2 推奨フロー：パターン A（DB のみ Docker、Next はホスト）

日常のコード編集・**Cursor / VS Code からのデバッグ**に向く。リポジトリの `.vscode/launch.json` は **ホスト上の `npm run dev`** を想定している。

**起動順（毎回の作業イメージ）**

1. **Docker Desktop** を起動し、デーモンが応答するまで待つ（`docker version` で確認可）。
2. プロジェクトルートで **PostgreSQL のみ**起動する。

   ```powershell
   Set-Location d:\application\CoreDataIntegrationPortal
   docker compose up -d postgres
   ```

3. **`docker compose ps`** で `postgres` が **Up**（および **healthy** が付く構成なら healthy）であることを確認する。
4. **初回**、または `prisma/schema.prisma` を変えたあとは、ホストからスキーマ反映とシードを実行する（`.env` の `DATABASE_URL` が **`localhost:5432`** の例と一致していること）。

   ```powershell
   npx prisma db push
   npx prisma db seed
   ```

5. **Next.js 開発サーバー**をホストで起動する。
   - ターミナル: `npm run dev`
   - またはエディタの **実行とデバッグ** から「**Next.js: npm run dev（インスペクタ付き）**」（`NODE_OPTIONS=--inspect` が付く）
6. ブラウザで **`http://localhost:3000`** を開く（**5 のあと**）。`AUTH_DEV_MODE=true` なら開発ユーザーでサインイン可能（README 参照）。

**Node インスペクタ（ブレークポイントで止めたいとき）**

- Next.js 15 + Turbopack では、インスペクタが **9229 ではなく 9230** に出る案内がログに出ることがある。
- リポジトリの **「Node にアタッチ（…9230…）」** 構成で、開発サーバー起動 **後** にアタッチする。

### 13.3 代替フロー：パターン B（app・DB・nginx をすべて Docker）

本番に近い経路で動作確認するとき。**コンテナ内の Node** にホストのデバッガをアタッチするには、`docker compose` 側の `command` や `NODE_OPTIONS` の追加など **別途設定** が必要になることが多い。コード行単位のデバッグを頻繁に行う場合は、**§13.2 のパターン A** の方が手順が単純である。

起動例は **§5.6**、停止は **§5.6** を参照する。

### 13.4 ポートとプロセスの対応（参照用）

| リソース | ホストから見た例 | 備考 |
|----------|------------------|------|
| Next.js（開発） | `http://localhost:3000` | パターン A・B とも app が 3000 を公開する想定 |
| PostgreSQL | `localhost:5432` | パターン A: `docker-compose.yml` の `ports: "5432:5432"`。パターン B のコンテナ内アプリは **`postgres:5432`**（§5.5） |
| nginx（任意） | 例: `http://localhost:8080` | リポジトリの Compose 例（README） |
| Node インスペクタ | 例: **9230**（Turbopack 時はログで確認） | `.vscode/launch.json` のアタッチ先と合わせる |

### 13.5 よくある誤り

- **DB を起動せずに** `npm run dev` だけ動かし、ブラウザでページを開く → レイアウトの Prisma が即失敗する。
- **Docker Desktop を起動していない**まま `docker compose up` する → §10.3。
- **アプリ用に `docker compose up -d`（全サービス）** と **ホストの `npm run dev`** を **同時に** 動かし、**どちらも 3000 番を奪い合う** → どちらか一方に統一する（デバッグ主体なら postgres のみ + ホスト Next）。
