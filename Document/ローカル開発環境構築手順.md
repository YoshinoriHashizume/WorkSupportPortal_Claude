## 2. 推奨構成（社内標準）

**主手順は DevContainer** とする（社内テンプレート `django_docker_env` 相当）。

| 項目 | 内容 |
|------|------|
| Compose | `docker-compose.devcontainer.yaml` |
| サービス | `web-app`（Django）、`db`（PostgreSQL） |
| ホスト公開ポート | **Django: 8990**、**PostgreSQL: 5440** |
| コンテナ内 workspace | **`/django_app/src`**（Django ソース） |
| 環境変数 | リポジトリ **ルートの `.env`**（テンプレート: `.env.example`） |
| プロジェクト全体のマウント | `/django_app`（ルート一式。`Document/` も含む） |

旧構成（ルート直下の `manage.py` + `docker-compose.yml`、ポート 3000/3100 等）は **§10 旧構成** に残す。新規セットアップでは使わない。

## 4. リポジトリの配置と `.env`

```powershell
cd D:\application\WorkSupportPortal_Claude
Copy-Item .env.example .env
# 本番用テンプレートを使う場合:
Copy-Item .env.production.example .env.production
```

`.env` / `.env.production` を編集する（最低限: `SECRET_KEY`、`POSTGRES_*`、必要なら Oracle / 認証関連）。**Git にコミットしない**。

旧リポジトリ `D:\application\WorkSupportPortal` の `.env.example` / `.env.production.example` にあった Oracle・desknet's・Entra ID 等のキーは、現行テンプレート（およびローカル用実体）に移植済み。ポートは旧 3000/3100 ではなく **8990**、DB は `DATABASE_URL` ではなく **`POSTGRES_*`**（Compose サービス名 `db`）を使う。

主な変数（詳細は `.env.example`）:

| 変数 | 例・注意 |
|------|----------|
| `PYTHONPATH` | `/django_app/src` |
| `DJANGO_SETTINGS_MODULE` | `config.settings.development` |
| `POSTGRES_HOST` | Compose 内では **`db`** |
| `DEBUG` | 開発時 `True` |
| `ORACLE_HOST` 等 | 基幹接続。届かないときは `ORACLE_USE_MOCK=true` |

## 5. DevContainer で起動する（メイン手順）

### 5.1 サービス構成

| サービス | 役割 | ホストポート |
|----------|------|----------------|
| **db** | PostgreSQL | `5440` → コンテナ `5432` |
| **web-app** | Django（entrypoint + 開発サーバー） | `8990` → コンテナ `8880` |

### 5.2 Cursor / VS Code から開く

1. Docker Desktop を起動する。
2. リポジトリルートを開く。
3. **Dev Containers: Reopen in Container**（または同等）を実行する。
4. `.devcontainer/devcontainer.json` が `docker-compose.devcontainer.yaml` の **`web-app`** を参照し、workspace が **`/django_app/src`** になる。
5. 初回はイメージビルドに時間がかかる。完了後、統合ターミナルの cwd が `/django_app/src` であることを確認する。

**SSH 鍵について**: ホスト個人の `.ssh` は **マウントしない**（他 PC でパス不一致による起動失敗・秘密鍵のコンテナ内露出を避けるため）。GitHub 操作は HTTPS またはホスト側の認証（`gh auth login` 等）を使う。Claude Code 設定のみ名前付きボリュームで永続化する。

ホストから Compose のみ起動する場合:

```powershell
cd D:\application\WorkSupportPortal_Claude
docker compose -f docker-compose.devcontainer.yaml up --build -d
docker compose -f docker-compose.devcontainer.yaml ps
```

`web-app` は **`entrypoint.sh` をメインプロセス（PID 1 相当）** として起動する（`sleep infinity` は使わない）。Django 起動失敗時はコンテナが止まる。`WEB_BIND_PORT`（既定 **8880**）で listen し、HTTP healthcheck は `8880/login`（失敗時は `8000/login`）で healthy を判定する。`DEBUG=false` でも開発 compose では 8880 に固定するため、ホスト `http://localhost:8990` と食い違わない。

ブラウザ: **http://localhost:8990**

開発用 `.env` と本番用 `.env.production` を両方置いてもよい。`DJANGO_SETTINGS_MODULE=config.settings.development` のときは **`.env.production` を読まない**（開発 DB のパスワードを上書きしないため）。

### 5.3 アクセス

- アプリ: **`http://localhost:8990`**
- PostgreSQL（ホストツールから）: `localhost:5440`（ユーザー / DB は `.env` の `POSTGRES_*`）

### 5.4 よく使うコマンド（DevContainer 内）

workspace が `/django_app/src` のとき:

```bash
python manage.py migrate
python manage.py runserver 0.0.0.0:8880   # entrypoint が既に起動している場合は不要なことが多い
pytest
```

ホスト側から exec する場合:

```powershell
docker compose -f docker-compose.devcontainer.yaml exec web-app bash -lc "cd /django_app/src && python manage.py migrate"
docker compose -f docker-compose.devcontainer.yaml exec web-app bash -lc "cd /django_app/src && pytest"
```

### 5.5 停止

```powershell
docker compose -f docker-compose.devcontainer.yaml down
```

ボリュームも消す場合: `docker compose -f docker-compose.devcontainer.yaml down -v`（**DB データが消える**）。

### 5.6 Oracle・認証の注意

- **Oracle（基幹）** は社内ネットワーク等で `ORACLE_HOST` に届く場合のみ接続する。
- `.env` の **`ORACLE_PASSWORD` が空だと** `Oracle 接続情報が不足しています: password` になる。ローカル開発の既定は旧 Compose と同様 **`EXPJ`**（ユーザー `EXPJ` と対）。`docker-compose.devcontainer.yaml` でも `${ORACLE_PASSWORD:-EXPJ}` を明示する。本番は担当者から受け取った値を `.env.production` に設定する。
- エディタで `.env` を直したら **保存したうえで** `docker compose ... up -d --force-recreate --no-deps web-app` する（未保存・空のままだとコンテナにパスワードが渡らない）。
- 基幹に届かない／つなぎたくないときは `ORACLE_USE_MOCK=true` にしてコンテナを再作成する。
- Docker 開発では **`ORACLE_THICK_MODE=true`**（Instant Client）が必要。thin モードだと `DPY-3015`、libaio リンク破損だと `DPI-1047` になり、画面上は「得意先候補の取得に失敗しました。」と出る。
- **Microsoft Entra ID** を試す場合、リダイレクト URI をブラウザが実際に使うオリジン（例: `http://localhost:8990`）に合わせる。
- desknet's NEO 認証の詳細は `アプリケーション仕様書.md` および認証関連手順を参照。

## 7. トラブルシューティング

| 現象 | 確認すること |
|------|----------------|
| コンテナが起動しない | Docker Desktop 起動、`docker compose -f docker-compose.devcontainer.yaml ps -a`、`logs web-app` / `logs db` |
| DB に接続できない | `.env` の `POSTGRES_HOST=db`（コンテナ内）、ホストからは `localhost:5440`。healthcheck 待ち |
| 8990 で繋がらない | ポート競合、`forwardPorts`、Compose の `8990:8880` |
| pytest / import 失敗 | cwd が `/django_app/src` か、`PYTHONPATH=/django_app/src` |
| ホットリロードしない | Docker Desktop のファイル共有、Windows パスのマウント遅延 |
| PowerShell で `&&` が使えない | PowerShell 5.x では行を分けるか `;` を使う |

## 10. 旧構成（参考・新規では使わない）

2026-07 以前のローカル手順（ルート直下 Django + `docker-compose.yml`、ホストポート 3000/3100、サービス名 `django_app` / `django_postgres` 等）。

当時のパターン概要:

| パターン | 内容 |
|----------|------|
| A. DB のみ Docker | PostgreSQL だけコンテナ。Django はホストで `runserver`（ポート 3000） |
| B. すべて Docker | app・PostgreSQL・nginx。ブラウザは `http://localhost:3100` 等 |

主な違い（現行との対照）:

| 項目 | 旧 | 現行（社内標準） |
|------|----|------------------|
| Django ソース | リポジトリルート | **`src/`** |
| Compose | `docker-compose.yml` | **`docker-compose.devcontainer.yaml`** |
| アプリポート | 3000 / 3100 | **8990** |
| DB ホストポート | 5432 | **5440** |
| 環境変数ファイル | `.env.local` 等 | **ルート `.env`** |
| 作業ディレクトリ | ルート | **`/django_app/src`** |

旧手順の詳細コマンドが必要な場合は、Git 履歴上の本ファイル旧版、または `社内標準移行メモ.md` を参照する。
