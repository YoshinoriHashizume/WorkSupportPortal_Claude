## 2. 本番の前提（仕様・実装との対応）

| 項目 | 本番での想定 |
|------|----------------|
| サーバー | **Windows Server 仮想マシン**。**仮想サーバーで Docker が使えない場合は §10.3（Python 直実行）**。Docker が使える場合は WSL2 Ubuntu + Docker Engine（§10）または Linux VM（§10.4） |
| 本番 URL | **`http://192.168.3.196`**（ユーザーがブラウザで開くオリジン。`AUTH_URL` 等と一致させる） |
| 公開 | **社内 LAN** から上記 URL でアクセス。HTTPS 終端（nginx / IIS 等）を追加する場合は **その公開 URL** に合わせて `AUTH_URL`・`DJANGO_CSRF_TRUSTED_ORIGINS` を更新する |
| アプリ | **Python 3.12 + Django**（本番は **gunicorn** 等のアプリケーションサーバーで実行する。現行開発用 `Dockerfile` は `runserver` のため本番用イメージ要整備） |
| リバースプロキシ | **任意**。nginx、IIS（ARR）、または Docker のポート公開（`80:3000`）のいずれか |
| ポータル DB | **PostgreSQL**（Compose 内または専用 VM / マネージド DB） |
| 基幹 | **Oracle** への **読み取りのみ**、**同一セグメント** 到達（仕様書 3.3・8.2.1） |
| 認証（現行） | **desknet's NEO Login API**（`AUTH_PROVIDER=desknet`）。社員番号 + desknet パスワードでログイン |
| 認証（将来） | **Microsoft Entra ID**（Authlib 連携は未実装。切替時は `Microsoft認証（Entra ID）構築手順.md` を参照） |
| 開発専用 | 本番では **`AUTH_DEV_MODE` を `false` または未設定** とし、開発者専用ログインを **表示・実行不可** にする |

ローカル用の `docker-compose.yml` は **開発向け**（ソースマウント、`runserver`、`AUTH_DEV_MODE=true` 等）のため、本番では **別ファイル**（例: `docker-compose.prod.yml`）または **イメージレジストリ＋マニフェスト** で運用する。

## 3. 移植前に揃えるもの

| 区分 | 内容 |
|------|------|
| **ソース** | 本番用にタグ付けした Git リビジョン（例: `master` のリリースタグ） |
| **本番 URL** | **`http://192.168.3.196`**（ポートを付ける運用なら `http://192.168.3.196:<ポート>`）。`AUTH_URL` 等のオリジンと一致させる |
| **秘密情報** | `DJANGO_SECRET_KEY`、PostgreSQL 接続、Oracle 読み取りユーザー、desknet 連携に必要な値等。**リポジトリに含めない** |
| **desknet's NEO** | 本番サーバから desknet Login API（`DESKNETS_LOGIN_URL`）へ到達できること |
| **Entra ID** | **将来切替用**。現行リリースでは必須ではない（§6 参照） |
| **ネットワーク** | VM から **Oracle**（例: `192.168.3.204:1521`）、**PostgreSQL** への到達（ポート・ファイアウォール） |
| **TLS 証明書** | HTTPS 運用時に nginx / IIS / LB で利用する証明書・鍵の配置方針 |

### 2.1 仮想サーバー（VM）上での制約

本番 VM が **Hyper-V / VMware 等の仮想マシン** の場合、次の制約がある。

| 方式 | VM 上で動くか | 備考 |
|------|---------------|------|
| **Docker Desktop** | 多くの場合 **×** | Engine が `Starting...` で止まる |
| **WSL2 + Docker Engine** | **ホスト側でネストした仮想化が有効なら ○** | 無効だと WSL2 / Docker が起動しない |
| **Linux 専用 VM + Docker Engine** | **○（いちばん安定）** | 物理 or ネスト仮想化済み Linux VM |
| **Windows 直実行（§10.3）** | **○** | Docker 不要。Python + PostgreSQL + waitress |

**ネストした仮想化** が無効な Windows Server VM では、**§10.3（Docker なし）** または **別途 Linux VM（§10.4）** を選ぶ。インフラ担当に VM の **nested virtualization** 有効化を依頼できる場合は §10 も再検討できる。

### 3.1 GitHub リポジトリ名（`CoreDataIntegrationPortal` → `WorkSupportPortal`）

製品名・作業フォルダ名は **WorkSupportPortal** に統一する。GitHub 上のリポジトリ名がまだ **CoreDataIntegrationPortal** の場合は、次のいずれかで **WorkSupportPortal** に揃える。

**方法 A（推奨）: GitHub でリポジトリ名を変更する**

1. GitHub で対象リポジトリを開く。  
2. **Settings** → **General** → **Repository name** を **`WorkSupportPortal`** に変更して **Rename** する。  
3. 旧 URL（`.../CoreDataIntegrationPortal`）は自動で新 URL にリダイレクトされる。  
4. 開発 PC で remote URL を更新する:

```cmd
cd /d d:\application\WorkSupportPortal
git remote set-url origin https://github.com/YoshinoriHashizume/WorkSupportPortal.git
git remote -v
```

**方法 B: GitHub 名はそのまま、クローン先フォルダだけ `WorkSupportPortal` にする**

```cmd
cd Application
git clone https://github.com/YoshinoriHashizume/CoreDataIntegrationPortal.git WorkSupportPortal
cd WorkSupportPortal
```

**既に `CoreDataIntegrationPortal` フォルダでクローン済みの VM** では、フォルダをリネームするか取り直す。

```cmd
cd /d C:\Application
ren CoreDataIntegrationPortal WorkSupportPortal
cd WorkSupportPortal
```

## 4. 本番用コンテナイメージの考え方

開発用 `Dockerfile` は Django **開発サーバー**（`runserver`）向けのため、本番では次を行う。

1. **本番用 Dockerfile（`Dockerfile.prod`）**  
   - `python manage.py collectstatic --noinput` で静的ファイルを `staticfiles/` に収集  
   - `gunicorn config.wsgi:application --bind 0.0.0.0:3000` で起動（`docker/entrypoint-prod.sh`）  
   - **`AUTH_DEV_MODE=true` の場合は起動を拒否**（`bootstrap_local_dev` は実行しない）  
2. **CI でテスト・イメージビルド** を行うパイプライン（推奨）

本番 Compose（**`docker-compose.prod.yml`**）では **ソースのボリュームマウントを行わない**、`DJANGO_DEBUG=false` とする。環境変数テンプレートは **`.env.production.example`** を `.env.production` にコピーして編集する。

### 4.1 静的ファイル（CSS / JS）

本番 Compose では **WhiteNoise** を利用する（`DJANGO_DEBUG=false` 時に有効）。`Dockerfile.prod` ビルド時に `collectstatic` 済みの `staticfiles/` を gunicorn から配信する。

nginx / IIS を前段に置く場合も、 `/static/` を直接配信するか、アプリに任せるかを選べる。

## 5. 環境変数（本番）

リポジトリの **`.env.example`** をベースに、本番専用の値を **サーバー上の環境ファイル** または **シークレットストア** に設定する。Django が参照するのは **`DJANGO_DEBUG`**（`DEBUG` 単体は未使用）。

### 5.1 Django / 公開

| 変数 | 説明 |
|------|------|
| `DJANGO_DEBUG` | **`false`**（必須） |
| `DJANGO_SECRET_KEY` | 十分に長いランダム値（ローカルと別にする） |
| `DJANGO_ALLOWED_HOSTS` | 本番ホスト。例: `192.168.3.196` |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | 本番オリジン。HTTP の例: `http://192.168.3.196`。HTTPS 終端時は `https://...` |
| `AUTH_URL` | **本番のオリジン**（例: **`http://192.168.3.196`**） |
| `DATABASE_URL` | 本番 PostgreSQL の接続文字列 |

### 5.2 認証（現行: desknet's NEO）

| 変数 | 説明 |
|------|------|
| `AUTH_PROVIDER` | **`desknet`**（デフォルト。本番リリース時） |
| `DESKNETS_LOGIN_URL` | desknet Login API URL（例: `https://maruei01.dn-cloud.com/cgi-bin/dneo/dneo.cgi`） |
| `DESKNETS_TIMEOUT_SECONDS` | API タイムアウト秒（例: `10`） |
| `AUTH_DEV_MODE` | **未設定または `false`**。`true` にすると開発ログイン・`bootstrap_local_dev` が有効になり **本番禁止** |

### 5.3 認証（将来: Microsoft Entra ID）

Entra 切替実装後に設定する。現行コードではログインエンドポイントは **予約のみ**（未接続）。

| 変数 | 説明 |
|------|------|
| `AUTH_MICROSOFT_ENTRA_ID_ID` | Entra アプリ登録のクライアント ID |
| `AUTH_MICROSOFT_ENTRA_ID_SECRET` | クライアントシークレット |
| `AUTH_MICROSOFT_ENTRA_ID_ISSUER` | テナント issuer（例: `https://login.microsoftonline.com/<tenant-id>/v2.0`） |

### 5.4 Oracle / アプリ連携

接続情報（ホスト・ポート・SID・ユーザー ID）は [`アプリケーション仕様書.md` §8.2.1](./アプリケーション仕様書.md#821-接続パラメータ確定) を参照。**パスワードはシークレット**。**読み取り専用**アカウントを使う。

| 変数 | 説明 |
|------|------|
| `ORACLE_USE_MOCK` | **`false`**（本番） |
| `ORACLE_HOST` / `ORACLE_PORT` / `ORACLE_SID` | 仕様書 §8.2.1 |
| `ORACLE_USER` / `ORACLE_PASSWORD` | 読み取り専用ユーザー |
| `ORACLE_THICK_MODE` | Docker Linux イメージでは **`true`** 推奨（Instant Client 同梱） |
| `ORACLE_CLIENT_LIB_DIR` | コンテナ内パス（例: `/opt/oracle/instantclient_21_13`） |
| `ORACLE_CONNECT_TIMEOUT_SECONDS` | 接続タイムアウト（例: `5`） |
| `GONENKUKUMI_COMPANY_CD` | 5年9組 Oracle 検索用の会社コード（環境に応じて設定） |

## 6. Microsoft Entra ID（将来切替）

**現行リリースでは desknet's NEO 認証で公開する。** Entra ID はアプリ側未実装のため、Azure 登録だけではログインできない。

Entra へ切り替える際は [`Microsoft認証（Entra ID）構築手順.md`](./Microsoft認証（Entra ID）構築手順.md) に従い、次を行う。

1. Azure ポータルで **アプリ登録**（本番用、または環境別）。  
2. **リダイレクト URI（Web）** に **`http://192.168.3.196/api/auth/callback/microsoft-entra-id`** を登録（ポート付き公開ならオリジンに合わせて変更）。実装の URL パスは `apps/identity/urls.py` と一致させる。  
3. Authlib 連携の **アプリ実装リリース** 後、`AUTH_PROVIDER` の切替とチェックリスト（§11）を Entra 用に更新する。

## 7. PostgreSQL（本番）

1. 本番用 **データベース・ユーザー・パスワード** を作成する。  
2. 初回起動前または起動時に **マイグレーション**（`python manage.py migrate`）を適用する。  
3. **バックアップ**（スナップショット等）をインフラ標準に合わせる。在庫発注アラートの確認状態・SLIMS 取込データ等が蓄積される。  
4. 接続は **TLS** が使える場合は有効化を検討する。

### 7.1 初回管理者

desknet ログインで **初めて** 入ったユーザーは **承認待ち** となり、メニューが使えない。公開前または公開直後に、次のコマンドで **最初の管理者を1名** 用意する（§10.3 ステップ 8 参照）。

**Windows 直実行（§10.3）** の CMD 例:

```cmd
cd /d C:\Application\WorkSupportPortal
.venv\Scripts\python manage.py bootstrap_production_admin --username 51705 --last-name 橋爪 --first-name 良典
```

**Docker（§10.0）** の WSL Ubuntu 例:

```bash
cd /mnt/c/Application/WorkSupportPortal
bash scripts/wsl/bootstrap-production-admin.sh 51705 橋爪 良典
```

または:

```bash
docker compose -f docker-compose.prod.yml exec django_app \
  python manage.py bootstrap_production_admin --username 51705 --last-name 橋爪 --first-name 良典
```
- `--username` は **desknet's NEO の社員番号** と同じ値にする。  
- 作成後、その社員番号と **desknet パスワード** でログインする（ポータル専用パスワードは不要）。  
- `bootstrap_local_dev` は **本番では使用しない**。

## 9. リバースプロキシ（任意）

社内 HTTP のみ（`http://192.168.3.196`）で公開する場合、Docker の **ポートマップのみ** でもよい。HTTPS や複数サービス統合時は nginx / IIS 等を前段に置く。

1. **TLS**: 組織基準に合わせて証明書を設定する。  
2. **アプリへの転送**: `proxy_pass`（nginx）または ARR（IIS）で `http://127.0.0.1:3000`（またはコンテナ `django_app:3000`）へ。  
3. **ヘッダ**: `X-Forwarded-Proto`、`Host` を渡し、`AUTH_URL` が **ユーザーに見える URL** と一致するようにする。  
4. **静的ファイル**: `/static/` を `staticfiles/` から配信する設定を含める（§4.1）。  
5. 本番用設定ファイルはリポジトリ外または `deploy/nginx/` 等で **別管理** する（現行リポジトリに nginx 設定は含まれない）。

## 10. デプロイ作業の流れ（Windows Server VM + WSL2 Ubuntu + Docker Engine）

**Docker / WSL が使える場合の手順。** 仮想サーバーで WSL2 が動かない場合は **§10.3（Windows 直実行）** を使う。Linux VM を用意できる場合は **§10.4** が最も安定する。

| 項目 | 値 |
|------|-----|
| Windows 作業フォルダ | `C:\Application\WorkSupportPortal` |
| WSL（Ubuntu）からのパス | `/mnt/c/Application/WorkSupportPortal` |
| リポジトリ名 | **WorkSupportPortal** |

### 10.0 手順一覧

| # | どこで | 作業 |
|---|--------|------|
| 1 | Windows（管理者 PowerShell） | WSL2 + Ubuntu 導入（§10.0.1） |
| 2 | Windows（CMD） | ソース `git clone`（§10.0.2） |
| 3 | Ubuntu（WSL） | Docker Engine 導入（§10.0.3） |
| 4 | Ubuntu または Windows | `.env.production` 作成（§10.0.4） |
| 5 | Ubuntu（WSL） | `docker compose` で起動（§10.0.5） |
| 6 | Windows（CMD） | ファイアウォール TCP 80（§10.0.6） |
| 7 | Ubuntu（WSL） | 初回管理者（§10.0.7） |
| 8 | ブラウザ | §11 チェックリスト |

> **Docker Desktop を既に入れている場合:** タスクトレイから **Quit Docker Desktop** し、WSL の `docker-desktop` と競合しないようにする。

#### §10.0.1 WSL2 + Ubuntu を入れる（Windows・初回のみ）

**管理者 PowerShell** で実行:

```powershell
powershell -ExecutionPolicy Bypass -File C:\Application\WorkSupportPortal\scripts\windows\Install-WslUbuntu.ps1
```

スクリプトが無い場合は手動:

```powershell
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart
wsl --install -d Ubuntu
```

**VM を再起動** → スタートメニューから **Ubuntu** を開き、Linux ユーザー名・パスワードを設定。

確認（Windows CMD）:

```cmd
wsl --status
wsl -l -v
```

`Ubuntu` が **VERSION 2** であること。

### 作業内容の補足

1. **VM 準備** — Windows Server 更新、**WSL2 + Ubuntu**、社内 IP（例: `192.168.3.196`）。  
2. **ソース配置** — `C:\Application\WorkSupportPortal` に clone。

### ステップ 5：設定ファイル `.env.production` を作る

これが **本番の設定ファイル** です。パスワードなどを書きます。**Git には載せません。**

```cmd
cd /d C:\Application\WorkSupportPortal
copy .env.production.example .env.production
notepad .env.production
```

メモ帳が開いたら、**次の行を必ず書き換える**（例。IP とパスワードは環境に合わせる）:

```env
POSTGRES_PASSWORD=MyDbPassword2026
APP_PUBLISH_PORT=3000
DATABASE_URL=postgresql://worksupportportal:MyDbPassword2026@localhost:5432/worksupportportal
DJANGO_SECRET_KEY=ここに長いランダム文字列
DJANGO_ALLOWED_HOSTS=192.168.3.196
DJANGO_CSRF_TRUSTED_ORIGINS=http://192.168.3.196:3000
AUTH_URL=http://192.168.3.196:3000
ORACLE_PASSWORD=担当者から受け取ったOracleパスワード
AUTH_DEV_MODE=false
DJANGO_DEBUG=false
```

> **重要:** 同じキーを2回書かないこと。`.env.production.example` をそのまま編集すると `APP_PUBLISH_PORT=80` と `=3000` が両方残りやすい。**§10.3 では `APP_PUBLISH_PORT=3000` のみ**にし、`AUTH_URL` / `DJANGO_CSRF_TRUSTED_ORIGINS` も **`:3000` 付きの行だけ**残す。

**ポイント:**

| 項目 | 注意 |
|------|------|
| `POSTGRES_PASSWORD` | ステップ 3 で PostgreSQL に設定したパスワードと **同じ** |
| `DATABASE_URL` | 中のパスワードも **同じ** |
| `AUTH_URL` / `CSRF` | **`:3000` を付ける**（付けないとログインでエラー） |
| `change-me` | そのまま残さない |

秘密鍵の例（CMD で1行生成）:

```cmd
powershell -NoProfile -Command "[Convert]::ToBase64String([byte[]](1..50 | ForEach-Object { Get-Random -Maximum 256 }))"
```

表示された1行を `DJANGO_SECRET_KEY=` の右に貼り付ける。

**メモ帳で「保存」してから閉じる。**

### ステップ 5.5：Oracle Instant Client を入れる（5年9組・検収書比較を使う場合）

開発 Docker と同じ Oracle（`192.168.3.204` / `EXPJ`）へ接続するには、Windows 直実行では **Oracle Instant Client** と **Thick モード** が必要です。  
接続テストで `DPY-3015: password verifier type ... is not supported ... in thin mode` と出たら **必須** です。

1. [Oracle Instant Client for Windows](https://www.oracle.com/database/technologies/instant-client/winx64-64-downloads.html) から **Basic Light**（または Basic）の **64bit** ZIP をダウンロード（開発 Docker と同じ **21.x** 推奨）。
2. ZIP を **`C:\oracle\instantclient_21_13`** などに展開（パスに **空白を入れない**）。
3. `.env.production` に次を追加（パスは展開先に合わせる）:

```env
ORACLE_THICK_MODE=true
ORACLE_CLIENT_LIB_DIR=C:\oracle\instantclient_21_13
```

4. 接続確認:

```cmd
cd /d C:\Application\WorkSupportPortal
.venv\Scripts\python manage.py shell -c "from apps.gonenkukumi.infrastructure.oracle.client import list_customers; print(list_customers()[:5])"
```

得意先コードのリストが表示されれば OK。

> ログイン・メニューだけ使う場合は PostgreSQL のみで動きますが、**5年9組・検収書比較・在庫発注アラート** は Oracle 接続が必要です。

### ステップ 7：データベースの表を作る（migrate）

**まず接続設定を確認する:**

```cmd
cd /d C:\Application\WorkSupportPortal
.venv\Scripts\python manage.py check_production_env
```

`PostgreSQL 設定 OK` と出れば次へ。`SQLite が使われています` と出た場合は **ステップ 5 の `.env.production` を見直す**（下記「よくある失敗」参照）。

```cmd
cd /d C:\Application\WorkSupportPortal
.venv\Scripts\python manage.py migrate
```

`Applying ... OK` のような表示がたくさん出れば OK。  
`connection refused` と出たら PostgreSQL が起動していない。Windows のサービスで **postgresql** を開始する。

**migrate 前の確認（PostgreSQL に繋がっているか）:**

```cmd
cd /d C:\Application\WorkSupportPortal
.venv\Scripts\python manage.py shell -c "from django.conf import settings; print(settings.DATABASES['default']['ENGINE'])"
```

表示が `django.db.backends.postgresql` であること。`sqlite3` の場合は `.env.production` の `DATABASE_URL` が未設定か、VM の `config\settings.py` が古い（`load_dotenv` 未対応）。`git pull origin master` で更新する。

**`near "CONSTRAINT": syntax error`（sqlite3）が出た場合:**

Django が **PostgreSQL ではなく SQLite**（`db.sqlite3`）に接続しています。

1. **ファイル名** — `.env.production` であること（`.env.production.txt` になっていないか。エクスプローラーで「拡張子を表示」を ON にして確認）
2. **場所** — `C:\Application\WorkSupportPortal\.env.production`（`manage.py` と同じフォルダ）
3. **`DATABASE_URL=`** — 行頭に `#` が無いこと
4. **`config\settings.py`** — `load_dotenv` があること。無ければ `git pull` または開発 PC からコピー
5. 誤って作った **`db.sqlite3`** を削除してから migrate を再実行

**すぐ試す回避策（CMD で migrate の直前に1行）:**

```cmd
set DATABASE_URL=postgresql://worksupportportal:パスワード@localhost:5432/worksupportportal
.venv\Scripts\python manage.py migrate
```

（`パスワード` は `POSTGRES_PASSWORD` と同じ値）

## 13. ローカルとの主な違い（整理）

| 項目 | ローカル（Docker 開発） | 本番 |
|------|-------------------------|------|
| URL | `http://localhost:3100` 等 | **`http://192.168.3.196`** |
| 実行環境 | Docker Desktop（開発 PC） | **§10 Docker** / **§10.3 Windows 直実行** / **§10.4 Linux VM** |
| Django | `runserver`（開発用 Dockerfile） | **gunicorn**（Docker）または **waitress**（Windows 直実行） |
| `AUTH_DEV_MODE` | `true` 可（開発ログイン表示） | **`false` 必須** |
| 認証 | desknet + 開発ログイン | **desknet のみ**（現行） |
| 秘密情報 | `.env.local` / Compose 環境 | サーバー専用ファイル・シークレット |
| DB | Compose 内 Postgres | 運用 DB |
| ソースマウント | あり（ホットリロード） | **なし** |
| TLS | 省略可 | 社内 HTTP 可。ポリシーに応じて HTTPS |
