## 2. 本番の前提（仕様との対応）

| 項目 | 本番での想定 |
|------|----------------|
| 本番 URL | **`http://192.168.3.196`**（ユーザーがブラウザで開くオリジン。`AUTH_URL` / `NEXTAUTH_URL` と一致させる） |
| 公開 | **社内 LAN** から上記 URL でアクセス。HTTPS 終端（nginx 等）を追加する場合は **その公開 URL** に合わせて Entra のリダイレクト URI と `AUTH_URL` を更新する |
| アプリ | **Next.js**（本番は `next build` の成果物を `next start` で実行する構成を推奨） |
| リバースプロキシ | **nginx**（TLS 終端またはバックエンドまで HTTP） |
| ポータル DB | **PostgreSQL**（本番はマネージド DB や専用 VM の利用を推奨） |
| 基幹 | **Oracle** への **読み取りのみ**、**同一セグメント** 到達（仕様書 3.3・5.5） |
| 認証 | **Microsoft Entra ID**、本番 URL を **リダイレクト URI** に登録 |
| 開発専用 | **`AUTH_DEV_MODE`** は **本番では設定しない**（`false` または未定義） |

ローカル用の `docker-compose.yml` は **開発向け**（ソースマウント、`next dev`）のため、本番では **別ファイル**（例: `docker-compose.prod.yml`）または **イメージレジストリ＋マニフェスト** で運用する。

## 3. 移植前に揃えるもの

| 区分 | 内容 |
|------|------|
| **ソース** | 本番用にタグ付けした Git リビジョン（ブランチ／コミット） |
| **本番 URL** | **`http://192.168.3.196`**（ポートを付ける運用なら `http://192.168.3.196:<ポート>`）。`AUTH_URL` / `NEXTAUTH_URL` のオリジンと一致させる |
| **秘密情報** | `AUTH_SECRET`、Entra ID のクライアントシークレット、PostgreSQL 接続、Oracle 読み取りユーザー等。**リポジトリに含めない** |
| **Entra ID** | 本番の **リダイレクト URI**（後述）、必要なら **証明書ベース認証** や **グループ／ロール** の整理 |
| **ネットワーク** | 本番アプリサーバから **Oracle**、**PostgreSQL** への到達（ポート・ファイアウォール） |
| **TLS 証明書** | nginx または LB で利用する証明書・鍵の配置方針 |

## 4. 本番用コンテナイメージの考え方

開発用 `Dockerfile` は `npm run dev` 向けのため、本番では次のいずれかとする。

1. **マルチステージ Dockerfile**  
   - ステージ1: `npm ci` → `npm run build`  
   - ステージ2: 本番用イメージに `.next/standalone`（Standalone 出力を使う場合）または `next start` 用ファイルをコピーし、`CMD ["npm", "run", "start"]`  
2. **CI で `next build` し、成果物のみをランタイムイメージにコピー** するパイプライン

本番 `docker-compose`（例）では **ソースのボリュームマウントを行わない**、`NODE_ENV=production` とする。

**Standalone 出力**を使う場合は `next.config.ts` に `output: "standalone"` を追加する（実装時に検討）。

## 5. 環境変数（本番）

リポジトリの **`.env.example`** をベースに、本番専用の値を **サーバー上の環境ファイル** または **シークレットストア** に設定する。

| 変数 | 説明 |
|------|------|
| `NODE_ENV` | `production` |
| `AUTH_SECRET` | 十分に長いランダム値（ローカルと別にする） |
| `AUTH_URL` / `NEXTAUTH_URL` | **本番のオリジン**（例: **`http://192.168.3.196`**。HTTPS 終端後の URL を使う場合は `https://...` に合わせる） |
| `AUTH_MICROSOFT_ENTRA_ID_ID` | Entra アプリ登録のクライアント ID |
| `AUTH_MICROSOFT_ENTRA_ID_SECRET` | クライアントシークレット（ローテーション手順を別途） |
| `AUTH_MICROSOFT_ENTRA_ID_ISSUER` | テナントの issuer URL（例: `https://login.microsoftonline.com/<tenant-id>/v2.0`） |
| `DATABASE_URL` | 本番 PostgreSQL の接続文字列 |
| Oracle 関連 | 接続情報（ホスト・ポート・SID・ユーザー ID）は [`アプリケーション仕様書.md` §8.2.1](./アプリケーション仕様書.md#821-接続パラメータ確定) を参照。変数名は実装で定義。**パスワードはシークレット**。**読み取り専用**アカウント |
| **`AUTH_DEV_MODE`** | **未設定** または `false`（開発用ログインを無効化） |

## 6. Microsoft Entra ID（本番）

1. Azure ポータルで **アプリ登録** を開く（本番用アプリ、または環境別に分割）。  
2. **リダイレクト URI（Web）** に次を登録する（Auth.js / プロバイダ ID に合わせる）。  
   - 本環境: **`http://192.168.3.196/api/auth/callback/microsoft-entra-id`**（ポート付き公開ならオリジンに合わせて変更）  
3. **フロントチャネルのログアウト URL** 等が必要なら組織ポリシーに従う。  
4. **クライアントシークレット** の有効期限・更新手順を運用ドキュメントに残す。  
5. ステージング URL がある場合は、**別のリダイレクト URI** として追加する。

---

## 7. PostgreSQL（本番）

1. 本番用 **データベース・ユーザー・パスワード** を作成する。  
2. アプリ起動前に **マイグレーション**（Prisma 等）を適用する。  
3. **バックアップ**（スナップショット・ポイントインタイム復旧）をインフラ標準に合わせる。  
4. 接続は **TLS** が使える場合は有効化を検討する。

---

## 8. Oracle（基幹・読み取り）

1. 仕様どおり **SELECT のみ** の権限を付与した **専用ユーザー** を使う。  
2. 本番アプリサーバから **同一セグメント／ルーティング** で到達できることをネットワーク担当と確認する。  
3. **リスナーポート**・**TNS**・**接続プール**（必要なら）をアプリ実装に合わせて設定する。

### 8.1 接続パラメータ

接続情報（ホスト・ポート・SID・ユーザー ID）の確定値は **[`アプリケーション仕様書.md` §8.2.1](./アプリケーション仕様書.md#821-接続パラメータ確定)** を参照する（このドキュメントには値を再掲しない）。実装では **パスワードをリポジトリに含めず**、サーバの環境変数またはシークレットに設定する。

環境変数名は実装に従う（`ORACLE_HOST`、`ORACLE_PORT`、`ORACLE_SID`、`ORACLE_USER`、`ORACLE_PASSWORD`、`ORACLE_CLIENT_LIB_DIR` など。詳細は `.env.example` および `src/infrastructure/oracle/config.ts`）。

---

## 9. nginx（本番）

1. **TLS**: `listen 443 ssl`、証明書パス、`ssl_protocols` 等を組織基準に合わせる。  
2. **リバースプロキシ**: `proxy_pass` をアプリ（例: `http://127.0.0.1:3000` または Docker ネットワーク内の `app:3000`）へ。  
3. **ヘッダ**: `X-Forwarded-Proto`、`Host` を適切に渡し、`AUTH_URL` が **ユーザーに見える URL**（`http://192.168.3.196` または HTTPS 終端後の URL）と一致するようにする。  
4. **HTTP→HTTPS リダイレクト** は、HTTPS を運用する場合に設定する。  
5. ローカルの `docker/nginx/local.conf` は **開発用** のため、本番用は **別ファイル** で管理する。

---

## 10. デプロイ作業の流れ（例：単一サーバ＋Docker）

以下は **一例** である。実際のコマンドは OS・オーケストレーションに合わせて置き換える。

1. **サーバー準備**  
   - OS アップデート、Docker / Docker Compose のインストール、時刻同期（NTP）。  
2. **アーティファクトの配置**  
   - Git からクローン、または CI が配置したイメージを pull。  
3. **本番用 Compose またはスタック定義**  
   - `postgres`（または外部 DB の場合はアプリのみ）、`app`（本番イメージ）、`nginx`。  
4. **秘密情報の注入**  
   - `/etc/.../env` や Docker secrets、クラウドのパラメータストア等。**Git に含めない**。  
5. **DB マイグレーション**  
   - コンテナ内または専用ジョブで `prisma migrate deploy` 等（採用時）。  
6. **起動**  
   - `docker compose -f docker-compose.prod.yml up -d` 等。  
7. **疎通確認**  
   - 後述チェックリスト。  
8. **監視・ログ**  
   - nginx アクセスログ、アプリの stdout、必要なら APM を接続。

## 11. リリース後の確認チェックリスト

- [ ] ブラウザで **本番 URL**（例: **`http://192.168.3.196`**）が開く  
- [ ] **Microsoft ログイン**が完了し、メニューに遷移できる  
- [ ] **未ログイン**で保護 URL にアクセスするとログインへ誘導される（仕様 6.4）  
- [ ] **開発用ログイン**が表示されない／動作しない（`AUTH_DEV_MODE` 無効）  
- [ ] **PostgreSQL** への読み書きが期待どおり（該当機能実装後）  
- [ ] **Oracle** 参照が期待どおり（該当機能実装後、ネットワーク・権限）  
- [ ] **ログアウト**後、保護ページに入れない

## 12. ロールバックの考え方

- **コンテナイメージ**を前バージョンに戻す。  
- **DB マイグレーション**を伴う場合は、**下位互換**と **復旧手順**（バックアップからのリストア）を事前に決める。  
- Entra／証明書の変更とアプリの変更を **同一リリース** にまとめすぎない（切り戻ししやすくする）。

## 13. ローカルとの主な違い（整理）

| 項目 | ローカル | 本番 |
|------|----------|------|
| URL | `http://localhost:3000` 等 | **`http://192.168.3.196`**（HTTPS 運用時はその URL） |
| Next.js | 多くの場合 `next dev` | `next build` + `next start`（または同等） |
| `AUTH_DEV_MODE` | 開発時のみ `true` 可 | **無効** |
| 秘密情報 | `.env.local` | サーバー専用ストア・権限付きファイル |
| DB | ローカル／Compose 内 Postgres | マネージドまたは運用 DB |
| TLS | 省略可 | 社内 HTTP のみの場合は任意。外部公開やポリシーで必須なら HTTPS 終端を行う |
