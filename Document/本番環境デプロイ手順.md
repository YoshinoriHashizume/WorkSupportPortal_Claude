## 2. 本番の前提（仕様・実装との対応）

| 項目 | 本番での想定 |
|------|----------------|
| サーバー | **Windows Server 仮想マシン**。**仮想サーバーで Docker が使えない場合は §10.3（Python 直実行）**。Docker が使える場合は WSL2 Ubuntu + Docker Engine（§10）または Linux VM（§10.4） |
| 本番 URL | **`http://192.168.3.196`**（ユーザーがブラウザで開くオリジン。`AUTH_URL` 等と一致させる） |
| 公開 | **社内 LAN** から上記 URL でアクセス。HTTPS 終端（nginx / IIS 等）を追加する場合は **その公開 URL** に合わせて `AUTH_URL`・`DJANGO_CSRF_TRUSTED_ORIGINS` を更新する |
| アプリ | **Python 3.12 + Django**。Docker 本番は **`entrypoint.sh`** が `DEBUG=false` 時に **gunicorn（`:8000`）** を起動。Windows 直実行は **waitress（`:3000`）** |
| リバースプロキシ | 本番 Compose は **nginx（ホスト `:80` → `web-app:8000`）**。Windows 直実行は IIS / ポート公開（`:3000`）も可 |
| ポータル DB | **PostgreSQL**（Compose サービス **`db`**、または専用 VM / マネージド DB） |
| 基幹 | **Oracle** への **読み取りのみ**、**同一セグメント** 到達（仕様書 3.3・8.2.1） |
| 認証（現行） | **desknet's NEO Login API**（`AUTH_PROVIDER=desknet`）。社員番号 + desknet パスワードでログイン |
| 認証（将来） | **Microsoft Entra ID**（Authlib 連携は未実装。切替時は `Microsoft認証（Entra ID）構築手順.md` を参照） |
| 開発専用 | 本番では **`AUTH_DEV_MODE` を `false` または未設定** とし、開発者専用ログインを **表示・実行不可** にする |

ローカル用の `docker-compose.devcontainer.yaml` は **開発向け**（ソースマウント、`runserver`、`AUTH_DEV_MODE=true` 等）のため、本番では **別ファイル**（例: `docker-compose.production.yaml`）または **イメージレジストリ＋マニフェスト** で運用する。

### 2.1 仮想サーバー（VM）上での制約

本番 VM が **Hyper-V / VMware 等の仮想マシン** の場合、次の制約がある。

| 方式 | VM 上で動くか | 備考 |
|------|---------------|------|
| **Docker Desktop** | 多くの場合 **×** | Engine が `Starting...` で止まる |
| **WSL2 + Docker Engine** | **ホスト側でネストした仮想化が有効なら ○** | 無効だと WSL2 / Docker が起動しない |
| **Linux 専用 VM + Docker Engine** | **○（いちばん安定）** | 物理 or ネスト仮想化済み Linux VM |
| **Windows 直実行（§10.3）** | **○** | Docker 不要。Python + PostgreSQL + waitress |

**ネストした仮想化** が無効な Windows Server VM では、**§10.3（Docker なし）** または **別途 Linux VM（§10.4）** を選ぶ。インフラ担当に VM の **nested virtualization** 有効化を依頼できる場合は §10 も再検討できる。

## 4. 本番用コンテナイメージの考え方

`docker/django/Dockerfile` とルートの **`entrypoint.sh`** を本番でも使う。

1. **依存パッケージ**  
   - ランタイムの**宣言**の正: **`requirements-prod.txt`**
   - Docker イメージのインストールの正: **`requirements-docker.lock.txt`**（再生成は `scripts/generate_requirements_lock.sh`）
   - Docker イメージ: **`requirements-docker.txt`**（prod + gunicorn + 開発依存）  
   - Windows 直実行: **`requirements-windows-prod.txt`**（prod + waitress）  
2. **起動**  
   - Compose サービス名は **`web-app`** / **`db`** / **`nginx`**  
   - `DJANGO_SETTINGS_MODULE=config.settings.production`、`DEBUG=false` のとき entrypoint が **gunicorn `0.0.0.0:8000`** を起動  
   - nginx がホスト **`:80`** を受け、`web-app:8000` へ転送  
3. **ソース**  
   - 本番 Compose は **リポジトリ全体の bind マウントをしない**（イメージに `COPY` した `src/` を正とする）  
4. **環境変数**  
   - テンプレート: **`.env.production.example`** → サーバー上の **`.env.production`**  
   - 起動は必ず **`docker compose ... --env-file .env.production`**（`src/scripts/wsl/start-production.sh` が実施）

`AUTH_DEV_MODE=true` は本番禁止。`bootstrap_local_dev` は実行しない。

### 4.1 静的ファイル（CSS / JS）

本番 Compose では **WhiteNoise**（`DEBUG=false` 時）と **nginx の `/static/`**（`static` ボリューム）を利用する。entrypoint が `collectstatic` を実行する。

## 5. 環境変数（本番）

リポジトリの **`.env.example`** をベースに、本番専用の値を **サーバー上の環境ファイル** または **シークレットストア** に設定する。Django が参照するのは **`DJANGO_DEBUG`**（`DEBUG` 単体は未使用）。

### 5.1 Django / 公開

| 変数 | 説明 |
|------|------|
| `DJANGO_DEBUG` | **`false`**（必須） |
| `DJANGO_SECRET_KEY` | 十分に長いランダム値（ローカルと別にする） |
| `DJANGO_ALLOWED_HOSTS` | 本番ホスト。例: `192.168.3.196` |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | 本番オリジン。HTTP の例: `http://192.168.3.196`。HTTPS 終端時は `https://...` |
| `AUTH_URL` | **本番のオリジン**（例: **`http://192.168.3.196`**） |
| `DATABASE_URL` | 本番 PostgreSQL の接続文字列 |

### 5.2 認証（現行: desknet's NEO）

| 変数 | 説明 |
|------|------|
| `AUTH_PROVIDER` | **`desknet`**（デフォルト。本番リリース時） |
| `DESKNETS_LOGIN_URL` | desknet Login API URL（例: `https://maruei01.dn-cloud.com/cgi-bin/dneo/dneo.cgi`） |
| `DESKNETS_TIMEOUT_SECONDS` | API タイムアウト秒（例: `10`） |
| `DESKNETS_ASSET_INVENTORY_LOGIN_ID` | **資産棚卸結果** AppSuite API 用 desknet's 社員番号（棚卸関連アプリの参照権限を持つアカウント） |
| `DESKNETS_ASSET_INVENTORY_PASSWORD` | 上記アカウントのパスワード |
| `AUTH_DEV_MODE` | **未設定または `false`**。`true` にすると開発ログイン・`bootstrap_local_dev` が有効になり **本番禁止** |

### 5.3 認証（将来: Microsoft Entra ID）

Entra 切替実装後に設定する。現行コードではログインエンドポイントは **予約のみ**（未接続）。

| 変数 | 説明 |
|------|------|
| `AUTH_MICROSOFT_ENTRA_ID_ID` | Entra アプリ登録のクライアント ID |
| `AUTH_MICROSOFT_ENTRA_ID_SECRET` | クライアントシークレット |
| `AUTH_MICROSOFT_ENTRA_ID_ISSUER` | テナント issuer（例: `https://login.microsoftonline.com/<tenant-id>/v2.0`） |

### 5.4 Oracle / アプリ連携

接続情報（ホスト・ポート・SID・ユーザー ID）は [`アプリケーション仕様書.md` §8.2.1](./アプリケーション仕様書.md#821-接続パラメータ確定) を参照。**パスワードはシークレット**。**読み取り専用**アカウントを使う。

| 変数 | 説明 |
|------|------|
| `ORACLE_USE_MOCK` | **`false`**（本番） |
| `ORACLE_HOST` / `ORACLE_PORT` / `ORACLE_SID` | 仕様書 §8.2.1 |
| `ORACLE_USER` / `ORACLE_PASSWORD` | 読み取り専用ユーザー |
| `ORACLE_THICK_MODE` | Docker Linux イメージでは **`true`** 推奨（Instant Client 同梱）。§10.3 Windows では **`true` 必須**（`DPY-3015` 対策） |
| `ORACLE_CLIENT_LIB_DIR` | Instant Client の展開先（Docker 例: `/opt/oracle/instantclient_21_13`、Windows 例: `C:\oracle\instantclient_23_0`） |
| `ORACLE_CONNECT_TIMEOUT_SECONDS` | 接続タイムアウト（例: `5`） |

**現行リリースでは desknet's NEO 認証で公開する。** Entra ID はアプリ側未実装のため、Azure 登録だけではログインできない。

Entra へ切り替える際は [`Microsoft認証（Entra ID）構築手順.md`](./Microsoft認証（Entra ID）構築手順.md) に従い、次を行う。

2. **リダイレクト URI（Web）** に **`http://192.168.3.196/api/auth/callback/microsoft-entra-id`** を登録（ポート付き公開ならオリジンに合わせて変更）。実装の URL パスは `application/identity/urls.py` と一致させる。  
3. Authlib 連携の **アプリ実装リリース** 後、`AUTH_PROVIDER` の切替とチェックリスト（§11）を Entra 用に更新する。

## 7. PostgreSQL（本番）

1. 本番用 **データベース・ユーザー・パスワード** を作成する。  
2. 初回起動前または起動時に **マイグレーション**（`python src\manage.py migrate`）を適用する。  
3. **バックアップ**（スナップショット等）をインフラ標準に合わせる。在庫発注アラートの確認状態・SLIMS 取込データ等が蓄積される。  
4. 接続は **TLS** が使える場合は有効化を検討する。
5. **容量監視**の対象に `portal_menuusagelog`（メニュー利用ログ）を加える。手順は §7.2 を参照。

### 7.1 初回管理者

desknet ログインで **初めて** 入ったユーザーは **承認待ち** となり、メニューが使えない。公開前または公開直後に、次のコマンドで **最初の管理者を1名** 用意する（§10.3 ステップ 8 参照）。

**Windows 直実行（§10.3）** の CMD 例:

```cmd
cd /d C:\Application\WorkSupportPortal
.venv\Scripts\python src\manage.py bootstrap_production_admin --username 51705 --last-name 橋爪 --first-name 良典
```

**Docker（§10.0）** の WSL Ubuntu 例:

```bash
cd /mnt/c/Application/WorkSupportPortal
bash src/scripts/wsl/bootstrap-production-admin.sh 51705 橋爪 良典
```

または:

```bash
docker compose -f docker-compose.production.yaml --env-file .env.production exec web-app \
  bash -lc 'cd /django_app/src && python manage.py bootstrap_production_admin --username 51705 --last-name 橋爪 --first-name 良典'
```
- `--username` は **desknet's NEO の社員番号** と同じ値にする。  
- 作成後、その社員番号と **desknet パスワード** でログインする（ポータル専用パスワードは不要）。  
- `bootstrap_local_dev` は **本番では使用しない**。

### 7.2 容量監視（メニュー利用ログ）

`portal_menuusagelog`（**メニュー利用ログ**）は、ポータルのメニュー表示・出力操作を 1 件ずつ追記するテーブルで、**利用状況** 画面の集計元になる。**保持期間は無期限**（古いログを削除する運用は行わない）ため、単調に増加する。容量監視の対象に加える。

| 項目 | 実測値（50 万件） | 1 行あたり |
|------|------------------|-----------|
| 本体（heap） | 36.5 MB | 76.6 バイト |
| 索引（4 本） | 60.9 MB | 127.7 バイト |
| **合計** | **97.4 MB** | **204.3 バイト** |

想定利用量は 1 日約 2,000 件・年約 50 万件のため、**年間およそ 100MB** の増加を見込む。索引 4 本の合計が本体を上回るため、容量は索引が支配的である（設計の根拠は [`利用状況 機能設計書 §5.6`](../src/application/portal/docs/spec/01_usage-status/design.md) を参照）。

**確認手順**（月次程度で実施し、想定を大きく上回る増え方をしていないか確認する）:

```sql
SELECT
  pg_size_pretty(pg_total_relation_size('portal_menuusagelog')) AS 合計,
  pg_size_pretty(pg_table_size('portal_menuusagelog'))          AS 本体,
  pg_size_pretty(pg_indexes_size('portal_menuusagelog'))        AS 索引,
  (SELECT count(*) FROM portal_menuusagelog)                    AS 件数;
```

**Windows 直実行（§10.3）** の CMD 例:

```cmd
psql -U worksupportportal -d worksupportportal -c "SELECT pg_size_pretty(pg_total_relation_size('portal_menuusagelog')), (SELECT count(*) FROM portal_menuusagelog);"
```

**Docker（§10.0）** の例:

```bash
docker compose -f docker-compose.production.yaml --env-file .env.production exec db \
  psql -U worksupportportal -d worksupportportal -c "SELECT pg_size_pretty(pg_total_relation_size('portal_menuusagelog')), (SELECT count(*) FROM portal_menuusagelog);"
```

- 年 100MB を大きく超えて増える場合は、利用状況の記録対象または索引構成の見直しを開発担当に依頼する。
- ログを削除する運用は行わない。ディスク使用量は §7 の 3.（バックアップ）とあわせてインフラ標準の監視に載せる。

## 9. リバースプロキシ（任意）

社内 HTTP のみ（`http://192.168.3.196`）で公開する場合、Docker の **ポートマップのみ** でもよい。HTTPS や複数サービス統合時は nginx / IIS 等を前段に置く。

1. **TLS**: 組織基準に合わせて証明書を設定する。  
2. **アプリへの転送**: nginx は Compose 内で `web-app:8000` へ `proxy_pass`。Windows 直実行では IIS ARR 等で `http://127.0.0.1:3000` へ。
3. **ヘッダ**: `X-Forwarded-Proto`、`Host` を渡し、`AUTH_URL` が **ユーザーに見える URL** と一致するようにする。  
4. **静的ファイル**: `/static/` を `staticfiles/` から配信する設定を含める（§4.1）。  
5. 本番用設定ファイルはリポジトリ外または `deploy/nginx/` 等で **別管理** する（現行リポジトリに nginx 設定は含まれない）。

## 10. デプロイ作業の流れ（Windows Server VM + WSL2 Ubuntu + Docker Engine）

**Docker / WSL が使える場合の手順。** 仮想サーバーで WSL2 が動かない場合は **§10.3（Windows 直実行）** を使う。Linux VM を用意できる場合は **§10.4** が最も安定する。

| 項目 | 値 |
|------|-----|
| Windows 作業フォルダ | `C:\Application\WorkSupportPortal` |
| WSL（Ubuntu）からのパス | `/mnt/c/Application/WorkSupportPortal` |
| リポジトリ名 | **WorkSupportPortal** |

### 10.0 手順一覧

| # | どこで | 作業 |
|---|--------|------|
| 1 | Windows（管理者 PowerShell） | WSL2 + Ubuntu 導入（§10.0.1） |
| 2 | Windows（CMD） | ソース `git clone`（§10.0.2） |
| 3 | Ubuntu（WSL） | Docker Engine 導入（§10.0.3） |
| 4 | Ubuntu または Windows | `.env.production` 作成（§10.0.4） |
| 5 | Ubuntu（WSL） | `docker compose` で起動（§10.0.5） |
| 6 | Windows（CMD） | ファイアウォール TCP 80（§10.0.6） |
| 7 | Ubuntu（WSL） | 初回管理者（§10.0.7） |
| 8 | ブラウザ | §11 チェックリスト |

> **Docker Desktop を既に入れている場合:** タスクトレイから **Quit Docker Desktop** し、WSL の `docker-desktop` と競合しないようにする。

#### §10.0.1 WSL2 + Ubuntu を入れる（Windows・初回のみ）

**管理者 PowerShell** で実行:

```powershell
powershell -ExecutionPolicy Bypass -File C:\Application\WorkSupportPortal\src\scripts\windows\Install-WslUbuntu.ps1
```

スクリプトが無い場合は手動:

```powershell
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart
wsl --install -d Ubuntu
```

**VM を再起動** → スタートメニューから **Ubuntu** を開き、Linux ユーザー名・パスワードを設定。

確認（Windows CMD）:

```cmd
wsl --status
wsl -l -v
```

`Ubuntu` が **VERSION 2** であること。

#### §10.0.2 ソースを Windows に取得（git clone）

**CMD** で実行:


### ステップ 5：設定ファイル `.env.production` を作る

これが **本番の設定ファイル** です。パスワードなどを書きます。**Git には載せません。**


メモ帳が開いたら、**次の行を必ず書き換える**（例。IP とパスワードは環境に合わせる）:

```env
POSTGRES_PASSWORD=MyDbPassword2026
```

| 項目 | 注意 |
|------|------|

| `DATABASE_URL` | 中のパスワードも **同じ** |
| `AUTH_URL` / `CSRF` | **`:3000` を付ける**（付けないとログインでエラー） |
| `change-me` | そのまま残さない |

```cmd
powershell -NoProfile -Command "[Convert]::ToBase64String([byte[]](1..50 | ForEach-Object { Get-Random -Maximum 256 }))"
```

表示された1行を `DJANGO_SECRET_KEY=` の右に貼り付ける。

### ステップ 7：データベースの表を作る（migrate）

**まず接続設定を確認する:**

```cmd
cd /d C:\Application\WorkSupportPortal
.venv\Scripts\python src\manage.py check_production_env
```

`PostgreSQL 設定 OK` と出れば次へ。`SQLite が使われています` と出た場合は **ステップ 5 の `.env.production` を見直す**（下記「よくある失敗」参照）。

```cmd
cd /d C:\Application\WorkSupportPortal
.venv\Scripts\python src\manage.py migrate
```

`Applying ... OK` のような表示がたくさん出れば OK。  
`connection refused` と出たら PostgreSQL が起動していない。Windows のサービスで **postgresql** を開始する。

**migrate 前の確認（PostgreSQL に繋がっているか）:**

```cmd
cd /d C:\Application\WorkSupportPortal
.venv\Scripts\python src\manage.py shell -c "from django.conf import settings; print(settings.DATABASES['default']['ENGINE'])"
```

表示が `django.db.backends.postgresql` であること。`sqlite3` の場合は `.env.production` の `DATABASE_URL` が未設定か、VM の `config\settings.py` が古い（`load_dotenv` 未対応）。`git pull origin master` で更新する。

**`near "CONSTRAINT": syntax error`（sqlite3）が出た場合:**

Django が **PostgreSQL ではなく SQLite**（`db.sqlite3`）に接続しています。

1. **ファイル名** — `.env.production` であること（`.env.production.txt` になっていないか。エクスプローラーで「拡張子を表示」を ON にして確認）
2. **場所** — `C:\Application\WorkSupportPortal\.env.production`（リポジトリルート。`src\manage.py` の親）
3. **`DATABASE_URL=`** — 行頭に `#` が無いこと
4. **`config\settings.py`** — `load_dotenv` があること。無ければ `git pull` または開発 PC からコピー
5. 誤って作った **`db.sqlite3`** を削除してから migrate を再実行

**すぐ試す回避策（CMD で migrate の直前に1行）:**

```cmd
set DATABASE_URL=postgresql://worksupportportal:パスワード@localhost:5432/worksupportportal
.venv\Scripts\python src\manage.py migrate
```

（`パスワード` は `POSTGRES_PASSWORD` と同じ値）

| 表示 | 対処 |
|------|------|

| `DATABASE_URL が未設定` | `.env.production` に `DATABASE_URL=postgresql://...` を追加 |
| `check_production_env` / `SQLite` | ステップ 7 の DB 接続確認 |
| `migrate が失敗` | PostgreSQL サービス起動、`set DATABASE_URL=...` 後に再実行 |

## 10.5 既存環境の更新手順（Docker 不要・2 回目以降）

**すでに §10.3 で公開済みの VM に、新しい変更を反映する手順。** 初回構築は §10.3 を使う。

Python・PostgreSQL・`.env.production`・`.venv` は作り直さない。**ソースを更新して再起動するだけ**で、
`migrate` と `collectstatic` は起動スクリプトが自動で実行する。

### 全体の流れ

```
A. 開発 PC: develop を master にマージして push     ← 開発担当
B. VM: アプリを停止する
C. VM: PostgreSQL をバックアップする                 ← マイグレーションがある場合は必須
D. VM: git pull で新しいソースを取得する
E. VM: 依存ライブラリを更新する（requirements が変わった場合のみ）
F. VM: 起動スクリプトを実行する（migrate + collectstatic + 起動）
G. ブラウザで確認し、§11 / §11.2 のリリース後作業を実施する
```

### ステップ A：開発 PC で `master` を更新する（開発担当）

本番が見るのは **`master`** である。開発は `develop` で進めるため、`develop` にしかない変更は本番に出ない。

```powershell
git switch develop
git pull
git push                      # develop を最新にする
git switch master
git pull
git merge --no-ff develop
git push origin master
```

`git log --oneline origin/master -1` で、意図したコミットが `master` の先頭に来たことを確認する。

> **先に全テストを通すこと。** `docker compose -f docker-compose.devcontainer.yaml exec -T web-app bash -lc "cd /django_app/src && python -m pytest application config -q"`

### ステップ B：アプリを停止する

起動中の PowerShell ウィンドウで **Ctrl + C**。ウィンドウを閉じても止まる。

### ステップ C：PostgreSQL をバックアップする

**マイグレーションを伴う更新では必須**（§12）。新しいマイグレーションがあるかは、開発担当に確認するか
`git log --oneline origin/master..origin/develop -- "*/migrations/*"` で分かる。

```cmd
cd /d C:\Application\WorkSupportPortal
"C:\Program Files\PostgreSQL\16\bin\pg_dump.exe" -U worksupportportal -h localhost -F c -f backup_before_release.dump worksupportportal
```

パスを聞かれたら `.env.production` の `POSTGRES_PASSWORD` を入力する。
`backup_before_release.dump` ができていることを `dir backup_before_release.dump` で確認する。

> **列を削除するマイグレーション**（例: `0014_remove_safety_days_watch_months`）が含まれる場合、
> このバックアップが**唯一の戻し手段**になる。必ず取ること。

### ステップ D：ソースを取得する

```cmd
cd /d C:\Application\WorkSupportPortal
git remote -v
git status
git pull origin master
git log --oneline -1
```

> **`git remote -v` の `origin` が `WorkSupportPortal_Claude.git` であることを毎回確認する。**
> `_Claude` なしの `WorkSupportPortal.git` だと、更新したつもりで**古い別リポジトリを引いている**。
> 違っていた場合は §3.1 の手順で付け替える。

> `git status` で**変更されたファイルが出る場合は止まる**。VM 上で直接ファイルを直した跡があるため、
> 内容を開発担当に報告してから進める（`git pull` が競合して失敗する）。
> `.env.production` は Git 管理外なので `git status` には出ない（出たら設定が誤っている）。

### ステップ E：依存ライブラリを更新する（必要な場合のみ）

`requirements-prod.txt` / `requirements-windows-prod.txt` が変わったときだけ実行する。

```cmd
cd /d C:\Application\WorkSupportPortal
.venv\Scripts\pip install -r requirements-windows-prod.txt
```

### ステップ F：起動する

```cmd
cd /d C:\Application\WorkSupportPortal
src\scripts\windows\Start-ProductionApp.cmd
```

画面に次の順で出れば成功。**このウィンドウは閉じない。**

```
==> Loading .env.production
==> Checking database configuration     ← check_production_env
==> Running migrate                     ← 新しいマイグレーションがここで適用される
==> Running collectstatic               ← CSS / JS の更新がここで反映される
==> Starting waitress on 0.0.0.0:3000
```

> **CSS / JS を変更したリリースでは `collectstatic` が成功していることを必ず確認する。**
> ここが飛ばされると、ブラウザが古い CSS / JS を読み続けて画面が変わらない。
> テンプレートの `?v=` （キャッシュバスター）はブラウザ側のキャッシュ対策で、
> `collectstatic` の代わりにはならない。

### ステップ G：確認とリリース後作業

§11 のチェックリストと、**§11.2（該当リリースのアプリ固有作業）** を実施する。

### 更新でつまずいたときの戻し方

| 状況 | 対処 |
|------|------|
| 起動しない・画面が壊れた（**マイグレーションなし**） | `git log --oneline -5` で前のコミットを調べ、`git checkout <前のコミット>` → 再起動 |
| 起動しない・画面が壊れた（**マイグレーションあり**） | §12。`git checkout <前のコミット>` だけでは DB が戻らない。ステップ C のバックアップから `pg_restore` する |
| `migrate failed` | PostgreSQL サービスが起動しているか、`.env.production` の `DATABASE_URL` を確認（§10.3 ステップ 7） |
| `collectstatic failed` | ディスク空き容量と `C:\Application\WorkSupportPortal\src\staticfiles` の書き込み権限を確認 |

### 11.2 在庫発注アラート — 判定結果を保存するリリースでは SLIMS 再取込が必須

**在庫発注アラートの判定の大半は「SLIMS 在庫 CSV の取込時」に計算して集計スナップショットに保存している。**
そのため、**アプリを更新しただけでは新しい判定が画面に出ない。** 更新後に必ず再取込する。

| 取込時に計算・保存するもの | 根拠 |
|---|---|
| 需要予測（V-220）・在庫切れ予測月（V-221）・在庫月数（V-222） | spec/05 |
| **対応区分（S-204）・在庫切れ日（V-232）・発注期限（V-233）** | spec/08（取込時点の在庫・内示・発注残で判定するため**保存する**） |
| 日次出荷（V-234）・日次入荷（V-235）・予定入荷（V-236）＝**在庫シミュレーションの材料** | spec/09 |
| 安全在庫（V-231）・リードタイム（V-225）・発注方式（V-227）・工程の連鎖 | spec/06・08 |

> 流動区分（S-203）だけは**読込のたびに再判定**するので再取込なしでも新しい区分になる。
> ただし在庫なしの行の振り分けには需要予測が必要なため、**再取込しないと流動区分も正しくならない**。

#### 再取込の手順

1. 管理者アカウントで **在庫発注アラート一覧**（`/app/production/inventory-order-alert`）を開く
2. ツールバーの **「SLIMS在庫CSV」** ボタンから、SLIMS からエクスポートした最新の CSV を選ぶ
3. 取込完了メッセージ（件数・自動で未確認に戻した件数）が出るまで待つ
4. 一覧に **対応区分**（発注遅れ / 納期確認 / 要発注 / 要監視 / 対象外）の列と色が出ること、
   行をクリックして**詳細ダイアログに在庫シミュレーションのグラフが描かれる**ことを確認する

> **集計スナップショットは最新 1 世代のみ保持する**（spec/07.2）。取込のたびに古い世代は削除される。
> 取込が失敗した場合は直前の成功分が残るため、画面が空になることはない。

#### 表示だけの変更なら再取込は不要

spec/10（詳細ダイアログの整理）のように**表示の再編だけ**のリリースは、再取込は不要。
代わりに **`collectstatic` が成功していること**（§10.5 ステップ F）と、ブラウザの**強制リロード**
（Ctrl + F5）で CSS / JS が新しくなっていることを確認する。

- [ ] 更新後に SLIMS 在庫 CSV を再取込した

## 12. ロールバックの考え方

- **コンテナイメージ**を前バージョンに戻す（Docker 構成）。Windows 直実行では `git checkout <前のコミット>` → 再起動（§10.5）。  
- **DB マイグレーション**を伴う場合は、**下位互換**と **復旧手順**（バックアップからのリストア）を事前に決める。  
- 認証方式（desknet / Entra）・証明書の変更とアプリの変更を **同一リリース** にまとめすぎない。

### 12.1 列を削除するマイグレーションがある場合（ソースを戻すだけでは復旧しない）

`migrate` には**前に戻せないもの**がある。とくに**列・テーブルを削除する**マイグレーションは、
`git checkout` でソースを戻しても **DB の列は戻らない**。古いコードが消えた列を読もうとして起動に失敗する。

**該当する実例:**

| マイグレーション | 内容 |
|---|---|
| `inventory_order_alert/0014_remove_safety_days_watch_months` | 設定の **安全日数・監視期間** の列を削除（spec/08） |

**そのため、列削除を含むリリースでは次を守る。**

1. **適用前に必ず `pg_dump` を取る**（§10.5 ステップ C）
2. 戻すときは **ソースと DB の両方**を戻す

```cmd
REM 1) アプリを停止（Ctrl + C）してから DB を戻す
"C:\Program Files\PostgreSQL\16\bin\pg_restore.exe" -U worksupportportal -h localhost -d worksupportportal -c backup_before_release.dump

REM 2) ソースを前のコミットに戻す
cd /d C:\Application\WorkSupportPortal
git log --oneline -5
git checkout <戻したいコミット>

REM 3) 起動
src\scripts\windows\Start-ProductionApp.cmd
```

> `pg_restore -c` は**既存のオブジェクトを削除してから復元する**。復元後の DB は
> バックアップを取った時点に戻るため、**その間に入力された確認状態・メモ・お知らせは失われる**。
> 判断に迷う場合は戻さず、前進して直す（修正をリリースする）方が安全なことが多い。

> **逆方向の `migrate <app> <前の番号>` は使わない。** 列削除の巻き戻しは列を作り直すだけで、
> **中のデータは復元されない**ため、バックアップからのリストアが唯一の正しい手段である。
