# 検収書比較 機能仕様書（旧受領書比較 MARI 解析反映版）

本書は、旧 VB.NET WinForms アプリ `ProductionManegementSystem` の **受領書比較(MARI)** 機能を解析し、業務支援ポータル上で **Django + PostgreSQL + Oracle(MARI参照)** に置き換えるための仕様を整理する。

旧プログラムのメニュー、ログイン、TopLink 版、受領書比較以外の機能は本書の対象外とする。

## 2. 概要

### 2.1 目的

客先または取引先から受領する受領書データと、MARI(Oracle) の出荷/売上/受入データを突合し、受領内容が MARI 側と一致しているかを確認する。

旧実装では、次の2種類を同一フォームで扱っていた。

| 区分 | 旧メニュー表示 | `CompareKey` | 旧テーブル接頭辞 | 概要 |
|---|---|---|---|---|
| 完成品 | 完成品受領チェック | `FinishedProduct` | `FINISHED_PRODUCT` | 得意先向け出荷/売上データと客先受領CSVを比較 |
| 支給品 | 支給品受領チェック | `SuppliedParts` | `SUPPLIED_PARTS` | 支給先/外注先の受入データと受領TXTを比較 |

Django 版では、生産管理配下で **5年9組** と同じ階層に **検収書比較** を配置し、検収書比較を展開して **完成品** / **支給品** の各画面を開く構成とする。

### 2.2 旧実装から引き継ぐこと

- MARI は参照のみとする。
- 受領書ファイルを取り込み、MARI データと比較する。
- 比較結果は `〇` / `△` / `×` で管理する。
- 一致判定は、品番・日付・数量の3点一致を基本とする。
- 比較結果は保存できる。
- 保存済みの未完了データは、次回同じ取引先・期間を開いたときにも表示する。
- 比較結果は CSV 出力できる。
- 納品場所/受入場所の対象・除外設定を持つ。

### 2.3 旧実装から引き継がないこと

- WinForms 固有のフォーム遷移、メッセージボックス、ドラッグ&ドロップ専用操作。
- 旧アプリ側のログイン、メニュー、スタッフ表示。
- 印刷ダイアログによる直接印刷。Django 版では CSV/Excel/PDF 出力で代替する方針とする。
- MySQL は使用しない。旧 MySQL 相当の保存データは PostgreSQL に置き換える。
- `TopLinkReceiptForm` 系の TopLink 版受領書比較は対象外とする。

### 4.2 検収書比較画面

旧 `ReceiptForm` 相当。

#### 入力・操作項目

| 項目 | 必須 | 旧実装 | Django版仕様 |
|---|---|---|---|
| 比較区分 | - | メニューで完成品/支給品を分岐 | メニューリンクの `type` で決定。タイトルに完成品/支給品を表示し、画面内では切替しない |
| 比較日 | 必須 | 開始日・終了日の DateTimePicker | 開始日・終了日を指定。開始日は終了日以下、終了日は開始日以上 |
| 得意先 | 必須 | コンボボックス | PostgreSQL の比較対象得意先マスタから選択 |
| 受領書ファイル | 比較時必須 | 一覧へドラッグ&ドロップ | ファイル選択。**比較** ボタンで取込・突合のみ実行し DB には保存しない |
| 表示 | - | - | 保存済み比較結果を DB から読み込んで一覧表示する。未登録の比較プレビューはクリアする。比較結果エリア右上に **ファイル選択** を表示する |
| 比較 | - | ファイル取込後に一覧表示 | 受領書と MARI を突合し、結果をセッションに保持して **未登録** として一覧表示する。**表示** 後は比較結果右上のファイル選択で取込でき、選択と同時に比較を実行する |
| 登録 | - | 確定 | 未登録の比較結果を確認後、比較結果一覧右上の **登録** ボタンから PostgreSQL に保存する |
| 一覧ソート | 任意 | 列ヘッダ操作 | 比較結果一覧の各列見出しクリックで昇順/降順を切り替える（`sort`, `dir` クエリ）。**表示**・**比較**直後の初回表示は **結果** 列の昇順（`×` → `〇` → `△`）でソートする |
| 結果・備考を更新 | - | 既存結果の編集 | 保存済み結果のみ。比較結果一覧右上のボタンから `receipt_flag` と `remarks` を更新する |
| CSV | - | `比較データ.csv` 出力 | 表示中の比較結果を CSV 出力（未登録プレビュー含む） |
| 印刷 | - | DataGridView 直接印刷 | 初期実装では対象外。必要ならPDF/Excel出力で代替 |
| 設定 | - | 歯車アイコンで設定画面を開く | **管理者のみ** 設定画面へ遷移可能 |

#### 状態メッセージ

旧実装の進行状態は次の通り。

| 状態 | 条件 | メッセージ |
|---|---|---|
| 得意先未選択 | 初期状態 | 得意先を選択してください。 |
| ファイル待ち | 取引先と比較日が選択済み | 取引先受領書を上の表枠内にドラッグ＆ドロップして下さい。 |
| 確定待ち | 比較結果表示済み | 問題なければ確定ボタンを押して下さい。 |

Django 版では、比較・登録・更新の **成功時には画面上部メッセージを出さない**（比較結果一覧の表示で状態が分かるため）。**エラー・警告**（ファイル未選択、取込失敗、Oracle エラー等）のみメッセージを表示する。未登録の比較結果は一覧見出しの「（未登録）」で示す。

### 4.3 受入/納品場所設定画面

旧 `ReceiptReceivingForm` 相当。

画面上部にページ見出しを配置し、その下を **左: 得意先追加**（完成品は直送先得意先コード入力あり）、**右: 得意先一覧** の2カラムで横並びに表示する（`receipt-settings-body` の CSS Grid）。一覧エリアは画面の高さいっぱいに表示し、表本体は縦スクロールする。一覧の行をクリックすると、`<dialog>` によるポップアップで当該得意先の受入/納品場所（表形式）の登録・削除、および変更可能な設定（完成品は直送先得意先コード・除外、支給品は除外のみ）を行う。ポップアップ **見出し** に得意先コード・名称を表示し、設定エリアには変更可能な項目のみを縦並びで表示する（得意先の重複表示はしない）。完成品は **直送先得意先コード（ラベル→プルダウン）→ 除外チェック → 更新/削除ボタン** の順。**登録済み得意先コードは変更できない**。ポップアップ内の保存後は、同じ得意先のポップアップを再度開いた状態で一覧に戻る（`supplier_id` クエリ）。

#### 入力・表示項目

| 項目 | 内容 |
|---|---|
| 取引先 | 設定対象の取引先（PostgreSQL に登録したもののみ比較画面に表示） |
| 得意先 | 完成品・支給品とも **3桁** のコード。MARI（Oracle）`M_CUST` の得意先候補から選択する（DB カラム名: `customer_code`）。画面ラベルは **得意先** |
| 子取引先（購買取引先コード） | **支給品設定のみ**。Oracle `M_VEND_CTRL` の **4桁** 取引先候補から選択（`includes/vendor_select.html`）。登録時に `vendor_name` も保存。MARI `VEND_CD IN (...)` と受領TXT 2列目照合に使用 |
| Oracle 購買取引先 | **表示しない**（完成品は実行時に Oracle 解決）。支給品は子取引先（コード・名称）を PostgreSQL に保存 |
| 追加取引先コード | **廃止**（子取引先に統合） |
| 取引先名 | 画面には表示せず、選択した客先コードに対応する `M_CUST.CUST_NAME` を裏側で保存する |
| 直送先得意先コード | **完成品設定のみ**。MARI（Oracle）`M_CUST` の得意先候補から任意選択する |
| 除外 | 完成品: チェックONの場合、設定された受入/納品場所を除外する。OFFの場合、設定された受入/納品場所のみ対象とする。支給品: チェックONの場合、設定された**品番**を除外する。OFFの場合、設定された**品番**のみ対象とする |
| 受入/納品場所（完成品） | 受入/納品場所コードの設定。MARI 取得・受領CSV取込の絞り込みに使用 |
| 品番（支給品） | 10桁品番の設定。受領TXT取込の絞り込みに使用（DB カラム名は `delivery_place` のまま） |
| 登録 | 取引先の除外設定と明細行を保存する |
| 削除 | 得意先・受入/納品場所（完成品）または品番（支給品）を削除できる。取引先削除時は比較結果明細と取込ファイル履歴も合わせて削除する |

#### 重複制御

同一取引先内で同じ `DELIVERY_PLACE` を重複登録しない。登録済み行の変更は行わず、削除後に再登録する。

## 5. ファイル取込仕様

### 5.1 共通

- 旧実装は `TextFieldParser` を `Text.Encoding.Default` で読み取る。
- 区切り文字はカンマ。
- Django 版では、文字コードは Shift_JIS / CP932 を基本とし、必要に応じて UTF-8 も受け付ける。

### 5.2 完成品

| 項目 | 内容 |
|---|---|
| 拡張子 | `.csv` |
| ヘッダー | あり |
| ダブルクォート | 旧実装では `HasFieldsEnclosedInQuotes=False` |
| 必須列 | `カードNO`, `品番`, `納入月日`, `納入数`, `納入取消数` |
| 除外条件 | `カードNO = "S"` の行は比較対象外 |
| 取込項目 | 品番、納入月日、納入数、納入取消数 |
| 取引先名 | 空文字 |

### 5.3 支給品

| 項目 | 内容 |
|---|---|
| 拡張子 | `.txt` |
| ヘッダー | なし |
| ダブルクォート | 旧実装では `HasFieldsEnclosedInQuotes=True` |
| 区切り | カンマ |
| 対象行条件1 | 2列目のコードが、登録済み**子取引先（購買取引先コード）** の `VENDOR_CODE`、または当該得意先の **親得意先コード（3桁 `CUSTOMER_CODE`）** と **完全一致** する |
| 対象行条件2 | 4列目の品番が、登録済み品番設定（`ReceiptReceivingInfo.DELIVERY_PLACE` 相当）と **トリム後の完全一致** で照合される。取引先の `除外` 設定に従う。品番設定が未登録のときは `除外=ON` なら通過、`除外=OFF` なら全行除外 |
| 対象行条件3 | 4列目をトリムした品番が **ちょうど10桁** の行のみ対象（旧 `GetSuppliedPartsData` と同じ） |
| 日付 | 3列目の日付文字列から `/` を除去し、右4桁を `納入月日(MMDD)` とする |
| 数量 | 6列目を数値化して整数の `納入数` とする（`1800.00` 等の小数表記に対応）。0以下は対象外 |
| キャンセル数 | 0 固定 |
| 取引先名 | 2列目のコード |

## 6. MARI(Oracle) 参照仕様

### 6.1 完成品 MARI データ

旧 `clsMariShipmentData.vb` 相当。

#### 取得元

| テーブル | 用途 |
|---|---|
| `T_SHIP` | 出荷実績 |
| `T_SHIP_ODR` | 出荷オーダー |
| `T_SALES_TEMP` | 売上仮データ |

#### 抽出条件

- 取引先コードは、取引先マスタの `DIRECT_DELIVERY_CUSTOMER_CODE` があればそれを優先し、なければ `CUSTOMER_CODE` を使用する。
- `T_SHIP` は `CUST_CD = 取引先コード`、`SHIP_DATE BETWEEN 開始日 AND 終了日`。
- `T_SALES_TEMP` は `CUST_CD = 取引先コード`、`SALES_DATE BETWEEN 開始日 AND 終了日`、`SHIP_SEQ_NO IS NULL`。
- どちらも数量合計が 0 より大きいもののみ対象。

#### 取得項目

| Django内部名 | 旧SQL列 | 内容 |
|---|---|---|
| item_cd | `ITEM_CD` / `CUST_ITEM_CD` | 得意先品目番号 |
| ship_date | `SHIP_DATE` / `SALES_DATE` | 売上計上日 |
| ship_qty | `SHIP_QTY` / `SALES_QTY` | 出荷/売上数量 |
| delivery_place | `CUST_DESINATED_DLV_LOC_CD` | 得意先指定納品場所コード |

#### 納品場所の対象/除外

登録済み受入/納品場所設定がある場合、取引先の `除外` 設定に従う。

| 除外設定 | 条件 |
|---|---|
| ON | `DELIVERY_PLACE NOT IN (設定されたコード)` |
| OFF | `DELIVERY_PLACE IN (設定されたコード)` |

### 6.2 支給品 MARI データ

旧 `clsMariAcptData.vb` 相当。

#### 取得元

| テーブル | 用途 |
|---|---|
| `T_ACPT_RSLT` | 受入実績 |
| `T_RLSD_PUCH_ODR` | リリース済み購買オーダー |
| `M_VEND_CTRL` | 仕入先管理 |

#### 抽出条件

- 比較対象取引先は PostgreSQL に登録された得意先（`customer_code`、3桁）のみ。比較画面の取引先一覧も登録済みのみ表示する。
- MARI・受領TXT照合に使う取引先コードは、当該得意先に紐づく **子取引先（`SuppliedPartsSubcontractor.vendor_code`）** の一覧。
- `T_RLSD_PUCH_ODR.VEND_CD IN (子取引先コード一覧)`。
- `T_ACPT_RSLT.ACPT_DATE BETWEEN 開始日 AND 終了日`。
- `T_ACPT_RSLT.PUCH_ODR_CD = T_RLSD_PUCH_ODR.PUCH_ODR_CD`。
- `T_RLSD_PUCH_ODR.VEND_CD = M_VEND_CTRL.VEND_CD`。

#### 取得項目

| Django内部名 | 旧SQL列 | 内容 |
|---|---|---|
| vend_cd | `VEND_CD` | 取引先コード |
| item_cd | `SUBSTR(ITEM_CD, 1, LENGTH(ITEM_CD) - 5)`（**LENGTH > 10 のときのみ**。10桁以下は TRIM した値をそのまま使用） | 品目番号末尾5桁を除いた値（TXT側正規化と一致） |
| ship_date | `ACPT_DATE` | 受入日 |
| ship_qty | `ACPT_QTY` | 受入数 |
| delivery_place | `WH_CD` | 受入場所 |

旧コードでは受入/納品場所設定による Oracle 側除外条件がコメントアウトされているため、Django 版では旧挙動に合わせて **支給品のMARI取得SQLには品番除外を適用しない**。ただし受領TXT側の取込行絞り込みでは品番設定を使用する。

## 7. 比較ロジック

### 7.1 MARI行と受領書行の一致判定

旧 `CheckReceiptData` の判定を引き継ぐ。

| 比較項目 | MARI側 | 受領書側 | 正規化 |
|---|---|---|---|
| 品番 | `ITEM_CD` | `品番` | MARI側の `-` を除去。支給品は TXT/MARI とも末尾5桁除去ルールを揃えて比較 |
| 日付 | `SHIP_DATE` / `ACPT_DATE` | `納入月日` | MARI日付を `MMdd` に変換して比較 |
| 数量 | `SHIP_QTY` / `ACPT_QTY` | `納入数` | 文字列/数値として同値比較 |

3項目すべて一致した場合は `〇` とする。

### 7.2 不一致・片側のみの扱い

| 状態 | 旧表示 | 内容 |
|---|---|---|
| 一致 | `〇` | MARI側行と受領書側行が品番・日付・数量で一致 |
| 不一致/片側のみ | `×` | MARI側のみ、または受領書側のみ、または3項目が一致しない |
| 手動調整 | `△` | ユーザーが結果列で手動選択する中間状態 |

旧実装は、数量差異・日付差異・品番差異を個別分類せず、比較キーが一致しなければ `×` として表示する。Django 版では初期実装として旧挙動を維持し、必要に応じて差異理由列を追加する。

### 7.3 受領書ファイル取込後の表示処理

1. MARI データを一覧に追加する。
2. 保存済み比較結果を読み込み、MARI 行と品番・日付・数量が一致すれば同じ行へ保存済み受領書側情報を反映する。
3. 受領書ファイルデータを1行ずつ MARI 行と比較する。
4. 一致した MARI 行は `〇` とし、受領書側の品番・納入月日・納入数・キャンセル数・取引先名をセットする。
5. 一致しなかった MARI 行は、結果が空なら `×` とする。
6. MARI 行に一致しなかった受領書側の残行は、MARI側列を空にして `×` 行として追加する。

### 7.4 保存済み未完了データの引き継ぎ

旧 `SelectReceiptData` は、指定期間内の比較結果に加えて、開始日より前の `RECEIPT_FLAG != 1`（`〇` 以外）の結果も取得する。  
Django 版でも、過去の未完了(`×` / `△`)を次回比較対象に残す。

## 12. 実装時の注意点

- 旧実装ではSQL文字列連結が多いが、Django版では必ずパラメータバインドまたはORMを使用する。
- MARI(Oracle) は参照のみで、更新しない。
- PostgreSQL に保存する比較結果は、旧 MySQL の2系統テーブルを1つの汎用モデルにまとめ、比較区分で分ける方が保守しやすい。
- 旧支給品のファイル読み込みでは「4列目を品番/受入場所の両方の判定に使う」実装になっているため、実ファイルを入手して列定義を業務確認すること。
- 完成品の受領CSVでは `カードNO = S` を除外する仕様を必ず維持する。
- `〇` 以外の過去データを次回に持ち越す仕様は、担当者の未解決差異管理として重要なため維持する。

## 付録A. 入荷なし出荷の検証（検証用・将来機能）

入荷がないのに出荷だけあり在庫が減っている品目を洗い出し、入荷をかけるか判断するための検証用仕様。5年9組と同じ Oracle テーブルを使用する。

### A.1 目的

- 階層1仕入先の入荷実績（最終入荷日）より後に、得意先向け出荷だけが発生している品目を一覧化する。
- 入荷発注の要否判断材料とする。

### A.2 データソース（5年9組準拠）

| 区分 | 5年9組 | テーブル | 用途 |
|---|---|---|---|
| 最終入荷日 | 仕入先ブロック 階層1「入荷実績」（NYDATA_GET） | `T_PAST_INSPC_ACPT` | BOM 階層1構成子 × 仕入先コードの `MAX(ACPT_DATE)` |
| 出荷回数・出荷数合計 | 得意先ブロック「出荷実績」（SKDATA_GET） | `T_SHIP` | 最終入荷日より後の `COUNT(*)` / `SUM(SHIP_QTY)`（`DEL_FLG != 1`） |

- BOM 展開・階層1判定・仕入先コード解決は 5年9組 `M_PS` / `M_ITEM` / `M_PUCH_UNIT_COST_H` と同じ。
- 受領書 CSV は使用しない。

### A.3 検証スクリプト

| 項目 | 内容 |
|---|---|
| スクリプト | `scripts/verify_post_receipt_shipment_count.py` |
| 出力先 | `var/exports/post_receipt_shipment/` |

#### 実行例

```bash
python scripts/verify_post_receipt_shipment_count.py
```

#### 出力 CSV 列

| 列 | 内容 |
|---|---|
| 得意先コード / 得意先名 | `T_SHIP.CUST_CD` / `M_CUST` |
| 品番 | 完成品 `T_SHIP.ITEM_CD` |
| 階層1品番 / 仕入先コード / 仕入先名 | BOM 階層1構成子と仕入先（入荷実績がなくても表示） |

| 最終出荷日 | `T_SHIP` の最終日 |

| 最終入荷日以降の出荷数合計 | 上記出荷の数量合計 |
