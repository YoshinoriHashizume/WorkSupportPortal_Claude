## 1. 目的

リポジトリ構成と Django app レイヤーを社内標準に揃え、新規参加者・エージェントが迷わず開発できるようにする。

---

## 2. 移行内容（要約）

### 2.1 Docker / リポジトリ分離

| 変更前（概要） | 変更後（社内標準） |
|----------------|--------------------|
| Django ソースがリポジトリルート直下 | Django ソースは **`src/`** |
| ルートに `Dockerfile` / 旧 `docker-compose.yml` 等 | **`docker/`** 配下にイメージ定義、`docker-compose.devcontainer.yaml` / `docker-compose.production.yaml` |
| ローカルはホスト Python または旧 Compose 中心 | **DevContainer** 前提（workspace: `/django_app/src`） |
| アプリポート 3000/3100、DB 5432 等 | ホスト **8990**（Django）、**5440**（PostgreSQL） |
| `.env.local` 等 | ルート **`.env`**（`.env.example` をテンプレート） |

### 2.2 レイヤー改称・配置

各業務 app は次の形に統一する。

```text
src/application/<app>/
  domain/
    entities/
    value_objects/
    repositories/   # ABC / Protocol（ports）
  use_cases/        # Django 非依存。動詞+名詞のクラス
  infrastructure/   # domain IF の実装
  interfaces/       # views.py, urls.py, wiring.py
  models.py         # ORM 定義の正（マイグレーション互換）。infrastructure/django/models からリエクスポート
  tests/
```

依存の向き: **interfaces → use_cases → domain ← infrastructure**

> **ORM 補足**: 社内 reference は infrastructure 側定義だが、本リポジトリは Django migrations 互換のため **app 直下 `models.py` を定義の正** とする。

### 2.3 composition 廃止

| 廃止 | 代替 |
|------|------|
| app 直下の `composition.py` | **`interfaces/wiring.py`** で手動 DI |
| app 直下の `views.py` / `urls.py` | **`interfaces/views.py`** / **`interfaces/urls.py`** |
| DI コンテナ | **使用しない** |

### 2.4 Document の維持

- **`Document/` はリポジトリルートに残す**（`src/` 配下へは移さない）。
- 仕様・手順書は Docker 分離後もルートから参照する。

## 5. 開発者向けメモ

1. 作業は **DevContainer を開いてから**行う（cwd = `/django_app/src`）。
2. 新規 app は §5.0 のフォルダと依存ルールに従う。`wiring.py` で組み立て、views から infrastructure を直接 import しない。
3. 仕様変更は **`Document/` に記載**し、単体テストを追加する（既存のプロジェクトルールどおり）。
4. pytest は `src/` を cwd / `PYTHONPATH` にし、必要なら `WSP_REPO_ROOT` にリポジトリルートを指定する。SQLite では一部マイグレーションが失敗するため、`conftest.py` で **nomigrations**（モデルからスキーマ生成）とする。

### 7.1 Docker 開発起動の注意（同日追記）

- 起動: `docker compose -f docker-compose.devcontainer.yaml up --build -d` → **http://localhost:8990**
- `config.settings.development` では **`.env.production` を読み込まない**（`.env` / Compose の `POSTGRES_*` を優先）。両方ファイルがあると以前は本番側パスワードで migrate が失敗していた。

### 7.2 エージェント規約の移行（同日追記）

| 変更前 | 変更後 |
|--------|--------|
| `.cursor/rules/clean-architecture.mdc` | **`CLAUDE.md`** + `src/.claude/skills/` |

Cursor IDE 自体は利用してよいが、**プロジェクトルールは Claude Code 側（CLAUDE.md）に統一**する。

### 7.4 本番 requirements 単一化・手順書現行化（同日追記）

| ファイル | 役割 |
|----------|------|
| `requirements-prod.txt` | ランタイム依存の正（gunicorn / waitress なし） |
| `requirements-docker.txt` | prod + gunicorn + 開発依存 |
| `requirements-windows-prod.txt` | prod + waitress |
| `requirements-dev.txt` | pytest / ruff 等 |

本番 Compose サービスは **`db` / `web-app` / `nginx`**。起動は `docker compose ... --env-file .env.production`。ソースの bind マウントは行わない。`web-app` は entrypoint を PID1（`exec`）とし HTTP healthcheck を持つ。

### 7.5 portal / asset_inventory の interfaces 痩せ化（同日追記）

| app | 変更概要 |
|-----|----------|
| `asset_inventory` | `views` から `infrastructure.desknet.service_access_key` 直 import を除去。`ResolveAccessKey` ユースケースを `wiring` 経由で呼ぶ |
| `portal` | ダッシュボード／利用申請／ユーザー管理／お知らせ／DB ブラウザ／お気に入り更新を `use_cases` + `infrastructure/persistence` へ移し、`views` は HTTP + wiring のみ |
| 検証 | `config/tests/test_clean_architecture.py` に **views → 自 app infrastructure 直 import 禁止** を追加 |

単体テスト: `asset_inventory/tests/test_resolve_access_key.py`、`portal/tests/test_portal_interfaces_thinning.py`。
